# Устройство сервиса

## Общая схема

```
                    ┌──────────────────────────────────────────┐
   браузер ───────► │  api        REST + SSE, сессии, аудит     │
                    ├──────────────────────────────────────────┤
                    │  monitor    опрос → оповещения → действия │
                    │  scheduler  cron заданий + обслуживание   │
                    │  backup     движок копий, проверки, restore│
                    ├──────────────────────────────────────────┤
                    │  ovirt      REST-клиент движка (пул)      │
                    │  imageio    поток данных дисков           │
                    │  repo       local / S3 / SFTP             │
                    │  store      SQLite или PostgreSQL         │
                    └──────────────────────────────────────────┘
                              │                    │
                              ▼                    ▼
                   движок oVirt (443)      хранилище бэкапов
                   ovirt-imageio (54322)
```

Пакеты:

| Пакет | Ответственность |
|---|---|
| `internal/config` | конфигурация: YAML + переопределения `JHV_*`, валидация |
| `internal/model` | доменные типы, общие для всех слоёв |
| `internal/store` | репозитории поверх `database/sql`, миграции |
| `internal/secret` | AES-256-GCM для паролей подключений и ключей хранилищ |
| `internal/ovirt` | REST-клиент движка: SSO, инвентарь, питание, снапшоты, Backup API, передачи |
| `internal/imageio` | клиент `ovirt-imageio`: extents, диапазонное чтение/запись, checksum |
| `internal/repo` | хранилища бэкапов и раскладка объектов |
| `internal/retention` | правила «дед-отец-сын» с учётом цепочек |
| `internal/backup` | формат, копирование, восстановление, проверки, рекомендатель |
| `internal/monitor` | опрос состояния, оповещения, восстановительные действия |
| `internal/scheduler` | cron заданий и служебные задачи |
| `internal/events` | внутренняя шина для SSE |
| `internal/api` | HTTP-слой |

## Принятые решения

### Одна схема БД на две СУБД

Схема написана на пересечении диалектов SQLite и PostgreSQL: идентификаторы —
`TEXT` (UUID), моменты времени — `BIGINT` (Unix-миллисекунды), длительности —
`BIGINT` (секунды), структуры — `TEXT` с JSON. Благодаря этому один набор
миграций и одна реализация репозиториев обслуживают обе СУБД; различается только
стиль плейсхолдеров (`?` против `$N`), и это единственное место с ветвлением по
диалекту.

SQLite по умолчанию: сервис, который должен работать, когда сломалось всё
остальное, не должен зависеть от внешней базы. PostgreSQL — для установок, где
уже есть централизованная СУБД и требования к ней.

### Синхронизация инвентаря помечает проход, а не время

Кэш инвентаря обновляется upsert-ом, после чего удаляется всё, что не было
затронуто. Маркером служит случайный идентификатор прохода, а не отметка
времени: два прохода могут попасть в одну миллисекунду, и сравнение по времени
тогда молча оставляет объекты, которые должны были исчезнуть. Это не гипотеза —
тест `TestSyncVMsPreservesOperatorIntent` ловил ровно этот случай.

Поля, которыми владеет оператор (`desired_state`, `remediation_opt_out`),
исключены из списка обновляемых: опрос движка не должен затирать намерение
человека.

### Сетка чанков фиксируется на всю цепочку

Образ диска разбивается на сетку чанков фиксированного размера. Инкремент
сохраняет чанк целиком, даже если изменился один байт. Это немного
переизбыточно — и взамен слияние цепочки при восстановлении сводится к правилу
«побеждает самый свежий запуск, в котором есть чанк i», без арифметики диапазонов
и без возможности частично перекрывающихся записей.

Размер сетки берётся у корня цепочки: инкремент, записанный на другой сетке,
невозможно слить с родителем, поэтому такая цепочка отвергается на входе.

### Ретенция никогда не рвёт цепочку

Правила хранения работают по бакетам (последние N, часовые, суточные, недельные,
месячные, годовые, предельный возраст). Поверх них — правило, которое делает
ретенцию безопасной: если сохраняется инкремент, сохраняются все его предки
вплоть до полного бэкапа. Предельный возраст перекрывает бакеты, но не
перекрывает это правило: устаревшее звено, от которого кто-то зависит, остаётся.

Плюс страховка: последняя копия ВМ не удаляется никогда.

### Действия по оживлению проходят три ворот

1. Класс действия разрешён политикой (`allow_vm_start`, `allow_host_fence`, …).
2. С прошлой попытки прошло больше `cooldown`.
3. Не исчерпан лимит попыток за час.

Всё, что не прошло, записывается со статусом `skipped` и причиной. Иначе на
вопрос «почему ночью ничего не произошло» нет ответа.

Пропущенные решения не расходуют лимит попыток — иначе постоянно заблокированное
действие само себя исчерпало бы.

Ручной запуск через интерфейс обходит cooldown и лимит: они ограничивают
автоматику, а не человека, который посмотрел на стойку.

### Что делается автоматически, а что — нет

| Ситуация | Действие | Почему |
|---|---|---|
| ВМ на паузе, `pause_status=eio/enospc` | снять с паузы | хранилище вернулось — ВМ продолжит работу; не вернулось — снова встанет на паузу, вреда нет |
| ВМ на паузе без причины | ничего | её поставил человек |
| ВМ выключена, `desired_state=up` | запустить | оператор явно объявил, что она должна работать |
| Состояние ВМ `unknown` | ничего | движок потерял связь с хостом, ВМ может работать; запуск копии на другом хосте — две системы, пишущие на один диск |
| Хост `non_responsive`, есть управление питанием | fence restart | только так его вернуть; выключено по умолчанию |
| Хост `non_responsive`, питания нет | ничего | нечем |
| Хост `maintenance` | ничего | это решение человека |

### Проверка, которой нужен гипервизор

Семь режимов проверки рассуждают о байтах в хранилище, и движок выполняет их
сам. Восьмой — пробный запуск — требует гипервизора, а код запуска живёт в
`internal/kvm`, который сам построен на `internal/backup`. Прямая ссылка дала бы
цикл импортов.

Решение — реестр внешних проверок: `Engine.RegisterVerifier` принимает
обработчик для режима, которого движок не знает, а диспетчер регистрирует в нём
пробный запуск. Всё, что вокруг проверки — запись о ней, прогресс, сохранённый
отчёт, отметка на бэкапе — остаётся в движке в одном экземпляре, вместо того
чтобы дублироваться у владельца libvirt-соединения.

Хост для запуска выбирается явно. По умолчанию берётся тот, с которого снят
бэкап, но только если это подключение типа `kvm`: для бэкапа с oVirt такого
ответа нет — движок не поднимет чужой образ, — и API отказывает, перечисляя
подходящие подключения. Поднимать копию боевой системы на сервере, который
оператор не называл, недопустимо.

Образ уходит на гипервизор потоком через `io.Pipe`, без промежуточного файла:
проверить терабайтный диск на машине с десятками гигабайт свободного места иначе
нельзя. Дыры разреженного диска передаются настоящими нулями — `dd` на той
стороне пишет последовательно, и пропуск дыры сдвинул бы весь хвост образа;
`gzip` в потоке сжимает их почти в ничто, а `conv=sparse` не даёт им занять
место на диске. Перед передачей проверяется свободное место: проверка не должна
становиться тем, что уронило гипервизор.

### Передача данных

Чтение диска идёт напрямую с гипервизора через `ovirt-imageio` (54322).
Соседние чанки объединяются в один диапазонный GET (до 32 МиБ), сетевые сбои
диапазона повторяются. Если бэкап-сервер не видит гипервизоры напрямую (типично,
когда они на изолированной сети хранения), `backup.transfer.prefer_proxy`
переключает поток на прокси движка (54323).

Запись в хранилище идёт потоком через `io.Pipe`: манифест строится на лету, а
объект данных уходит в хранилище без промежуточного файла. Бэкап-серверу не нужен
свободный терабайт под staging.

### Обязательные хвосты

Открытый бэкап на движке держит блокировку на дисках ВМ. Он закрывается через
`defer` с контекстом, переживающим отмену (`context.WithoutCancel`) — иначе
прерванный бэкап заблокировал бы все последующие. То же для временных снапшотов
и разморозки файловых систем гостя.

При старте сервис ищет запуски, оставшиеся в состоянии «выполняется» от
предыдущего процесса, закрывает их бэкапы на движке и убирает снапшоты.

## Формат хранения

Подробно — в [BACKUP-FORMAT.md](BACKUP-FORMAT.md). Коротко: каталог запуска
самодостаточен, `run.json` описывает запуск и его диски, каждый диск — пара
`.manifest` (zstd-сжатый JSON с картой чанков и их SHA-256) и `.data` (чанки
подряд). Архив читается без базы данных сервиса.

## Что осталось за рамками

Честный список того, чего в этой версии нет:

- **Копирование между хранилищами без повторного чтения.** Если в задании
  указано несколько хранилищ, бэкап выполняется в каждое отдельно, то есть диск
  читается N раз. Правило 3-2-1 работает, но платит за это трафиком к
  гипервизору.
- **Экспорт OVA не попадает в хранилище бэкапов.** Движок пишет файл на
  локальную ФС выбранного гипервизора и не даёт его вычитать; сервис фиксирует
  путь, дальше — забота оператора.
- **Общие (shareable) диски не бэкапятся.** Они принадлежат нескольким ВМ, и
  копирование по одному разу на каждую ВМ размножило бы данные и сделало
  восстановление неоднозначным.
- **Смешанный бэкап ВМ с частью дисков без CBT.** Если хотя бы у одного диска
  выбранной ВМ выключён инкрементальный режим, вся ВМ бэкапится запасным типом
  (через снапшот). Рекомендатель показывает, какие диски мешают.
- **Аутентификация только локальная.** Ни LDAP, ни SSO; сервис рассчитан на
  размещение внутри периметра оператора.
- **Пробный запуск по расписанию работает не везде.** `verify_after: boot` в
  задании использует гипервизор, с которого снят бэкап; для oVirt-подключения
  хост надо указать руками, то есть запустить проверку из интерфейса. Поле
  «хост для проверок» в задании не заведено сознательно: это миграция схемы и
  ещё одна форма ради случая, который в расписании встречается редко.
- **Восстановленный файл не отдаётся через веб.** Образ собирается в каталог на
  сервере бэкапов, его путь виден в истории восстановлений; забирает оператор.
  Гонять терабайт через HTTP-сессию браузера — не тот способ.

Отдельно про подключения типа `kvm` (голый libvirt):

- **Нет понятий кластера и домена хранения.** Хост представлен одной синтетической
  записью: для одиночного гипервизора это и есть правда, но группировать такие
  хосты в кластеры сервис не умеет.
- **Обслуживание и fencing недоступны.** Над голым хостом нет движка, который мог
  бы перевести его в обслуживание или перезагрузить по питанию; API отвечает на
  такие запросы объяснением, а не молчаливым отказом.
- **Миграция недоступна.** Переносить ВМ некуда, общего хранилища у одиночного
  хоста нет.
- **Включение CBT не является действием.** В libvirt битмап живёт в заголовке
  qcow2, поэтому отслеживание изменённых блоков определяется форматом диска, а не
  переключателем. Диск `raw` придётся конвертировать средствами QEMU.

## Два драйвера, один конвейер

Выбор драйвера делает `internal/dispatch`, а не движок бэкапа. Причина
техническая и стоит того, чтобы её зафиксировать: `internal/kvm` построен на
`internal/backup` (формат хранения, сетка чанков, писатель манифестов), поэтому
`internal/backup` не может обратиться к `internal/kvm` — получился бы цикл
импортов. Диспетчер встраивает движок oVirt (`*backup.Engine`) и добавляет путь
libvirt, так что всё, что не зависит от гипервизора — проверка, восстановление,
ретенция, сборка цепочек — наследуется без изменений.

Граница между драйверами проходит ровно по получению данных:

| Общее для обоих | Своё у каждого |
|---|---|
| формат хранения и сетка чанков | как открыть точку согласованности |
| цепочки, ретенция, проверки | как узнать карту изменённых блоков |
| хранилища, расписания, оповещения | как прочитать данные (imageio HTTP против NBD) |
| действия «оживления» и их ограничители | как выполнить действие на гипервизоре |
