# Диагностика и исправление ошибок

Документ построен по симптому: сначала короткая проверка, затем причина и
исправление. Команды выполняйте на сервере приложения, если не указано иное.

Пути по умолчанию:

| Установка | Рабочий каталог | Конфигурация |
|---|---|---|
| Docker из репозитория | `<репозиторий>/deploy` | `<репозиторий>/deploy/.env`, `<репозиторий>/config/ovirt-backup.yaml` |
| Docker из `.run` | `/opt/jhvirt/compose` | `/opt/jhvirt/compose/.env`, `/opt/jhvirt/config/ovirt-backup.yaml` |
| systemd | `/opt/jhvirt` | `/opt/jhvirt/config/jhvirt.env`, `/opt/jhvirt/config/ovirt-backup.yaml` |

При другом `PREFIX` замените `/opt/jhvirt` фактическим путём.
Полная карта конфигурации и данных находится в
[CONFIGURATION.md](CONFIGURATION.md).

## 1. Универсальная последовательность проверки

### Шаг 1. Процесс отвечает?

```bash
curl -i --max-time 5 http://127.0.0.1:8080/healthz
curl -i --max-time 5 http://127.0.0.1:8080/readyz
```

- `/healthz` проверяет, что HTTP-процесс работает;
- `/readyz` дополнительно проверяет БД и возвращает состояние фоновых работ;
- `200` у `/healthz` и ошибка у `/readyz` обычно означают проблему БД или
  миграций;
- отказ соединения у обоих означает, что служба не запущена, слушает другой
  порт или завершилась при старте.

Если задан другой `--port`, используйте его.

### Шаг 2. Служба или контейнер запущены?

Docker:

```bash
docker compose ps
docker compose logs --tail 150 ovirt-backup
docker compose logs --tail 100 postgres
```

Systemd:

```bash
sudo systemctl status jhvirt --no-pager
sudo journalctl -u jhvirt -n 150 --no-pager
sudo systemctl status postgresql --no-pager
```

На RHEL имя службы PostgreSQL может содержать версию. Найти её:

```bash
systemctl list-units --type=service 'postgresql*'
```

### Шаг 3. Проверьте фактические настройки

Docker:

```bash
grep -E '^(JHV_EXTERNAL_URL|JHV_PORT|JHV_BACKUP_DIR|JHV_RESTORE_DIR)=' .env
docker compose config --quiet
```

Systemd:

```bash
sudo grep -E '^(JHV_SERVER_EXTERNAL_URL|JHV_SERVER_PORT|JHV_DATABASE_URL)=' \
  /opt/jhvirt/config/jhvirt.env
sudo systemctl cat jhvirt
sudo systemd-run --quiet --wait --pipe --collect \
  --uid=jhvirt --gid=jhvirt --working-directory=/opt/jhvirt \
  --property=EnvironmentFile=/opt/jhvirt/config/jhvirt.env \
  /opt/jhvirt/bin/ovirt-backup-server \
  -config /opt/jhvirt/config/ovirt-backup.yaml -check-config
```

Не публикуйте вывод `jhvirt.env` или `.env` целиком: там находится DSN или
пароль PostgreSQL.

### Шаг 4. Отделите API от браузера

```bash
BASE=http://127.0.0.1:8080
read -rsp 'Пароль local-admin: ' JHV_PASSWORD; echo
curl -sS -D /tmp/jhv.headers -c /tmp/jhv.cookies \
  -X POST "$BASE/api/v1/auth/login" \
  -H 'Content-Type: application/json' \
  -d "{\"username\":\"local-admin\",\"password\":\"$JHV_PASSWORD\"}"
unset JHV_PASSWORD
curl -i -b /tmp/jhv.cookies "$BASE/api/v1/auth/me"
grep -i '^set-cookie:' /tmp/jhv.headers
rm -f /tmp/jhv.headers /tmp/jhv.cookies
```

Если login и `/auth/me` успешны, backend и БД исправны; ищите проблему в URL,
cookie, прокси или кэше браузера.

## 2. Ошибки установщика

### `нет терминала — укажите способ ключом`

Скрипт запущен через SSH/CI без TTY. В unattended-режиме явно передайте режим
и URL:

```bash
sudo sh ovirt-backup-*.run --mode systemd \
  --url http://10.20.30.40:8080 --port 8080
```

### `без диалога внешний адрес обязателен`

Добавьте `--url`. Не подставляйте случайный адрес: его схема управляет флагом
`Secure` у cookie.

### `адрес должен начинаться с http:// или https://`

Передавайте только схему, хост и необязательный порт, без пути:

```text
http://10.20.30.40:8080
https://virt.example.org
```

Значения вида `virt.example.org`, `https://host/path` и URL с логином не
принимаются.

### `порт должен быть в диапазоне 1..65535`

`--port` принимает только целое число от 1 до 65535. Это порт публикации
Docker и `JHV_SERVER_PORT` для systemd.

### `docker compose недоступен`

Проверьте:

```bash
docker --version
docker info
docker compose version
```

Частые причины: Docker daemon не запущен, пользователь не имеет доступа к
socket, установлен только CLI или команда `docker` является эмуляцией Podman.
Podman проектом не поддерживается. Используйте настоящий Docker или systemd.

### `systemd не найден`

Systemd должен быть запущен как init-система, а не только установлен как
пакет. В обычном непривилегированном контейнере режим systemd не работает.

### `неподдерживаемая платформа`

Автоматическая systemd-установка поддерживает Ubuntu/Debian с `apt` и
RHEL/AlmaLinux/Rocky Linux с `dnf`. Для другой системы распакуйте `.run` через
`--extract` и подготовьте БД/unit своим средством управления конфигурацией.

### `файл строки подключения ... должен иметь права 0600`

```bash
sudo chown root:root /root/jhvirt.dsn
sudo chmod 600 /root/jhvirt.dsn
stat -c '%a %U:%G' /root/jhvirt.dsn
```

Файл должен содержать ровно одну непустую строку.

### `контрольная сумма не сошлась`

`.run` был обрезан или изменён при переносе. Скопируйте его заново в бинарном
виде, предпочтительно `scp`, и выполните:

```bash
sh ovirt-backup-*.run --check
```

Не открывайте `.run` редактором: после shell-заголовка находится двоичный
архив.

### `комплект собран под ..., а система ...`

Сверьте:

```bash
uname -m
sh ovirt-backup-*.run --version
```

`x86_64` соответствует `linux/amd64`, `aarch64` — `linux/arm64`.

### `за 3 минуты сервис не стал готов`

Установщик уже выводит последние строки журнала. Дополнительно проверьте
`/healthz`, `/readyz`, БД, занятость порта и полные журналы по алгоритму из
раздела 1. Не запускайте установщик многократно, пока не понятна первая ошибка.

### Импорт миграции отклоняет непустой целевой сервер

`--migrate-from` рассчитан на пустой `PREFIX`/unit/набор Docker volumes и не
сливает две инсталляции. Не удаляйте целевые данные вслепую. Убедитесь, что
указали правильный новый сервер и путь; нужную существующую инсталляцию сначала
сохраните отдельно либо выберите другой `PREFIX`.

Если предыдущий импорт оборвался, marker в `PREFIX` разрешает продолжение
только с **тем же архивом**. Повторите исходную команду без ручной раскладки
файлов. Другой архив поверх marker отклоняется, потому что продолжение двух
разных состояний не определено.

### После миграции нет доступа к backup/file/restore каталогу

Миграционный пакет переносит настройки путей, но не содержимое внешних
файловых систем. До импорта подключите NFS/SMB/local mounts по ожидаемым путям.
Для systemd проверьте сохранённые `ReadWritePaths` и фактический UID/GID
пользователя; если старые числовые ID заняты, установщик использует локальные и
предупреждает о необходимости поправить ACL/NFS export. Для Docker проверяйте
запись от UID `10001` внутри контейнера.

Не исправляйте терабайтное дерево рекурсивным `chown`, пока не проверены mount,
ACL и root squash: это может разрушить права других клиентов хранилища.

### После миграции браузер не принимает TLS или OIDC-вход

Сохранённый сертификат обязан содержать новое имя/IP в SAN. Повторите импорт с
`--tls self-signed` либо `--tls files`; доверие к self-signed CA на клиентах
устанавливается отдельно. Если менялся `--url`, добавьте новый callback в OIDC
provider: установщик обновляет локальный env, но не изменяет внешний Keycloak.

### Внешняя PostgreSQL используется старым и новым сервером

Для внешней БД архив переносит DSN, а не dump. Старый экземпляр должен быть
остановлен: два scheduler-а против одной БД опасны даже при ранее выключенном
leader election. Snapshot/`pg_dump` внешней БД делается её штатными средствами
до cutover; миграционный архив его не заменяет.

## 3. Docker Compose

### `required variable ... is missing a value`

`.env` отсутствует или обязательное значение пусто. `.env.example` не является
готовой production-конфигурацией: пароль БД там пуст намеренно.

Исправление:

```bash
cd deploy
./install.sh --mode docker --url http://10.20.30.40:8080 --port 8080
```

Установщик создаст `.env` с правами `0600` и случайными паролями.

### Том PostgreSQL остался, а `.env` потерян

Симптомы:

- установщик сообщает, что том существует без `.env`;
- приложение циклически перезапускается;
- PostgreSQL пишет `password authentication failed`.

Пароль задаётся при первом создании тома. Новый `.env` не меняет пароль внутри
существующей БД.

Без потери данных исправление одно: восстановить прежний `.env` из резервной
копии. Удаление тома создаст пустую БД и потеряет подключения, задания и
историю. Копии ВМ во внешнем хранилище останутся, но их придётся повторно
обнаружить и привязать.

### Порт уже занят

Симптом Docker:

```text
failed to bind host port 0.0.0.0:8080/tcp: address already in use
```

Актуальный установщик проверяет host-порт до сборки образа. В интерактивном
режиме он предложит свободный порт; при запуске с ключами завершится сразу и
покажет пример команды с другим портом.

Найдите владельца порта:

```bash
docker ps --filter publish=8080
sudo ss -ltnp 'sport = :8080'
```

Остановите обнаруженный ненужный сервис либо повторите установку на другом
порту. Уже созданные `.env`, PostgreSQL-том и ключ не удаляйте:

```bash
./install.sh --mode docker \
  --url http://10.20.30.40:18080 --port 18080
```

За обратным прокси внешний URL может остаться без внутреннего порта:
`--url https://virt.example.org --port 18080`.

### Контейнер приложения `unhealthy`

```bash
docker compose ps
docker inspect --format '{{json .State.Health}}' \
  "$(docker compose ps -q ovirt-backup)"
docker compose logs --tail 150 ovirt-backup
```

Если PostgreSQL ещё запускается, дождитесь её `healthy`. Если приложение
пишет об ошибке подключения, сверяйте пароль только с восстановленным `.env`,
не меняйте его наугад.

### Compose v2 предупреждает, что `version` устарел

Это предупреждение, не ошибка. Поле `version: "2.4"` сохранено ради
поддерживаемого `docker-compose` v1 и игнорируется Compose v2.

## 4. Systemd и PostgreSQL

### `jhvirt.service` сразу завершилась

```bash
sudo systemctl status jhvirt --no-pager
sudo journalctl -u jhvirt -b -n 200 --no-pager
sudo systemctl cat jhvirt
```

Проверьте, что пути в `WorkingDirectory`, `ExecStart` и `EnvironmentFile`
соответствуют фактическому `PREFIX`. Повторная установка из текущего `.run`
перерендерит unit без удаления данных.

### `/healthz` работает, `/readyz` не работает

Процесс запущен, но не готов. Чаще всего недоступна PostgreSQL или не прошли
миграции:

```bash
sudo journalctl -u jhvirt -n 200 --no-pager
sudo -u postgres psql -d jhvirt -c 'select 1'
sudo -u jhvirt psql -d jhvirt -c 'select 1'
```

Вторая команда проверяет сервер БД, третья — тот же peer-путь, которым
пользуется локальная systemd-установка.

### Внешняя PostgreSQL недоступна

Проверьте DNS, маршрут, порт, `pg_hba.conf`, TLS и DSN:

```bash
getent hosts db.example.org
nc -vz db.example.org 5432
```

Не выводите DSN в общий журнал. Для `sslmode=require` сервер должен реально
поддерживать TLS. `prefer`, `allow`, `disable` и отсутствие режима для внешней
БД намеренно отклоняются, поскольку допускают передачу данных открытым текстом.
Для проверки сертификата используйте `verify-full` и настройки
PostgreSQL-клиента вашей организации.

### `permission denied` при записи копии или восстановлении

Проверьте все уровни:

1. каталог существует и доступен пользователю `jhvirt`;
2. каталог восстановления входит в `backup.restore_dirs`;
3. путь добавлен в `ReadWritePaths` unit;
4. для NFS разрешена запись с фактическим UID/GID;
5. SELinux/AppArmor не запрещает доступ.

```bash
sudo -u jhvirt test -w /srv/restores && echo writable
sudo systemctl cat jhvirt | grep ReadWritePaths
```

После правки unit:

```bash
sudo systemctl daemon-reload
sudo systemctl restart jhvirt
```

В Docker временные образы oVirt 4.3 создаются в `/restores/.tmp`. Штатный
установщик и обновление создают этот каталог с владельцем `10001:10001`,
режимом `0700` и проверяют запись из непривилегированного контейнера. Если
каталог был подключён или создан вручную, проверьте фактический host-путь:

```bash
sudo grep '^JHV_RESTORE_DIR=' /opt/jhvirt/compose/.env
sudo docker compose --env-file /opt/jhvirt/compose/.env \
  -f /opt/jhvirt/compose/docker-compose.yml exec -T ovirt-backup \
  sh -c 'ls -ldn /restores /restores/.tmp; test -w /restores/.tmp'
```

Сам движок бэкапа также проверяет `backup.temp_dir` до заморозки ВМ и создания
снапшота, поэтому неверные права больше не оставляют новый снапшот-остаток.

### Служба была остановлена до обновления и не запустилась

Это штатно: обновление перезапускает только ранее активную службу.

```bash
sudo systemctl enable --now jhvirt
```

## 5. Авторизация

### Неверный логин или пароль (`401 unauthorized`)

Проверьте отсутствие пробелов и переносов при копировании. Bootstrap-пароль
печатается отдельной строкой и после первого старта не хранится в открытом
виде.

Штатный сброс из установки `.run` (режим определяется автоматически):

```bash
sudo /opt/jhvirt/bin/ovirt-backup-recover-admin --user local-admin
```

Для запуска Compose непосредственно из репозитория:

```bash
sudo sh deploy/recover-admin.sh --mode docker --compose-dir deploy \
  --user local-admin
```

Команда требует `/opt/jhvirt/config/recovery.token` (для репозитория —
`deploy/.recovery-token`) с правами `0600`. Токен никогда не монтируется в
рабочий контейнер. Скрипт генерирует новый пароль, включает отключённую локальную
запись, отзывает все сессии, API-токены и делегирования и пересоздаёт приложение.
Прямой запуск бинаря с одним `-reset-password` намеренно отклоняется.

Если token-файл потерян, остановите приложение и повторно запустите проверенный
установщик той же версии или новее: он создаст новый токен и заменит только его
SHA-256 в env. Не переносите token-файл внутрь volume приложения.

На установках, обновлённых со старой версии, имя может оставаться `admin`:
проверьте `JHV_AUTH_BOOTSTRAP_USER` в `.env` или `jhvirt.env`. Установщик не
переименовывает существующую запись и не меняет ей пароль. После входа
её можно переименовать в **«Настройки → Пользователи»**: откройте
`admin`, задайте `local-admin` и оставьте поле нового пароля пустым. Это
меняет только логин; сессия продолжает работать. Внешние OIDC-записи
так переименовать нельзя: их имя задаёт Keycloak.

### `403 local_login_disabled` при правильном пароле

Это ожидаемо при OIDC: локальная форма выключена целиком и `local-admin` не
обходит Keycloak. `kc-bootstrap-admin` здесь тоже не подходит — он действует
только в master realm Keycloak.

Если после чистой установки в Keycloak существует только
`kc-bootstrap-admin`, использована версия установщика, которая ещё не создавала
первого пользователя realm `jhvirt`. Повторно запустите актуальный `.run` с
теми же параметрами. Он создаст `backup-admin`, включит его в `virt-admins` и
один раз выведет отдельный пароль, не сбрасывая master-admin, realm или клиент.

Если `backup-admin` уже есть, повторная установка намеренно не меняет его
пароль. Сбросьте пароль в Admin Console:
**realm jhvirt → Users → backup-admin → Credentials → Reset password**.
При утраченном пароле самой консоли сначала выполните
`sudo /opt/jhvirt/bin/ovirt-backup-recover-keycloak --user kc-bootstrap-admin`.

Для документированного аварийного доступа сначала повторно запустите Docker-
установщик с прежними `--url`/`--mode` и `--local-login enabled`, затем сбросьте
пароль `local-admin` командой выше. После ремонта OIDC повторите установку с
`--local-login disabled`. Не оставляйте этот вход включённым постоянно: на него
не распространяются MFA и блокировки провайдера.

### Слишком много попыток (`429 too_many_attempts`)

Ответ содержит `Retry-After`. Пауза начинается после серии неудачных попыток и
растёт до 15 минут. Она считается по имени пользователя, а не по IP.

Предпочтительно дождаться указанного времени и проверить аудит. Для аварийного
снятия паузы перезапустите процесс, потому что счётчик хранится в памяти:

```bash
sudo systemctl restart jhvirt
# или
docker compose restart ovirt-backup
```

Сброс пароля отдельной командой сам по себе счётчик работающего процесса не
обнуляет.

### Пароль принят, но снова появляется форма входа

Это исторически встречавшаяся ошибка конфигурации. Типичная последовательность:

1. `POST /api/v1/auth/login` возвращает `200`;
2. ответ содержит `Set-Cookie: jhvirt_session=...; Secure`;
3. интерфейс фактически открыт по `http://`;
4. браузер не отправляет Secure-cookie по HTTP;
5. `GET /api/v1/auth/me` возвращает `401`, SPA снова показывает login.

Диагностика:

```bash
BASE=http://10.20.30.40:8080
read -rsp 'Пароль local-admin: ' JHV_PASSWORD; echo
curl -i -c /tmp/jhv.cookies \
  -X POST "$BASE/api/v1/auth/login" \
  -H 'Content-Type: application/json' \
  -d "{\"username\":\"local-admin\",\"password\":\"$JHV_PASSWORD\"}"
unset JHV_PASSWORD
curl -i -b /tmp/jhv.cookies "$BASE/api/v1/auth/me"
rm -f /tmp/jhv.cookies
```

Если первый ответ `200`, содержит `Secure`, а второй `401`, схема
`external_url` не совпадает с адресом браузера.

Проверить значение:

```bash
# systemd
sudo grep '^JHV_SERVER_EXTERNAL_URL=' /opt/jhvirt/config/jhvirt.env

# Docker
grep '^JHV_EXTERNAL_URL=' .env
```

Исправить безопаснее повторным запуском установщика, чтобы одновременно
обновить окружение и перезапустить нужный процесс:

```bash
# прямой HTTP, systemd
sudo sh /tmp/ovirt-backup-*.run --mode systemd \
  --url http://10.20.30.40:8080 --port 8080

# прямой HTTP, Docker
./install.sh --mode docker \
  --url http://10.20.30.40:8080 --port 8080
```

Для реального HTTPS, включая TLS на обратном прокси, URL должен начинаться с
`https://`. После исправления очистите cookie сайта или откройте новую
приватную вкладку и войдите снова.

Обратное несоответствие тоже неправильно: если браузер работает по HTTPS, а
`external_url` задан как HTTP, вход будет работать, но cookie уйдёт без флага
`Secure` и сможет передаваться по открытому каналу.

### Keycloak: `провайдер недоступен`

Сначала отделите внешний доступ, realm и связь внутри Compose:

```bash
# Из рабочего Compose-каталога.
grep -E '^(COMPOSE_PROFILES|JHV_OIDC_ISSUER|JHV_OIDC_BACKCHANNEL_URL|JHV_KEYCLOAK_URL|KEYCLOAK_(DIRECT_TLS|CONTAINER_PORT|BIND_ADDRESS))=' .env
docker compose ps

# Keycloak доступен внутри сети Compose, а прикладной realm существует.
docker compose exec -T ovirt-backup \
  wget -S -O /dev/null \
  http://keycloak:8080/realms/jhvirt/.well-known/openid-configuration

# Браузерный адрес realm доступен снаружи.
KEYCLOAK_URL="$(sed -n 's/^JHV_KEYCLOAK_URL=//p' .env)"
curl -k -i "$KEYCLOAK_URL/realms/jhvirt/.well-known/openid-configuration"

# Приложение смогло выполнить discovery: Location должен быть абсолютным
# адресом Keycloak, а не /login?oidc_error=...
APP_URL="$(sed -n 's/^JHV_EXTERNAL_URL=//p' .env)"
curl -k -sS -D - -o /dev/null \
  "$APP_URL/api/v1/auth/oidc/start" | grep -i '^location:'
```

Для встроенного Keycloak значения должны иметь такой смысл:

```dotenv
JHV_OIDC_ISSUER=https://keycloak.example.org/realms/jhvirt
JHV_OIDC_BACKCHANNEL_URL=http://keycloak:8080
```

Если Keycloak получает сертификат напрямую от установщика, дополнительно
ожидаются:

```dotenv
KEYCLOAK_DIRECT_TLS=1
KEYCLOAK_CONTAINER_PORT=8443
KEYCLOAK_BIND_ADDRESS=0.0.0.0
```

Для TLS на отдельном reverse proxy значения другие: `DIRECT_TLS=0`, внутренний
порт `8080`, bind `127.0.0.1`. Комбинация публичного `https://...` и порта
контейнера `8080` без реально настроенного reverse proxy приводит к ошибке TLS
и сообщению `провайдер недоступен`. Повторите установку актуальным `.run` с
теми же `--url`, `--tls` и `--keycloak-url`: режим исправится без пересоздания
realm и без смены пользователей.

`issuer` нельзя менять на имя `keycloak`: оно существует только внутри
Compose, недоступно браузеру и не совпадёт с `iss` токена. Если
`backchannel_url` пуст или равен адресу хоста, контейнер может упереться в
hairpin NAT/firewall и через 15 секунд вернуть `провайдер недоступен`.
Обновите проект и повторно запустите установщик: существующий режим OIDC и
секрет клиента сохраняются, а внутренний адрес добавляется автоматически.

Если discovery отвечает `404` и JSON `Realm does not exist`, контейнер
Keycloak запущен, но realm `jhvirt` отсутствует. Не возвращайте пароль в
`.env`: новые установки хранят секреты только файлами в volumes. Повторно
запустите актуальный `.run` с теми же параметрами OIDC. Если база Keycloak уже
инициализирована, установщик остановит Keycloak, штатной offline-командой
создаст случайного временного администратора, настроит realm и удалит эту
учётную запись. Постоянный пароль администратора при этом не меняется.

Если потерян доступ администратора Keycloak, не возвращайте bootstrap-пароль в
конфигурацию и не удаляйте БД. Для установки из `.run` выполните:

```bash
sudo /opt/jhvirt/bin/ovirt-backup-recover-keycloak \
  --user kc-bootstrap-admin
```

Для запуска из checkout: `sudo sh deploy/recover-keycloak.sh --compose-dir
deploy --user kc-bootstrap-admin`. Команда сама останавливает все контейнеры
сервиса Keycloak, создаёт временный admin service account штатной offline-
командой, меняет пароль постоянного администратора, проверяет его права,
отзывает старые сессии и удаляет временный client. Если аварийная очистка не
смогла удалить его, скрипт печатает точный client ID: после возврата доступа
удалите его из **master realm → Clients**.

Если realm действительно нужно пересоздать на пустом тестовом стенде, сначала
проверьте последний файл в `<JHV_DR_BACKUP_DIR>/keycloak/postgres`, затем
удалите только БД Keycloak и повторите установку. На production не удаляйте её:
там находятся пользователи, federation-настройки и второй фактор.

Локальный `local-admin` приложения не помогает войти в консоль Keycloak. И
наоборот, `kc-bootstrap-admin` не принимается парольной формой ovirt-backup.

### Keycloak не видит пользователей или группы Active Directory

Проверьте по порядку:

1. DNS-имена всех DC разрешаются внутри контейнера Keycloak;
2. `Connection URL` использует `ldaps://...:636`, а корпоративный CA находится
   в `/opt/jhvirt/keycloak-truststores`;
3. `Users DN` содержит нужные OU, а `Search scope` равен `Subtree`;
4. username mapper читает `sAMAccountName`, не `cn`;
5. `LDAP Groups DN` указывает на OU с `virt-admins`, `virt-operators` и
   `virt-readers`;
6. пользователь является непосредственным членом одной из этих групп.

Простой мастер строит Base DN из DNS-домена и ищет DC по записи
`_ldap._tcp.dc._msdcs.<домен>`. Сообщение `контроллер домена не найден через
DNS SRV` не запрещает интеграцию: проверьте AD DNS и повторите установку с
`--keycloak-ad-controller dc01.example.org`. Указывайте FQDN из SAN
сертификата, а не случайный IP.

`Synchronize all users: 0 imported users` без ошибки обычно означает слишком
узкий `Users DN`, `One Level` или LDAP filter. Успешный импорт пользователей не
доказывает, что импортированы группы: Group LDAP Mapper синхронизируется
отдельно.

Проверьте vault без печати секрета:

```bash
cd /opt/jhvirt/compose
sudo stat -c '%U:%G %a %n' \
  /opt/jhvirt/keycloak-vault/jhvirt_ad-bind
sudo docker compose exec -T --user 1000:0 keycloak \
  sh -c 'test -s /opt/keycloak/conf/vault/jhvirt_ad-bind'
sudo docker compose logs --since=15m keycloak |
  grep -Ei 'ldap|vault|pkix|certificate|sync'
```

Ожидаемые права host-файла: `root:root 440`. Ошибка `Vault key 'ad-bind' not
found` означает, что файл отсутствует, пуст или недоступен UID 1000:GID 0.
Повторите интерактивную установку и скрыто введите новый пароль; при одном
provider он будет выбран автоматически. Для unattended-запуска используйте то
же `--keycloak-ad-provider` и новый `--keycloak-ad-bind-password-file`; пароль
в базу или `.env` не записывайте.

Если пользователь виден в **Users**, но ovirt-backup отклоняет вход, откройте
его вкладку **Groups**. Нужна хотя бы одна из трёх групп без префикса пути.
После изменения членства выполните sync mapper, завершите Keycloak-сессии
пользователя и начните новый вход: существующая cookie приложения не меняет
роль сама. Полная команда установки и модель ролей приведены в
[KEYCLOAK-AD.md](KEYCLOAK-AD.md).

Если установщик сообщает о нескольких LDAP-компонентах с одним именем, не
удаляйте случайный. В **User federation** временно отключите старый provider,
сравнив `Users DN`, username attribute и число привязанных пользователей.
Проверьте вход учётной записью из нового provider и только затем удаляйте
старый. Пользователи, импортированные через разные provider под разными
username (`cn` и `sAMAccountName`), могут представлять одних и тех же людей;
перед удалением выгрузите список и проверьте активные записи. Установщик
намеренно не выбирает первый дубликат и не удаляет пользователей автоматически.

### После пароля Keycloak открывает `Update Account Information`

Провайдер принял пароль, но считает профиль пользователя неполным. Заполните
email, имя и фамилию в этой форме либо заранее задайте их в административной
консоли Keycloak: **Users → пользователь → Details**. После сохранения Keycloak
продолжит тот же OIDC-вход. Для допуска в ovirt-backup пользователь также должен
состоять в `virt-admins`, `virt-operators` или `virt-readers`.

Для доменного пользователя проверьте, кем управляется членство. Если выбран
ручной режим: **realm jhvirt → Users → пользователь → Groups → Join Group**.
Если используется LDAP Group Mapper, меняйте членство в Active Directory и
запускайте sync, а не добавляйте пользователя локально. Полный порядок и
разбор LDAPS/DNS: [KEYCLOAK-AD.md](KEYCLOAK-AD.md).

### Keycloak возвращает `invalid_scope`

Keycloak отклоняет запрос до показа формы входа, а приложение возвращает
браузер на `/login?oidc_error=...invalid_scope`. Чаще всего в
`auth.oidc.scopes` ошибочно добавлен `groups`: для встроенного Keycloak это
утверждение токена, которое создаёт mapper клиента, а не стандартный scope.

Оставьте стандартный набор и перезапустите приложение:

```yaml
auth:
  oidc:
    scopes: ["openid", "profile", "email"]
```

Отдельный scope групп добавляют только тогда, когда администратор провайдера
явно создал его и назначил клиенту. Современный установщик проверяет ответ
authorization endpoint встроенного Keycloak и завершает установку ошибкой,
если тот сразу возвращает OIDC `error`.

### Вход работает через curl, но не через браузер

Проверьте в DevTools браузера:

- запрос login и его `Set-Cookie`;
- наличие `jhvirt_session` в Storage/Application → Cookies;
- запрос `/api/v1/auth/me` и переданный заголовок `Cookie`;
- ошибки CORS и mixed content;
- совпадение схемы и хоста страницы с production URL.

SPA и API должны раздаваться с одного origin. `server.cors_origins` оставляйте
пустым, если интерфейс обслуживает само приложение. Не добавляйте `*` для
запросов с cookie.

### После смены пароля старые вкладки получили `401`

Это ожидаемо: сброс пароля закрывает все сессии пользователя. Войдите заново.

## 6. Обратный прокси и TLS

### За nginx нет живых обновлений или долгие операции обрываются

Нужны:

```nginx
proxy_buffering off;
proxy_read_timeout 24h;
client_max_body_size 0;
```

Проверьте также передачу `Host`, `X-Forwarded-For` и `X-Forwarded-Proto`.

### Браузер сообщает mixed content

Страница открыта по HTTPS, но один из URL ссылается на HTTP. Задайте
`external_url=https://...`, не публикуйте отдельный HTTP API для SPA и
проверьте конфигурацию прокси.

### Циклический redirect

TLS завершается на прокси, но прокси и приложение по-разному определяют схему.
Не перенаправляйте внутренний `proxy_pass http://127.0.0.1:8080` на HTTPS.
Внешний URL при этом должен оставаться `https://...`.

## 7. Подключение к oVirt, Proxmox и KVM

### `lookup ... on 127.0.0.11:53: server misbehaving`

`127.0.0.11` — встроенный DNS Docker. Он пересылает запросы DNS-серверам
host-системы, поэтому сначала сравните результат на двух уровнях:

```bash
# На Docker-host.
getent ahostsv4 dengine.example.local
resolvectl query dengine.example.local

# В контейнере приложения.
cd <каталог-compose>
docker compose exec -T ovirt-backup \
  getent ahostsv4 dengine.example.local
```

Если host тоже не разрешает имя, исправляйте host DNS. Для корпоративного
`.local` обычно требуется unicast DNS route-domain в `systemd-resolved`.
Постоянная настройка Ubuntu/Netplan и RHEL/NetworkManager, Docker-only
override и готовый пример для тестового сервера описаны в
[DNS.md](DNS.md).

Не заменяйте DNS-имя движка IP-адресом без отдельной проверки: это может
нарушить TLS и абсолютные URL SSO.

### oVirt: `engine_auth`

Движок отверг учётные данные. Проверьте имя в полном формате, например
`admin@internal`, пароль, срок действия и права роли. Адрес задавайте без
`/ovirt-engine/api`: клиент добавляет API-путь сам.

### Ошибка сертификата oVirt

Не отключайте проверку TLS как постоянное решение. Загрузите CA через форму,
сверьте отпечаток независимым каналом и сохраните подключение с проверенным
сертификатом. Проверьте имя хоста: сертификат должен соответствовать адресу.

### `ovirt-imageio` недоступен

Проверьте порт 54322 каждого гипервизора с сервера приложения. Если сеть
хранения изолирована, включите:

```yaml
backup:
  transfer:
    prefer_proxy: true
```

Тогда данные пойдут через прокси движка на 54323, обычно медленнее.

### Proxmox VE: API-токен и права

Адрес задаётся как `https://pve01.example.org:8006`; путь `/api2/json` клиент
добавляет сам. Рекомендуется отдельный API-токен с разделением привилегий.
Пример минимальной роли для инвентаря и доступных в интерфейсе действий над ВМ:

```bash
pveum user add backup@pve
pveum role add JHVMonitor -privs "Datastore.Audit Sys.Audit VM.Audit VM.PowerMgmt VM.Migrate"
pveum acl modify / -user backup@pve -role JHVMonitor
pveum user token add backup@pve jhvirt -privsep 1
pveum acl modify / -token 'backup@pve!jhvirt' -role JHVMonitor
```

Последняя команда создания токена показывает secret один раз. В форме
`API token ID` — это `backup@pve!jhvirt`, а `Secret API token` — выданное
значение. При `401` проверьте обе части токена; при `403` — ACL пользователя и
токена. Для режима только наблюдения исключите `VM.PowerMgmt` и `VM.Migrate`.

Сертификат `pveproxy` можно получить в форме, но такое первое соединение ещё не
проверено. Сверьте показанный SHA-256 на узле или через доверенный канал. Режим
без проверки TLS оставляйте только для лаборатории.

### Proxmox VE: API работает, backup/restore недоступен

Управление требует только HTTPS API, а передача архива — отдельный SSH data
plane ко всем узлам. В форме должны быть заданы пользователь SSH, приватный
ключ и закреплённые ключи узлов. Выполните на каждом узле:

```bash
sudo test -x /usr/local/sbin/jhvirt-pve-data-plane
sudo /usr/local/sbin/jhvirt-pve-data-plane probe
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Проверьте строку публичного ключа приложения в `/root/.ssh/authorized_keys`: ей
нужны `restrict` и
`command="/usr/local/sbin/jhvirt-pve-data-plane"`. Кнопка **Получить ключи
узлов** должна вернуть каждый узел, а **Проверить подключение** — подтвердить
backup/restore. Частичный набор ключей служба намеренно отклоняет.

При `Permission denied (publickey)` проверьте пользователя `root`, соответствие
приватного и публичного ключей и права каталога `.ssh`. При `invalid forced
command` удалите дополнительные SSH options/обёртки, которые меняют
`SSH_ORIGINAL_COMMAND`. Обычный интерактивный `ssh root@node` этим ключом
завершится ошибкой — это ожидаемо, shell для ключа отключён.

### Proxmox VE: оборвалось восстановление

Helper удаляет гостя, если ошибка случилась после успешного импорта, но не
имеет отдельной команды удаления произвольного VMID. Если соединение оборвалось
внутри `qmrestore` или `pct restore`, Proxmox может оставить неполную запись.
Найдите VMID из журнала восстановления, убедитесь, что это именно новый
незавершённый гость, и удалите его вручную. Автоматически удалять VMID после
сетевой ошибки опасно: за время разрыва этот идентификатор мог занять другой
оператор.

### KVM: TCP 22 открыт, но SSH зависает на banner

TCP connect не доказывает работоспособность SSH. Проверьте:

```bash
ssh -vvv -o ConnectTimeout=15 user@kvm-host true
```

Если таймаут происходит до строки с версией SSH-сервера, приложение также не
подключится. Проверяйте `sshd`, firewall/LB, fail2ban, лимиты `MaxStartups` и
маршрут. Пароль и ключ ещё не участвуют в обмене, пока banner не получен.

### KVM: доступ запрещён к libvirt socket

На гипервизоре под тем же SSH-пользователем:

```bash
virsh -c qemu:///system list --all
```

Настройте членство в группе libvirt или polkit согласно политике системы. Не
выдавайте полный root только для обхода одной ошибки без оценки риска.

### В журнале хоста много входов службы

Служба держит SSH-соединения открытыми между операциями (см.
[ARCHITECTURE.md](ARCHITECTURE.md#соединения-с-хостами)). Вход по ключу в
`journalctl -u sshd` или `/var/log/secure` должен появляться:

- на хосте KVM — один раз, пока соединение не оборвётся;
- на хосте СУБД и узле Proxmox — один раз на серию операций, если между ними
  меньше 5 минут. На время бэкапа ВМ с привязанной СУБД это один вход, а не вход
  на каждый замер статистики;
- на сервере SFTP-хранилища — один раз, пока служба обращается к нему хотя бы
  раз в 20 минут.

Сколько раз служба входила на каждый хост, видно по метрике
`ovirt_backup_ssh_connections_total` с метками `host` и `component`: `libvirt`,
`db-dump`, `proxmox`, `sftp-repo`, `discovery`, `host-key`.

Если входов больше, соединение рвёт что-то между службой и хостом:

- межсетевой экран или NAT закрывают простаивающие соединения — увеличьте их
  тайм-аут простоя. Соединение с хостом KVM служба держит keepalive-запросом
  раз в 30 секунд; если хост на него не отвечает, в журнале службы появится
  «гипервизор не отвечает на keepalive». Само соединение keepalive не рвёт:
  пул переподключится при следующей операции;
- на хосте включены `ClientAliveInterval` с малым `ClientAliveCountMax` — служба
  отвечает на такие проверки, а обрыв виден в журнале sshd;
- sshd ограничивает `MaxSessions` меньше 8 — служба откроет второе
  соединение, когда сессий на первом не хватит.

При `LogLevel VERBOSE` sshd пишет ещё и строку на каждую сессию
(`Starting session: …`) — это не вход, а команда на уже открытом соединении.
Частые замеры служба делает одной сессией на бэкап: статистику СУБД — через
`stats-watch` хелпера дампов, место под scratch на KVM — через SFTP. Если на
хосте СУБД таких строк по одной на замер, там старый хелпер: обновите его из
текущего комплекта. На хосте KVM — выключен SFTP (`Subsystem sftp` в
`sshd_config`). Остальные строки — это несколько команд на каждый бэкап. Чтобы
убрать и их, верните `LogLevel INFO` или отфильтруйте эти строки для
пользователя службы в rsyslog/journald.

## 8. Бэкапы и инкременты

### `Disk is locked` (HTTP 409) и `диски заблокированы`

Бэкап движка, который не закрыли, держит диски ВМ, и следующий бэкап получает
`409 Cannot backup VM: Disk is locked`. Так бывает, если служба упала или
перезапустилась посреди бэкапа, оборвалась связь с движком или старая версия не
разобрала ответ движка.

Отдельный кратковременный вариант встречается на oVirt 4.3 сразу после
создания снапшота или завершения передачи предыдущего тома: снапшот уже имеет
статус `ok`, но `POST /imagetransfers` ещё отвечает `Cannot transfer Virtual
Disk: ... locked`. Служба повторяет только такой HTTP 409 каждые 5 секунд до
10 минут. Ошибки запроса, доступа и сети не повторяются. Если блокировка не
снялась за это время, это уже не переходное состояние — проверьте остатки по
инструкции ниже.

Служба убирает за собой сама: перед каждым бэкапом, ещё до заморозки гостя, она
закрывает на движке свои брошенные бэкапы и отменяет их передачи образов. Для
snapshot-бэкапов oVirt 4.3 связь определяется также по `image_id` тома: именно
его старый API возвращает в `image_transfer.snapshot.id` вместо UUID снапшота
ВМ. После `cancel` служба ждёт терминальной фазы передачи и только затем
открывает новый ticket — один принятый HTTP-ответ ещё не означает, что диск
уже разблокирован.

Остальное убирается по кнопке — например, после аварии хоста, когда он
вернулся в строй. На странице ВМ (карточка «Остатки бэкапов на движке») и в
карточке упавшего запуска («Остатки бэкапа на движке»):

- **Проверить остатки** — ничего не меняет, показывает открытые бэкапы движка,
  зависшие передачи образов и брошенные снапшоты по ВМ: чьё это (служба или
  нет), состояние, будет ли убрано и почему;
- **Убрать остатки службы** — после подтверждения со списком действий служба
  закрывает свои брошенные бэкапы, отменяет их передачи и запускает удаление
  своих снапшотов, включая служебный снапшот, который движок создал под бэкап.
  Если oVirt 4.3 ещё держит диск после закрытия передачи, DELETE повторяется
  каждые 5 секунд до 10 минут; принудительная разблокировка не выполняется.
  Слияние слоёв при удалении снапшота идёт на движке: диски освободятся, когда
  снапшот исчезнет из списка («Проверить остатки» ещё раз). Пока идёт бэкап
  ВМ, кнопка ничего не делает — он убирает за собой сам.

Нужно право «Восстанавливать, проверять, удалять» (`backups.write`); действие
пишется в журнал аудита. Если бэкап не закрывается, в отчёте указан хост, на
котором он шёл: закрытие выполняет VDSM на этом хосте, и пока хост недоступен,
бэкап висит в `ready`.

Снимать блокировку в базе движка (`unlock_entity.sh`) служба не будет никогда:
движок не знает, закончилась ли операция на хосте, и снятая блокировка с диска,
по которому ещё идёт слияние или бэкап, портит образ.
В хронологии запуска это видно как «Закрыт брошенный бэкап движка». Своим
считается бэкап с описанием `jhvirt run <id>`, бэкап, чей идентификатор записан
в запуске, и бэкап, оставленный запуском с ошибкой разбора ответа движка
(его время создания совпадает с запуском).

Чужие бэкапы, например другой системы копирования, служба не трогает. Если диски
держит такой бэкап, или свой закрыть не удалось, или блокировку держит что-то
другое (передача образа, снапшот, перенос диска), запуск завершается ошибкой, а
в его карточке появляется блок **«Что сделать вручную»**. Там готовые команды:
адрес движка, пользователь, идентификаторы ВМ, бэкапов, передач и дисков, а
также сертификат движка уже подставлены. Команды не нужно править: скопируйте и
выполните по порядку, пароль curl спросит сам. Шаги с пометкой «осторожно» —
закрытие чужого бэкапа и `unlock_entity.sh` на хосте движка — выполняйте, только
если выполнены условия, описанные в шаге.

Не запускайте новый бэкап, пока диски не освободились: команда «Проверить, что
диски освободились» должна показать `"status": "ok"` у всех дисков.

### `получение карты экстентов … HTTP 500` от ovirt-imageio

Карту занятых областей диска строит `ovirt-imageio` на хосте, и 500 означает,
что он сам не смог её посчитать. Причину пишет его журнал на хосте, где
открыта передача (в сообщении — адрес вида `node-01…:54322`):

```bash
sudo grep -iE 'error|exception|extents' /var/log/ovirt-imageio/daemon.log | tail -40
```

Служба переспрашивает карту через 10 секунд. Если снова отказ, **полный**
бэкап продолжается без карты: диск читается целиком, а нулевые области не
сохраняются, потому что при восстановлении отсутствующий чанк и так нулевой.
В хронологии это отметка «Карта экстентов недоступна — диск прочитан целиком».
Бэкап идёт дольше — читается весь выделенный объём, а не только занятый, — но
копия полная и корректная. **Инкрементальный** бэкап без карты изменённых
блоков невозможен: он завершается ошибкой, и нужно разбираться с журналом
`imageio`.

### `imageio PUT …: HTTP 500` при восстановлении или проверке загрузкой

Запись диска на движок через imageio оборвалась ответом 500 через несколько
секунд или минут после начала. Если целевой домен блочный (iSCSI, FC) и диск
создаётся тонким qcow2, причина обычно в размере тома: движок создаёт такой
том маленьким (около 1 ГиБ) и расширяет его, только пока в него пишет
запущенная ВМ. Во время загрузки через imageio ВМ не запущена, и запись
упирается в конец тома.

Служба задаёт начальный размер тома (`initial_size`) под объём данных копии и
метаданные qcow2 — так же, как это делают инструменты oVirt при загрузке
дисков. Для диска 300 ГиБ с 181 ГиБ данных это около 182 ГиБ, а не полный
размер. Если ошибка повторяется на файловом домене (NFS), смотрите журнал
imageio на хосте: `sudo journalctl -u ovirt-imageio --since -1h`.

### В движке долго стоит `Sent N of M MB` при восстановлении

Счётчик движка сравнивает переданные диапазоны с полным виртуальным размером
диска. Для нового тонкого диска служба не посылает нулевые области. Поэтому у
диска 300 ГиБ с 27 ГиБ занятых блоков значение может остановиться примерно на
`Sent 27000 of 307200 MB`, хотя все полезные данные уже переданы: после этого
ImageIO выполняет `flush` и движок завершает transfer. Во время `flush` этот
счётчик не растёт.

В Web нужно смотреть этап и строку «последнее продвижение», а в журнале —
сообщение `операция передачи долго не завершается`. Оно различает:

- `reading_backup` — служба ждёт чтение или декодирование блока из хранилища
  резервных копий;
- `writing_imageio` — не завершился HTTP PUT на узел imageio; проверяются сеть,
  `ovirt-imageio` и задержки домена хранения;
- `imageio_flush` — данные отправлены, но imageio ещё фиксирует их и метаданные
  qcow2 на домене.

В сообщении также есть ID передачи, ID и имя диска, узел imageio, смещение и
длина текущего диапазона. Ticket URL в журнал не выводится.

Если диск с таким статусом остался после перезапуска службы, это брошенный
ImageTransfer, а не продолжающийся `flush`. Служба сохраняет `transfer_id` у
восстановления. При следующем запуске она отменяет незавершённые собственные
upload-передачи, ждёт освобождения диска и помечает прерванные восстановления
и проверки ошибкой. Для старых записей без `transfer_id` собственная передача
находится по UUID созданного ими диска.

Если данные диска передались полностью, но создание проверочной ВМ закончилось
ошибкой `Cannot attach Virtual Disk: Disk is locked`, приложение попыталось
подключить диск раньше завершения ImageTransfer. Ответ на `finalize` означает
только принятие команды движком, а не немедленное снятие блокировки. Служба
теперь ждёт фазу `finished_success`, затем статус диска `ok` и только после
этого создаёт disk attachment.

### `чтение диапазона … imageio GET …: HTTP 500` на oVirt 4.3

Так выглядела ошибка полного бэкапа, сравнения блоков и основы цепочки QCOW2
на движке без Backup API:

```text
ни один диск не сохранён: копирование диска ADV-GITLAB_Disk1: чтение диапазона 0+33554432
после 5 попыток: imageio GET https://host:54322/images/<ticket>: HTTP 500: Server failed to perform the request
```

`ovirt-imageio` 1.x из oVirt 4.3 отдаёт файл тома как есть. У тома qcow2 —
тонкого диска или любого диска, у которого уже есть снапшоты, — это байты
формата qcow2 одного слоя, а не содержимое диска. Служба же читала том
диапазонами как сырой диск. Когда слой короче диапазона, демон падал на конце
файла с 500. А когда длиннее, в копию легли бы неверные данные. Превращать
qcow2 в сырой поток imageio умеет только с oVirt 4.4.

Теперь том qcow2 на таком движке скачивается целиком вместе с цепочкой
предков из снапшотов ВМ, слои связываются через `qemu-img`, и на чанки
раскладывается собранный сырой образ. Том raw без предков — это и есть диск,
его служба по-прежнему читает диапазонами. Нужно:

- `qemu-img` на сервере службы (`backup.qemu_img_path`). Без него запуск
  останавливается до заморозки гостя и снапшота, а страница ВМ предупреждает
  заранее;
- место в `backup.temp_dir` под тома цепочки и собранный образ самого большого
  диска. Образ разреженный: он занимает столько, сколько в диске данных.

Если ошибка 500 остаётся и на новой сборке, причину пишет журнал демона на
хосте из сообщения:

```bash
sudo grep -iE 'error|exception|traceback' /var/log/ovirt-imageio-daemon/daemon.log | tail -40
```

### Таймаут `POST /imagetransfers` при проверке загрузкой

Если после готовности диска открытие передачи обрывается через 20 секунд с
`Client.Timeout exceeded while awaiting headers`, это лимит API-клиента, а не
ошибка копирования. Движок мог уже создать ImageTransfer и заблокировать диск,
хотя служба не получила ответ. Для открытия передачи восстановления используется
`backup.transfer.request_timeout` (по умолчанию 2 минуты), независимо от короткого
таймаута опроса инвентаря. В журнале сохраняются начало ожидания, лимит запроса,
ID передачи и её фаза; длительное открытие также выдаёт предупреждения.

После потери ответа служба ищет передачу только для нового диска этой операции:
по `disk.id`, а на oVirt 4.3 — также по `image.id`. Найденная единственная загрузка
продолжается без повторного POST. Передачи существующих дисков автоматически
не подхватываются. Если нужную передачу не удалось определить, проверьте её
состояние в движке до повторного запуска проверки.

Длительная подготовка может быть связана с VDSM, ImageIO или доступом к домену
хранения. События `Multipath devices without valid paths` требуют проверки
путей к LUN на указанном гипервизоре; один таймаут API не доказывает эту причину.

### `Cannot remove Snapshot: The following disks are locked`, хотя диск свободен (oVirt 4.3)

Удаление снапшота (или новая передача тома) получает HTTP 409 `The following
disks are locked`, а в портале администратора диск в состоянии OK. Блокировку
держит незавершённая передача образа (ImageTransfer): движок блокирует диск в
памяти на всё время передачи и не показывает это в статусе диска. На oVirt 4.3
брошенная передача переходит в `paused_system` и остаётся там до отмены — у
старого движка нет `timeout_policy=cancel`. Так бывает, если служба
перезапустилась посреди скачивания тома.

Пометить передачу на 4.3 нечем, поэтому служба записывает идентификатор каждой
открытой ею передачи в хронологию запуска («Открыта передача образа»). По этой
записи:

- при старте службы передачи прерванных запусков отменяются до удаления их
  снапшотов;
- перед каждым snapshot-бэкапом отменяются передачи завершившихся запусков этой
  ВМ, и служба ждёт, пока движок их закроет;
- кнопка «Убрать остатки» сначала закрывает такие передачи, потом удаляет
  снапшоты.

Если диск держит передача, которую служба не открывала или открыла версия до
этой записи, служба её не трогает: её могла открыть другая система или
администратор. Бэкап тогда останавливается **до создания снапшота**, с номером
передачи в ошибке и командами в блоке «Что сделать вручную». Убедитесь, что
передача брошена, и отмените её:

```bash
curl -s -k -u 'admin@internal' -X POST -H 'Content-Type: application/json' -d '{}'   'https://<engine>/ovirt-engine/api/imagetransfers/<id>/cancel'
```

Передачи ВМ с фазами видны так:

```bash
curl -s -k -u 'admin@internal' -H 'Accept: application/json'   'https://<engine>/ovirt-engine/api/imagetransfers' | grep -oE '"(id|phase)" *: *"[^"]*"'
```

После отмены передача переходит в `cancelled` за несколько секунд — минуту, и
блокировка снимается. Затем повторите «Убрать остатки» или бэкап.
`unlock_entity.sh` здесь не нужен: блокировка не в базе движка, а в памяти
команды передачи.

### «Движок держит диск»: следующий том цепочки ждёт (oVirt 4.3)

На движке без Backup API тома снапшота скачиваются по одному, и каждый том —
отдельная передача того же диска. Движок открывает её, только когда диск
свободен, иначе отвечает HTTP 409 `The following disks are locked`. На oVirt
4.3.10 бывает, что после завершения передачи предыдущего тома (finalize,
передача уже в конечной фазе) движок продолжает держать диск десятки минут —
до вмешательства администратора.

Пока движок отвечает 409, служба раз в минуту спрашивает его, что держит
диск, и пишет ответ в журнал и в хронологию запуска («Движок держит диск»):
статус диска, незавершённые передачи диска с фазами, тома в статусе `locked`,
снапшоты в операции. Если диск держит передача, открытая этим же запуском,
служба отменяет её сама. Ждёт она не дольше `backup.transfer.lock_wait`
(10 минут по умолчанию) и не повторяет ожидание: отказ движка — не обрыв
потока. После этого запуск останавливается с диагнозом по тому, что показал
движок, а в блоке «Что сделать вручную» появляются команды.

| Что показал движок | Что это значит | Что делать |
|---|---|---|
| Незавершённая передача диска | Её открыл не этот запуск: администратор, другая система или прежняя версия службы | Если передача брошена — отменить командой из карточки |
| Снапшот в операции (`locked`) | Идёт создание или удаление снапшота со слиянием | Дождаться окончания; прерывать нельзя |
| Том в статусе `locked`, передач нет | Том остался заблокированным после отменённой передачи (см. ниже) | Администратор oVirt: `unlock_entity.sh -t disk <id>` на хосте движка |
| Ничего | Блокировку держит незавершённая команда в памяти движка | Администратор oVirt: перезапуск `ovirt-engine` |

**Том застрял в `locked` после отменённой передачи.** На oVirt 4.3.10
наблюдалось: после отмены (cancel) передачи тома снапшота этот том остаётся в
статусе `locked` в базе движка, тогда как после finalize — нет. Сам он не
отпускается: каждая
следующая передача тома и удаление снапшота с этим томом получают 409, хотя
диск в портале в состоянии OK, а передач нет. Так застрял том после
запусков, которые обрывались на HTTP 500 и отменяли передачу.

Служба больше не отменяет передачи скачивания: и после сбоя она закрывает их
через finalize, а cancel использует, только если движок finalize не принял.
Finalize скачивания образ не меняет — движок лишь закрывает сеанс, — и том
отпускается штатно. Уже застрявший том служба показывает в карточке «Остатки
бэкапов на движке» (предупреждение и блок «Что движок показывает о дисках») и
даёт команды администратору oVirt: сначала посмотреть блокировки
(`unlock_entity.sh -t disk -q`), затем снять их с томов диска
(`unlock_entity.sh -t disk <id диска>`). Снимать можно, только если передач
диска нет и снапшоты не в операции — это видно в том же отчёте. После этого
нажмите «Убрать остатки».

**Уборка перед каждым бэкапом.** На движке без Backup API служба перед
созданием нового снапшота сама удаляет брошенные снапшоты ВМ (не дольше 30
минут; если движок ещё сливает слои, бэкап дождётся окончания). Снапшот с
застрявшим томом пропускается сразу, без 10 минут ожидания 409, и не мешает
удалить остальные. Если застрявший том входит в цепочку диска — а у диска со
снапшотами это любой его том, — бэкап останавливается до создания нового
снапшота: движок этот том не отдаст, а новый снапшот только удлинил бы
цепочку. Как только администратор oVirt снимет блокировку, следующий бэкап сам
удалит оставшийся снапшот и пройдёт.

**Бэкап через клон снапшота, пока блокировку не сняли.** По умолчанию
(`backup.transfer.clone_fallback: true`) служба не останавливается, а
обходит застрявший том: как обычно замораживает гостя и создаёт снапшот,
затем просит движок клонировать из снапшота временную ВМ. Цепочку томов
движок собирает сам на хосте — статус locked в его базе этому не мешает, —
и у дисков клона по одному тому. Служба скачивает их одной передачей на диск
в копию исходной ВМ, затем удаляет клон вместе с дисками и свой снапшот. В
хронологии запуска это видно как «Бэкап через клон снапшота».

Цена обхода — полная копия дисков на том же домене хранения на время бэкапа
(движок сам проверит, хватит ли места) и время на копирование: оно ограничено
`backup.transfer.clone_timeout` (6 часов по умолчанию). Клон создаётся
выключенным и в сеть не подключается. Имя клона — `jhv-clone-<ВМ>-<запуск>`,
в описании — метка `jhv-clone:<id запуска>`; если служба оборвётся посреди
бэкапа, брошенный клон удаляется перед следующим бэкапом этой ВМ. Снапшот с
застрявшим томом при этом остаётся — удалить его по-прежнему можно только
после снятия блокировки администратором oVirt.

Диск клона в формате raw (на файловых доменах движок обычно создаёт такой)
служба читает диапазонами прямо в хранилище — временный каталог не нужен.

### `no space left on device` во временном каталоге (oVirt 4.3)

На движке без Backup API тома qcow2 скачиваются целиком и собираются в образ
локально, и только потом данные пишутся в хранилище. Пока идёт скачивание, в
карточке запуска растёт только «прочитано», «записано» остаётся 0 — в
хронологии это видно как «Сборка образа из томов» с каталогом, где идёт
сборка. Места нужно под данные диска (для цепочки qcow2 — примерно вдвое
больше).

Установщик по умолчанию ставит `backup.temp_dir` (`JHV_BACKUP_TEMP_DIR`) в
`/restores/.tmp` — на корневой раздел сервера, который обычно мал. Служба
проверяет место до заморозки гостя и снапшота. Если во временном каталоге
места мало, а хранилище бэкапа локальное, образ собирается в его служебной
области `<хранилище>/.jhvirt/tmp` — там, куда потом пишутся и данные. Если
места нет и там, бэкап останавливается до снапшота с объяснением. Чтобы
выбрать каталог явно, укажите `JHV_BACKUP_TEMP_DIR` на разделе с местом.

**Без доступа к хосту движка.** Всё, что нужно для диагноза, служба берёт
через REST API движка с правами своего подключения:

- на странице ВМ, в карточке «Остатки бэкапов на движке», кнопка
  «Проверить остатки» показывает по каждому диску статус, незавершённые
  передачи с фазами, тома и снапшоты в `locked`, а ниже — последние события
  движка по ВМ (его журнал через API);
- тот же журнал событий в ошибке запуска и в журнале службы;
- брошенную передачу можно отменить через API — команда в блоке «Что сделать
  вручную» выполняется с сервера службы.

Через API нельзя только снять блокировку, которую движок держит без видимой
причины: для этого нужен хост движка (`unlock_entity.sh` или перезапуск
`ovirt-engine`), и это делает администратор oVirt. Перезапуск не
останавливает ВМ, но прерывает идущие через движок операции (миграции,
снапшоты, передачи), а портал недоступен пару минут.

События движка по диску через API, с сервера службы:

```bash
curl -sS -u 'admin@internal' -H 'Accept: application/json'   'https://<движок>/ovirt-engine/api/events?max=300'   | grep -oE '"description" *: *"[^"]*ADV-GITLAB_Disk1[^"]*"' | head -20
```

Для администратора oVirt — что искать в журнале на хосте движка:

```bash
sudo grep -E 'ADV-GITLAB_Disk1|<id диска>|<id передачи>' /var/log/ovirt-engine/engine.log | tail -80
sudo grep -iE 'EngineLock|Failed to (acquire|release) lock' /var/log/ovirt-engine/engine.log | tail -40
```

Каждый упавший запуск на 4.3 может оставить свой снапшот, а каждый снапшот
удлиняет цепочку ещё на один том — и на одну передачу. Поэтому, сняв
блокировку, сначала уберите остатки ВМ кнопкой «Убрать остатки» и только
потом запускайте бэкап.

### Бэкап oVirt 4.3 остановился на одном объёме данных

Полное скачивание qcow2-тома — один длинный HTTP-поток. TCP-соединение может
остаться формально открытым, хотя `ovirt-imageio`, прокси или сеть больше не
передают байты. Раньше у этого потока не было предела бездействия: размер
временного файла и счётчик в интерфейсе (например, 659 МиБ) переставали расти,
а запуск продолжал считаться работающим.

Теперь `backup.transfer.request_timeout` для такого потока означает именно
**время без единого полученного байта**, а не общую длительность скачивания.
Таймер сбрасывается на каждом блоке, поэтому исправная передача большого диска
может идти часами. Если данных нет дольше предела, служба отменяет ticket,
дожидается его закрытия и открывает новый. Выполняется не более трёх попыток.

`ovirt-imageio` 1.x не поддерживает надёжное продолжение полного тома через
HTTP `Range`, поэтому каждая попытка текущего тома начинается с нуля и
перезаписывает только временный файл. Уже сохранённые точки и чанки не
повреждаются. Если движок не подтвердил отмену ticket, автоматический повтор
не начинается: запуск останавливается с командами диагностики в блоке
«Что сделать вручную», чтобы не открыть две передачи одного диска.

### `HTTP 403: … No such ticket` при копировании диска

Билет передачи на хосте удалён: движок закрыл передачу посреди копирования —
чаще всего по таймауту неактивности (`inactivity_timeout`), когда по билету
долго не было запросов. Так случалось на больших дисках: запрос карты
экстентов идёт один и долго, а движок, судя по всему, не считает его
активностью.

Служба выставляет передачам таймаут неактивности не короче самой долгой
операции на них: для копирования — 30 минут (предел запроса карты), при
сверке с источником и восстановлении — предел от размера диска. Если билет
всё же пропал, служба открывает новую передачу того же диска и продолжает с
того же блока — уже прочитанное не повторяется. В хронологии это отметка
«Передача образа открыта заново». После трёх потерь на одном диске запуск
завершается ошибкой: это уже не случайность. Причину покажет журнал движка:

```bash
sudo grep -iE 'inactivity|Transfer was stopped|paused' /var/log/ovirt-engine/engine.log | tail -20
```

### `dial tcp …:54322: connect: no route to host` при копировании

Сервер копий читает диск прямо с хоста, где работает ВМ (`ovirt-imageio`,
порт 54322), и в какой-то момент перестал до него доставать. «No route to
host» бывает, когда хост пропал из сети или межсетевой экран отвечает
отказом (`REJECT … icmp-host-prohibited` у firewalld).

Служба пережидает такие сбои: сетевые ошибки повторяются с нарастающей
паузой в течение минуты. Если хост так и не ответил, чтение продолжается
через прокси движка (порт 54323) тем же билетом — ещё до 5 минут повторов. В
хронологии это отметка «Чтение переключено на прокси движка». Если прокси
выбран изначально (`backup.transfer.prefer_proxy: true`), запасного пути нет.

Что проверить, если сбой повторяется:

```bash
timeout 5 bash -c '</dev/tcp/10.249.16.51/54322' && echo доступен || echo недоступен
```

```bash
sudo firewall-cmd --list-all | grep -E '54322|imageio'; sudo journalctl -u firewalld -u ovirt-imageio --since '-2h' | tail -40
```

Первую команду выполните на сервере копий (подставьте адрес хоста из
ошибки), вторую — на хосте. Если прямой путь к хостам ненадёжен, а к движку
надёжен, включите `backup.transfer.prefer_proxy: true`: весь поток пойдёт
через движок, медленнее, но одним маршрутом.

### Бэкап стал полным вместо инкрементального

Это может быть защитным fallback, а не ошибка. Проверьте причину в карточке
запуска:

- отсутствует родительская точка;
- checkpoint удалён или не совпадает;
- диск raw и не поддерживает persistent dirty bitmap;
- изменился состав дисков;
- политика задания разрешает полный fallback.

Не переключайте fallback на `fail`, пока не устранена причина: это превращает
полную, но более дорогую копию в отсутствие копии.

После каждого успешного бэкапа служба удаляет свои checkpoint-ы, которые уже не
станут основой: остаются точки последней копии и последней полной по каждому
хранилищу. Если основа всё же пропала — например, у задания после ротации
удалили последние копии, — следующий бэкап станет полным. Это ожидаемо. Как
устроена ротация — в [HOT-BACKUP.md](HOT-BACKUP.md#2-инкременты-и-checkpoint-ы).

### KVM: `на хосте кончается место под временные файлы бэкапа`

Сработал сторож scratch. Пока бэкап был открыт, гость перезаписал столько ещё
не прочитанных блоков, что свободного места на томе `scratch_dir` стало меньше
запаса. Служба закрыла бэкап, чтобы запись гостя не начала получать ошибки;
scratch освобождён, ВМ работает.

- Посмотрите место на томе: `df -h <scratch_dir>` на хосте.
- Перенесите `scratch_dir` подключения на том побольше или освободите место.
- Запускайте бэкап этой ВМ в часы меньшей записи.
- Уберите или ослабьте предел чтения у задания: чем быстрее служба читает, тем
  меньше блоков успевает отложиться.

Пик scratch у удачных запусков виден в хронологии, в отметке «Данные
скопированы», — по нему удобно подобрать размер тома. Подробнее — в
[HOT-BACKUP.md](HOT-BACKUP.md#5-место-под-scratch-на-kvm).

### Proxmox: `предел чтения не применён` или `fleecing не применён`

Бэкап прошёл, но без части параметров; причина — в отметке «Данные
скопированы»:

- **«помощник на узле его не поддерживает»** — на узле старый
  `jhvirt-pve-data-plane`. Переустановите его из текущего комплекта
  (см. [DEPLOY.md](DEPLOY.md#proxmox-ve-канал-данных-для-backuprestore)) и
  проверьте: `probe` должен ответить `jhvirt-pve-data-plane/2`.
- **«на узле Proxmox VE старше 8.2»** — fleecing появился в 8.2; обновите узел
  или оставьте поле «Хранилище для fleecing» пустым.

Если `vzdump` падает с ошибкой про хранилище fleecing, проверьте, что указанное
хранилище есть на узле, где работает ВМ: `pvesm status`.

### Инкременты недоступны

Для KVM нужны qcow2, libvirt с Backup API и рабочие persistent dirty bitmap.
Для oVirt нужны поддерживаемая версия движка и режим incremental хотя бы на
одном диске. Raw-диски копируются полностью — на oVirt 4.4.5+ в том же
инкрементальном бэкапе, остальные диски которого идут изменениями.

Если в хронологии «Инкремент снят полной копией», движок старше 4.4.5 не принял
смешанный бэкап. Обновите движок или включите режим incremental на всех дисках
ВМ (для raw — сначала перевести их в qcow2). Следующие 7 дней инкременты этой
ВМ по заданию сразу идут полными, причина — в отметке «Бэкап запущен». Чтобы
после обновления движка не ждать неделю, запустите разовый инкремент со
страницы ВМ: разовый запуск память не учитывает. Если движок его примет,
следующие запуски по заданию снова пойдут инкрементами.

### Временный snapshot не удалился

Оставленный snapshot `jhvirt backup <run-id>` растит цепочку образов, замедляет
диск, расходует место storage domain и занижает оценки объёма: движок считает
занятым только верхний том.

Служба убирает такие snapshot сама. После каждого бэкапа ВМ на oVirt она в
фоне удаляет свои брошенные snapshot — по одному, дожидаясь конца слияния
слоёв. В хронологии запуска это отметки «Удалён брошенный снапшот». Брошенным
считается snapshot с описанием `jhvirt backup <run-id>`, если этот запуск уже
закончился; если запуска нет в базе — только snapshot старше 6 часов: свежий
мог создать запуск, который ещё идёт, в том числе на другой установке службы.
Не трогаются snapshot администратора, snapshot в состоянии `locked`, а при ВМ в
режиме предпросмотра snapshot уборка не выполняется вовсе.

Слияние держит диски, поэтому следующий бэкап ВМ сначала ждёт его окончания —
до часа, с отметкой «Ожидание операции со снапшотом». Если бэкап начался, пока
уборка не закончилась, уборка останавливается и продолжится после него.

Если движок отказался удалить snapshot (например, не хватает места в storage
domain), в хронологии появляется «Не удалось удалить брошенный снапшот», а в
карточке запуска — блок «Что сделать вручную» с готовыми командами:
посмотреть snapshot ВМ, удалить нужный, проверить результат. То же можно
сделать в интерфейсе oVirt: ВМ → Snapshots → Delete.

### Задание отвечает `409 job_busy`

Предыдущий запуск того же задания ещё выполняется. Второй экземпляр намеренно
не стартует. Проверьте скорость хранилища, превратился ли инкремент в полный,
расписание и `max_duration`. При необходимости отмените текущий запуск.

### Хранилище недоступно

В интерфейсе нажмите **Проверить**: операция делает запись, чтение, сверку и
удаление пробного объекта. Затем проверяйте DNS, сеть, учётные данные, права,
свободное место и квоту целевого хранилища.

Для SMB и WebDAV частые причины разобраны отдельно, с расшифровкой кодов
`NT_STATUS_*` и ответов `401`/`403`/`405`/`409`, — в разделе «Сетевые хранилища:
SMB и WebDAV» руководства по эксплуатации.

### В «Защите» запуск просрочен, хотя ручная копия свежая

Качество привязано к заданию и реплике. Разовая копия или копия другого
задания не доказывает, что проверяемое расписание работает. Сверьте:

```bash
# часовой пояс и догоняющий запуск
grep -A4 '^scheduler:' /opt/jhvirt/config/ovirt-backup.yaml

# фактические общие запуски через API
curl -s -b cookies.txt 'http://127.0.0.1:8080/api/v1/job-runs?limit=20'
```

Проверьте `next_run_at`, системное время и часовой пояс контейнера/службы. После
простоя строка со статусом `missed` содержит `missed_intervals`. При
`catch_up_missed: true` выполняется только последняя пропущенная точка; при
`false` ни одна не запускается. Если причина `предыдущий запуск ещё
выполняется`, расписание короче реальной длительности: ускорьте хранилище,
разредите cron или скорректируйте `max_duration`.

### Основная копия успешна, но ВМ всё равно в ошибке

Откройте колонку «Худшая реплика». Каждое хранилище обязательно: сбой любой
реплики не закрывается успехом локальной копии. Исправьте именно указанное хранилище и
дождитесь следующего общего запуска. Явно исключённые в задании диски не
считаются дефектом; любой другой пропущенный диск делает реплику неполной.

### Хранилище показывает «квота неизвестна»

Это штатно для S3: протокол не сообщает свободное место bucket. Для SFTP
сервер мог не реализовать `statvfs`, а для WebDAV — не отвечать на свойства
квоты из RFC 4331; простой `mod_dav` их обычно не отдаёт, Nextcloud и ownCloud
отдают. SMB сообщает место всегда. Занятый объём и суточный рост при этом
остаются достоверными; не заменяйте неизвестную квоту вымышленным размером.
Для локального/NFS пути проверьте, что служба видит нужное монтирование, а не
пустой каталог на системном разделе.

### `/metrics` отвечает `404`

Экспорт выключен. Проверьте эффективные параметры:

```bash
sudo grep '^JHV_METRICS_' /opt/jhvirt/config/jhvirt.env
sudo test -s /opt/jhvirt/config/metrics.token && echo token-ok
```

Нужны `JHV_METRICS_ENABLED=true` и путь к непустому файлу. После ручной правки
перезапустите службу. Docker-установка хранит token-файл внутри
`ovirt-backup_jhvirt-data` по пути `/app/data/metrics.token`.

### `/metrics` отвечает `401`

Не передана схема `Bearer`, токен не тот либо Prometheus читает другой файл:

```bash
curl -v -H "Authorization: Bearer $(sudo cat /opt/jhvirt/config/metrics.token)" \
  http://127.0.0.1:8080/metrics
```

Не используйте пароль пользователя, cookie или `auth.api_tokens`. Проверьте,
что копия token-файла у Prometheus не содержит лишней строки/пробела и доступна
его системному пользователю. Исходный файл оставьте `0600` владельца `jhvirt`.

### Служба не стартует после включения метрик

`-check-config` отклоняет отсутствующий, пустой, не обычный или доступный группе
token-файл. Для systemd:

```bash
sudo chown jhvirt:jhvirt /opt/jhvirt/config/metrics.token
sudo chmod 600 /opt/jhvirt/config/metrics.token
sudo systemctl restart jhvirt
```

Не помещайте токен непосредственно в unit или командную строку: они видны в
`systemctl show` и истории оболочки.

## 9. Проверка `boot` на KVM

### Проверка через движок: «места не хватит»

Проверочная ВМ восстанавливается на выбранный домен хранения. Перед созданием
служба сверяет место по свежим цифрам движка и оставляет запас, как сторож
домена при горячем бэкапе: 5 % объёма домена, но не меньше 10 ГиБ. Если данные
дисков с запасом не помещаются, проверка не начинается и ничего не создаёт.

- Выберите другой домен: форма задания и диалог проверки показывают оценку
  по каждому домену.
- Или освободите место.
- На блочном домене (iSCSI, FC) движка без Backup API диск восстанавливается
  полным, поэтому там нужен весь размер дисков, а не только данные.

### Проверка через движок: «ВМ запустилась, но гостевой агент не ответил»

Движок сообщает ответ агента не сразу: VDSM опрашивает агента раз в
минуту-другую. Ожидание по умолчанию — 15 минут. Если агента в госте нет,
загрузку ОС подтвердить нечем: установите `qemu-guest-agent` в исходной ВМ.

Проверочная ВМ называется `jhv-verify-<имя ВМ>-<идентификатор>`. Если убрать
её не удалось, отчёт проверки об этом скажет — удалите её в портале вместе с
дисками.

### `KVM-хост не поддерживает профиль`

Целевой хост не подтвердил сочетание архитектуры и machine type через
`ConnectGetDomainCapabilities`. Проверьте:

- архитектура хоста совпадает с гостем;
- установлен QEMU нужной архитектуры;
- для UEFI установлен OVMF/AAVMF;
- для Secure Boot доступна прошивка с enrolled keys;
- machine family `pc`, `q35` или `virt` доступна на хосте.

### `/dev/kvm` отсутствует

Проверка требует аппаратной виртуализации. Убедитесь, что она включена в
BIOS/UEFI хоста и модуль KVM загружен:

```bash
test -c /dev/kvm && echo ok
lsmod | grep '^kvm'
```

Docker Desktop без проброса `/dev/kvm` не является реальным KVM-стендом.

### Не хватает места в scratch

Сервис заранее сравнивает свободное место с суммой занятых чанков дисков.
Освободите место или измените scratch-каталог в подключении KVM. Не размещайте
scratch на системном разделе без запаса.

### ВМ запустилась, но guest agent не ответил

Проверочная ВМ создаётся без сети. Ответ должен прийти по virtio channel.
Проверьте в исходном госте:

```bash
systemctl status qemu-guest-agent
```

Агент должен быть установлен, включён и ожидать канал
`org.qemu.guest_agent.0`. Без агента результат не доказывает, что ОС не
загрузилась; он означает, что автоматического подтверждения нет.

### Проверочная ВМ выключилась или аварийно завершилась

Смотрите консоль и журнал libvirt/QEMU на гипервизоре. Частые причины:
несовместимая прошивка, отсутствующий загрузчик, неправильный boot order,
драйвер дисковой шины или повреждённая цепочка. Временно включайте
`keep_on_failure` только для диагностики и затем вручную удаляйте transient-ВМ
и все `jhv-verify-*` образы.

### Почему у проверочной ВМ нет сети

Это обязательная защита, а не ошибка. Восстановленная production-ВМ может
занять существующий IP, зарегистрироваться в каталогах и начать писать во
внешние системы. Успех подтверждается guest agent, сеть для этого не нужна.

## 10. Восстановление

### `каталог не разрешён`

Добавьте путь в `backup.restore_dirs`. Для systemd также добавьте его в
`ReadWritePaths`; для Docker смонтируйте каталог в контейнер и перечислите в
`JHV_RESTORE_DIRS`. Перезапустите приложение.

### `permission denied` при записи файла

Проверьте права пользователя/контейнера, NFS root squash, SELinux/AppArmor,
mount в Docker и systemd sandbox. Не запускайте приложение от root как
постоянное исправление.

### Цепочка повреждена или отсутствует родитель

Нельзя восстановить инкремент без всех родителей до полной точки. Проверьте
архив независимо от БД:

```bash
jvbackup list -repo /srv/backups
jvbackup verify -repo /srv/backups -run <run-id>
```

Восстанавливайте другую целую точку. Не редактируйте `run.json` и манифесты
вручную: это скроет симптом, но не вернёт отсутствующие данные.

### `qemu-img` не найден

Он нужен для qcow2-дисков на oVirt 4.3, экспорта qcow2 и проверки `qemu`.
Проверяется среда процесса службы: пакет, установленный только на узле Docker
или Kubernetes, контейнеру не виден. В разделе «Параметры системы» показаны
найденный путь или точная ошибка.

Для systemd на Debian/Ubuntu установите `qemu-utils`. На RHEL-подобной системе
сначала найдите пакет для конкретной версии дистрибутива:

```bash
dnf provides '*/qemu-img'
```

Затем установите найденный пакет или укажите `backup.qemu_img_path`. Для
Docker/Kubernetes пересоберите образ с пакетом внутри; штатные Dockerfile уже
включают его.

### Создание новой ВМ отклонено на preview

Не обходите blocker прямым запросом запуска. Проверьте конфликт имени,
архитектуру/firmware, объём целевого storage domain/pool и каждое
`network_mapping`. Поддерживаются только oVirt→oVirt и KVM→KVM. Исходные MAC не
переносятся, а несопоставленный NIC остаётся отключённым.

Для точки `config` отсутствие дисков ожидаемо; такая ВМ не содержит данных и не
может автоматически стартовать.

### Восстановление новой ВМ завершилось ошибкой очистки

Откройте соответствующий `restore_run`: поле результата перечисляет VM,
volumes/disks и другие ресурсы, которые rollback не смог удалить. Сначала
проверьте, что фоновая операция действительно закончилась, затем удаляйте
остатки на целевой платформе по сохранённым ID. Повторное удаление безопаснее,
чем поиск по похожему имени.

### Файловый бэкап не видит root или восстановление отвергает путь

Функция включена всегда. Без дополнительной настройки используйте root
`default`: в Docker его host-пути заданы `JHV_FILE_BACKUP_DIR` и
`JHV_FILE_RESTORE_DIR`, в systemd это `<PREFIX>/file-sources` и
`<PREFIX>/file-restores`. API принимает ID и относительный путь, не
абсолютный путь клиента. Для дополнительного Docker-root тот же абсолютный путь
должен быть bind-mounted в контейнер; для дополнительного systemd restore root
должен входить в `ReadWritePaths`.

Проверка Docker:

```bash
cd /opt/jhvirt/compose
grep -E '^JHV_FILE_(BACKUP|RESTORE)_DIR=' .env
docker compose exec ovirt-backup sh -c \
  'test -r /app/file-sources && test -w /app/file-restores'
```

Сервис отвергает `..`, выход canonical path из allowlist и переход через
symlink-родителя. Это защита, а не ошибка сопоставления. Symlink внутри набора
сохраняется как ссылка и при сканировании не обходится.

### Файловая точка имеет статус `partial`

Посмотрите `unstable_paths`. Каждый такой файл изменился во время первого
чтения и повторно изменился при единственной повторной попытке. Остановите или
переведите приложение в штатный backup mode и запустите новую точку; не
переименовывайте `partial` в success вручную.

## 11. Ключ шифрования и потеря сервиса

### `secret.key` потерян

Восстановить его математически невозможно. Без исходного ключа нельзя
расшифровать сохранённые пароли подключений и зашифрованные копии. Не создавайте
новый ключ поверх старой установки как «исправление»: он не подходит к уже
зашифрованным данным.

Восстановите точную резервную копию `secret.key` с правами `0600` и владельцем
службы, затем перезапустите приложение.

### База потеряна, но копии остались

Формат хранилища самодостаточен. Используйте `jvbackup list`, `verify` и
`restore`. Для шифрованных копий передайте сохранённый ключ. После
восстановления сервиса заново создайте подключения и задания.

## 12. Репликация, Object Lock и каталог

### Реплика остаётся `pending`

Проверьте, включено ли хранилище, есть ли свободный replication-worker и готова
ли родительская цепочка. Отключённая цель намеренно не извлекается из очереди.
Для инкремента `pending` также означает ожидание полной точки или предыдущего
инкремента в том же назначении.

```bash
curl -b cookie.txt http://127.0.0.1:8080/api/v1/replications
```

Не удаляйте очередь из БД. После исправления хранилища нажмите **Повторить**:
готовые объекты будут перепроверены, передача продолжится с первого отсутствующего.

### Реплика `failed`, хотя файлы появились

Появление части объектов ещё не означает готовую копию. Сервис полностью читает
каждый объект назначения и сравнивает SHA-256. `run.json` публикуется последним.
Проверьте свободное место, права SFTP/local, S3 `GetObject`, `PutObject`, `List*`
и, для оптимизированной копии, `CopyObject`. При отказе server-side copy сервис
может перейти на потоковую передачу, но чтение назначения всё равно обязательно.

### Реплика `locked`

Если в ошибке указан отсутствующий родитель, здоровой цепочки-источника больше
нет. Верните исходное хранилище, импортируйте доступного родителя через каталог
или создайте новую полную точку. Если `locked_until` заполнен, удаление запрещено
S3 Governance Object Lock до указанного времени; сервис не использует обход
Governance и повторит ретенцию позже.

### S3 Object Lock не включается

Object Lock должен быть включён при создании bucket; включить его только флагом
в приложении нельзя. Учётной записи нужны операции получения конфигурации
retention и публикации объекта с Governance retention. Укажите срок `1..36500`
дней. Health-объекты не блокируются, поэтому успешная обычная проверка S3 сама
по себе не доказывает поддержку Object Lock.

### Каталог показывает `conflict` или `corrupt`

`conflict` означает одинаковый `run_id`, но различающийся SHA-256 `run.json`.
Автоматически объединять такие записи нельзя: определите доверенную копию и
сохраните вторую под отдельным префиксом для расследования. `corrupt` означает,
что манифест не разобран или хеш объекта не совпал. `missing_object` и
`missing_parent` исправляются возвратом недостающих данных; импорт не создаёт
пустые заглушки.

### Аварийная готовность сообщает об ошибке

`dump stale` исправляется новым внешним `pg_dump`; `key mismatch` означает, что
скопирован не активный `secrets.key_file`. Скопируйте ключ байт в байт и задайте
файлу `0600`. Не генерируйте новый ключ: сохранённые пароли и зашифрованные
чанки старым ключом после этого не расшифровать.

## 13. Уведомления

### Оповещение есть в web, но наружу ничего не приходит

Проверьте последовательно:

1. в YAML настроен хотя бы один канал и его credentials;
2. в **Настройки → Уведомления** доставка включена, severity проходит порог, а
   per-kind policy не отключена;
3. alert не muted/snoozed и, если включено `ack_stops_repeats`, не принят;
4. в `/api/v1/notification-deliveries` есть строка нужного канала и её
   `last_error`.

`queued`/`sending` переживают перезапуск и повторяются через 1, 5, 15 и 60
минут, всего до пяти попыток. Это transport retry, а не reminder. Успешный
канал не отправляется заново из-за ошибки другого.

### Webhook получил дубликат

Доставка at-least-once. Если получатель принял запрос, а процесс завершился до
фиксации `sent`, lease вернёт строку в очередь. Дедуплицируйте webhook по
`alert_id`, `event` и `sequence`; один и тот же alert после устранения и нового
возникновения является новым событием, а не дублем.

### Напоминания слишком частые или не нужны для одного типа

Глобальный интервал и максимум задаются в **Настройки → Уведомления**. Добавьте
per-kind policy, чтобы, например, отключить внешнюю доставку
`backup_unprotected` либо назначить ей другой интервал и каналы. Для отдельного
текущего alert используйте snooze/mute: запись останется видимой в web.

## 14. Что приложить к обращению

Передавайте только необходимое и удаляйте секреты:

- версия: `ovirt-backup-server -version` или `sh ovirt-backup-*.run --version`;
- ОС и архитектура: `cat /etc/os-release`, `uname -m`;
- способ установки и фактический внешний URL без паролей;
- ответы `/healthz` и `/readyz`;
- `systemctl status`/`docker compose ps`;
- релевантный фрагмент журнала вокруг ошибки;
- код и текст HTTP-ошибки;
- для KVM: версия libvirt/QEMU, архитектура гостя, BIOS/UEFI и machine type.

Не прикладывайте `.env`, `jhvirt.env`, DSN, приватные SSH-ключи,
`secret.key`, cookie `jhvirt_session` и полные URL S3 с учётными данными.
