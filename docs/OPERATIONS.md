# Эксплуатация

Установка по шагам находится в [DEPLOY.md](DEPLOY.md). Полный каталог ошибок
Docker, systemd, PostgreSQL, авторизации, oVirt и KVM находится в
[TROUBLESHOOTING.md](TROUBLESHOOTING.md). Здесь описаны регулярные операции
после успешного развёртывания.

Пути файлов настройки, приоритет YAML и `JHV_*`, а также сохранность при
обновлении и удалении описаны в [CONFIGURATION.md](CONFIGURATION.md).

## Проверка живости

```bash
curl -fsS http://localhost:8080/healthz    # процесс отвечает
curl -fsS http://localhost:8080/readyz     # база доступна, сколько бэкапов идёт
```

Оба эндпоинта не требуют аутентификации — их вызывает балансировщик.

## Первый запуск

При установке Docker или systemd с новой локальной базой через `install.sh`
пароль `local-admin` печатает сам установщик, в конце, вместе с адресом
интерфейса. Он задаёт пароль через временный файл `0600`, после успешного
старта удаляет файл и пересоздаёт контейнер либо перезапускает службу. Поэтому
обычный рабочий процесс уже не содержит bootstrap-пароль. При включённом OIDC локальный вход по умолчанию выключен,
а пароль намеренно не показывается: повседневные администраторы должны входить
через группу `virt-admins` в Keycloak.

При подключении новой внешней PostgreSQL установщик не может заранее знать,
пуста ли удалённая таблица пользователей. Если база действительно пустая,
служба создаст администратора и один раз напечатает пароль в
`journalctl -u jhvirt`. Альтернатива — сразу выполнить описанный ниже сброс
пароля `local-admin`.

Ниже — про запуск в обход установщика (свой `.env`, systemd, ручной старт).
Тогда пароль генерирует служба и выводит один раз, отдельным блоком в stderr:

```
════════════════════════════════════════════════════════════
  СОЗДАНА УЧЁТНАЯ ЗАПИСЬ АДМИНИСТРАТОРА

  пользователь: local-admin
  пароль:       <...>
════════════════════════════════════════════════════════════
```

Блок, а не поле в строке журнала: в поле пароль оказывался в конце длинной
фразы, узкий терминал её переносил, и при копировании в пароль попадал перенос
строки. Вход тогда отвечал «неверный пароль» — сообщение, из которого причину
не видно.

В открытом виде пароль не хранится нигде: в PostgreSQL находится bcrypt-хеш.
Для сброса используется отдельный токен хоста, которого нет в рабочем
контейнере. В установке из `.run` команда одинакова для Docker и systemd:

```bash
sudo /opt/jhvirt/bin/ovirt-backup-recover-admin --user local-admin
```

Для Compose, запущенного непосредственно из репозитория:

```bash
sudo sh deploy/recover-admin.sh --mode docker --compose-dir deploy \
  --user local-admin
```

Скрипт сначала останавливает приложение, затем передаёт host-only токен по
stdin одному доверенному процессу, генерирует новый пароль и атомарно отзывает
в PostgreSQL все сессии, API-токены и делегирования. После этого рабочий
контейнер пересоздаётся из установленного образа, а systemd-служба запускается
заново. Токен не попадает в аргументы, environment, `docker inspect` или
постоянный volume. Новый пароль печатается только в терминал.

При OIDC сначала временно включите `--local-login enabled`; после ремонта
провайдера верните `--local-login disabled`. Удалять строку из `users` руками
не нужно.

Администратор приложения и администратор Keycloak — разные учётные записи.
После повторной установки пароль `kc-bootstrap-admin` намеренно не меняется и
не печатается. Если он утрачен, выполните на Docker-хосте:

```bash
sudo /opt/jhvirt/bin/ovirt-backup-recover-keycloak \
  --user kc-bootstrap-admin
```

Для Compose, запущенного из checkout:

```bash
sudo sh deploy/recover-keycloak.sh --compose-dir deploy \
  --user kc-bootstrap-admin
```

Скрипт останавливает все контейнеры сервиса `keycloak`, создаёт в master realm
одноразовый admin service account штатной командой `bootstrap-admin`, запускает
Keycloak, сбрасывает или заново создаёт постоянного администратора, проверяет
вход и права, отзывает прежние сессии и удаляет временный client. Новый пароль
печатается один раз. Realm приложения, пользователи, группы, federation, MFA и
OIDC-клиент сохраняются, поэтому после входа можно полностью перенастроить их в
административной консоли без переустановки.

Для обычного входа через кнопку Keycloak используется не эта запись, а
`backup-admin` из realm `jhvirt` или другой пользователь одной из групп
допуска. На чистой установке `backup-admin` создаёт установщик, включает его в
`virt-admins` и один раз печатает отдельный пароль. Если установка обновлена с
версии, которая не создавала прикладного пользователя, повторный запуск нового
`.run` добавит его, не меняя существующие realm и master-admin.

Потерянный пароль прикладного пользователя не сбрасывается переустановкой.
Войдите в Admin Console как `kc-bootstrap-admin`, переключитесь на realm
`jhvirt`, откройте **Users → backup-admin → Credentials → Reset password**.
Если утрачен и пароль master-admin, сначала выполните host-only
`ovirt-backup-recover-keycloak`, как описано выше.

Захват контейнера и потеря пароля — разные инциденты. При захвате процесс имеет
прикладной доступ к БД, `secret.key`, OIDC client secret и учётным данным
движков/хранилищ. Сброс закрывает доступ через приложение, но не отменяет уже
скопированные секреты и не доказывает целостность БД. Полная последовательность
ротации и проверки находится в [SECURITY.md](SECURITY.md#восстановление-после-захвата-приложения).

## Режим проверки авто-восстановления

Авто-восстановление начинает работу в режиме проверки: решения принимаются и
записываются, но не выполняются. Это не настройка, а наблюдение — у него есть
начало и конец, и оба видны в «Настройки → Система».

Этот режим относится только к автоматическому устранению сбоев: запуску VM,
активации хоста и fencing. Он не означает, что восстановление бэкапов является
тестовым, и не ограничивает проверки образов или ручное восстановление.

Пока режим включён, каждое решение сохраняется в PostgreSQL, истории режима и
его JSON-архиве: объект, подключение, предложенное действие, причина, номер
попытки и результат проверки политики. Повторяющиеся решения не засоряют
обычный журнал, шапку, список оповещений и всплывающие уведомления. Для
временной подробной диагностики установите уровень `debug`: на нём решения
пишутся в файловый журнал или поток службы.

Переключение — тумблером в интерфейсе, на ходу, без перезапуска. Выход из
режима требует подтверждения и основания: после него автоматика начнёт трогать
боевые машины. В этот момент все решения периода собираются в архив — JSON со
сводкой и полным списком, — который остаётся в `monitor.remediation.archive_dir`
и открывается из истории режимов. Это и есть обоснование того, что автоматике
доверили боевые машины.

Выбранный режим хранится в базе и переживает перезапуск: оператор, не
закончивший наблюдение, не должен получить работающую автоматику из-за
перезагрузки службы.

## Мониторинг ввода-вывода и путей до хранилища

Вкладка «Ввод-вывод» на странице подключения отвечает на два разных вопроса, и
их важно не путать.

**Медленно ли работает диск гостю.** Верхний график: сплошные линии — объём в
секунду, пунктир — задержка на операцию. Смотреть надо на пунктир. Диск с низкой
скоростью и низкой задержкой просто не нагружен; низкая скорость при высокой
задержке — это и есть «тормозит». По одному объёму эти два случая неразличимы:
оба выглядят как линия у нуля. Задержка берётся из накопленного времени операций
QEMU; если гипервизор её не отдаёт (старая версия, неподдерживаемый драйвер),
пунктир отсутствует, а не рисуется нулём.

**Доходит ли трафик до СХД.** Нижняя таблица и график. NFS о потере пакетов не
сообщает — сообщает о том, что она с ним сделала:

| Показатель | Что означает |
|---|---|
| Повторы | вызов остался без ответа и был отправлен снова |
| Таймауты | клиент исчерпал расписание повторов; гость увидел зависший диск |
| Плохие xid | ответ пришёл на вызов, который уже сочли потерянным |
| Отклик | среднее время ответа сервера за интервал |

Единичные повторы бывают на исправной сети. Устойчивый процент (порог — 1% от
операций) и **любой** таймаут поднимают оповещение `storage_path_degraded`.
Разорванная сессия iSCSI — оповещение критическое сразу.

Источники данных: `/proc/self/mountstats` для NFS, sysfs для состояния сессий
iSCSI, `DomainBlockStatsFlags` libvirt для дисков.

**Постоянный мониторинг путей до СХД работает только для KVM.** Он требует
доступа к гипервизору по SSH; движок oVirt статистику монтирований своих хостов
наружу не отдаёт. Во время самого бэкапа приложение отдельно снимает I/O
целевой ВМ для всех поддерживаемых платформ: через libvirt, статистику дисков
oVirt или накопительные счётчики гостя Proxmox. Эти точки видны в карточке
запуска вместе с полосой заморозки. Для oVirt частота фактического обновления
значений зависит от движка, даже если приложение запрашивает их чаще.

Сбор включается `monitor.collect_io_stats` (по умолчанию включён), срок хранения
— `monitor.io_retention` (неделя). В обычное время KVM-метрики снимаются тем же
проходом, что и состояние; на время бэкапа целевая ВМ опрашивается раз в две
секунды (oVirt — раз в пять секунд).

## Журнал службы

Вкладка «Настройки → Журнал», только для администратора: журнал не содержит
секретов, но перечисляет все ВМ, хосты и операторов установки — это карта
инфраструктуры.

**Ротация двойная.** По размеру — перед тем, как файл перерастёт
`max_size_mb`. И раз в
сутки в полночь, даже если размер не достигнут. Второе нужно потому, что
`max_age_days` чистит архивы, а не активный файл: на тихой установке он иначе
рос бы годами, ни разу не сменившись, и предельный возраст к нему бы не
применился. Пустой файл в полночь не меняется — иначе каталог заполнили бы
пустые архивы и вытеснили настоящие из `max_backups`. Архивы всегда сжимаются
gzip одним фоновым worker.

Размер файла, число архивов и срок хранения меняются на этой же вкладке и
сохраняются в PostgreSQL. Новая политика применяется без перезапуска, в том
числе во время записи. Допустимые диапазоны: `1..10240` МиБ, `1..1000` архивов,
`1..3650` дней. Интерфейс показывает источник `config` или `database`; сброс
удаляет переопределение из БД. Если `logging.file` пуст, политика всё равно
сохраняется, но начнёт работать после включения файлового журнала и перезапуска.

Сменить файл вручную можно кнопкой; смена, как и изменение уровня, попадает в
аудит.

**Уровень меняется на ходу.** `trace, debug, info, warn, error` — переключение
действует немедленно и до перезапуска службы, постоянное значение остаётся в
`logging.level`. Это сделано ради разбора аварий: поднять подробность обычно
нужно тогда, когда перезапускать мониторинг меньше всего хочется. Само
изменение пишется в журнал — иначе внезапно замолчавший или, наоборот,
залитый журнал ничем себя не объясняет.

| Параметр | Значение по умолчанию |
|---|---|
| `logging.file` | `./logs/jhvirt.log`; пусто — только поток службы |
| `logging.level` | `info` |
| `logging.format` | `console` (в Docker — `json`) |
| `logging.max_size_mb` | 100 |
| `logging.max_backups` | 7 |
| `logging.max_age_days` | 30 |

В Docker файл задаётся переменной `JHV_LOG_FILE`, которая передаётся приложению
как `JHV_LOGGING_FILE`. По умолчанию — `/app/data/logs/jhvirt.log`, то есть в
томе с данными: история переживает пересоздание контейнера, и просмотр журнала
из интерфейса работает.

Путь обязан лежать внутри `/app/data`. Остальной корень контейнера доступен
только для чтения (`read_only: true`), а каталог `/app/logs` вдобавок находится
в слое контейнера и исчезает при каждом пересоздании.

**Установки, развёрнутые раньше, могут хранить в `.env` старое значение**
`JHV_LOG_FILE=/app/logs/jhvirt.log`. С неизменяемым корнем служба с ним не
поднимется. Проверьте перед обновлением:

```bash
grep JHV_LOG_FILE deploy/.env
```

## Качество защиты

Раздел «Покрытие бэкапами» рассчитывается от cron-расписаний. Для каждой комбинации
`задание × ВМ × хранилище` проверяются свежесть, последний исход, полнота
неисключённых дисков, настроенная проверка восстановления и скорость. Если ВМ
входит в несколько заданий или имеет несколько реплик, её состояние равно
худшему результату. Успешная основная копия не закрывает ошибку второй реплики.

| Состояние | Условие |
|---|---|
| Нет защиты | ВМ не входит во включённое задание с расписанием либо полной успешной копии ещё нет |
| Ошибка реплики | последний запуск в назначенное хранилище завершился ошибкой |
| Неполная копия | не записан обязательный диск; явно исключённый диск дефектом не считается |
| Просрочено | полная успешная копия старше `stale_intervals` интервалов задания |
| Проверка просрочена | у задания есть `verify_after`, но за срок не было успеха того же режима |
| Скорость снизилась | несколько запусков подряд ниже порога от медианы предыдущих сопоставимых запусков |
| В порядке | все перечисленные проверки успешны для всех реплик |

Сопоставимыми для скорости считаются запуски той же ВМ, задания, реплики, типа
бэкапа и алгоритма сжатия. По умолчанию три последних запуска должны быть ниже
50% медианы предыдущих десяти. Смена zstd на gzip поэтому не создаёт ложную
деградацию.

Каждое срабатывание расписания создаёт `backup_job_runs`, а дочерние
`backup_runs` получают его `job_run_id`. Итог общего запуска рассчитывается
только по этим дочерним строкам. После простоя число точек агрегируется в одну
строку `missed`; при `scheduler.catch_up_missed: true` запускается одна последняя
точка, при `false` пропуск только фиксируется. Конфликт с ещё выполняющимся
экземпляром также считается пропуском.

## Что резервировать в самом сервисе

| Что | Зачем |
|---|---|
| `data/secret.key` | без него не расшифровать пароли подключений и зашифрованные бэкапы |
| База PostgreSQL | каталог копий, задания, история, учётные записи |
| YAML и `.env`/`jhvirt.env` | настройки и секреты; точные пути зависят от режима и перечислены в [CONFIGURATION.md](CONFIGURATION.md) |

Снимок базы снимается на живой службе, останавливать её не нужно:

```bash
pg_dump -U jhvirt jhvirt > /srv/backups/jhvirt-$(date +%F).sql
```

В Docker — `docker compose exec -T postgres pg_dump -U jhvirt jhvirt > …`.



Данные бэкапов самодостаточны: каталог запуска содержит `run.json` и манифесты,
и разбирается без базы (см. [BACKUP-FORMAT.md](BACKUP-FORMAT.md)).

`secret.key` копируйте **отдельно от базы и не в то хранилище, где лежат
копии**. Резерв, уехавший вместе с тем, что он защищает, спасает ровно от тех
аварий, от которых и так спасла бы вторая копия базы, — и ни от одной из тех,
ради которых он делается.

## Локальное хранилище на отдельном диске

Локальное хранилище — это каталог, который видит сама служба. В установке из
контейнера путь в форме хранилища задаётся **внутри контейнера**: каталог хоста
попадает туда только монтированием и там называется по-своему. Штатно
смонтированы два каталога:

| На хосте | Переменная в `.env` | В контейнере | Назначение |
|---|---|---|---|
| `/opt/jhvirt/backups` | `JHV_BACKUP_DIR` | `/backups` | копии |
| `/opt/jhvirt/restores` | `JHV_RESTORE_DIR` | `/restores` | восстановление в файлы |

Служба работает от UID `10001` (`jhvirt`), поэтому каталог копий должен быть
доступен на запись именно ему. Права проверяются пробой, а не чтением режима:
при сохранении хранилища служба создаёт и удаляет пробный объект, и ошибка прав
видна сразу, а не ночью в задании.

### Второй диск под копии

Пример: том `/storage` нужно использовать под копии рядом с основным каталогом.

1. Каталог с владельцем службы. Корень диска можно не трогать — служба пишет
   только в свой подкаталог:

   ```bash
   sudo mkdir -p /storage/backups
   sudo chown 10001:10001 /storage/backups
   sudo chmod 0750 /storage/backups
   ```

   Если владельца менять нельзя, достаточно ACL:

   ```bash
   sudo setfacl -m u:10001:rwx /storage/backups
   ```

2. Смонтировать диск в контейнер файлом `docker-compose.override.yml` рядом с
   `docker-compose.yml` (для стандартной установки — `/opt/jhvirt/compose/`):

   ```yaml
   services:
     ovirt-backup:
       volumes:
         - /storage:/storage
   ```

3. Проверить, что compose увидел монтаж, и пересоздать контейнер службы:

   ```bash
   cd /opt/jhvirt/compose
   docker compose config | grep -A1 'source: /storage'
   docker compose up -d ovirt-backup
   ```

4. В интерфейсе: **Хранилища → Добавить хранилище → Локальный каталог**, путь
   `/storage/backups`.

**Почему override, а не правка `docker-compose.yml`.** Установщик `.run` при
обновлении заново кладёт свои файлы — `docker-compose.yml`, `.env.example`,
Dockerfile-ы — и удаляет только `bin/` и `web/`. Посторонний
`docker-compose.override.yml` он не трогает, а `docker compose` без ключа `-f`
подхватывает этот файл сам. Правка в `docker-compose.yml` исчезла бы при первом
же обновлении. После обновления монтаж проверяется той же командой
`docker compose config`.

**Корень только для чтения — это нормально.** Обзор каталогов в форме
показывает смонтированные корни, которые служба может читать, даже если писать
в сам корень нельзя: из него спускаются в записываемый подкаталог вроде
`/storage/backups`. Внутренние каталоги службы (`/app`, `/tmp`) в обзоре не
показываются: хранить копии рядом с `secret.key` — плохая идея.

**systemd.** Служба работает от своего пользователя (по умолчанию `jhvirt`) и
видит каталоги хоста напрямую: монтирование не нужно, достаточно выдать права
этому пользователю.

## Сетевые хранилища: SMB и WebDAV

Служба подключается к сетевой папке и к коллекции WebDAV сама. Монтировать их на
хосте не нужно, и это не только вопрос удобства: при монтировании учётные данные
лежат в `/etc/fstab` или в файле credentials, о шаре знает только администратор
хоста, а в интерфейсе видно локальный каталог. Отвалившаяся сеть выглядит тогда
как «нет прав на локальный путь» — сообщение, из которого причину не видно.

Монтирование остаётся рабочим способом: тип «локальный каталог» на точке
монтирования работал раньше и работает сейчас. Смысл имеет там, где шара уже
смонтирована для других задач.

**SMB/CIFS.** Работает с сетевой папкой Windows, Samba, TrueNAS, Synology —
всем, что говорит на SMB2 или SMB3.

| Поле | Что вводить |
|---|---|
| Сервер | имя или адрес: `nas.example.org` |
| Порт | 445, если не переопределён |
| Сетевая папка | только имя шары: `backups`, а не `\\nas\backups` |
| Домен | домен Active Directory или рабочая группа; для локальной учётной записи NAS оставляется пустым |
| Пользователь, пароль | учётная запись с правом записи в шару |
| Путь внутри папки | необязательно; каталог создаётся сам |

Анонимный доступ к шаре не поддерживается: бэкапы — это данные, за доступ к
которым кто-то должен отвечать по имени.

**WebDAV.** Работает с Nextcloud, ownCloud и сервисом WebDAV на NAS. Адрес
указывается полностью, вплоть до пути сервиса:
`https://nas.example.org/remote.php/dav/files/backup`. В Nextcloud лучше завести
отдельный пароль приложения — обычный пароль перестанет работать в тот день,
когда пользователю включат второй фактор.

Возобновления прерванной передачи в WebDAV нет: оборванный объект передаётся
заново целиком. Для дисков в сотни гигабайт это заметно, поэтому основным
хранилищем WebDAV стоит делать только при небольших объёмах, а для крупных
предпочесть SMB, S3 или локальный каталог.

Проверка сертификата отключается отдельным флагом и только для WebDAV. Нужна она
для NAS с самоподписанным сертификатом; пока проверка отключена, соединение
можно подменить.

**Как объект появляется в хранилище.** Данные пишутся под временным именем и
переименовываются, когда объект дописан. Обрыв оставляет файл с пометкой
`.jhv-tmp`, а не усечённый объект под именем готового: отсутствующий объект — это
«точка не состоялась», обрезанный — «точка есть, но внутри мусор», и второе
обнаруживается позже и дороже. Оставшиеся `.jhv-tmp` от прерванных запусков
удаляются вручную и ни на что не влияют.

Проверка хранилища записывает пробный объект, читает его обратно, сравнивает и
удаляет. «Доступно» означает именно «можно писать и читать», а не «сервер
отвечает». Каталог хранилища создаётся при первой проверке и перед первой
записью.

| Симптом | Причина |
|---|---|
| `NT_STATUS_LOGON_FAILURE` | неверный логин, пароль или домен |
| `NT_STATUS_BAD_NETWORK_NAME` | нет такой шары; проверьте, что в поле имя, а не путь |
| `NT_STATUS_ACCESS_DENIED` | учётная запись видит шару, но писать в неё не может |
| WebDAV `401` | сервер не принял логин или пароль; в Nextcloud — нужен пароль приложения |
| WebDAV `403` | доступ есть, прав на запись нет |
| WebDAV `405` | по этому адресу WebDAV не отвечает: адрес указан не до коллекции |
| WebDAV `409` | нет родительского каталога; каталог сервиса создать нельзя, он должен существовать |
| `x509: certificate signed by unknown authority` | самоподписанный сертификат; либо добавьте доверие, либо снимите проверку осознанно |

## Согласованность копий СУБД

Копия диска работающей ВМ одинакова на любом уровне — меняется то, что
происходит в госте в момент фиксации точки. Уровень выбирается в задании
(шаг «Проверка и параметры», поле «Согласованность копии»):

| Уровень | Что делает служба | Что нужно в госте | Что получает СУБД при запуске копии |
|---|---|---|---|
| `crash` — как после сбоя питания | ничего | ничего | восстановление по журналу, как после выключения |
| `filesystem` — файловые системы | заморозка ФС через агент | qemu-guest-agent | то же восстановление, но ФС гарантированно целы |
| `application` — приложения | та же заморозка | агент + сценарии `fsfreeze-hook` (Linux) или VSS (Windows) | чистый старт с минимальным восстановлением |

Служба команд в госте не выполняет. Уровень `application` дают сценарии,
которые агент сам вызывает перед заморозкой: служба видит только, удалась ли
заморозка целиком.

### Сценарии для PostgreSQL и MySQL/MariaDB

Комплект лежит в `guest-hooks/` установочного комплекта (в репозитории —
`deploy/guest-hooks`) и ставится **в каждую ВМ с СУБД**:

```bash
sudo sh guest-hooks/linux/install.sh --postgresql
```

```bash
sudo sh guest-hooks/linux/install.sh --check
```

`--mysql` ставит сценарий для MySQL и MariaDB; флаги можно сочетать.
Установщик кладёт:

- строгий диспетчер на место штатного `/etc/qemu-ga/fsfreeze-hook`
  (`/etc/qemu/fsfreeze-hook` в Debian, Ubuntu и Astra Linux); штатный
  сохраняется рядом как `fsfreeze-hook.jhvirt-orig`;
- сценарии в `fsfreeze-hook.d/` с правами `root 0700`;
- `/etc/jhvirt/guest-hooks.conf` с закомментированными значениями по умолчанию.

Строгий диспетчер нужен потому, что штатный из QEMU всегда завершается с кодом
0: сценарий СУБД мог не сработать, а агент всё равно заморозил бы ФС, и точка
получила бы уровень, которого нет. Строгий при ошибке отдаёт уже подготовленным
сценариям `thaw` и возвращает ошибку — агент отменяет заморозку, служба
записывает причину.

| Сценарий | freeze | thaw |
|---|---|---|
| `50-jhvirt-postgresql` | `CHECKPOINT` от пользователя `postgres` через Unix-сокет | ничего |
| `50-jhvirt-mysql` | фоновая сессия `FLUSH TABLES WITH READ LOCK`, удерживается до thaw, не дольше 120 с | `KILL` сессии — блокировка снята |

Для PostgreSQL этого достаточно: заморозка фиксирует все файлы кластера в один
момент, а документация PostgreSQL для таких снимков советует `CHECKPOINT`,
чтобы восстановление при старте копии было коротким. `pg_backup_start` нужен при
копировании файлов по одному и здесь не применяется.

Паролей сценарии не используют. MySQL подключается как root из консоли (в
MariaDB — `unix_socket`); если это не так, создайте запись только с правом
`RELOAD` и положите её в `/etc/jhvirt/mysql-freeze.cnf` (`root`, `0600`, раздел
`[client]`).

**Агент должен вызывать хук.** В семействе RHEL (РЕД ОС, AlmaLinux, Rocky) это
`FSFREEZE_HOOK_PATHNAME` в `/etc/sysconfig/qemu-ga`, обычно включённый по
умолчанию. В Debian и производных добавьте в `/etc/qemu/qemu-ga.conf`
раздел `[general]` с `fsfreeze-hook=/etc/qemu/fsfreeze-hook` и перезапустите
`qemu-guest-agent`. Установщик проверяет это и печатает, что поправить. При
включённом SELinux он восстанавливает метки через `restorecon`.

`--check` прогоняет `freeze` и `thaw` сценариев **без заморозки файловых систем**
и показывает, сколько заняла подготовка. Прогоните его после установки и после
обновления СУБД.

### Windows

Сценарии не нужны: qemu-guest-agent с VSS-провайдером (ставится вместе с
virtio-win guest tools) вызывает VSS-писателей при каждой заморозке. SQL Server
пишет свой VSS-писатель сам; PostgreSQL под Windows писателя не имеет, и для него
реальный уровень — `filesystem`.

### Если уровень не достигнут

Причина — нет агента, сценарий вернул ошибку или не уложился во время, движок
не зафиксировал точку за предел заморозки службы — записывается в точку и видна
у неё в списке копий и в подробностях. Дальше решает пункт задания «Если
согласованность не достигнута»:

- **Сохранить копию как после сбоя питания** (по умолчанию) — задание поднимает
  оповещение «Копия ниже заявленной согласованности»; оно снимается само, когда
  очередная точка уровень достигнет;
- **Не сохранять копию** — запуск завершается ошибкой, копии нет. Если неудача
  видна заранее (нет агента, служба не смогла заморозить гостя), бэкап на
  движке даже не открывается; если позже (движок не смог заморозить гостя,
  точка не уложилась в предел) — служба закрывает уже открытый бэкап.

Выключенная ВМ не замораживается — её диски не меняются, и точка получает
заявленный уровень с пометкой «ВМ не работала».

Типовые причины понижения:

| Причина в точке | Что проверить |
|---|---|
| «гостевой агент не отвечает» | установлен и запущен ли `qemu-guest-agent`, есть ли у ВМ канал агента |
| «fsfreeze hook has failed with status N» | `/var/log/qga-fsfreeze-hook.log` в госте; `install.sh --check` |
| «FLUSH TABLES WITH READ LOCK не получен» | длинные запросы в момент копии: перенесите расписание или увеличьте `JHVIRT_HOOK_TIMEOUT` |
| тайм-аут заморозки на KVM | вся заморозка со сценариями должна укладываться в 60 с |
| «гипервизор не зафиксировал точку за N с заморозки» | движок долго готовил бэкап (scratch-диски, очередь задач); см. «Предел заморозки» ниже |

### Предел заморозки

Пока гипервизор фиксирует точку, запись в госте стоит целиком. На KVM это
доли секунды, а oVirt в фазе `initializing` готовит scratch-диски и под
нагрузкой может делать это минутами. Поэтому у заморозки есть предел: по его
истечении служба размораживает гостя сама, не дожидаясь движка. Копия от
этого не портится — она становится такой, как после сбоя питания, а в точку
записывается причина. Задание со строгим флагом в этом случае прерывается, и
бэкап на движке закрывается.

Предел задаётся в задании (поле «Предел заморозки, с»), по умолчанию —
`backup.max_freeze` (60 с). Хронология запуска показывает, сколько запись
стояла на самом деле: событие «разморожено» с длительностью.

### Кто замораживает гостя: служба или движок

У заданий на oVirt и его производных (РЕД Виртуализация, OLVM, RHV) есть
выбор «Кто замораживает гостя»:

| Режим | Как работает | Сколько стоит запись |
|---|---|---|
| **Движок** (по умолчанию для новых заданий) | служба передаёт движку `require_consistency=true`; движок сам замораживает гостя на момент фиксации точки, уже после подготовки scratch-дисков или снапшота | доли секунды |
| **Смешанный** | замораживает служба, как в режиме «Служба»; если она не смогла заморозить гостя или движок не зафиксировал точку за предел, заморозку перехватывает движок | как у службы, пока она укладывается в предел; после перехвата — доли секунды |
| **Служба** (у заданий, созданных раньше) | служба замораживает гостя до запроса бэкапа и держит заморозку, пока движок не зафиксирует точку | вся фаза `initializing` — на oVirt 4.5 это 20+ секунд, не дольше предела |

Сценарии `fsfreeze-hook` в госте работают в обоих режимах: их вызывает
гостевой агент, кто бы ни попросил заморозку. Предел заморозки в режиме
«Движок» не нужен.

Если движок не смог заморозить гостя (сценарий СУБД вернул ошибку, агент не
ответил), бэкап с `require_consistency` завершается ошибкой на движке. Задание
со строгим флагом на этом прерывается. Остальные закрывают неудачный бэкап,
повторяют без флага и получают уровень «как после сбоя питания» с причиной в
точке. Длительность заморозки движок не сообщает, поэтому в хронологии вместо
«разморожено» стоит «Движок заморозил гостя на момент фиксации точки».

**Как устроен перехват в смешанном режиме.** Подключить движок к уже идущему
бэкапу нельзя: `require_consistency` задаётся при создании. Поэтому, когда
предел службы истёк, сторож размораживает гостя, бэкап службы закрывается и
открывается новый — с заморозкой силами движка. Это вторая подготовка бэкапа
на движке (на oVirt 4.5 — ещё 20+ секунд), но не вторая пауза записи. В
хронологии это отметка «Заморозку перехватил движок».

Перехват запоминается: следующие 7 дней смешанный режим на этой ВМ сразу
отдаёт заморозку движку, без попытки службы, — иначе каждый запуск платил бы
паузой записи и двойной подготовкой. Через неделю служба пробует снова. Если
служба не смогла заморозить гостя (ошибка вызова или сценария СУБД), движок
подключается сразу, но это не запоминается: причина обычно разовая.

Смешанный режим нужен там, где важно видеть точную длительность заморозки, а
движок обычно укладывается в предел. Для узлов Kubernetes и ВМ, где движок
заведомо готовит бэкап дольше предела, проще сразу выбрать «Движок».

Режим «Служба» остаётся для движков старше 4.4 и для случаев, когда нужно
видеть точную длительность заморозки. Путь через снапшот (диски без CBT)
замораживает служба в любом режиме: там окно — только запрос снапшота.

### Нагрузка на хранилище ВМ

Бэкап работающей ВМ читает её диски с того же хранилища, с которого работает
она сама. Чтобы копия не отнимала у приложений всю пропускную способность, у
задания есть поле «Предел чтения, МБ/с», а у службы — значение по умолчанию
`backup.transfer.max_read_mbps` (0 — без ограничения). Предел общий на все
диски одного запуска: диски читаются параллельно (`max_parallel_disks`), а
хранилище у них одно. Меньше 10 МБ/с задать нельзя: паузы между блоками по
32 МиБ приблизились бы к таймауту неактивности передачи на движке.

Предел удлиняет бэкап, а значит, и время, пока бэкап на движке открыт и
записи гостя копируются в scratch-диск. Для первого полного бэкапа большой ВМ
подберите его так, чтобы копия укладывалась в окно низкой нагрузки.

### Kubernetes и СУБД

Узел Kubernetes переносит заморозку хуже обычной ВМ. Пока запись стоит, etcd
не может сделать `fsync` и через секунду-другую теряет лидера,
kube-controller-manager и kube-scheduler не продлевают аренду (10–15 с) и
перезапускаются, а kubelet через 40 с без отметок переводит узел в NotReady.
Приложения в подах при этом продолжают работать, но всё, что пишет на диск,
стоит вместе с ними.

| Где СУБД | Копия узлов k8s | Копия СУБД |
|---|---|---|
| в поде, данные на диске узла (local-path, hostPath) | `application` со сценариями для подов, предел 10–15 с | та же копия узла + логический дамп через `kubectl exec` |
| в поде, данные на внешнем томе (Ceph RBD, NFS, Longhorn, iSCSI) | `filesystem` или `crash`, предел 10–15 с | **только** логический дамп: данных тома в копии ВМ нет |
| вне кластера, на своей ВМ | `filesystem` или `crash`, предел 10–15 с | копия ВМ СУБД с `application` + логический дамп |
| вне кластера, на физическом сервере | `filesystem` или `crash` | логический дамп |

Для узлов управления с etcd уровень `crash` — не компромисс, а разумный
выбор: etcd и PostgreSQL восстанавливаются по журналу, а без заморозки
кластер не замечает бэкапа вовсе. Рабочие узлы без etcd
переносят `filesystem` с коротким пределом.

**СУБД в поде на узле.** Сценарии из `guest-hooks/` ставятся на каждый узел,
где может оказаться под СУБД, а цели задаются в `/etc/jhvirt/guest-hooks.conf`:

```sh
JHVIRT_PG_K8S_TARGETS="shop/postgres"          # пространство_имён/контейнер
JHVIRT_PG_K8S_PASSWORD_ENV=                     # пусто для официального образа
#JHVIRT_MYSQL_K8S_TARGETS="shop/mysql"
#JHVIRT_MYSQL_K8S_PASSWORD_ENV=MYSQL_ROOT_PASSWORD
#JHVIRT_CRICTL="k3s crictl"                      # k3s и RKE2
```

Сценарий находит контейнер через `crictl` по меткам kubelet только на своём
узле и выполняет `CHECKPOINT` (или берёт `FLUSH TABLES WITH READ LOCK`) внутри
него. Учётные данные Kubernetes узлу не нужны; пароль, если он нужен, берётся
из окружения самого контейнера — в настройках указывается только имя
переменной. Под, работающий на другом узле, пропускается: его данных на
дисках этой ВМ нет. Когда цели заданы, СУБД на самом узле не готовится, пока
это не сказано явно (`JHVIRT_PG_PORTS`, `JHVIRT_MYSQL_ON_HOST=1`).

**СУБД вне кластера.** Приложение в подах ждёт СУБД, пока её ВМ заморожена:
`CHECKPOINT` запись не останавливает, а блокировка MySQL/MariaDB держит её до
разморозки. Держите у задания ВМ СУБД предел, который приложение переживает
без обрыва соединений (обычно 10–30 с), и не ставьте его копию на то же время,
что копии узлов: каждая заморозка — пауза для приложения.

Для Proxmox заморозку выполняет сам `vzdump` при `agent=1` в настройках гостя, и
сценарии `fsfreeze-hook` вызываются так же. Служба не видит её результата,
поэтому требовать уровень в задании Proxmox нельзя.

## Логические дампы СУБД

Копия ВМ сохраняет машину целиком. Логический дамп — отдельную базу: его можно
восстановить в другую версию СУБД, на другой хост, выборочно, и он защищает
СУБД на физических серверах, где копировать нечего, кроме самой базы.
Раздел **Дампы СУБД** в интерфейсе.

| | Копия ВМ с уровнем «приложения» | Логический дамп |
|---|---|---|
| Что сохраняется | вся машина: ОС, СУБД, данные | одна база (`pg_dump`, `mysqldump`) |
| Восстановление | ВМ целиком или диск | новая база на хосте СУБД |
| Между версиями СУБД | нет | да |
| Физические серверы | нет | да |
| Нагрузка на СУБД | доли секунды заморозки | чтение всей базы |

### Как это устроено

На хост СУБД ставится хелпер `jhvirt-db-dump`. Служба заходит на хост по SSH
ключом, который в `authorized_keys` привязан к хелперу через
`restrict,command=…`: shell по этому ключу недоступен, выполняются только
операции протокола — `probe`, `list`, `dump`, `globals` и, если разрешено на
хосте, `restore` в новую базу. Хелпер работает от отдельного пользователя
(не root) и входит в СУБД через Unix-сокет: паролей СУБД нет ни на хосте, ни в
службе.

Поток дампа идёт по SSH прямо в хранилище копий тем же конвейером, что диски
ВМ: чанки, SHA-256 открытых данных, сжатие, AES-256-GCM. Шифрование в задании
включено по умолчанию — дамп содержит все данные базы открытым текстом.

### Установка на хост СУБД

Комплект `db-dump/` лежит в установочном архиве (в репозитории —
`deploy/db-dump`). Сгенерируйте для службы отдельную пару ключей, публичную
часть скопируйте на хост и выполните там:

```bash
ssh-keygen -t ed25519 -N '' -C jhvirt-db-dump -f jhvirt-db-dump
```

```bash
sudo sh db-dump/setup.sh --pubkey jhvirt-db-dump.pub --postgresql
```

`setup.sh` создаёт пользователя `jhvirt_dump` без пароля, ставит хелпер в
`/usr/local/sbin`, кладёт ключ с `restrict,command` и создаёт роль в СУБД:

| СУБД | Роль | Права |
|---|---|---|
| PostgreSQL 14+ | `jhvirt_dump`, вход `peer` | `pg_read_all_data`, `pg_read_all_stats` |
| MariaDB | `jhvirt_dump@localhost IDENTIFIED VIA unix_socket` | `SELECT, SHOW VIEW, TRIGGER, EVENT, LOCK TABLES` |
| MySQL | `jhvirt_dump@localhost IDENTIFIED WITH auth_socket` | то же |

`--allow-restore` дополнительно даёт право создавать базы (PostgreSQL:
`CREATEDB`) и включает `JHVIRT_DB_ALLOW_RESTORE=1` в
`/etc/jhvirt/db-dump.conf`. Без него восстановление из службы на этом хосте
невозможно — это сознательная граница: ключ, который умеет только читать,
безопаснее ключа, который умеет и писать.

Проверка на самом хосте, без SSH:

```bash
sudo runuser -u jhvirt_dump -- /usr/local/sbin/jhvirt-db-dump probe
```

### СУБД в Kubernetes

Если СУБД работает в поде, хелпер ставится не в под и не на узел, а на любую
машину с `kubectl` и доступом к API кластера (узел управления, бастион).
Клиенты СУБД запускаются внутри контейнера пода через `kubectl exec`, поэтому
под может переезжать между узлами:

```bash
sudo sh db-dump/setup.sh --pubkey jhvirt-db-dump.pub --kubernetes --user jhvirt_dump_shop
```

Установщик не создаёт ролей в СУБД, а кладёт профиль
`/etc/jhvirt/db-dump.d/jhvirt_dump_shop.conf`. В нём задаются пространство
имён, контейнер и под — именем или селектором ведущего экземпляра:

```sh
JHVIRT_K8S_NAMESPACE=shop
JHVIRT_K8S_CONTAINER=postgres
JHVIRT_K8S_SELECTOR=cnpg.io/cluster=main,cnpg.io/instanceRole=primary
JHVIRT_K8S_DB_USER=postgres
JHVIRT_K8S_PASSWORD_ENV=                 # имя переменной в контейнере, если нужен пароль
```

Учётной записи `kubectl` нужны только `get/list pods` и `create pods/exec` в
этом пространстве имён — готовый манифест `db-dump/k8s-rbac.yaml`. Секреты
кластера она не читает: пароль СУБД остаётся в окружении контейнера, хелпер
передаёт только имя переменной.

Профиль выбирает SSH-пользователь, а не служба: для второй базы заведите
второго пользователя (`--user`) со своим ключом и добавьте его в интерфейсе
отдельным хостом СУБД. Так один хост хелпера обслуживает и базы на себе, и
базы в разных пространствах имён.

### Подключение в интерфейсе

1. **Дампы СУБД → Хост СУБД**: адрес, пользователь `jhvirt_dump`, приватный
   ключ. «Получить» ключ хоста и сверить отпечаток с
   `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` на хосте.
2. «Проверить» — хелпер отвечает протоколом `jhvirt-db-dump/1`, списком СУБД с
   версиями и тем, разрешено ли восстановление.
3. **Новое задание**: хост, СУБД, базы («Загрузить список» или пусто — все),
   для PostgreSQL — роли и табличные пространства, хранилища, расписание,
   правила хранения.

Чтобы видеть транзакции рядом с бэкапом ВМ, в форме хоста дополнительно
выберите подключение виртуализации, ВМ и СУБД. Во время её бэкапа служба раз в
две секунды вызывает фиксированную read-only операцию `stats`: читает число
коммитов, откатов, активных соединений и позицию WAL/redo. Разницы между
соседними значениями превращаются в графики. Пользовательский SQL, строки
таблиц и пароль СУБД через этот протокол не передаются. Для уже установленного
хелпера повторно запустите актуальный `setup.sh`, чтобы установить команду
`stats` и выдать PostgreSQL роль `pg_read_all_stats`.

Первое хранилище основное. После дампа служба переносит объекты в остальные
байт в байт, перечитывает назначение и сверяет SHA-256; манифест `dumps.manifest`
публикуется последним — без него каталог запуска точкой не считается.

### Что попадает в дамп

| СУБД | Команда на хосте | Формат |
|---|---|---|
| PostgreSQL | `pg_dump --format=custom --compress=0` | custom: `pg_restore` умеет выборочно |
| PostgreSQL, роли | `pg_dumpall --globals-only --no-role-passwords` | SQL, без хешей паролей |
| MySQL / MariaDB | `mysqldump --single-transaction --routines --events --triggers --hex-blob --no-tablespaces` | SQL |

«Все базы» — пользовательские: `template0/1`, `information_schema`,
`performance_schema`, `sys` и `mysql` пропускаются, как и базы из
`JHVIRT_DB_EXCLUDE`. Базы с именами вне алфавита `[A-Za-z0-9_.-]` хелпер не
отдаёт: служба не смогла бы безопасно запросить их дамп.

Если одна база не снялась, остальные сохраняются, а точка получает статус
«частично» с ошибкой по этой базе. Неудачный или частичный запуск поднимает
оповещение «Ошибка бэкапа»; следующий успешный его снимает. Если запуск не
смог опубликовать манифест, уже записанные объекты удаляются: без манифеста
они точкой не являются.

### Проверка точек

С флагом задания **Проверять точку сразу после дампа** (включён по умолчанию)
служба перечитывает каждую базу тем же путём, что восстановление, но в никуда:
чанки расшифровываются, распаковываются и сверяются по SHA-256, а длина — с
манифестом. Итог виден у точки («проверено» или «проверка не пройдена» с
причиной); неудача поднимает оповещение «Ошибка проверки». Кнопка **Проверить**
у точки делает то же вручную — например, для старой точки перед учениями по
восстановлению.

Проверка доказывает, что дамп читается и не изменился с момента съёмки. Что
СУБД его примет, доказывает только восстановление: время от времени
восстанавливайте базу в новую и проверяйте её приложением.

### Восстановление

В точке у каждой базы есть кнопка **В новую базу**. Служба читает объект,
расшифровывает и сверяет SHA-256 каждого чанка по пути, а хелпер создаёт новую
базу и загружает в неё дамп (`pg_restore --no-owner --no-privileges
--exit-on-error` или клиент MySQL). Если база с таким именем есть, хелпер
откажет — существующая база не перезаписывается никогда. При ошибке загрузки
хелпер удаляет только ту базу, которую создал в этом же вызове.

Роли из `globals` служба не применяет: это решение администратора СУБД. Файл
роли лежит в точке и применяется вручную через `psql` после проверки.

Переименовать восстановленную базу на место боевой — ручной шаг администратора
СУБД после проверки данных.

### Если что-то не так

| Сообщение | Что проверить |
|---|---|
| «несовместимый протокол хелпера» | на хосте не тот файл или старая версия; `jhvirt-db-dump probe` |
| «invalid forced command» | в `authorized_keys` нет `restrict,command=…` или служба старше хелпера |
| «PostgreSQL на хосте недоступна: … peer authentication failed» | в `pg_hba.conf` нет `local … peer` для роли или роли нет |
| «permission denied for large object» | большие объекты требуют отдельного права |
| «restore is disabled on this host» | `JHVIRT_DB_ALLOW_RESTORE=1` и право создавать базы |
| «… must be owned by root» | `/etc/jhvirt/db-dump.conf` должен быть `root:root 0644` |

## Репликация и физические копии

У нового задания первое хранилище является основным, остальные обязательными
репликами. Способ доставки в реплики выбирается в форме задания списком «как
данные попадают в остальные хранилища»:

| Способ | Что происходит | Чем платите |
|---|---|---|
| Копирование из основного | ВМ читается один раз в основное, оттуда очередь переносит в реплики | основное хранилище читается второй раз; копия появляется с задержкой |
| Параллельная запись | данные идут во все хранилища за один проход по диску | скорость равна скорости самого медленного хранилища |
| Отдельный бэкап на каждое | на каждое хранилище выполняется свой запуск | диск снимается с гипервизора столько раз, сколько хранилищ |

Существующие задания при обновлении сохраняют прежнее поведение: включённая
репликация становится «копированием из основного», выключенная — «отдельным
бэкапом на каждое».

При параллельной записи недоступность реплики не прерывает запуск: основная
копия публикуется, а для отвалившегося хранилища заводится заявка, и его догоняет
та же очередь. Реплика, записанная параллельно, сразу учитывается как готовая
физическая копия.

Дальше описан режим копирования из основного. Гипервизор читается только в
основную копию. После публикации `run.json` постоянная очередь передаёт те же
объекты в реплики двумя workers по умолчанию. Для одинакового S3 endpoint используется server-side copy; для
local, S3 и SFTP данные идут потоком через сервис с действующими лимитами.
Лимит задаётся в форме хранилища в МиБ/с и является общим для параллельных
потоков записи. Значение `0` означает отсутствие ограничения. Нативный
server-side copy внутри одного S3 endpoint лимит не использует. SMB и WebDAV
переливаются так же, как local и SFTP: потоком через службу.

Статусы видны в **Бэкапы → Копии** и **Бэкапы → Репликация**:

| Статус | Значение |
|---|---|
| `pending` | ожидает свободного worker или родительскую цепочку |
| `copying` | объекты передаются |
| `verifying` | назначение перечитывается и сверяется по SHA-256 |
| `succeeded` | копия опубликована и пригодна для чтения |
| `failed` | попытка неуспешна, назначен автоматический повтор |
| `canceled` | оператор отменил передачу; автоматический повтор остановлен |
| `locked` | цепочка структурно недоступна либо удаление запрещено Object Lock |

Повторы выполняются через `1m, 5m, 15m, 1h, 4h, 12h`, затем каждые `24h` без
ограничения числа попыток. Успешные объекты фиксируются в PostgreSQL. При
повторе сервис перепроверяет их хеш в назначении и пропускает только реально
сохранившиеся объекты; оборванный объект передаётся заново целиком.

Для инкремента сначала догоняются родители от полной точки к последней. Пока
родитель не опубликован, дочерний `run.json` не создаётся. Если здорового
источника больше нет, копия блокируется и создаётся критическое оповещение.

Ошибка реплики не удаляет основную точку, но общий запуск задания остаётся
частичным. После успешного повтора итог пересчитывается, оповещение закрывается,
а защита возвращается в норму. Отключение обязательного хранилища приостанавливает
очередь, но не делает реплику необязательной.

### Проверка и восстановление из реплики

В диалогах проверки и восстановления выберите физическую копию. Без явного
выбора сервер пробует успешную основную, затем первую успешную реплику. Вся
цепочка должна находиться в одном хранилище: звенья из разных мест не смешиваются.
Практическая аварийная проверка: отключить основное хранилище, выполнить
`verify`, восстановить из выбранной реплики и загрузить изолированную ВМ.

### Ретенция

Политика применяется к логическим точкам, а не к каждой копии независимо.
Основной источник не удаляется, пока обязательная реплика не завершена.
Физические реплики удаляются раньше основной, а родитель, от которого зависит
оставшийся инкремент, сохраняется. Объект под Governance Object Lock остаётся
учтённым как `locked`; удаление будет повторено после истечения retention.

### Каталог после потери PostgreSQL

Откройте хранилище и запустите **Сканировать каталог**. Просмотр ничего не
импортирует автоматически. Состояния `importable` и `additional_copy` можно
выбрать для явного импорта; при выборе инкремента доступные родители добавляются
автоматически. `conflict`, `corrupt`, `missing_parent` и `missing_object`
требуют устранить причину. Импорт транзакционный и идемпотентный.

## Оповещения наружу

Оповещения видны в интерфейсе всегда, но узнаёт о них только тот, кто в эту
минуту смотрит на экран. Настройте доставку — почтой, в Telegram или на свой
webhook: `notifications` в конфигурации, подробности в
[CONFIGURATION.md](CONFIGURATION.md#оповещения-наружу).

По умолчанию сообщение уходит **один раз**. В **Настройки → Уведомления** можно
задать напоминания, максимум повторов, сообщение об устранении и отдельные
правила по типу. На странице активного оповещения можно приостановить внешнюю
доставку или отключить её только для этого случая; из web оно не исчезает.

По умолчанию наружу уходят только критические. Порог меняется параметром
`notifications.min_severity`.

Что проверить, если сообщения не приходят:

1. `notifications.enabled: true` и настроен хотя бы один канал — иначе служба
   не запустится и скажет об этом при старте;
2. в web-настройках перечислен хотя бы один настроенный канал;
3. в «Последних доставках» нет `failed`, а у `queued` видна причина следующей
   попытки;
4. транспортная ошибка повторяется из PostgreSQL outbox и переживает
   перезапуск. Успешный webhook не отправляется заново из-за отказа SMTP.

## Active Directory через Keycloak

Источник ролей production-пользователей — три группы AD:
`virt-admins`, `virt-operators`, `virt-readers`. Изменяйте членство в AD, затем
синхронизируйте mapper `ovirt-backup-groups` и завершайте старые сессии при
срочном отзыве. Роль выбирается при новом OIDC-входе; уже выданная cookie
мгновенно не меняется.

Состояние контейнеров и безопасная проверка файлов:

```bash
cd /opt/jhvirt/compose
sudo docker compose ps keycloak
sudo docker compose logs --since=15m keycloak
sudo stat -c '%U:%G %a %n' \
  /opt/jhvirt/keycloak-vault/jhvirt_ad-bind \
  /opt/jhvirt/keycloak-truststores
```

Для ротации пароля read-only service account смените его в AD и повторно
запустите текущий `.run`, выберите Keycloak → Active Directory → простой
режим и введите тот же домен и новый пароль. При одном LDAP provider установщик
выберет его автоматически. Для unattended-запуска передайте то же имя provider
и новый файл пароля `0600`. Установщик атомарно заменит file vault, обновит
provider и выполнит sync. После успеха уничтожьте входной файл. Не помещайте
пароль в shell history, `.env` или YAML.

Пошаговая настройка, PowerShell-команды создания групп, проверка LDAPS и
диагностика: [KEYCLOAK-AD.md](KEYCLOAK-AD.md).

## Аварийная готовность самого сервиса

Бэкапы ВМ недостаточны для восстановления управляющего сервиса. Отдельно нужны:

1. свежий `pg_dump` PostgreSQL;
2. байт-в-байт копия активного `secret.key`;
3. конфигурация и token-файлы;
4. доступ к физическим хранилищам копий.

Штатный `install.sh` для локальной PostgreSQL включает эту проверку и создаёт
ежедневный dump автоматически. Docker использует контейнеры `dr-backup` и
`keycloak-backup`, systemd — `jhvirt-dr-backup.timer`. Сначала dump пишется во
временный файл, проверяется через `pg_restore --list`, затем атомарно
публикуется с правами `0600`; пустой или оборванный файл не становится
последней копией.

Страница **Настройки → Аварийная готовность** и endpoint
`POST /api/v1/disaster-recovery/check` запускают проверку сразу. Сервис требует
непустой свежий дамп, чтение и права `0600`, а у внешнего ключа сверяет SHA-256 с
активным. Для внешней PostgreSQL или ручной установки настройте `pg_dump`
сами. Каталог по умолчанию находится на том же узле, поэтому вынесите его на
отдельный mount или регулярно забирайте внешней системой.

Для планового переноса используйте installer migration, а не ручное копирование
отдельных файлов. Экспорт согласованно останавливает приложение, упаковывает
PostgreSQL, YAML/env, `secret.key`, токены и TLS. Для встроенного Keycloak туда
также входят его dump, LDAPS truststore и AD bind-файл из file vault; импорт проверяет права,
UID/GID, SAN сертификата и умеет продолжить оборванную раскладку. Репозитории и
разрешённые file/restore roots заранее подключаются на новом сервере. Пошаговый
cutover: [DEPLOY.md](DEPLOY.md#перенос-приложения-на-другой-сервер).

## Типовые ситуации

Ниже оставлены частые эксплуатационные случаи. Расширенная диагностика с
проверками установки и точными командами исправления находится в
[TROUBLESHOOTING.md](TROUBLESHOOTING.md).

### Движок недоступен

Оповещение `engine_unreachable`, состояние сервера `offline`. Сервис
автоматически пересоздаёт клиент (единственное, что он делает сам в этом случае).

Если в сообщении «отверг учётные данные» — это не авария движка, а истёкший или
изменённый пароль. Поправьте подключение: **Серверы → изменить**.

### ВМ на паузе из-за хранилища

Оповещение `vm_paused`, `pause_status = eio` или `enospc`. Сначала разберитесь с
хранилищем — сервис снимет ВМ с паузы сам (если разрешено `allow_vm_unpause`),
и она снова встанет на паузу, если проблема не устранена.

`enospc` почти всегда означает тонкий том, упершийся в границу домена. Смотрите
оповещение `storage_domain_low_space` по тому же серверу.

### Хост не отвечает

Оповещение `host_non_responsive`. Автоматическая перезагрузка по питанию
выключена по умолчанию и требует одновременно:

- `monitor.remediation.allow_host_fence: true` в конфигурации,
- настроенного управления питанием на самом хосте в oVirt,
- `failure_threshold` подряд неудачных проверок.

Она останавливает все ВМ хоста. Включайте, только если хосты действительно
одноразовые и ВМ переедут сами.

### Бэкап завершается ошибкой «диски заблокированы»

Признак незакрытого бэкапа на движке от прерванного запуска. Сервис
разбирает такие хвосты при старте; если он не перезапускался — перезапустите.
Вручную:

```bash
# посмотреть открытые бэкапы ВМ
curl -k -u admin@internal:PASS \
  "https://engine/ovirt-engine/api/vms/<vm-id>/backups" -H "Accept: application/json"
# закрыть
curl -k -u admin@internal:PASS -X POST \
  "https://engine/ovirt-engine/api/vms/<vm-id>/backups/<backup-id>/finalize" \
  -H "Content-Type: application/json" -d '{}'
```

### Бэкап неожиданно стал полным вместо инкрементального

Штатное поведение в трёх случаях, и каждый попадает в журнал с причиной:

- нет опорной точки (первый запуск или предыдущие удалены ретенцией);
- движок больше не знает checkpoint предыдущего запуска;
- цепочка достигла длины `full_every`.

### Инкременты не включаются

Инкрементальный бэкап требует, чтобы **у всех** дисков ВМ был режим
`incremental`, а он возможен только для qcow2. Экран ВМ показывает, какие диски
мешают, и даёт включить режим. Диски `raw` придётся конвертировать средствами
движка или согласиться на копию через снапшот.

Изменённые блоки начинают отслеживаться со следующего полного бэкапа — первый
запуск после включения будет полным.

**Диски `raw` при этом бэкапятся как обычно и без остановки ВМ.** Недоступны им
только инкременты: битмап изменённых блоков хранится в заголовке qcow2, и для
raw его негде держать. На oVirt такая ВМ копируется через временный снапшот, на
KVM — тем же горячим pull-режимом, только без checkpoint. Разница не в полноте
копии (данных в ней столько же), а в том, что каждый запуск читает весь занятый
объём.

### Контейнеры не поднимаются: «required variable … is missing a value»

В docker-compose v1 это может выглядеть как трейсбек Python, в конце которого
`RuntimeError` с тем же текстом про незаполненное обязательное значение.

Значит, Compose запущен напрямую с `.env`, собранным вручную из
`.env.example`. Теперь это только справочник: пароли административной роли БД,
роли приложения, Keycloak и OIDC client secret находятся в отдельных файлах
`0600` внутри volumes и не показываются через `docker inspect`.

Готовит `.env` установщик:

```bash
cd deploy && ./install.sh
```

Он создаст или мигрирует защищённые файлы, отдельные роли БД и запустит стек.
Повторный запуск сохраняет БД, ключ, конфигурацию и уже выданные секреты. Не
добавляйте `POSTGRES_PASSWORD` обратно в `.env`: это вернёт пароль в окружение
контейнера и всё равно не заменит пароль уже существующей роли внутри БД.

### Задание не запустилось: «предыдущий ещё выполняется»

В журнале — предупреждение, в интерфейсе — отказ с кодом `job_busy` (409).
Задание не укладывается в свой интервал: прошлый запуск ещё идёт, а по
расписанию подошёл следующий.

Второй экземпляр не запускается намеренно. Два одновременных бэкапа одной ВМ
соревнуются за родительский чекпоинт, и цепочка после этого оказывается в
неопределённом состоянии.

Что делать: посмотреть, что именно затянулось, в списке запусков. Обычные
причины — хранилище стало медленнее, добавились ВМ, инкремент выродился в
полный. Лечится либо разрежением расписания, либо `max_duration` у задания,
чтобы затянувшийся запуск обрывался сам, либо отменой текущих бэкапов вручную.

### Не пускает по правильному паролю: «слишком много попыток»

Код 429 и заголовок `Retry-After`. Включилась пауза после пяти неудач подряд;
она растёт с каждой следующей до 15 минут и снимается сама.

Считается по учётной записи, поэтому паузу мог вызвать кто-то другой, кто
подбирал пароль к этому же имени — посмотрите аудит: попытки записаны там с
адресом. Учётная запись при этом **не заблокирована**: жёсткая блокировка
после N попыток дала бы любому желающему возможность закрыть вход
администратору, зная только логин.

Снимают паузу три вещи: истечение её срока, успешный вход и перезапуск службы —
счётчик живёт в памяти процесса и наружу не сохраняется.

Смена пароля с консоли паузу **не** снимает: это отдельный процесс, он до
таблицы работающей службы не дотягивается. Если ждать нельзя:

```bash
sudo systemctl restart jhvirt
```

В Docker — `docker compose restart ovirt-backup`.

### Пароль принят, но интерфейс снова показывает вход

Полная проверка login-cookie-`/auth/me` и команды исправления приведены в
[разделе «Авторизация»](TROUBLESHOOTING.md#пароль-принят-но-снова-появляется-форма-входа).

Проверьте схему внешнего URL. Если браузер открыт по `http://`, а
`JHV_SERVER_EXTERNAL_URL` начинается с `https://`, ответ login создаёт cookie с
флагом `Secure`, которую браузер не отправляет по открытому HTTP. В результате
сам login отвечает 200, а следующий `/api/v1/auth/me` — 401.

Для systemd значение лежит в `/opt/jhvirt/config/jhvirt.env`, для Docker — в
`.env` как `JHV_EXTERNAL_URL`. Исправьте его так, чтобы схема совпадала с
фактическим адресом браузера, и перезапустите службу. `https://` указывайте при
реальном TLS, в том числе когда его завершает обратный прокси.

### Восстановление в файл отклонено: «каталог не разрешён»

Код 400. Каталог из запроса не входит ни в один из разрешённых: это
`backup.temp_dir` и всё, что перечислено в `backup.restore_dirs`.

Ограничение существует потому, что путь задаёт клиент, а результат — образ на
десятки гигабайт: без списка любой оператор мог бы заполнить раздел с базой
или положить файл в каталог конфигурации.

Нужен другой каталог — добавьте его в `backup.restore_dirs` и перезапустите
службу. В Docker путь должен быть ещё и смонтирован в контейнер, а при
установке через systemd — прописан в `ReadWritePaths` юнита, иначе запись
отклонит уже ядро.

### Временный снапшот не удалился

Сообщение «не удалось удалить временный снапшот». Снапшот с описанием
`jhvirt backup <run-id>` удаляется в интерфейсе движка. Оставленный снапшот
наращивает цепочку образов диска и со временем упирается в место домена.

### Хранилище бэкапов недоступно

Оповещение `storage_target_unreachable`, проверка идёт каждые 15 минут.
Кнопка **Проверить** на странице хранилищ делает полный круг: запись, чтение,
сверка, удаление пробного объекта — то есть проверяет права на запись, а не
только сетевую доступность.

## Восстановление

Порядок от наименее рискованного к наиболее:

1. **В файл** — ничего в oVirt не трогает. Годится для выемки отдельных файлов:
   получившийся raw монтируется через `losetup`/`kpartx`.
2. **В новый диск** — создаёт диск в выбранном домене и заливает образ.
   Существующие данные не затрагиваются.
3. **Поверх существующего диска** — необратимо. Остановите ВМ, которая его
   использует. Интерфейс требует явного подтверждения.
4. **В новую ВМ** — поддерживается для oVirt→oVirt и KVM→KVM. Сначала выполните
   preview, сопоставьте каждый нужный NIC, затем отдельно решите, запускать ли
   машину. Межплатформенной конвертации нет.

Восстановление из инкремента само собирает цепочку. Если какое-то звено удалено,
операция отклоняется до начала записи, а не на середине.

При создании новой ВМ сеть по умолчанию отсоединена, а MAC генерируются заново:
копия production-гостя не должна оказаться рядом с оригиналом автоматически.
Следите за `restore_runs`, а не только за HTTP-ответом `202`: там видны фаза,
процент, целевой VM ID и ошибки rollback. Для `config`-точки допустима ВМ без
дисков, но автоматический старт запрещён.

### Файлы, каталоги и снимки Engine

Нативный файловый бэкап доступен всегда и использует только именованные roots.
Корень `default` указывает на установленные каталоги `file-sources` и
`file-restores`; дополнительные roots задаются в YAML. Перед первым боевым
запуском проверьте:

1. source root смонтирован read-only, если службе не нужна запись;
2. restore root доступен на запись UID службы/контейнера;
3. include/exclude не захватывают временные и socket-файлы;
4. выборочное восстановление выполняется без `overwrite`, затем сравнивается с
   источником; перезапись включается только для конкретного запроса;
5. `partial` и список `unstable_paths` разобраны — это файлы, которые дважды
   менялись во время чтения.

Symlink сохраняется как ссылка и не обходится; hardlink восстанавливается как
ссылка на первую запись. Смена allowlist требует изменения конфигурации и
перезапуска, она намеренно не является runtime-настройкой web.

Снимки конфигурации oVirt Engine создаются отдельными server-level заданиями.
После первого запуска скачайте JSON, проверьте число missing sections и
сравните два последовательных снимка. Они страхуют топологию, profiles, роли и
разрешения, но не содержат секреты Engine и не применяются автоматически.

### Проверка перед тем, как она понадобится

Раз в период (месяц — разумный интервал) прогоняйте по одной ВМ проверку в
режиме `restore`: она собирает образ целиком тем же кодом, что и настоящее
восстановление. Режим `manifest` дешевле и ловит порчу в хранилище, но не
проверяет, что цепочка складывается.

Настройте `verify_after` в заданиях: `chain` почти бесплатен и ловит разрыв
цепочки в тот же день, когда он возник.

Для критичных ВМ заведите отдельное редкое задание с `verify_after: boot` и
выберите KVM-хост для проверки. Сервис соберёт все диски, передаст их на
гипервизор, запустит ВМ без сети с сохранёнными архитектурой, BIOS/UEFI,
шинами и порядком загрузки, дождётся `qemu-guest-agent` и удалит временные
ВМ и образы. Нулевые память и vCPU означают исходные ресурсы. Опцию сохранения
при ошибке включайте только на время диагностики:
оставленные объекты удаляются вручную.

## Обслуживание

Служебные задачи работают сами:

| Задача | Период | Что делает |
|---|---|---|
| ретенция | 1 ч | применяет политики заданий |
| просроченные бэкапы | 1 ч | удаляет копии с истёкшим сроком |
| проверка хранилищ | 15 мин | доступность и запись |
| качество бэкапов | 15 мин | свежесть по расписанию, реплики, проверки и деградация скорости |
| очистка истории | 6 ч | пробы состояния и ёмкости, закрытые оповещения, истёкшие сессии |

### Ретенция: сначала посмотреть, потом применить

Предпросмотр показывает построчно, что политика оставит и что удалит, с
причиной по каждой копии:

```bash
curl -s -b cookies.txt -X POST http://localhost:8080/api/v1/retention/preview \
  -H 'Content-Type: application/json' \
  -d '{"server_id":"…","vm_id":"…","storage_target_id":"…",
       "policy":{"keep_last":3,"keep_daily":7,"keep_weekly":4,"keep_monthly":6}}'
```

Пустая политика (все нули) означает «не удалять ничего» — так форма, отправленная
с нулями, не сносит архив.

## Журналы

`logging.format: json` для сбора в централизованную систему, `console` — для
чтения человеком. Уровень `debug` показывает каждый HTTP-запрос к движку.

Сообщения, требующие внимания:

| Текст | Что делать |
|---|---|
| `НЕ УДАЛОСЬ РАЗМОРОЗИТЬ файловые системы гостя` | проверить ВМ: гость может остаться с замороженной ФС |
| `не удалось закрыть бэкап на движке` | закрыть вручную, иначе диски ВМ заблокированы |
| `не удалось удалить временный снапшот` | удалить в интерфейсе движка |
| `хранилище приняло N байт вместо M` | объект повреждён; бэкап помечен неуспешным |

## Ёмкость хранилищ

Служба сохраняет результат `Usage` каждые 15 минут и хранит его по умолчанию
90 дней. График использует медиану проб внутри суток. Прогноз появляется только
после семи суток истории и равен `текущее свободное место / медианный суточный
рост занятого места`. Нулевой или отрицательный рост означает, что дата
заполнения не вычисляется.

Локальный backend получает квоту через `statfs`. SMB спрашивает свободное место
у самой шары и отвечает всегда. SFTP использует расширение `statvfs`, если сервер
его поддерживает. WebDAV читает свойства `quota-available-bytes` и
`quota-used-bytes` из RFC 4331 — Nextcloud и ownCloud их отдают, простой
`mod_dav` обычно нет. S3 сообщает сумму объектов, но не свободное место bucket:
интерфейс показывает объём и рост со статусом «квота неизвестна». Значение `0`
для свободного места в таком случае не означает заполненный bucket.

## Prometheus и Grafana

Проверка endpoint с systemd-установки:

```bash
TOKEN_FILE=/opt/jhvirt/config/metrics.token
curl -fsS -H "Authorization: Bearer $(sudo cat "$TOKEN_FILE")" \
  http://127.0.0.1:8080/metrics | head
```

Рекомендуемая конфигурация Prometheus на том же хосте:

```yaml
scrape_configs:
  - job_name: ovirt-backup
    metrics_path: /metrics
    scheme: http
    bearer_token_file: /etc/prometheus/secrets/ovirt-backup.token
    static_configs:
      - targets: ["127.0.0.1:8080"]
```

Скопируйте token-файл в каталог, читаемый только пользователем Prometheus;
сам сервисный файл не делайте group-readable ради scrape. При удалённом
Prometheus передавайте `/metrics` только через TLS или защищённую сеть: Bearer
даёт доступ к операционным именам и состояниям, хотя пароли и ключи в метрики
никогда не попадают.

Основные ряды используют стабильные `vm_id`, `job_id` и `storage_target_id`.
Имена вынесены в `ovirt_backup_vm_info`, `ovirt_backup_job_info` и
`ovirt_backup_storage_info`, чтобы переименование ВМ не создавало новый
временной ряд. Для панели Grafana используйте:

- `ovirt_backup_protection_state` и `ovirt_backup_last_success_timestamp_seconds`;
- `rate(ovirt_backup_runs_total[24h])`, длительность и скорость последних копий;
- `ovirt_backup_storage_free_bytes` и `ovirt_backup_storage_forecast_days`;
- `ovirt_backup_alerts_open{severity="critical"}`;
- стандартные `go_*` и `process_*`.
