# Безопасность развёртывания

Документ фиксирует фактические границы защиты штатных установок Docker Compose
и systemd. Он не заменяет hardening ОС, Docker daemon, PostgreSQL и внешних
хранилищ.

## Модель доступа

ovirt-backup хранит административные учётные данные движков, ключи хранилищ и
ключ шифрования копий. Захват процесса приложения означает доступ к этим
секретам и к данным, которые разрешено читать его сервисной записи. Поэтому
службу размещают в отдельной управляющей сети, а доступ к хосту и Docker socket
считают привилегированным.

Пароль `local-admin` не является границей от захваченного процесса. Процесс уже
имеет прикладное подключение к PostgreSQL и может менять пользователей, сессии
и задания напрямую. Защищённый сброс нужен для возврата управления после
остановки недоверенного процесса, а не для ограничения уже выполняемого в нём
произвольного кода.

Контейнер приложения не получает Docker socket, `/dev/kvm`, host network,
privileged mode или каталоги хоста целиком. Подключение к libvirt выполняется
по явно настроенному URI и учётным данным, а не через проброс сокета хоста.

## Контейнеры

| Контроль | Реализация |
|---|---|
| Неизменяемый root | `read_only: true`; запись только в объявленные volumes и ограниченный tmpfs |
| Пользователь приложения | UID/GID `10001`, без root |
| Capabilities приложения/Keycloak/backup | `cap_drop: ALL` |
| PostgreSQL capabilities | только `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETGID`, `SETUID` для штатного entrypoint |
| Повышение прав | `no-new-privileges:true` у всех сервисов |
| Исчерпание ресурсов | лимиты CPU, RAM и PID; ротация `json-file` |
| Сеть БД | сеть `database` помечена `internal: true`, порт 5432 на хост не публикуется |
| Цепочка поставки | базовые образы закреплены tag и digest; обновления принимаются заменой проверенного digest, Keycloak оптимизируется на этапе build |

PostgreSQL-образ поверх закреплённой основы обновляет исправленные OpenSSL
пакеты и заменяет встроенный `gosu`, собранный старым Go, на Alpine `su-exec`.
Это сохраняет снижение привилегий штатного entrypoint без уязвимого Go-бинаря.

Docker daemon остаётся границей доверия: пользователь с доступом к socket
может запустить привилегированный контейнер и получить root на хосте. Не
добавляйте обычных операторов в группу `docker`; управление стеком должно быть
доступно только администраторам ОС.

## PostgreSQL

Во встроенном кластере три роли:

| Роль | Назначение |
|---|---|
| `jhvirt` | обслуживание кластера; приложение её пароль не получает |
| `ovirt_backup_app` | владелец БД приложения, без SUPERUSER/CREATEDB/CREATEROLE |
| `keycloak_app` | владелец отдельной БД Keycloak с теми же ограничениями |

`CONNECT` и `CREATE` для `PUBLIC` отозваны. Пароли ролей — разные случайные
значения. Они находятся в файлах `0600` в отдельных volumes и не передаются
процессам приложения через environment. Для внешней PostgreSQL используйте
`verify-full`, собственный CA, сетевой ACL и отдельную непривилегированную роль.
Режимы `prefer`, `allow`, `disable` и неуказанный `sslmode` для внешнего хоста
отклоняются. Открытое соединение разрешено только для loopback/Unix socket или
точного `trusted_plaintext_host` комплектной внутренней Compose-сети.

## Учётные записи и Keycloak

- `local-admin` — локальная запись приложения. Без OIDC это первый вход.
- `kc-bootstrap-admin` — постоянный администратор master realm Keycloak; в
  приложение им войти нельзя. Случайная bootstrap-запись первой установки
  удаляется после создания и проверки этого администратора.
- участник `virt-admins` входит через OIDC и получает роль `admin` приложения.

Новая OIDC-установка задаёт `JHV_OIDC_ALLOW_LOCAL_LOGIN=false`. Поэтому
локальная форма и API входа возвращают отказ, а сгенерированный пароль
`local-admin` не показывается. Для аварийной процедуры вход включается явно,
пароль сбрасывается из root/Docker-контекста и после работ вход выключается.
Старые установки сохраняют прежнее значение при обновлении.

Для потери пароля Keycloak устанавливается отдельный root-helper
`ovirt-backup-recover-keycloak`. Он работает только с хоста и только после
остановки всех контейнеров сервиса Keycloak. Одноразовый admin service account
живёт до конца операции и удаляется через Admin API; его секрет и новый пароль
находятся в каталоге `0700` под `/run`, не записываются в `.env`, конфигурацию
или постоянный volume. После смены пароля helper отзывает прежние сессии и
проверяет, что постоянный администратор действительно имеет доступ к master
realm. Компрометация Docker daemon или root хоста остаётся полной
компрометацией этой процедуры.

Постоянного пароля администратора нет в environment, `keycloak.conf` или
рабочем контейнере: Keycloak хранит его необратимое представление в своей БД.
Но захват самого процесса Keycloak уже даёт злоумышленнику доступ его роли БД
и возможность менять провайдера без знания пароля. В таком инциденте helper
применяют только после замены недоверенного контейнера и проверки/восстановления
БД; затем меняют OIDC client secret, завершают внешние сессии и проверяют
federation, группы, MFA и клиентов. Один сброс admin-пароля расследование не
заменяет.

Публичные адреса приложения и Keycloak должны использовать HTTPS. Исключение —
loopback для локальной разработки. Внутренний backchannel
`http://keycloak:8080` остаётся внутри Compose и не меняет проверяемый issuer.

Cookie сессии имеет `HttpOnly`, `SameSite=Lax` и `Secure` при HTTPS. В БД лежит
только SHA-256 cookie-токена; OIDC `id_token`, нужный для выхода у провайдера,
зашифрован через `secret.key`. Смена локального пароля атомарно завершает все
сессии этой записи.

Изменяющие browser-запросы проверяют `Origin` относительно `external_url` или
явного CORS allowlist. Чужой Origin отклоняется; Bearer API и `curl`, который не
выдаёт себя за браузер через Fetch Metadata, продолжают работать без Origin.
Ответы получают CSP, запрет framing/MIME sniffing, Referrer/Permissions Policy,
`Cache-Control: no-store` для API и HSTS при HTTPS.

## Секреты

| Секрет | Docker | systemd |
|---|---|---|
| ключ приложения | `jhvirt-data:/app/data/secret.key` | `<PREFIX>/data/secret.key` |
| пароль приложения к БД | `jhvirt-data:/app/data/database.password` | peer через Unix socket или `<PREFIX>/config/database.url` |
| OIDC client secret | `jhvirt-data:/app/data/oidc-client.secret` | `<PREFIX>/config/oidc-client.secret`, если настроен вручную |
| metrics token | `jhvirt-data:/app/data/metrics.token` | `<PREFIX>/config/metrics.token` |
| админ-пароль PostgreSQL | `postgres-secrets:/run/secrets/admin-password` | не нужен при peer |
| конфигурация Keycloak | `keycloak-data:/opt/keycloak/data/ovirt-backup/keycloak.conf` | не применяется |
| recovery token | `<PREFIX>/config/recovery.token` на хосте, не смонтирован | `<PREFIX>/config/recovery.token`, `root:root 0600` |

Bootstrap-пароли удаляются из файлов после успешного старта/настройки. Затем
контейнер пересоздаётся или systemd-служба перезапускается, поэтому первый
процесс, читавший открытый пароль, не продолжает работу. В БД локальный пароль
хранится только как bcrypt-хеш.

Рабочая служба получает только `auth.recovery_token_hash`. Открытый
`recovery.token` не входит в Compose volume, не монтируется в контейнер и не
передаётся через environment. При восстановлении root-скрипт останавливает
службу и подаёт токен доверенному одноразовому процессу через stdin.

Не прикладывайте `.env`,
`jhvirt.env`, `keycloak.conf`, migration archive или вывод с токенами к issue.

## Подключение к хостам и хранилищам

### Ключ SSH-хоста обязателен

Пустое поле «ключ хоста» больше не означает «проверять не надо». Оно означает,
что ключ ещё не задан, и подключения не будет — ни к гипервизору, ни к
SFTP-хранилищу. Раньше пустое поле молча превращалось в подключение к кому
угодно, а заметить это нечем: перехваченное соединение выглядит ровно как
работающее, и через подключение к гипервизору проходят диски всех его
виртуальных машин.

Отказаться от проверки по-прежнему можно, но отдельным признаком —
«подключаться без проверки подлинности». Он виден в списке красной пометкой и
записывается в журнал аудита действием `host_key.verification_disabled`.

Отпечаток берётся кнопкой «Получить» рядом с полем: служба подключается к
адресу, забирает предъявленный ключ и не отправляет при этом никаких учётных
данных — рукопожатие прерывается до аутентификации. Сам по себе отпечаток
ничего не доказывает: тот, кто способен вклиниться в соединение, ответил бы и
на этот запрос. Сверьте его со снятым на самом хосте:

```
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

**При обновлении** уже заведённые подключения без ключа переводятся в явное «без
проверки»: до обновления они работали именно так, и останавливать ночное
копирование ради ужесточения задним числом нельзя. Разница в том, что теперь
это состояние записано и показано. Снимать его нужно по одному подключению за
раз — это единственная работа, которую обновление оставляет оператору.

### Вход по ключу, а не по паролю

Новое подключение к гипервизору и новое SFTP-хранилище заводятся только по
приватному ключу. Пароль для автоматических заданий означает, что он лежит в
базе расшифровываемым и предъявляется хосту при каждом подключении; ключ этим
свойством не обладает — хост видит подпись, а не секрет.

Отдельно закрыт случай, когда заданы и ключ, и пароль: раньше серверу
предлагались оба способа, и хосту, притворившемуся гипервизором, достаточно
было отклонить `publickey`, чтобы клиент сам предъявил пароль. Теперь это
альтернативы, и при наличии ключа пароль не отправляется вовсе.

Заведённые раньше подключения по паролю продолжают работать и помечены в списке
как «вход по паролю». Переводите их на ключи; требование распространяется
только на новые, чтобы обновление службы не остановило копирование ночью.

### Отключённая проверка сертификата — временный режим

У `insecure_tls` теперь есть срок. Служба запоминает, когда проверку отключили,
интерфейс показывает длительность рядом с подключением, а по истечении
`monitor.insecure_tls_grace` (по умолчанию 14 суток) поднимается оповещение
`insecure_tls_expired`. Ноль отключает напоминание — для установок, которые
действительно не могут исправить сертификаты: вечно горящее оповещение хуже
отсутствующего, потому что приучает не смотреть и на остальные.

Повторное сохранение формы отсчёт не сбрасывает, иначе срок не истёк бы никогда.

### Выбор каталога вместо пути по памяти

Пути сохранения выбираются мышью: хранилище, что бэкапить, куда восстанавливать.
Список показывает не файловую систему, а только корни, разрешённые для этого
назначения:

| Назначение | Корни | Право |
|---|---|---|
| хранилище | точки монтирования, доступные службе на запись | `storages:admin` |
| файловый бэкап | `file_backup.roots` | `jobs:admin` |
| восстановление файлов | `restore_roots` выбранного корня | `backups:write` |
| восстановление дисков | `backup.restore_dirs` и `backup.temp_dir` | `backups:write` |
| scratch-каталог на гипервизоре | `backup.scratch_roots` | `servers:admin` |

Выйти за корень нельзя ни через `..`, ни абсолютным путём в запросе, ни по
символьной ссылке: ссылки разыменовываются до проверки, а не после. Попытка
записывается в аудит как `fs.browse`.

Расположение именованных корней файловых бэкапов наружу не отдаётся — оператор
выбирает «Документы», а не `/srv/docs`. Заводить новые корни из интерфейса
по-прежнему нельзя: это остаётся правкой конфигурации, и именно поэтому
администратор в интерфейсе не может заставить службу прочитать `/etc/shadow`.

Путь нового локального хранилища и любое изменение пути проверяются тем же
правилом, что и выбиралка: он обязан лежать внутри каталога, доступного службе
на запись. Неизменённый путь старого хранилища продолжает работать для
совместимости.

Сам local backend открывает каталог через `os.Root` и выполняет чтение, запись,
list и delete относительно этого дескриптора. `..`, абсолютные object keys,
пустой префикс удаления и символические ссылки отклоняются; подмена
промежуточного каталога ссылкой не позволяет выйти за корень.

Последняя строка таблицы стоит особняком: каталоги читаются не у себя, а на
гипервизоре, через уже открытое SSH-соединение. Новых доступов при этом не
появляется — служба и так ходит на этот хост, — но появляется новая
возможность: право `servers:admin` позволяет менять учётные данные подключения
и не позволяет читать файлы хоста, а обзор без границ стёр бы эту разницу.
Поэтому корни заданы списком `backup.scratch_roots`, пустой список запрещает
обзор совсем, а символьные ссылки на удалённой стороне не раскрываются, а
пропускаются: путь, в который они ведут, находится на другой машине, и
проверять его пришлось бы ещё одним заходом на каждую строку списка.

Каталог экспорта OVA выбрать нельзя, и это не пропуск. Экспорт выполняет сам
движок на выбранном хосте кластера, а SSH-доступа к хостам кластера у службы
нет вовсе. Чтобы показать там список каталогов, службе пришлось бы завести
учётные данные к каждому гипервизору — цена несопоставима с удобством одного
поля.

## Восстановление после захвата приложения

Штатная команда для установки из `.run`:

```bash
sudo /opt/jhvirt/bin/ovirt-backup-recover-admin --user local-admin
```

Она выполняет одну транзакцию PostgreSQL: меняет пароль локальной записи,
разблокирует её, удаляет все локальные и OIDC-сессии, отключает все API-токены
из БД и отзывает делегирования. Перед этим рабочий контейнер или служба
останавливается; после операции приложение пересоздаётся из установленного
образа. Новый случайный пароль выводится в терминал и не сохраняется.

Это возвращает контроль, но не завершает расследование. Процесс приложения
мог прочитать рабочие секреты и изменить БД. После сброса:

1. Проверьте checksum и происхождение `.run`/образа и состояние Docker daemon;
   если скомпрометирован хост или socket, восстанавливайте весь хост.
2. Сравните PostgreSQL с известным исправным dump, проверьте список
   пользователей, ролей, заданий, хранилищ и аудит; при сомнении восстановите
   БД, а не доверяйте сбросу пароля.
3. Завершите сессии в Keycloak/внешнем IdP, смените OIDC client secret и
   проверьте группы `virt-admins`, `virt-operators`, `virt-readers`.
4. Смените пароли/ключи приложения к PostgreSQL, движкам oVirt, KVM-хостам,
   S3/SFTP/SMB/WebDAV и webhook/SMTP/Telegram.
5. Считайте `secret.key` раскрытым. Простая замена файла сделает существующие
   секреты и зашифрованные копии нечитаемыми; планируйте отдельную миграцию
   ключа и новые полные цепочки бэкапов.
6. После проверки OIDC снова задайте `--local-login disabled` и выполните
   тестовый вход, `verify` и восстановление из копии.

Статические `auth.api_tokens` нельзя отозвать через БД. Recovery-команда
откажется работать, пока они присутствуют в YAML: удалите их и повторите.
Сессии внешнего провайдера также закрываются у самого провайдера отдельно.

Если host-only token-файл потерян, остановите приложение и повторно запустите
доверенный установщик: он создаст новый токен и заменит verifier. Не копируйте
токен в volume приложения «для удобства».

## Аварийный комплект

Штатный установщик создаёт ежедневный custom-format `pg_dump`, проверяет его
через `pg_restore --list` и публикует атомарно с режимом `0600`. Вместе с БД
приложения копируется `secret.key`; с профилем Keycloak отдельно копируется его
БД. По умолчанию хранится семь дней.

Каталог на том же сервере не является полноценной резервной копией. Разместите
`--dr-backup-dir` на отдельном защищённом mount или забирайте его внешней
системой. Регулярно восстанавливайте оба dump на изолированном PostgreSQL и
сверяйте копию ключа. Для внешней БД дополнительно нужны PITR/WAL-архив и
проверка процедуры восстановления.

## Проверка после установки

```bash
docker compose config >/dev/null
docker compose ps
docker inspect "$(docker compose ps -q ovirt-backup)" \
  --format 'user={{.Config.User}} readonly={{.HostConfig.ReadonlyRootfs}} caps={{json .HostConfig.CapDrop}}'
docker inspect "$(docker compose ps -q postgres)" \
  --format 'ports={{json .NetworkSettings.Ports}} readonly={{.HostConfig.ReadonlyRootfs}}'
docker compose exec -T postgres psql -U jhvirt -d postgres -c \
  "select rolname, rolsuper, rolcreatedb, rolcreaterole from pg_roles where rolname in ('ovirt_backup_app','keycloak_app');"
```

Ожидается: UID приложения `10001`, read-only root, `ALL` в `CapDrop`, у 5432
нет host binding, обе прикладные роли не имеют административных флагов.

Полный Java-скан Keycloak может показать `CVE-2025-59250` для
`mssql-jdbc-13.2.1.jre11.jar`. Keycloak включает драйверы нескольких СУБД,
хотя эта установка использует PostgreSQL. Версию сверяйте с именем JAR:
[Microsoft указывает `13.2.1` как релиз с исправлением](https://learn.microsoft.com/en-us/sql/connect/jdbc/release-notes-for-the-jdbc-driver),
а старые сканеры
могут потерять суффик `.jre11`. Не добавляйте бессрочное глобальное
исключение CVE: при смене базового образа повторно проверяйте фактический
файл и release notes.

Дальнейшие проверки TLS, cookie, OIDC и DR находятся в
[DEPLOY.md](DEPLOY.md), штатные ошибки — в
[TROUBLESHOOTING.md](TROUBLESHOOTING.md).
