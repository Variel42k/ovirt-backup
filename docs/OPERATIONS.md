# Эксплуатация

Установка по шагам находится в [DEPLOY.md](DEPLOY.md). Полный каталог ошибок
Docker, systemd, PostgreSQL, авторизации, oVirt и KVM находится в
[TROUBLESHOOTING.md](TROUBLESHOOTING.md). Здесь описаны регулярные операции
после успешного развёртывания.

## Проверка живости

```bash
curl -fsS http://localhost:8080/healthz    # процесс отвечает
curl -fsS http://localhost:8080/readyz     # база доступна, сколько бэкапов идёт
```

Оба эндпоинта не требуют аутентификации — их вызывает балансировщик.

## Первый запуск

При установке Docker или systemd с новой локальной базой через `install.sh`
пароль администратора печатает сам установщик, в конце, вместе с адресом
интерфейса. Он задаёт пароль заранее и после успешного старта стирает его из
`.env`.

При подключении новой внешней PostgreSQL установщик не может заранее знать,
пуста ли удалённая таблица пользователей. Если база действительно пустая,
служба создаст администратора и один раз напечатает пароль в
`journalctl -u jhvirt`. Альтернатива — сразу выполнить описанный ниже сброс
пароля `admin`.

Ниже — про запуск в обход установщика (свой `.env`, systemd, ручной старт).
Тогда пароль генерирует служба и выводит один раз, отдельным блоком в stderr:

```
════════════════════════════════════════════════════════════
  СОЗДАНА УЧЁТНАЯ ЗАПИСЬ АДМИНИСТРАТОРА

  пользователь: admin
  пароль:       <...>
════════════════════════════════════════════════════════════
```

Блок, а не поле в строке журнала: в поле пароль оказывался в конце длинной
фразы, узкий терминал её переносил, и при копировании в пароль попадал перенос
строки. Вход тогда отвечал «неверный пароль» — сообщение, из которого причину
не видно.

В открытом виде пароль не хранится нигде. Если он потерян:

```bash
sudo systemd-run --quiet --wait --pipe --collect \
  --uid=jhvirt --gid=jhvirt --working-directory=/opt/jhvirt \
  --property=EnvironmentFile=/opt/jhvirt/config/jhvirt.env \
  /opt/jhvirt/bin/justhpc-virt-server -reset-password admin
```

Команда печатает новый пароль тем же блоком и завершается, не поднимая сервис;
свой пароль можно задать через `JHV_NEW_PASSWORD` (не короче 10 символов).
Все действующие сессии этой учётной записи закрываются, а если запись была
заблокирована — разблокируется. В Docker:

```bash
docker compose run --rm justhpc-virt-manager -reset-password admin
```

Удалять строку из таблицы `users` руками больше не нужно.

## Режим проверки авто-восстановления

Авто-восстановление начинает работу в режиме проверки: решения принимаются и
записываются, но не выполняются. Это не настройка, а наблюдение — у него есть
начало и конец, и оба видны в «Настройки → Система».

Этот режим относится только к автоматическому устранению сбоев: запуску VM,
активации хоста и fencing. Он не означает, что восстановление бэкапов является
тестовым, и не ограничивает проверки образов или ручное восстановление.

Пока режим включён, каждое решение попадает в журнал подробно: какой объект, на
каком подключении, что предложено, почему, какая это попытка за час и что
именно было бы сделано. Пропущенные решения — те, что не прошли ворота политики
или лимитов, — пишутся там же: во время наблюдения «хотел, но не стал» не менее
важно, чем «сделал бы».

```
РЕЖИМ ПРОВЕРКИ: действие зафиксировано, но не выполнено
  объект=db-01 подключение=prod действие=Запустить ВМ
  почему предложено="ВМ выключена, а должна работать"
  было бы выполнено="ВМ \"db-01\" была бы запущена"
  попытка за час=1
```

Переключение — тумблером в интерфейсе, на ходу, без перезапуска. Выход из
режима требует подтверждения и основания: после него автоматика начнёт трогать
боевые машины. В этот момент все решения периода собираются в архив — JSON со
сводкой и полным списком, — который остаётся в `monitor.remediation.archive_dir`
и открывается из истории режимов. Это и есть обоснование того, что автоматике
доверили боевые машины.

Выбранный режим хранится в базе и переживает перезапуск: оператор, не
закончивший наблюдение, не должен получить работающую автоматику из-за
перезагрузки службы.

## Мониторинг ввода-вывода и путей до хранилища

Вкладка «Ввод-вывод» на странице подключения отвечает на два разных вопроса, и
их важно не путать.

**Медленно ли работает диск гостю.** Верхний график: сплошные линии — объём в
секунду, пунктир — задержка на операцию. Смотреть надо на пунктир. Диск с низкой
скоростью и низкой задержкой просто не нагружен; низкая скорость при высокой
задержке — это и есть «тормозит». По одному объёму эти два случая неразличимы:
оба выглядят как линия у нуля. Задержка берётся из накопленного времени операций
QEMU; если гипервизор её не отдаёт (старая версия, неподдерживаемый драйвер),
пунктир отсутствует, а не рисуется нулём.

**Доходит ли трафик до СХД.** Нижняя таблица и график. NFS о потере пакетов не
сообщает — сообщает о том, что она с ним сделала:

| Показатель | Что означает |
|---|---|
| Повторы | вызов остался без ответа и был отправлен снова |
| Таймауты | клиент исчерпал расписание повторов; гость увидел зависший диск |
| Плохие xid | ответ пришёл на вызов, который уже сочли потерянным |
| Отклик | среднее время ответа сервера за интервал |

Единичные повторы бывают на исправной сети. Устойчивый процент (порог — 1% от
операций) и **любой** таймаут поднимают оповещение `storage_path_degraded`.
Разорванная сессия iSCSI — оповещение критическое сразу.

Источники данных: `/proc/self/mountstats` для NFS, sysfs для состояния сессий
iSCSI, `DomainBlockStatsFlags` libvirt для дисков.

**Работает только для подключений типа KVM.** Всё перечисленное требует доступа
к гипервизору по SSH; движок oVirt статистику монтирований своих хостов наружу
не отдаёт, и получить её через него неоткуда.

Сбор включается `monitor.collect_io_stats` (по умолчанию включён), срок хранения
— `monitor.io_retention` (неделя). Метрики снимаются тем же проходом, что и
состояние: отдельный опрос удвоил бы нагрузку на гипервизор ради тех же данных.

## Журнал службы

Вкладка «Настройки → Журнал», только для администратора: журнал не содержит
секретов, но перечисляет все ВМ, хосты и операторов установки — это карта
инфраструктуры.

**Ротация двойная.** По размеру — когда файл перерастает `max_size_mb`. И раз в
сутки в полночь, даже если размер не достигнут. Второе нужно потому, что
`max_age_days` чистит архивы, а не активный файл: на тихой установке он иначе
рос бы годами, ни разу не сменившись, и предельный возраст к нему бы не
применился. Пустой файл в полночь не меняется — иначе каталог заполнили бы
пустые архивы и вытеснили настоящие из `max_backups`. Архивы сжимаются.

Сменить файл вручную можно кнопкой; смена, как и изменение уровня, попадает в
аудит.

**Уровень меняется на ходу.** `trace, debug, info, warn, error` — переключение
действует немедленно и до перезапуска службы, постоянное значение остаётся в
`logging.level`. Это сделано ради разбора аварий: поднять подробность обычно
нужно тогда, когда перезапускать мониторинг меньше всего хочется. Само
изменение пишется в журнал — иначе внезапно замолчавший или, наоборот,
залитый журнал ничем себя не объясняет.

| Параметр | Значение по умолчанию |
|---|---|
| `logging.file` | `./logs/jhvirt.log`; пусто — только поток службы |
| `logging.level` | `info` |
| `logging.format` | `console` (в Docker — `json`) |
| `logging.max_size_mb` | 100 |
| `logging.max_backups` | 7 |
| `logging.max_age_days` | 30 |

В Docker `JHV_LOGGING_FILE` пуст: журнал уходит в поток контейнера, где его
собирает docker/journald. Задайте путь внутри тома, если нужен файл и просмотр
из интерфейса.

## Что не защищено

Раздел «Защита» отвечает на вопрос, который не задают, пока он не понадобился:
какие машины не переживут потерю. Счётчик «под защитой 14 из 17» на обзоре сам
по себе бесполезен — здесь эти три названы поимённо.

Список отсортирован по опасности, и это не украшение: машина без единой копии,
утонувшая среди десятка «копия устарела», не будет замечена.

| Состояние | Что значит |
|---|---|
| Не защищена | ни одной копии; при потере восстанавливать нечего |
| Последний бэкап не удался | годная копия есть, но свежая не создалась |
| Без задания | копии есть, но защита держится на том, что кто-то помнит запускать руками |
| Копия устарела | последняя удачная старше порога (по умолчанию 48 ч) |
| Защищена не полностью | копия свежая, но часть дисков в неё не попала |

Последнее состояние опирается на список пропущенных дисков, который теперь
сохраняется в каждом запуске. Раньше диски отбрасывались молча: общий
(shareable) том, диск с ISO, диск, исключённый настройкой задания. Оператор
видел «успешно, 2 диска» и не знал, что у машины есть третий.

Это самый опасный вид тишины в системе: **упавший бэкап хотя бы виден как
упавший, а успешный с дырой выглядит как защита, которой нет.** Теперь пропуски
видны и в списке запусков (метка «не всё»), и в карточке точки — с причиной и
пометкой, было это решением оператора или ограничением, о котором он мог не
знать.

## Что резервировать в самом сервисе

| Что | Зачем |
|---|---|
| `data/secret.key` | без него не расшифровать пароли подключений и зашифрованные бэкапы |
| База PostgreSQL | каталог копий, задания, история, учётные записи |
| `config/virt-manager.yaml` | настройки |

Снимок базы снимается на живой службе, останавливать её не нужно:

```bash
pg_dump -U jhvirt jhvirt > /srv/backups/jhvirt-$(date +%F).sql
```

В Docker — `docker compose exec -T postgres pg_dump -U jhvirt jhvirt > …`.



Данные бэкапов самодостаточны: каталог запуска содержит `run.json` и манифесты,
и разбирается без базы (см. [BACKUP-FORMAT.md](BACKUP-FORMAT.md)).

`secret.key` копируйте **отдельно от базы и не в то хранилище, где лежат
копии**. Резерв, уехавший вместе с тем, что он защищает, спасает ровно от тех
аварий, от которых и так спасла бы вторая копия базы, — и ни от одной из тех,
ради которых он делается.

## Типовые ситуации

Ниже оставлены частые эксплуатационные случаи. Расширенная диагностика с
проверками установки и точными командами исправления находится в
[TROUBLESHOOTING.md](TROUBLESHOOTING.md).

### Движок недоступен

Оповещение `engine_unreachable`, состояние сервера `offline`. Сервис
автоматически пересоздаёт клиент (единственное, что он делает сам в этом случае).

Если в сообщении «отверг учётные данные» — это не авария движка, а истёкший или
изменённый пароль. Поправьте подключение: **Серверы → изменить**.

### ВМ на паузе из-за хранилища

Оповещение `vm_paused`, `pause_status = eio` или `enospc`. Сначала разберитесь с
хранилищем — сервис снимет ВМ с паузы сам (если разрешено `allow_vm_unpause`),
и она снова встанет на паузу, если проблема не устранена.

`enospc` почти всегда означает тонкий том, упершийся в границу домена. Смотрите
оповещение `storage_domain_low_space` по тому же серверу.

### Хост не отвечает

Оповещение `host_non_responsive`. Автоматическая перезагрузка по питанию
выключена по умолчанию и требует одновременно:

- `monitor.remediation.allow_host_fence: true` в конфигурации,
- настроенного управления питанием на самом хосте в oVirt,
- `failure_threshold` подряд неудачных проверок.

Она останавливает все ВМ хоста. Включайте, только если хосты действительно
одноразовые и ВМ переедут сами.

### Бэкап завершается ошибкой «диски заблокированы»

Признак незакрытого бэкапа на движке от прерванного запуска. Сервис
разбирает такие хвосты при старте; если он не перезапускался — перезапустите.
Вручную:

```bash
# посмотреть открытые бэкапы ВМ
curl -k -u admin@internal:PASS \
  "https://engine/ovirt-engine/api/vms/<vm-id>/backups" -H "Accept: application/json"
# закрыть
curl -k -u admin@internal:PASS -X POST \
  "https://engine/ovirt-engine/api/vms/<vm-id>/backups/<backup-id>/finalize" \
  -H "Content-Type: application/json" -d '{}'
```

### Бэкап неожиданно стал полным вместо инкрементального

Штатное поведение в трёх случаях, и каждый попадает в журнал с причиной:

- нет опорной точки (первый запуск или предыдущие удалены ретенцией);
- движок больше не знает checkpoint предыдущего запуска;
- цепочка достигла длины `full_every`.

### Инкременты не включаются

Инкрементальный бэкап требует, чтобы **у всех** дисков ВМ был режим
`incremental`, а он возможен только для qcow2. Экран ВМ показывает, какие диски
мешают, и даёт включить режим. Диски `raw` придётся конвертировать средствами
движка или согласиться на копию через снапшот.

Изменённые блоки начинают отслеживаться со следующего полного бэкапа — первый
запуск после включения будет полным.

**Диски `raw` при этом бэкапятся как обычно и без остановки ВМ.** Недоступны им
только инкременты: битмап изменённых блоков хранится в заголовке qcow2, и для
raw его негде держать. На oVirt такая ВМ копируется через временный снапшот, на
KVM — тем же горячим pull-режимом, только без checkpoint. Разница не в полноте
копии (данных в ней столько же), а в том, что каждый запуск читает весь занятый
объём.

### Контейнеры не поднимаются: «required variable … is missing a value»

В docker-compose v1 это может выглядеть как трейсбек Python, в конце которого
`RuntimeError` с тем же текстом про незаполненный пароль.

Значит, `.env` собран вручную из `.env.example`, где пароль базы пуст
намеренно — иначе он оказался бы одинаковым во всех установках. Compose
считает пустое значение таким же отсутствующим, как незаданное.

Готовит `.env` установщик:

```bash
cd deploy && ./install.sh
```

Он же и запускает. В существующем `.env` сохраняются пароль базы и остальные
настройки; установщик меняет только внешний URL и порт. PostgreSQL держит
исходный пароль в томе и новый без явной миграции не примет.

Заполнить руками тоже можно:

```bash
sed -i "s|^POSTGRES_PASSWORD=$|POSTGRES_PASSWORD=$(openssl rand -hex 24)|" .env
```

### Задание не запустилось: «предыдущий ещё выполняется»

В журнале — предупреждение, в интерфейсе — отказ с кодом `job_busy` (409).
Задание не укладывается в свой интервал: прошлый запуск ещё идёт, а по
расписанию подошёл следующий.

Второй экземпляр не запускается намеренно. Два одновременных бэкапа одной ВМ
соревнуются за родительский чекпоинт, и цепочка после этого оказывается в
неопределённом состоянии.

Что делать: посмотреть, что именно затянулось, в списке запусков. Обычные
причины — хранилище стало медленнее, добавились ВМ, инкремент выродился в
полный. Лечится либо разрежением расписания, либо `max_duration` у задания,
чтобы затянувшийся запуск обрывался сам, либо отменой текущих бэкапов вручную.

### Не пускает по правильному паролю: «слишком много попыток»

Код 429 и заголовок `Retry-After`. Включилась пауза после пяти неудач подряд;
она растёт с каждой следующей до 15 минут и снимается сама.

Считается по учётной записи, поэтому паузу мог вызвать кто-то другой, кто
подбирал пароль к этому же имени — посмотрите аудит: попытки записаны там с
адресом. Учётная запись при этом **не заблокирована**: жёсткая блокировка
после N попыток дала бы любому желающему возможность закрыть вход
администратору, зная только логин.

Снимают паузу три вещи: истечение её срока, успешный вход и перезапуск службы —
счётчик живёт в памяти процесса и наружу не сохраняется.

Смена пароля с консоли паузу **не** снимает: это отдельный процесс, он до
таблицы работающей службы не дотягивается. Если ждать нельзя:

```bash
sudo systemctl restart jhvirt
```

В Docker — `docker compose restart justhpc-virt-manager`.

### Пароль принят, но интерфейс снова показывает вход

Полная проверка login-cookie-`/auth/me` и команды исправления приведены в
[разделе «Авторизация»](TROUBLESHOOTING.md#пароль-принят-но-снова-появляется-форма-входа).

Проверьте схему внешнего URL. Если браузер открыт по `http://`, а
`JHV_SERVER_EXTERNAL_URL` начинается с `https://`, ответ login создаёт cookie с
флагом `Secure`, которую браузер не отправляет по открытому HTTP. В результате
сам login отвечает 200, а следующий `/api/v1/auth/me` — 401.

Для systemd значение лежит в `/opt/jhvirt/config/jhvirt.env`, для Docker — в
`.env` как `JHV_EXTERNAL_URL`. Исправьте его так, чтобы схема совпадала с
фактическим адресом браузера, и перезапустите службу. `https://` указывайте при
реальном TLS, в том числе когда его завершает обратный прокси.

### Восстановление в файл отклонено: «каталог не разрешён»

Код 400. Каталог из запроса не входит ни в один из разрешённых: это
`backup.temp_dir` и всё, что перечислено в `backup.restore_dirs`.

Ограничение существует потому, что путь задаёт клиент, а результат — образ на
десятки гигабайт: без списка любой оператор мог бы заполнить раздел с базой
или положить файл в каталог конфигурации.

Нужен другой каталог — добавьте его в `backup.restore_dirs` и перезапустите
службу. В Docker путь должен быть ещё и смонтирован в контейнер, а при
установке через systemd — прописан в `ReadWritePaths` юнита, иначе запись
отклонит уже ядро.

### Временный снапшот не удалился

Сообщение «не удалось удалить временный снапшот». Снапшот с описанием
`jhvirt backup <run-id>` удаляется в интерфейсе движка. Оставленный снапшот
наращивает цепочку образов диска и со временем упирается в место домена.

### Хранилище бэкапов недоступно

Оповещение `storage_target_unreachable`, проверка идёт каждые 15 минут.
Кнопка **Проверить** на странице хранилищ делает полный круг: запись, чтение,
сверка, удаление пробного объекта — то есть проверяет права на запись, а не
только сетевую доступность.

## Восстановление

Порядок от наименее рискованного к наиболее:

1. **В файл** — ничего в oVirt не трогает. Годится для выемки отдельных файлов:
   получившийся raw монтируется через `losetup`/`kpartx`.
2. **В новый диск** — создаёт диск в выбранном домене и заливает образ.
   Существующие данные не затрагиваются.
3. **Поверх существующего диска** — необратимо. Остановите ВМ, которая его
   использует. Интерфейс требует явного подтверждения.

Восстановление из инкремента само собирает цепочку. Если какое-то звено удалено,
операция отклоняется до начала записи, а не на середине.

### Проверка перед тем, как она понадобится

Раз в период (месяц — разумный интервал) прогоняйте по одной ВМ проверку в
режиме `restore`: она собирает образ целиком тем же кодом, что и настоящее
восстановление. Режим `manifest` дешевле и ловит порчу в хранилище, но не
проверяет, что цепочка складывается.

Настройте `verify_after` в заданиях: `chain` почти бесплатен и ловит разрыв
цепочки в тот же день, когда он возник.

Для критичных ВМ заведите отдельное редкое задание с `verify_after: boot` и
выберите KVM-хост для проверки. Сервис соберёт все диски, передаст их на
гипервизор, запустит ВМ без сети с сохранёнными архитектурой, BIOS/UEFI,
шинами и порядком загрузки, дождётся `qemu-guest-agent` и удалит временные
ВМ и образы. Нулевые память и vCPU означают исходные ресурсы. Опцию сохранения
при ошибке включайте только на время диагностики:
оставленные объекты удаляются вручную.

## Обслуживание

Служебные задачи работают сами:

| Задача | Период | Что делает |
|---|---|---|
| ретенция | 1 ч | применяет политики заданий |
| просроченные бэкапы | 1 ч | удаляет копии с истёкшим сроком |
| проверка хранилищ | 15 мин | доступность и запись |
| свежесть бэкапов | 1 ч | оповещает о ВМ, не бэкапившихся два интервала расписания |
| очистка истории | 6 ч | пробы состояния, закрытые оповещения, истёкшие сессии |

### Ретенция: сначала посмотреть, потом применить

Предпросмотр показывает построчно, что политика оставит и что удалит, с
причиной по каждой копии:

```bash
curl -s -b cookies.txt -X POST http://localhost:8080/api/v1/retention/preview \
  -H 'Content-Type: application/json' \
  -d '{"server_id":"…","vm_id":"…","storage_target_id":"…",
       "policy":{"keep_last":3,"keep_daily":7,"keep_weekly":4,"keep_monthly":6}}'
```

Пустая политика (все нули) означает «не удалять ничего» — так форма, отправленная
с нулями, не сносит архив.

## Журналы

`logging.format: json` для сбора в централизованную систему, `console` — для
чтения человеком. Уровень `debug` показывает каждый HTTP-запрос к движку.

Сообщения, требующие внимания:

| Текст | Что делать |
|---|---|
| `НЕ УДАЛОСЬ РАЗМОРОЗИТЬ файловые системы гостя` | проверить ВМ: гость может остаться с замороженной ФС |
| `не удалось закрыть бэкап на движке` | закрыть вручную, иначе диски ВМ заблокированы |
| `не удалось удалить временный снапшот` | удалить в интерфейсе движка |
| `хранилище приняло N байт вместо M` | объект повреждён; бэкап помечен неуспешным |
| `авто-восстановление работает в режиме проверки` | напоминание: действия не выполняются |
