# Ролевая модель

Кто что может и как это настроить. Механику для клиентов API описывает
[API.md](API.md#роли-и-права); здесь — схема для того, кто раздаёт доступ.

## Как устроено

Доступ решает **право**, а не имя роли:

```
пользователь ──> роль ──> набор прав ──> проверка на маршруте
                  │
                  └─ имя роли нигде не сравнивается со строкой "admin"
```

Право имеет вид `раздел.действие`. Разделы совпадают с пунктами меню намеренно:
тот, кто раздаёт доступ, думает не о маршрутах HTTP, а о том, что человек
увидит на экране.

Роль — именованный набор прав. Ролей может быть сколько угодно: три встроенных
плюс любые свои.

### Почему не по именам ролей

Раньше проверка сравнивала имя роли со строкой. При таком устройстве
собственная роль невозможна: любое имя, кроме трёх известных, не проходило ни
одну проверку и молча запрещало всё. Теперь имя роли — только ярлык, а решает
набор прав.

Последствие, о котором стоит знать: `can_write` и `can_administer` в
`GET /auth/me` выводятся из прав, а не из имени роли.

## Действия

| Действие | Что открывает |
|---|---|
| `read` | видеть раздел и его содержимое |
| `write` | повседневные действия: запустить, отменить, подтвердить |
| `admin` | то, что настраивается однажды: подключения, хранилища, параметры |
| `disruptive` | обрыв чужой работы без остановки гостевой ОС |

Четвёртое заведено ровно под один случай и умножать его на разделы не следует:
каждая новая ступень удлиняет список, который человек читает глазами при выдаче
прав.

Таблица проверяется тестом: право, добавленное в каталог и забытое здесь,
роняет сборку. Документ, разошедшийся с кодом, хуже отсутствующего — по нему
раздают доступ.

### Что закрыто от оператора и почему

| Право | Почему не у оператора |
|---|---|
| `servers.disruptive` | фенсинг хоста уносит все ВМ на нём разом; для бэкапа не нужен никогда |
| `servers.admin` | смена адреса движка или его учётных данных — это подмена источника данных |
| `storages.admin` | смена адреса хранилища уводит копии в другое место, а ключ шифрования делает старые нечитаемыми |
| `jobs.admin` | смена основной копии меняет, откуда восстанавливать |
| `logs.read` | журнал службы перечисляет все ВМ, хосты и операторов установки |
| `audit.read` | в аудите видно, кто и когда входил, включая неудачные попытки |
| `settings.*` | параметры службы задаются однажды при установке |
| `dr.*` | проверка аварийной готовности разворачивает копию и нагружает хранилище |

Так было и до появления ролей. Переход на права не должен был ни у кого
отобрать доступ и тем более никому его добавить — это закреплено тестом
`TestBuiltinRolesPreservePreviousAccess`.

## Встроенные роли

```
viewer  ⊂  operator  ⊂  admin
  8          14          29
```

Вложенность строгая и проверяется тестом: право, попавшее наблюдателю, но не
оператору, — почти наверняка ошибка разметки.

| Роль | Для кого |
|---|---|
| `viewer` | смотрит состояние, ничего не запускает |
| `operator` | ведёт бэкапы: задания, восстановление, проверка, оповещения |
| `admin` | всё, включая выдачу прав |

Встроенные роли нельзя удалить и переименовать: на них ссылаются существующие
учётные записи, сопоставление групп внешнего провайдера и чужие скрипты.

Изменить их набор прав тоже нельзя. Нужен «оператор плюс аудит» — это своя
роль, а не правка встроенной: правка меняла бы доступ всем, у кого эта роль уже
стоит, включая тех, о ком забыли.

## Свои роли

`GET /permissions` возвращает каталог для редактора, `POST /roles` создаёт роль:

```json
{
  "name": "auditor",
  "title": "Аудитор",
  "description": "Читает журналы, ничего не меняет",
  "permissions": ["servers.read", "jobs.read", "backups.read", "audit.read", "logs.read"]
}
```

Правила:

- Имя латиницей — оно попадает в сессию и в сопоставление групп провайдера.
- Несуществующее право отвергается при сохранении. Роль с опечаткой выглядела
  бы настроенной, а работала бы как роль без этого права.
- Встроенное имя занять нельзя: роль `admin`, заведённая в обход, была бы
  отличным способом тихо расширить себе права.
- Роль, назначенную хоть одному пользователю, удалить нельзя.

### Задержка после правки

Роли кешируются на 30 секунд, но правка роли сбрасывает кеш сразу. Задержка
проявляется только при изменении в обход API — например, правкой в базе.

Отозвать доступ немедленно надёжнее сменой роли пользователя: сессия хранит имя
роли, а права берутся при каждой проверке.

## Внешний провайдер (OIDC)

Группа провайдера отображается на роль по `auth.oidc.role_mapping`. Свои роли
участвуют наравне со встроенными.

Порядок разрешения, когда пользователь состоит в нескольких группах:

1. встроенные — от старшей к младшей: `admin`, `operator`, `viewer`;
2. затем настраиваемые — по алфавиту.

Второй пункт существует не ради красоты: перебор map в Go идёт в случайном
порядке, и без сортировки роль пользователя менялась бы от входа к входу.

Пользователю без совпадений выдаётся `auth.oidc.default_role`; если он пуст,
вход отклоняется.

Подробности настройки — [CONFIGURATION.md](CONFIGURATION.md#внешний-вход-oidc).

## Что права не закрывают

Права решают, **кому** можно. Отдельно от них работают ещё три ограничения:

| Механизм | Что делает | Где описан |
|---|---|---|
| `management.enabled` | отключает управление ВМ и хостами целиком, независимо от прав | [CONFIGURATION.md](CONFIGURATION.md#управление-виртуализацией-как-выключить) |
| Согласование | опасные действия требуют кворума согласующих, даже у администратора | [API.md](API.md#согласование-опасных-действий) |
| Делегирование | согласующий передаёт своё право голоса на срок отсутствия — токен плюс отдельный пароль | [API.md](API.md#делегирование-права-голоса) |
| Карантин удаления | удалённая копия физически стирается не сразу | [API.md](API.md#карантин-удаления) |

Порядок проверок для запроса:

```
вход ──> право ──> выключатель управления ──> согласование ──> действие
```

Право проверяется первым: сообщать «действие требует согласования» тому, кому
оно не положено вовсе, незачем.

### Группы согласующих — не роли

Состав группы согласующих задаётся поимённо и с ролями не связан. Членство по
роли означало бы, что выдача роли молча меняет состав согласующих, — а это ровно
то, что само должно требовать согласования.

Отсюда же следует, что делегировать право голоса может только тот, кто в группе
состоит: передать можно лишь то, что есть.

## Токены API

Именной токен наследует роль своего владельца и живёт по своему сроку.
Отзывается по одному, без перезапуска. Формат и выдача — в
[API.md](API.md#токены-доступа).

Токены из файла настроек (`auth.api_tokens`) — прежний механизм: каждый даёт
права администратора, срока не имеет и отзывается только перезапуском. Служба
предупреждает о них при старте, пока список не пуст.
