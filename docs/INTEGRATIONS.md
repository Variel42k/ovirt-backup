# Интеграционные сценарии

Как служба встраивается в чужой контур: кто её опрашивает, куда она пишет, чем
управляет доступом. Каждый сценарий описан от задачи, а не от настройки — по
настройкам есть [CONFIGURATION.md](CONFIGURATION.md).

Отдельно отмечено, что **проверено**, а что написано, но на живой системе не
запускалось. Расширенный перечень непроверенного — [LIMITATIONS.md](LIMITATIONS.md).

## 1. Журнал аудита в SIEM

**Задача:** сохранить след действий там, где его не сотрёт тот, кто получил
права администратора в самой службе.

Журнал аудита лежит в PostgreSQL — в той же базе, до которой у администратора
есть доступ. Затирание следов делают первым делом, поэтому нужен второй
экземпляр за пределами системы.

```yaml
audit:
  file: /var/log/jhvirt/audit.jsonl
```

Формат — JSON Lines, одна запись в строке:

```json
{"time":"2026-08-23T11:04:22Z","actor":"operator1","action":"backup.delete","scope":"vm","object_id":"7f3c…","detail":"web-01","success":true,"remote_ip":"10.0.0.15","host":"jhv-01","service":"ovirt-backup"}
```

Поля объявлены отдельно от внутренней модели и являются внешним договором:
переименование поля в коде не меняет то, что читает сборщик.

| Поле | Смысл |
|---|---|
| `time` | UTC, RFC 3339 |
| `actor` | имя учётной записи или токена |
| `action` | `раздел.действие`, например `storage.delete` |
| `scope`, `object_id` | над чем |
| `detail` | человекочитаемое пояснение (обычно имя объекта) |
| `success` | в журнал попадают и неудачи, включая неудачный вход |
| `remote_ip` | откуда пришёл запрос |
| `host`, `service` | чтобы свести несколько установок в один сборщик |

### Защита от правки

Файл открывается с `O_APPEND` и без `O_TRUNC`, служба **не ротирует его сама**.
Оба решения нужны для режима «только дозапись»:

```bash
mkdir -p /var/log/jhvirt
chattr +a /var/log/jhvirt/audit.jsonl
```

С этим атрибутом строки можно добавлять и нельзя ни изменить, ни удалить — даже
от root, пока атрибут не снят. Ротацию выполняет сборщик или внешний
`logrotate` (с `copytruncate` он несовместим — нужен `create` после снятия
атрибута).

Если запись срывается, служба сообщает об этом в свой журнал **один раз**, а не
на каждое действие, и продолжает работать: недоступный сборщик не должен
останавливать бэкапы.

**Проверено:** запись внутри контейнера, неудачный вход попадает в файл
корректной строкой JSON.
**Не проверено:** приём конкретным SIEM (Splunk, Elastic, Loki), поведение при
`chattr +a` на смонтированном томе Docker.

### Filebeat, минимальный кусок

```yaml
filebeat.inputs:
  - type: filestream
    paths: ["/var/log/jhvirt/audit.jsonl"]
    parsers:
      - ndjson:
          target: ""
          add_error_key: true
```

Дополнительный разбор не нужен: строки уже структурированы.

## 2. Prometheus и Grafana

**Задача:** свести состояние защищённости в общий мониторинг и завести алерты
там, где их уже смотрят.

`/metrics` закрыт токеном из файла — отдельным от токенов API, потому что
Prometheus не умеет ходить с cookie и не должен получать доступ к остальному:

```yaml
metrics:
  enabled: true
  token_file: /etc/jhvirt/metrics.token
```

```yaml
scrape_configs:
  - job_name: ovirt-backup
    authorization:
      credentials_file: /etc/prometheus/jhvirt.token
    static_configs:
      - targets: ["jhv-01:8080"]
```

Метрики названы с префиксом `ovirt_backup_`. Опорные:

| Метрика | О чём |
|---|---|
| `ovirt_backup_protection_state` | текущее состояние защиты ВМ (1 у актуального состояния) |
| `ovirt_backup_last_success_timestamp_seconds` | когда последний раз получилась полная копия |
| `ovirt_backup_last_verification_timestamp_seconds` | когда копию последний раз проверяли |
| `ovirt_backup_vm_info`, `_job_info`, `_storage_info` | имена для подписей на графиках |

Правило «бэкапа не было сутки» строится на `last_success`, а не на счётчике
ошибок: задание, которое перестало запускаться вовсе, ошибок не даёт.

Подробности и готовые панели — [CONFIGURATION.md](CONFIGURATION.md#мониторинг-качества-и-prometheus).

**Проверено:** отдача метрик, проверка токена.

## 3. Оповещения наружу

**Задача:** доставить событие туда, где дежурный его увидит.

Три канала: почта, Telegram, webhook. Каждое оповещение адресовано одной из
четырёх аудиторий, и подписка настраивается по ним — иначе дежурный по
инфраструктуре получает письма про свободное место, перестаёт их читать и
пропускает то, ради чего подписывался.

| Аудитория | Что попадает |
|---|---|
| `backup` | результаты заданий, проверок, ретенции |
| `infrastructure` | хранилища, движки, хосты |
| `service` | сама служба: база, планировщик, лицензия |
| `security` | доступ и согласование: заявки, аварийный обход |

Webhook получает JSON:

```json
{"severity":"critical","kind":"break_glass_used","object":"storage/backup-s3",
 "message":"…","details":"…","at":"2026-08-23T11:04:22Z",
 "alert_id":"…","event":"raised","sequence":17}
```

`Authorization: Bearer <token>` добавляется, если токен задан. Поле `sequence`
растёт монотонно — по нему принимающая сторона отличает повтор от нового
события, а `event` показывает, поднято оповещение или закрыто.

**Проверено:** доставка по всем трём каналам, повторы, автозакрытие.
**Не проверено:** приём конкретными системами дежурств (PagerDuty, OpsGenie) —
готового преобразования полей под них нет, нужен промежуточный обработчик.

## 4. Внешний вход (Keycloak и другие OIDC)

**Задача:** не заводить вторую базу учётных записей и отзывать доступ
увольняющемуся в одном месте.

Группа провайдера отображается на роль службы:

```yaml
auth:
  oidc:
    enabled: true
    issuer: https://keycloak.example.org/realms/infra
    client_id: ovirt-backup
    role_mapping:
      "/infra/backup-admins": admin
      "/infra/backup-operators": operator
      "/infra/auditors": auditor      # своя роль работает наравне со встроенной
    default_role: ""                   # пусто — вход без совпадения отклоняется
```

Порядок разрешения при нескольких группах: сначала встроенные от старшей к
младшей, затем свои — по алфавиту. Второе не косметика: перебор в Go идёт в
случайном порядке, и без сортировки роль менялась бы от входа к входу.

Вход по паролю можно оставить рядом или выключить целиком. Полностью выключать
стоит только после проверки внешнего входа: иначе при недоступном провайдере в
систему не попасть никому.

Что нужно завести на стороне Keycloak — [CONFIGURATION.md](CONFIGURATION.md#keycloak-что-нужно-завести-на-его-стороне).

**Проверено:** вход, сопоставление групп, выбор роли, выключение локального входа.
**Не реализовано:** SCIM. Учётная запись заводится при первом входе, но
удаление пользователя в провайдере не удаляет её здесь — доступ теряется (вход
не проходит), а запись остаётся.

## 5. Скрипты, CI и оркестрация

**Задача:** запускать бэкап или проверку из чужого конвейера.

Именной токен:

```bash
curl -sS -X POST https://jhv-01:8443/api/v1/api-tokens \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -d '{"name":"ci-nightly","role":"operator","expires_in_days":30}'
```

Ответ содержит секрет **один раз**. Токен наследует роль, живёт по своему сроку
и отзывается по одному, без перезапуска службы.

Дальше — обычный REST с `Authorization: Bearer jhv.<prefix>.<secret>`:

```bash
curl -sS -X POST https://jhv-01:8443/api/v1/backups \
  -H "Authorization: Bearer $JHV_TOKEN" \
  -d '{"job_id":"…"}'
```

Для конвейера важны две вещи:

- Роль токена выдаётся под задачу. Токену ночного бэкапа не нужны ни
  `storages.admin`, ни `servers.disruptive` — заведите под него свою роль.
- Ответ 409 `job_busy` означает «занято сейчас», а не поломку: повторять,
  а не падать.

**Проверено:** выдача, срок, отзыв, проверка при каждом запросе.

### Согласование и автоматика

Если для действия включено согласование, запрос от скрипта вернёт **202** и
идентификатор заявки, а не результат. Конвейеру нужно либо не трогать
согласуемые действия, либо уметь дождаться заявки. Аварийный обход из скрипта
использовать нельзя: он поднимает оповещение критической важности и требует
письменного обоснования от человека.

## 6. Хранилище с защитой от удаления

**Задача:** копия должна пережить компрометацию самой службы.

Приложение защиту дать не может: если оно умеет удалить объект, то умеет и тот,
кто им завладел. Защита живёт на стороне хранилища.

| Хранилище | Чем защищать |
|---|---|
| S3 | Object Lock — настраивается в самой службе |
| SMB | NTFS ACL: дать запись, не давать удаление |
| SFTP | пользователь без `unlink` либо забор копий по pull |
| local, NFS | снапшоты ZFS/Btrfs/LVM — делает не служба |
| WebDAV | зависит от сервера; у большинства управления правами нет |

Служба умеет **проверить**, работает ли защита: пробует записать, перезаписать
и удалить пробный объект и показывает результат.

**Не проверено на живых хранилищах** — ни S3 с Object Lock, ни SMB с
ограниченными ACL. Подробности — [CONFIGURATION.md](CONFIGURATION.md#как-защитить-хранилище-если-это-не-s3).

## 7. Подключение к движку с безопасными правами

**Задача:** не хранить пароль администратора oVirt в службе бэкапа.

`POST /servers/provision` один раз подключается административной записью,
заводит роль с минимальным набором прав, выдаёт её сервисной учётной записи и
дальше работает только под ней. Пароль администратора не сохраняется.

Одно ограничение обойти нельзя: **создать учётную запись через REST движок не
даёт** — пользователи приходят из домена аутентификации. Сервисную запись
заводит оператор на самом движке:

```bash
ovirt-aaa-jdbc-tool user add jhvirt-backup
ovirt-aaa-jdbc-tool user password-reset jhvirt-backup
```

Служба берёт уже существующего пользователя и выдаёт ему права.

**Не проверено на живом движке.** Состав прав роли — предположение, имена групп
действий у разных версий отличаются. Смягчено проверкой: после настройки служба
переподключается под сервисной записью и проверяет фактический доступ; при
`ready: false` подключение не сохраняется.

Подробности — [API.md](API.md#безопасное-подключение).

## 8. Несколько установок

Экземпляры не общаются между собой. Свести их можно двумя способами:

- **аудит** — поля `host` и `service` в каждой строке;
- **метрики** — метка `instance` из Prometheus.

Общей консоли нет и не планируется: она означала бы учётную запись с доступом
ко всем установкам сразу, то есть ровно ту единую точку отказа, от которой
уводит остальная работа по безопасности.

## Чего нет

| Что | Состояние |
|---|---|
| syslog / CEF / LEEF | только JSON Lines в файл; преобразование — задача сборщика |
| SCIM | учётные записи не удаляются вслед за провайдером |
| Внешнее хранилище секретов (Vault, KMS) | ключ шифрования и пароли лежат в `secret.key` и базе |
| Готовые интеграции с системами дежурств | webhook общего вида, нужен промежуточный обработчик |
| Подпись строк аудита | защиту от правки даёт `chattr +a`, криптографической цепочки нет |
