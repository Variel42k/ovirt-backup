# Практические сценарии

Готовые порядки действий для типовых задач — от выдачи доступа сотрудникам до
восстановления машины в другой кластер. В каждом сценарии есть команды и
запросы, которые можно скопировать.

Подробности и крайние случаи — в профильных руководствах по ссылкам.

> [!TIP]
> Примеры рассчитаны на стандартную установку из `.run` в режиме Docker Compose:
> `PREFIX=/opt/jhvirt`, служба отвечает на `https://<адрес>:8080`. Для systemd
> пути и файлы перечислены в [CONFIGURATION.md](CONFIGURATION.md).

## 1. Доступ сотрудникам через Active Directory

Доменный пароль вводится только на странице Keycloak. Приложение получает из
токена список групп и по нему назначает роль. Роли вложены друг в друга:
`viewer` ⊂ `operator` ⊂ `admin` — наблюдатель только смотрит, оператор выполняет
повседневные операции, администратор управляет всем. Полная матрица прав — в
[ROLES.md](ROLES.md).

**Как настроить**

1. **Администрирование → Домен и единый вход.**
2. Включите **Назначать роли по группам Keycloak** и заполните поля
   **AD-группа → admin**, **AD-группа → operator**, **AD-группа → viewer**.
3. Поле **Если нет группы и ручного назначения** оставьте пустым: пользователь
   без подходящей группы не войдёт, а в отказе увидит, какие группы пришли.
4. Сохраните. Роль пересчитывается при каждом входе.

Так выглядит соответствие, в котором к трём группам доступа добавлены уже
существующие группы AD:

```json
{
  "virt-admins": "admin",
  "virt-operators": "operator",
  "virt-readers": "viewer",
  "Domain Admins": "admin",
  "_PROG_DEV": "viewer"
}
```

- Имена групп сравниваются без учёта регистра.
- Если у пользователя несколько групп, побеждает старшая роль.
- Выдать доступ одному человеку без групп AD: Keycloak → **Users** →
  пользователь → **Groups** → **Join Group** → `virt-admins`, `virt-operators`
  или `virt-readers`.

> [!IMPORTANT]
> Этот раздел меняется только из локальной сессии администратора с
> подтверждением пароля: администратор, вошедший через Keycloak, изменить его не
> может. После смены соответствия все сессии, открытые через Keycloak,
> отзываются — пользователи входят заново. Подробнее —
> [KEYCLOAK-AD.md](KEYCLOAK-AD.md#5-подключение-из-web-интерфейса).

> [!NOTE]
> Форма показывает для каждой роли одну группу — первую из соответствия.
> Дополнительные группы вроде `Domain Admins` выше при сохранении формы не
> теряются. Задать их можно через API: `PUT /api/v1/settings/identity`, поле
> `role_mapping`.

## 2. Подключение РЕД Виртуализации без хранения пароля администратора

Служба работает под отдельной сервисной учётной записью с минимальной ролью.
Пароль администратора движка нужен один раз — на время настройки — и нигде не
сохраняется. Мастер рассчитан на oVirt 4.3 и новее и на форки — РЕД
Виртуализацию, OLVM, RHV: состав прав он сверяет с каталогом самого движка, а
не с номером версии. Сквозной прогон выполнен на РЕД Виртуализации 7.3.

**Шаг 1. Сервисная запись на движке.** На хосте Engine от root. Права этой
записи не выдавайте — роль с минимальным набором прав создаст и назначит мастер:

```bash
ovirt-aaa-jdbc-tool user add jhvirt-backup --attribute=firstName=JustHPC --attribute=lastName=Backup
ovirt-aaa-jdbc-tool user password-reset jhvirt-backup --password-valid-to="2035-12-31 00:00:00Z"
```

Вторая команда обязательна: у только что созданной записи пароля нет, и войти
она не может.

**Шаг 2. Мастер.**

- Новое подключение: **Виртуализация → Подключить oVirt-контур**.
- Уже добавленное: меню ⋮ подключения → **Настроить сервисную запись**. Оставьте
  прежнюю учётную запись, чтобы только проверить и дополнить её права, или
  укажите новую, чтобы понизить права подключения.

Администратор — любая запись движка с правами администратора, например
`admin@internal`. Сервисная запись — `jhvirt-backup@internal`.

**Шаг 3. Отчёт.** Успешная настройка выглядит так:

| Шаг | Результат |
|---|---|
| подключение администратором | движок 7.3.0 |
| каталог прав движка | все запрошенные права существуют |
| роль jhvirt-backup | создана |
| учётная запись jhvirt-backup@internal | добавлена из домена internal-authz |
| назначение роли | на уровне системы |
| проверка доступа | всё необходимое доступно |

Подключение переводится на сервисную запись только после успешной проверки
доступа. Если проверка не прошла, прежняя учётная запись остаётся на месте.

> [!NOTE]
> Имя сервисной записи вводите так же, как для входа: `jhvirt-backup@internal`.
> Сам движок хранит её в домене авторизации `internal-authz` — мастер находит
> этот домен сам.

> [!TIP]
> Проверка доступа читает кластеры, ВМ, диски и домены хранения. Права на сам
> съём проявятся первым бэкапом — см.
> [сценарий 5](#5-разовый-бэкап-и-проверка-прав-сервисной-записи).

## 3. Второе хранилище на отдельном диске

Задача: том `/storage` использовать под копии рядом с основным каталогом. Путь
хранилища в интерфейсе задаётся **внутри контейнера**, а писать в каталог должна
служба — она работает от UID `10001`.

```bash
# 1. Каталог под копии, доступный службе
sudo mkdir -p /storage/backups
sudo chown 10001:10001 /storage/backups
sudo chmod 0750 /storage/backups
```

```yaml
# 2. /opt/jhvirt/compose/docker-compose.override.yml — диск внутрь контейнера
services:
  ovirt-backup:
    volumes:
      - /storage:/storage
```

```bash
# 3. Применить и убедиться, что служба пишет в каталог
cd /opt/jhvirt/compose
docker compose config | grep -A1 'source: /storage'
docker compose up -d ovirt-backup
docker compose exec ovirt-backup sh -c 'touch /storage/backups/.probe && rm /storage/backups/.probe && echo запись-ok'
```

4. **Хранилища → Добавить хранилище → Локальный каталог**, путь
   `/storage/backups`. При сохранении служба запишет и удалит пробный объект.

> [!WARNING]
> Путь хоста вроде `/opt/jhvirt/backups` в форме не сработает: внутри
> контейнера этот каталог называется `/backups`. Обзор каталогов в форме
> показывает ровно то, что видит служба; корень, куда писать нельзя, открыт
> только для просмотра — из него спускаются в подкаталог с правом записи.

Override переживает обновления `.run`, а правка `docker-compose.yml` — нет.
Почему так и что делать при установке через systemd — в
[OPERATIONS.md](OPERATIONS.md#локальное-хранилище-на-отдельном-диске).

## 4. Задание резервного копирования

**Задания ВМ → Новое задание.** Минимум: подключение, отбор ВМ, тип, расписание,
хранилище и правила хранения. Перед первым запуском откройте предпросмотр
отбора — он показывает, какие ВМ попали под задание и почему.

Пример ночного инкремента для машин с именами `prod-*`. В интерфейсе это те же
поля формы; через API — `POST /api/v1/jobs`:

```jsonc
{
  "name": "Ночной инкремент prod",
  "server_id": "…",
  "vm_name_regex": "^prod-",
  "type": "incremental",
  "full_every": 7,                  // каждый седьмой запуск — полный
  "fallback_type": "snapshot",      // диски без CBT снимаются через снапшот
  "schedule": "0 1 * * *",          // каждый день в 01:00
  "storage_target_ids": ["…"],      // первое хранилище — основное
  "retention": { "keep_last": 3, "keep_daily": 7, "keep_weekly": 4, "keep_monthly": 6 },
  "consistency": "filesystem"       // заморозить ФС гостя на время фиксации точки
}
```

Расписание — cron из пяти полей в системном часовом поясе (**Параметры
системы**):

| Выражение | Когда |
|---|---|
| `0 1 * * *` | каждый день в 01:00 |
| `30 22 * * 1-5` | по будням в 22:30 |
| `0 */6 * * *` | каждые 6 часов |
| `0 3 * * 0` | по воскресеньям в 03:00 |

- Все дисковые типы снимаются без остановки ВМ.
- Если опорной точки для инкремента нет, запуск честно выполнится как полный, а
  причина будет видна в записи о запуске.
- `full_every` ограничивает длину цепочки: чем она длиннее, тем больше звеньев
  нужно для восстановления.

Все поля задания — в [API.md](API.md#задания), выбор типа бэкапа — во вкладке
**Справочник** этой страницы.

### Если в ВМ работает СУБД

Уровень `filesystem` сохраняет файловые системы, но PostgreSQL или MySQL при
запуске копии пройдут восстановление по журналу. Чтобы копия стартовала чисто:

1. В каждой ВМ с СУБД поставьте сценарии заморозки из комплекта и проверьте их:

   ```bash
   sudo sh guest-hooks/linux/install.sh --postgresql
   ```

   ```bash
   sudo sh guest-hooks/linux/install.sh --check
   ```

2. В задании выберите **Согласованность копии → Приложения (СУБД)**. Флаг
   **Прервать запуск, если уровень не достигнут** включайте, когда копия
   «как после сбоя» для этих машин хуже, чем пропущенный запуск.
3. После первого запуска откройте точку: у неё должна стоять метка
   «приложения». Если уровень ниже, причина написана там же, а задание подняло
   оповещение «Копия ниже заявленной согласованности».

Как работают сценарии и что проверять при понижении уровня — в
[OPERATIONS.md](OPERATIONS.md#согласованность-копий-субд).

Нужна отдельная база, а не машина целиком, — переезд на другую версию СУБД,
выборочный возврат, физический сервер без виртуализации? Добавьте к копии ВМ
логические дампы: **Дампы СУБД → Хост СУБД**, затем задание. Хелпер ставится
на хост одной командой и не требует паролей СУБД; восстановление идёт только в
новую базу — подробно в [OPERATIONS.md](OPERATIONS.md#логические-дампы-субд).

## 5. Разовый бэкап и проверка прав сервисной записи

Первый реальный бэкап — лучшая проверка новой сервисной записи: проверка
доступа в мастере только читает инвентарь, а права на сам съём проявляются при
запуске.

1. **Виртуализация** → подключение → ВМ → **Запустить бэкап сейчас**. Выберите
   хранилище и полный тип.
2. **Точки восстановления** — дождитесь итога запуска.
3. Успех — роли хватает. Если движок отказал в доступе, роли не хватает права;
   его название будет в тексте ошибки.

Недостающее право добавляется повторным запуском мастера для этого подключения:
существующая роль только дополняется, ничего не пересоздаётся. Состав прав
передаётся полем `permits`, пока только через API. Пароли читаются с клавиатуры и
уходят в запрос через stdin — не в историю команд и не в список процессов:

```bash
read -rsp 'Пароль администратора движка: ' ADMIN_PASS; echo
read -rsp 'Пароль jhvirt-backup: ' SERVICE_PASS; echo
curl --cacert server.crt -X POST "https://<адрес>:8080/api/v1/servers/<id>/provision" \
  -H "Authorization: Bearer $JHV_TOKEN" -H 'Content-Type: application/json' --data @- <<EOF
{"admin_username": "admin@internal", "admin_password": "$ADMIN_PASS",
 "service_username": "jhvirt-backup@internal", "service_password": "$SERVICE_PASS",
 "permits": ["attach_disk"]}
EOF
unset ADMIN_PASS SERVICE_PASS
```

`<id>` подключения — из адреса его страницы (`/servers/<id>`); токен и
сертификат — в [сценарии 7](#7-автоматизация-через-api).

> [!NOTE]
> Права сверяются с каталогом самого движка: имя, которого нет в этой версии,
> мастер пропустит и назовёт в отчёте, а не сломает роль целиком.

## 6. Восстановление машины в другой кластер

Восстановление собирает **новую** ВМ из точки: создаёт машину, диски и
подключает их. Это не живая миграция — исходная машина не трогается. Целью может
быть другой кластер того же Engine или другой Engine того же семейства.

1. **Точки восстановления** → нужная точка → **Восстановить копию**.
2. Выберите **Собрать машину целиком: создать ВМ, диски и подключить их**.
3. Укажите подключение, кластер, домен хранения, имя и сеть. План покажет диски,
   объём, свободное место, предупреждения и блокеры — до того, как что-либо
   создано.
4. **Собрать машину** и следите за фазой восстановления до конечного статуса.

То же через API: сначала план, затем выполнение с тем же телом:

```bash
API=https://<адрес>:8080/api/v1
BODY='{"server_id":"…","cluster_id":"…","storage_domain_id":"…","name":"billing-restored","start":false}'

curl -s --cacert server.crt -H "Authorization: Bearer $JHV_TOKEN" -H 'Content-Type: application/json' \
  -X POST "$API/backups/<id>/restore-vm/plan" -d "$BODY"      # warnings, blockers, диски, место

curl -s --cacert server.crt -H "Authorization: Bearer $JHV_TOKEN" -H 'Content-Type: application/json' \
  -X POST "$API/backups/<id>/restore-vm" -d "$BODY"           # 202 и restore_id
```

| Блокер в плане | Что сделать |
|---|---|
| не выбран целевой кластер | укажите кластер целевого подключения |
| целевой кластер не найден | опросите подключение заново и выберите кластер из обновлённого списка |
| не выбран целевой домен хранения | выберите домен данных в дата-центре этого кластера |
| на целевом сервере уже есть VM с таким именем | задайте другое имя |
| межплатформенное восстановление не поддерживается | oVirt и KVM друг в друга не конвертируются — выберите подключение той же платформы |

> [!WARNING]
> Сеть новой машины по умолчанию отключена, автозапуск выключен: это копия
> боевой системы с теми же адресами, ключами и учётными данными. Подключайте
> сеть, только если оригинала больше нет или сегмент изолирован.

## 7. Автоматизация через API

**Администрирование → Роли и токены → Выпустить**: имя, роль и срок. Токен
показывается один раз — сразу сохраните его в хранилище секретов.

```bash
export JHV_TOKEN='jhv.XXXXXXXX.…'
API=https://<адрес>:8080/api/v1

# Сертификат службы для curl, если он самоподписанный
cd /opt/jhvirt/compose && docker compose cp ovirt-backup:/app/data/tls/server.crt ~/server.crt

# Неудачные запуски за сутки
curl -s --cacert ~/server.crt -H "Authorization: Bearer $JHV_TOKEN" "$API/backups?status=failed&days=1"

# Какие ВМ попадают под задание и почему
curl -s --cacert ~/server.crt -H "Authorization: Bearer $JHV_TOKEN" "$API/jobs/<id>/preview"

# Запустить задание немедленно
curl -s --cacert ~/server.crt -H "Authorization: Bearer $JHV_TOKEN" -X POST "$API/jobs/<id>/run"
```

- Роль токена работает так же, как роль пользователя: для мониторинга хватит
  `viewer`.
- В журнале аудита действие токена записывается как `токен:<имя>`.
- Коллекции приходят в виде `{"items": [...], "total": N}`. Полный справочник —
  [API.md](API.md).

## 8. Проверка после обновления

Пять минут после наката `.run`, которые экономят день:

```bash
cd /opt/jhvirt/compose
docker compose ps                                                     # все контейнеры up, служба healthy
curl -sk -o /dev/null -w '%{http_code}\n' https://127.0.0.1:8080/readyz   # 200
docker compose exec ovirt-backup /app/ovirt-backup-server --version     # собранный коммит
docker compose config | grep -A1 'source: /storage'                    # дополнительные монтажи на месте
```

Затем в интерфейсе:

- вход через Keycloak проходит, роль соответствует группе;
- **Виртуализация** — подключения на связи;
- **Хранилища** — проверка доступности зелёная;
- **Покрытие защитой** — нет новых просроченных ВМ.

Обновление сохраняет базу, realm Keycloak, `secret.key` и
`docker-compose.override.yml`. Перенос на другой сервер —
[DEPLOY.md](DEPLOY.md#перенос-приложения-на-другой-сервер).

| Симптом | Что проверить | Подробно |
|---|---|---|
| После входа через Keycloak снова форма входа | часы сервера, адрес возврата, cookie | [TROUBLESHOOTING.md](TROUBLESHOOTING.md#пароль-принят-но-снова-появляется-форма-входа) |
| «Группы пользователя не отображаются ни в одну роль» | какие группы перечислены в отказе и есть ли они в соответствии | [сценарий 1](#1-доступ-сотрудникам-через-active-directory), [TROUBLESHOOTING.md](TROUBLESHOOTING.md#5-авторизация) |
| В форме хранилища каталог «только для просмотра» | владелец каталога — UID `10001`; путь указан внутри контейнера | [сценарий 3](#3-второе-хранилище-на-отдельном-диске) |
| Инкремент выполнился как полный | причина в записи о запуске: нет checkpoint или CBT на диске | [TROUBLESHOOTING.md](TROUBLESHOOTING.md#8-бэкапы-и-инкременты) |
| Восстановление не начинается | блокеры в плане | [сценарий 6](#6-восстановление-машины-в-другой-кластер), [TROUBLESHOOTING.md](TROUBLESHOOTING.md#10-восстановление) |
| Подключение «недоступен» | DNS имени движка изнутри контейнера, сертификат, учётная запись | [DNS.md](DNS.md), [TROUBLESHOOTING.md](TROUBLESHOOTING.md) |

Всё, что сделано с оговорками или ещё не проверено на живой системе, честно
перечислено в [LIMITATIONS.md](LIMITATIONS.md).
