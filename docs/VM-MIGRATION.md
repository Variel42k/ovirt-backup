# Миграция виртуальных машин

Мастер переносит ВМ между двумя независимыми подключениями семейства oVirt:
oVirt, РЕД Виртуализация, RHV, OLVM. Открывается в разделе **Миграция виртуальных
машин**, кнопкой **Миграция ВМ** в списке машин или из карточки ВМ.
Для перемещения между хостами одного Engine остаётся отдельное действие
**Миграция между хостами** в меню ВМ.

## Выбор режима

**С остановкой:** источник штатно выключается, создаётся полная копия, на цели
собирается ВМ и запускается после повторной проверки выключенного источника.

**Предварительное копирование:** полная копия и наполнение целевых дисков
выполняются при работающем источнике. Цель остаётся выключенной, её сети
отсоединены. После подготовки изменения синхронизируются каждые две минуты;
можно запросить синхронизацию вручную. По кнопке **Переключить на целевую ВМ**
источник выключается, передаётся последняя дельта и запускается цель.

Второй режим требует Backup API и включённого incremental на всех дисках.
Он не переносит память и действующие сетевые соединения гостя. Потеря checkpoint,
подмена цепочки полной копией, изменение конфигурации или состава/размера дисков
останавливают операцию с объяснением. Полное восстановление не подставляется
вместо финальной дельты.

## Мастер

1. Выбрать исходное подключение, ВМ, другой Engine и имя целевой ВМ.
2. Выбрать кластер, домен целевых дисков и репозиторий промежуточной копии.
   Это разные назначения: репозиторий хранит бэкап, домен — рабочие диски ВМ.
   Доступные домены берутся из подключений без повторного добавления.
3. Сопоставить каждый NIC с целевым vNIC profile либо исключить его. Выбрать,
   какие сети подключать после переключения. При необходимости сохранить MAC:
   перед запуском проверяются конфликты в целевом Engine.
4. Выбрать режим, проверить план и подтвердить остановку и изменения идентичности.

На цели создаются новые UUID. Сохранение MAC не сохраняет VM UUID, BIOS serial
и состояние лицензий, зависящих от них. Для первой реализации поддерживается
x86_64; Secure Boot блокируется до отдельной приёмки переноса ключей/NVRAM.
Общие, Direct LUN и неактивные диски не допускаются: неполный перенос не
выдаётся за успешный. Остановка выполняется штатно; принудительное выключение
не используется при ошибке завершения работы гостя.

## Наблюдение и завершение

Страница операции показывает этап, процент, объём/скорость синхронизации,
идентификаторы созданной ВМ и ошибки. Длительность последней синхронизации
помогает оценить копирование финальных изменений; простой также включает
завершение работы и загрузку гостя и не гарантируется фиксированным числом.
Ошибки показываются на странице независимо от настройки всплывающих уведомлений.

После запуска цели проверить приложение, сеть и лицензии и нажать
**Подтвердить работу приложения**. Источник сохраняется выключенным. Его
автоматический запуск и команды через приложение блокируются до отката;
прямое управление вне приложения оператор согласует самостоятельно.

## Сбои и откат

**Приостановить** прерывает текущую задачу. **Откатить миграцию** выключает и
удаляет созданную целевую ВМ с дисками и только после подтверждения её отсутствия
восстанавливает исходное состояние источника и прежнюю политику мониторинга.
Данные, появившиеся только на цели, при таком откате теряются — это явно
подтверждается перед действием.

После рестарта службы незавершённые задачи помечаются приостановленными.
Сохраняются соответствия дисков, идентификаторы ресурсов и последняя применённая
точка. Для полностью подготовленной warm-цели доступны повторная синхронизация
и переключение. При незавершённом создании цели нужно выполнить откат и начать
заново; автоматического повторного создания ресурсов нет. Если выключение
или очистка цели не подтверждены, источник автоматически не запускается.

Пока операция не завершена, используемые бэкапы защищены от удаления;
конфликтующие бэкапы, восстановления и автодействия над ВМ блокируются.

Подробный объём работ: [PLAN-OVIRT-TRANSFER.md](PLAN-OVIRT-TRANSFER.md).


Техническая основа: [Incremental Backup — документация oVirt](https://www.ovirt.org/develop/release-management/features/storage/incremental-backup.html).
Для изолированной приёмки используется образ из [официального каталога CirrOS](https://download.cirros-cloud.net/0.6.3/) с проверкой SHA-256 до подготовки тестового диска.

После отмены или отката кнопка **Удалить запись** освобождает связи истории с подключениями и репозиторием. Завершённую работающую миграцию так удалить нельзя.

После подтверждения переноса настройте задания бэкапа для целевой ВМ: задания источника автоматически не переназначаются.

## Приёмка 25 октября 2026 года

На стенде `10.249.251.36` проверены отдельные тестовые ВМ CirrOS x86_64,
256 МБ RAM, один диск 1 ГБ, BIOS `q35_sea_bios`, без сетевых интерфейсов:

| Режим | Источник → цель | Результат |
| --- | --- | --- |
| С остановкой | engine.icctm.local → engine.pish.advengineering.local | Полная копия, восстановление, запуск цели, подтверждение и откат |
| Предварительное копирование | engine.pish.advengineering.local → engine-2.pish | Полная копия при работающем источнике, первая и ручная синхронизации, остановка источника, финальная дельта в существующий диск, запуск цели, подтверждение и откат |

Финальная синхронизация во втором сценарии заняла 79 секунд. Это измерение
конкретной тестовой ВМ, а не обещание простоя: к нему добавляются штатное
выключение гостя и загрузка цели. Рабочая ВМ `logos` не использовалась.
Работоспособность прикладного ПО, сети, лицензий, Windows и UEFI в этой
приёмке не проверялась. Secure Boot пока заблокирован.

Автоматические проверки: `go vet ./...`, полный `go test ./...` в Linux с
изолированной PostgreSQL, сборка Vue/TypeScript и 16 браузерных проверок.
Покрыты холодный/warm-порядок действий, повторное применение изменённых
и нулевых блоков, потеря опорной точки, рестарт, блокировки ресурсов,
ошибка выключения цели при откате, права и выключенное управление.
Установленная страница и открытие мастера дополнительно проверены в браузере
на настольном и мобильном экранах.

Ограничения самого стенда: на одном хосте не хватило RAM для тестовой ВМ;
ImageIO старого icctm-ovirt.ad.icctm.ru отклонил TLS из-за сертификата без SAN.
Неудачная миграция туда откатилась; проверка сертификатов не отключалась.

После неудачного выделения самого первого тестового диска на домене
`engine2bitrix` остался пустой диск `jhvirt-migration-test-20261025`,
ID `65dadf0b-adcf-4f3b-8b4f-3f9a91bf25e8`. Он не содержит данных рабочих ВМ.
oVirt сохраняет его в `locked` и отклоняет обычное удаление с HTTP 409
`Related operation is currently in progress`. Исходная пустая тестовая ВМ
удалена; диск принудительно не разблокировывался. Диагностика сохранена в
записи импорта `6c400a70-af45-4272-98fc-a9fa51caf3a1`.
