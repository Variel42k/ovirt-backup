# Боевое развёртывание

Инструкция для установки, на которую собираются полагаться. Отличается от
«Быстрого старта» в README тем, что там задача — посмотреть, а здесь — работать:
внешняя СУБД, TLS, сохранность ключа шифрования и проверка того, что копии
действительно восстанавливаются.

> **Прежде чем полагаться.** Ни один путь кода, обращающийся к гипервизору, не
> проверялся против настоящего oVirt или KVM. Пройдите
> [приёмочный прогон](#8-приёмочный-прогон) на стенде и держите систему параллельно
> существующей, пока он не пройден. Раздел [«Готовность»](#готовность) —
> о том, что именно проверено, а что нет.

---

## 1. Что нужно

| | Требование |
|---|---|
| Сеть до движка | HTTPS на 443 к oVirt; для KVM — SSH на 22 к гипервизору |
| Сеть до данных | 54322 к `ovirt-imageio` на **каждом** хосте; если хосты в изолированной сети хранения, см. `backup.transfer.prefer_proxy` |
| Учётная запись oVirt | достаточно роли с правами на чтение инвентаря и Backup API; для действий оживления — на управление ВМ и хостами |
| Хранилище копий | локальный каталог/NFS, S3-совместимое или SFTP |
| Место под сервис | база и ключ — десятки мегабайт; временный каталог — под сборку образа при восстановлении в файл |
| СУБД | PostgreSQL 13+ — обязательна, схема создаётся сама при первом запуске |

Гипервизоры трогать не нужно: ни агентов, ни изменений на стороне движка.

## 2. Docker — рекомендуемый путь

Один compose-файл поднимает сервис и его базу. Только боевой вариант:
обязательные переменные не имеют значений по умолчанию, поэтому установка не
может незаметно подняться с паролем «на первое время».

### 2.1. Что поднимается

| Служба | Порты наружу | Зачем |
|---|---|---|
| `justhpc-virt-manager` | `${JHV_PORT}:8080` | сервис и веб-интерфейс |
| `postgres` | **нет** | база сервиса |


### 2.2. О базе

PostgreSQL поднимается всегда: другой СУБД сервис не знает, и профиль для
единственной базы означал бы, что установка по умолчанию не работает.

Наружу она не публикуется намеренно — сервис ходит к ней по внутренней сети
compose, а открытый порт СУБД это лишняя дверь.

Строка подключения принимается в двух формах:

```
postgres://jhvirt:пароль@postgres:5432/jhvirt?sslmode=disable
host=postgres port=5432 user=jhvirt password=пароль dbname=jhvirt sslmode=disable
```

Вторая удобнее и стоит по умолчанию: в URL пароль обязан быть
percent-кодирован, а `openssl rand -base64` выдаёт `/` и `+` — то есть привычный
генератор пароля даёт строку, непригодную для URL.

### 2.3. Установка

```bash
git clone <репозиторий> /opt/jhvirt/src && cd /opt/jhvirt/src/deploy
```

```bash
./install.sh
```

Скрипт спросит, чем запускать, и покажет только то, что есть на машине:

```
Чем запускать?

  1) docker compose   — сервис и PostgreSQL в контейнерах
  2) docker-compose   — то же, старой командой через дефис
  3) podman-compose   — то же на podman
  4) systemd          — бинарь службой, PostgreSQL отдельно
```

Затем спросит внешний адрес, сгенерирует пароль базы, создаст `.env` с правами
`0600`, соберёт образ, запустит и напечатает пароль администратора:

```
════════════════════════════════════════════════════════════
  ГОТОВО

  интерфейс:     https://virt.example.org
  пользователь:  admin
  пароль:        hwCH4qkcl6HZccYyn4qmLZ-E

  Пароль показан один раз — запишите его.
════════════════════════════════════════════════════════════
```

| Ключ | Зачем |
|---|---|
| `--mode docker\|docker-compose\|podman\|systemd` | без диалога, для автоматизации |
| `--url https://virt.example.org` | внешний адрес без вопроса |
| `--no-start` | подготовить `.env`, но не запускать |
| `--uninstall` | остановить и снять; данные и тома остаются |
| `PREFIX=/srv/jhvirt` | другой каталог при установке из комплекта |

Права root нужны только при установке из комплекта `.run` и для службы
systemd — там скрипт раскладывает файлы в `/opt`, заводит пользователя и
ставит юнит. Запуск контейнеров из каталога репозитория обходится без sudo.

Повторный запуск ничего не ломает: существующий `.env` не перезаписывается —
в нём пароль работающей базы, а PostgreSQL держит свой в томе и новый не
примет.

Внешний адрес спрашивается, а не подставляется молча: из него выводится флаг
`Secure` у куки сессии, и `localhost` по умолчанию означал бы куку без `Secure`
в установке за обратным прокси.

### 2.7. Тома и что из них резервировать

| Том или каталог | Что внутри | Терять нельзя |
|---|---|---|
| `jhvirt-data` (`/app/data`) | `secret.key`, временные файлы | **да** |
| `postgres-data` | база: подключения, задания, история | да |
| `${JHV_BACKUP_DIR}` (`/backups`) | сами копии при локальном хранилище | да |
| `${JHV_RESTORE_DIR}` (`/restores`) | восстановленные образы | нет |

**`secret.key` — самое ценное в установке.** Им зашифрованы пароли подключений
к движкам, ключи хранилищ и зашифрованные копии. Восстановить его неоткуда:
без него копии останутся, а прочитать их будет нечем. Скопируйте отдельно от
базы и **не** в то хранилище, где лежат копии:

```bash
docker compose cp justhpc-virt-manager:/app/data/secret.key ./secret.key.backup
```

Снимок базы PostgreSQL:

```bash
docker compose exec -T postgres pg_dump -U jhvirt jhvirt > /srv/backups/jhvirt-$(date +%F).sql
```

### 2.8. Настройки, о которых стоит знать

**Каталог восстановления ограничен списком.** В контейнере разрешён `/restores`
и временный каталог сервиса. Путь приходит от клиента, а образ — десятки
гигабайт, поэтому произвольный каталог не принимается: попытка восстановить в
`/app/data` или `/etc` вернёт 400. Нужен ещё один каталог — смонтируйте его и
добавьте в `JHV_RESTORE_DIRS` (список через запятую).

**Просмотр журнала из интерфейса требует файла.** По умолчанию журнал уходит в
поток контейнера, и его забирает `docker logs` — для контейнера это правильно.
Но раздел «Настройки → Журнал» читает файл, поэтому без него он пуст. Нужен
просмотр из интерфейса:

```bash
JHV_LOG_FILE=/app/logs/jhvirt.log
```

**Межсайтовые запросы к API запрещены всем.** Список `cors_origins` пуст в
самой конфигурации, и это важно: очистить его переменной окружения нельзя —
пустое значение viper считает незаданным и берёт список из файла. Раньше там
стояли адреса dev-сервера, из-за чего боевая установка разрешала запросы со
страницы на `localhost:9000` у оператора вместе с его кукой сессии.

Заполнять `JHV_CORS_ORIGINS` нужно, только если интерфейс раздаётся с другого
адреса. Для разработки не нужно: dev-сервер проксирует `/api` через себя, и
браузер считает запросы same-origin.

**Тяжёлые операции стоят в очереди.** Одновременно выполняются не более
`backup.heavy_workers` проверок и восстановлений (по умолчанию 2) — обе
операции читают цепочку целиком из хранилища копий. Предел отдельный от
`backup.workers`: бэкапы упираются в гипервизор, и общий предел позволил бы
одному виду работы вытеснять другой. Всё сверх предела ждёт в очереди со
статусом «ожидает», видимым в интерфейсе.

**Авто-восстановление стартует в режиме проверки** и остаётся в нём, пока вы не
переключите тумблер в интерфейсе. Переменная `JHV_REMEDIATION_DRY_RUN`
задаёт только начальное значение при первом запуске — см. п. 7.

### 2.9. Сетевые требования

Контейнеру нужен доступ до инфраструктуры, а не наоборот:

| Куда | Порт | Зачем |
|---|---|---|
| движок oVirt | 443 | REST API, инвентарь, управление |
| гипервизоры oVirt | 54322 | `ovirt-imageio`, чтение и запись дисков |
| движок oVirt | 54323 | прокси передачи при `transfer.prefer_proxy` |
| хосты libvirt/KVM | 22 | libvirt поверх SSH и передача данных NBD |

Если гипервизоры на изолированной сети хранения и контейнер их не видит,
включите `JHV_BACKUP_TRANSFER_PREFER_PROXY=true`: поток пойдёт через движок.
Медленнее, но работает.

Обновление — в [п. 9](#9-обновление), оно одинаково устроено для обоих способов
установки.

## 2.10. Docker, docker-compose, podman

Compose-файл рассчитан на три реализации сразу, и каждая проверена разбором
этого самого файла:

| Реализация | Команда | Проверено |
|---|---|---|
| Docker Compose v2 (плагин) | `docker compose up -d` | разбор и запуск |
| docker-compose v1 (Python) | `docker-compose up -d` | разбор |
| podman-compose | `podman-compose up -d` | разбор |

Ради этого в файле две вещи, которые иначе выглядели бы странно:

- **`version: "2.4"`.** Docker Compose v2 его игнорирует и предупреждает, что
  поле устарело, — так и должно быть. Но `docker-compose` v1 без него
  разбирает файл по схеме первой версии, где ключа `services` вообще нет, и
  отказывается работать. Именно `2.4`, а не `3.x`: в третьей схеме нет
  `depends_on` с `condition`, а он здесь нужен, чтобы сервис не стартовал
  раньше готовой базы.
- **Имя проекта в `COMPOSE_PROJECT_NAME`,** а не ключом `name:` сверху. Ключ
  `name` понимают только v2 и podman-compose; v1 на нём отказывается разбирать
  файл целиком: `'name' does not match any of the regexes: '^x-'`.

По той же причине параметры базы передаются раздельными переменными, а не
собранной в YAML строкой подключения: сборка требовала бы вложенной
подстановки `${A:-…${B:?…}…}`, а на неё за пределами Docker Compose
рассчитывать нельзя.

### На RHEL, Alma, Rocky

Там `docker` — это обычно podman в режиме эмуляции, **и провайдера compose нет
ни одного**:

```
Emulate Docker CLI using podman.
Error: looking up compose provider failed
        * exec: "docker-compose": executable file not found in $PATH
        * exec: "podman-compose": executable file not found in $PATH
```

Сам podman установлен и работает — не хватает того, что читает
`docker-compose.yml`. Ставится из репозитория дистрибутива:

```bash
dnf install -y podman-compose
```

Дальше — та же одна команда, podman-compose появится в списке:

```bash
cd deploy && ./install.sh
```

Или без диалога:

```bash
./install.sh --mode podman --url https://virt.example.org
```

Если привычнее `docker compose`, podman умеет быть его провайдером — поставьте
плагин и включите сокет:

```bash
mkdir -p /usr/local/lib/docker/cli-plugins && curl -sSL https://github.com/docker/compose/releases/latest/download/docker-compose-linux-x86_64 -o /usr/local/lib/docker/cli-plugins/docker-compose && chmod +x /usr/local/lib/docker/cli-plugins/docker-compose
```

```bash
systemctl enable --now podman.socket
```

**Что проверено, а что нет.** Файл разбирается всеми тремя реализациями — это
проверено на podman-compose 1.4.1 из Fedora и docker-compose 1.29.2. Полный
запуск со сборкой образа прогонялся только на Docker Compose v2. Если под
podman что-то себя поведёт иначе, вероятнее всего это `depends_on` с
`condition`: при его игнорировании сервис стартует раньше базы, падает и
поднимается со второй попытки — `restart: unless-stopped` это закрывает.

Контейнеры не обязательны вовсе: на RHEL короче поставить бинарём под systemd
и взять PostgreSQL из репозитория дистрибутива — см. п. 3.

## 3. Бинарь и systemd

Когда Docker не вариант — и на RHEL это обычная ситуация, см. п. 2.10.

### 3.1. Соберите комплект

```bash
./run build --target linux/amd64
```

Получится один файл `dist/jhvirt-<версия>-linux-amd64.run` — установщик со
вшитым архивом. Подробности и ключи — в [BUILD.md](BUILD.md).

### 3.2. Установите

```bash
scp dist/jhvirt-<версия>-linux-amd64.run server:/tmp/
```

```bash
ssh server 'sudo sh /tmp/jhvirt-<версия>-linux-amd64.run'
```

Файл сам сверит контрольную сумму и архитектуру, распакуется во временный
каталог и запустит установку. Другой каталог — `sudo PREFIX=/srv/jhvirt sh ...`;
переменные через `sudo` передаются только явным присваиванием.

Скрипт создаёт пользователя `jhvirt`, раскладывает файлы в `/opt/jhvirt`, ставит
юнит и делает `daemon-reload`. Службу не запускает и конфигурацию не заполняет —
это ваши решения.

Юнит, который он ставит (`deploy/systemd/jhvirt.service` в репозитории):

```ini
[Unit]
Description=justhpc-virt-manager
After=network-online.target postgresql.service
Wants=network-online.target

[Service]
Type=simple
User=jhvirt
Group=jhvirt
WorkingDirectory=/opt/jhvirt
ExecStart=/opt/jhvirt/bin/justhpc-virt-server -config /opt/jhvirt/config/virt-manager.yaml
Restart=on-failure
RestartSec=5s

# Пароль СУБД — из файла с правами 0600, а не в юните: юнит читают все.
EnvironmentFile=-/opt/jhvirt/config/jhvirt.env

# Ограничения: сервису нужны только свои каталоги.
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/opt/jhvirt/data /opt/jhvirt/logs /srv/backups /srv/restores
# Восстановление и проверка держат много открытых объектов хранилища.
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target
```

**`ReadWritePaths` — самая частая причина непонятного отказа записи.** Всё, что
вне перечисленного, для службы доступно только на чтение: `ProtectSystem=strict`
делает это на уровне ядра, и ошибка приходит не от сервиса, а от системы, из-за
чего связь с юнитом видна не сразу. Добавляйте сюда локальное хранилище копий и
каждый каталог, куда разрешено восстанавливать.

Каталог восстановления, кроме того, нужно разрешить и самому сервису — в
`config/virt-manager.yaml`:

```yaml
backup:
  restore_dirs: ["/srv/restores"]
```

Два списка нужны потому, что закрывают разное: `restore_dirs` не даёт оператору
записать образ куда попало, `ReadWritePaths` не даёт этого сделать самой
службе, если её взломают. Каталог, прописанный только в одном из них, работать
не будет.

`/opt/jhvirt/config/jhvirt.env` (права `0600`, владелец `jhvirt`):

```bash
JHV_DATABASE_DRIVER=postgres
JHV_DATABASE_POSTGRES_HOST=127.0.0.1
JHV_DATABASE_POSTGRES_PASSWORD=<пароль>
JHV_SERVER_EXTERNAL_URL=https://virt.example.org
```

```bash
systemctl daemon-reload && systemctl enable --now jhvirt
journalctl -u jhvirt -n 50 --no-pager | grep -A6 "УЧЁТНАЯ ЗАПИСЬ"
```

## 4. TLS

Два варианта, оба рабочие.

**Обратный прокси** (обычный случай). Сервис слушает HTTP на localhost, TLS
терминирует nginx. Обязательно укажите `JHV_SERVER_EXTERNAL_URL=https://…` —
по нему сервис понимает, что куку сессии надо помечать флагом `Secure`; без
этого браузер отправит её и по открытому каналу.

```nginx
server {
    listen 443 ssl;
    server_name virt.example.org;

    ssl_certificate     /etc/ssl/certs/virt.crt;
    ssl_certificate_key /etc/ssl/private/virt.key;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Поток событий (SSE) и восстановление образов идут часами.
        proxy_buffering off;
        proxy_read_timeout 24h;
        client_max_body_size 0;
    }
}
```

`proxy_buffering off` — не украшение: с буферизацией живые обновления в
интерфейсе перестанут приходить, а восстановление оборвётся по таймауту.

**Свой TLS** — если прокси не нужен:

```yaml
server:
  tls:
    enabled: true
    cert_file: "/opt/jhvirt/config/tls/server.crt"
    key_file: "/opt/jhvirt/config/tls/server.key"
```

## 5. Обязательный чек-лист перед боем

- [ ] **Ключ шифрования вынесен в резерв.** `data/secret.key` — им зашифрованы
      пароли подключений, ключи хранилищ и зашифрованные копии. **Потеря ключа
      равна потере всех этих данных**, и восстановить его неоткуда. Копируйте
      отдельно от базы и не в то же хранилище, что и бэкапы.
- [ ] Пароль администратора выдан по назначению и не лежит в истории команд.
- [ ] Отдельные учётные записи операторам; роль «наблюдатель» тем, кому нужно
      только смотреть. Журнал службы и аудит доступны только администратору.
- [ ] TLS настроен, `external_url` указывает на `https://`.
- [ ] `logging.file` задан, если нужен просмотр журнала из интерфейса.
      В Docker по умолчанию журнал уходит в поток контейнера.
- [ ] Хранилище копий проверено кнопкой **Проверить** — она делает полный круг:
      запись, чтение, сверку и удаление пробного объекта, то есть проверяет
      права на запись, а не только доступность.
- [ ] Резервируются `secret.key`, база и `config/virt-manager.yaml`
      (см. [OPERATIONS.md](OPERATIONS.md#что-резервировать-в-самом-сервисе)).
- [ ] Авто-восстановление оставлено в режиме проверки — см. п. 7.

## 6. Первая настройка

1. **Серверы → Подключить сервер.** Адрес движка без `/ovirt-engine/api`,
   пользователь `admin@internal`. Кнопка **Получить** скачает CA-сертификат —
   сверьте отпечаток. **Проверить подключение** покажет версию и число хостов;
   при ошибке скажет, что именно исправить.
2. **Хранилища → Добавить.** Проверка выполняется сразу.
3. **Защита** — раздел покажет все ВМ и что с ними: у кого нет копий, у кого нет
   задания. Это ваш список работ.
4. **ВМ → Варианты бэкапа** — экран объясняет каждый вариант и рекомендует.
   Оттуда же создаётся задание из готового расписания.
5. Настройте `verify_after: chain` в заданиях — почти бесплатно и ловит разрыв
   цепочки в тот же день.

## 7. Авто-восстановление: не включайте сразу

Сервис стартует в **режиме проверки**: решения принимаются и подробно
записываются, но не выполняются. Это правильное состояние для новой установки.

Поживите так неделю. Смотрите «Настройки → Система»: там видно, что автоматика
предлагала сделать и почему. Когда решениям поверите — переключите тумблер;
наблюдения периода сохранятся в архив как обоснование.

Отдельно: `allow_host_fence` выключено по умолчанию и останавливает все ВМ
хоста. Включайте, только если хосты действительно одноразовые.

---

## 8. Приёмочный прогон

Пока он не пройден на вашем железе, готовность неизвестна, а не подтверждена.
Возьмите выбрасываемую ВМ и пройдите круг целиком:

```
полный бэкап → инкрементальный → проверка «пробное восстановление»
    → восстановление в новый диск → загрузка восстановленной машины
```

Что смотреть на каждом шаге:

| Шаг | Что должно получиться |
|---|---|
| Полный | ВМ не останавливалась; в записи есть checkpoint |
| Инкрементальный | объём заметно меньше полного; родитель проставлен |
| Проверка `restore` | образ собирается, контрольная сумма сходится |
| Восстановление | новый диск создан и залит |
| Загрузка | гость поднялся |

Если в карточке запуска есть метка «не всё» — разберитесь до того, как
полагаться: значит, часть дисков в копию не попала.

## 9. Обновление

Сначала — снимок базы. Миграции применяются при старте новой версии и обратной
дороги не имеют:

```bash
cd /opt/jhvirt/src/deploy && docker compose exec -T postgres pg_dump -U jhvirt jhvirt > /srv/backups/jhvirt-$(date +%F).sql
```

**Docker:**

```bash
cd /opt/jhvirt/src && git pull && cd deploy && docker compose up -d --build
```

Тома не пересоздаются, поэтому `secret.key`, база и копии остаются на месте.

**Бинарь и systemd:** тот же `.run` новой версии. Он определит установленную,
остановит службу на время замены и запустит обратно, если она работала:

```bash
sudo sh /tmp/jhvirt-<новая версия>-linux-amd64.run
```

Конфигурация не перезаписывается — новая версия кладётся рядом как
`virt-manager.yaml.new`.

Формат хранения копий самодостаточен и не зависит от версии сервиса: каталог
запуска разбирается утилитой `jvbackup` без базы и без сервера.

---

## 10. Если сервис потерян

Данные копий переживают потерю сервиса. Восстановление без него:

```bash
jvbackup list   -repo /srv/backups
jvbackup verify -repo /srv/backups -run <id>
jvbackup restore -repo /srv/backups -run <id> -out /mnt/restore
```

`-repo` принимает и `s3://ключ:секрет@endpoint/bucket`. Ради этого случая
второй бинарь и существует.

## Готовность

Проверено: слой хранения на PostgreSQL (тесты идут против настоящей базы,
не против упрощённой замены), работа с S3-совместимым хранилищем,
формат копий и сборка цепочек, ретенция,
протокол NBD, разбор ответов движка, API, роли, отдача интерфейса боевой
сборкой, установка и обновление в контейнере с systemd и через `.run`.

**Не проверено:** всё, что требует живого гипервизора — вход в движок,
`ovirt-imageio`, Backup API и checkpoint, бэкап через снапшот, pull-режим
libvirt, заморозка ФС гостя, пробный запуск ВМ, метрики NFS/iSCSI. Сюда же
относится отмена выполняющегося бэкапа: код исправлен, но прогнать её без
настоящего бэкапа нельзя.

Закрыто: ограничение попыток входа и одинаковое время ответа для существующей
и несуществующей учётной записи; список разрешённых каталогов восстановления;
защита от запуска задания поверх себя; разовые бэкапы идут через общий предел
`backup.workers` и поддаются отмене; проверки и восстановления — через
`backup.heavy_workers`; межсайтовые запросы к API запрещены по умолчанию.

Детектор гонок пройден: 13 пакетов, ноль гонок (./run race — в контейнере,
потому что ему нужен компилятор C).

Практический вывод: как система мониторинга — можно ставить сейчас. Как
единственная система бэкапа — после приёмочного прогона, и не раньше.

Причина не в том, что найдены дефекты, а в том, что **ни одна строка кода,
обращающегося к гипервизору, ни разу не исполнялась против настоящего oVirt
или KVM.** Всё остальное — хранение, формат, цепочки, API, установка,
обновление — проверено и прогонами, и тестами. Проверка этой части требует
вашего железа и ничем не заменяется.
