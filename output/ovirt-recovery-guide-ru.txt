ПОДРОБНАЯ ПОШАГОВАЯ ИНСТРУКЦИЯ
ВОССТАНОВЛЕНИЕ ВМ, VGPU, OVN, LVM THIN И XFS
============================================================

Контур — oVirt 4.3 / CentOS 7 / oVirt Node 4.3.9.
Основание — фактические работы 5–9 ноября 2026 года.
Формат — TXT, UTF-8, окончания строк Windows.

КАК ПОЛЬЗОВАТЬСЯ ИНСТРУКЦИЕЙ

Эта версия разбивает работу на 81 пронумерованный шаг.
У каждого шага указаны место выполнения, предварительные условия,
назначение команд, ожидаемый результат и действия при ошибке.

1. Выберите сценарий ниже по фактическому сообщению об ошибке.
2. Пройдите подготовку подключения и диагностику.
3. Перед каждым блоком проверьте поле «Где выполнять».
4. Затем проверьте поле «Перед выполнением».
5. Копируйте только строки между маркерами «НАЧАЛО КОМАНД» и
   «КОНЕЦ КОМАНД». Сами маркеры в терминал не вставляйте.
6. Сравните вывод с полем «Ожидаемый результат».
7. При отличии используйте поле «Если результат отличается».
8. Пройдите завершающие проверки выбранного сценария.

В контуре уже выполнены восстановительные работы. Значения UUID и путей
относятся к этому инциденту. Повторное изменение работающей инфраструктуры
начинается с новой диагностики и проверки условий выбранного сценария.

Условные шаги и откат выполняются только при описанном условии.
Все 81 шаг подряд к одному исправному серверу не применяются.

ТЕРМИНЫ

Engine — сервер управления конфигурацией и запуском ВМ.
Гипервизор — хост, на котором работают QEMU и VDSM.
Storage Domain — объект хранилища в engine.
NFS-экспорт — путь, предоставленный сервером хранения клиентам.
Точка монтирования — каталог подключённой файловой системы.
LV — логический том LVM.
Thin-pool — общий пул физических блоков для thin-томов.
Data% — доля занятых блоков данных thin-pool.
Meta% — заполнение метаданных отображения блоков thin-pool.
EIO — ошибка ввода-вывода.
ENOSPC — нехватка доступного пространства.
fsync — запрос синхронизации записанных данных.
inode — объект с метаданными файла в файловой системе.
mdev — подсистема mediated devices, применяемая в том числе для vGPU.

РАЗЛИЧИЕ UUID

VM ID выбирает виртуальную машину в API.
Disk ID выбирает диск и обычно совпадает с каталогом внутри images.
Volume ID выбирает конкретный файл тома или элемент цепочки диска.
Storage Domain ID выбирает домен хранения.

Пример пути:
  /точка-монтирования/SD_ID/images/DISK_ID/VOLUME_ID

У одного Disk ID могут быть несколько Volume ID при наличии снимков.
Для нашего восстановления использовался самостоятельный RAW-том.
Формат, размеры и принадлежность проверяются до копирования.

ЕСЛИ ПРОВЕРКА ОСТАНОВИЛАСЬ

AssertionError означает, что условие перед изменением не выполнено.
Прочитайте assert и проверьте объект и текущее состояние.
Удаление assert ради продолжения не исправляет это состояние.

Команда test обычно ничего не печатает при успехе. При несовпадении
возвращается ненулевой код, а оболочка с set -e может завершить сценарий.

Ответ API на асинхронный запрос означает принятие операции. Завершение
проверяется повторным чтением состояния, аудитом и фактическим состоянием
объекта на гипервизоре.

Статус Up дополняется проверкой диска, гостевого агента, консоли и сети.

На рабочем компьютере:


============================================================================
ШАГ 1. Открыть SSH-сеансы к engine и обоим гипервизорам
============================================================================

  Рабочий компьютер, PowerShell

Перед выполнением

Что делают команды

При первом подключении сверьте отпечаток SSH-ключа с доверенным источником. Для сохранённых ключей удобно выделить отдельный файл known_hosts.

Если доступ пропал, сначала проверьте Windows:


============================================================================
ШАГ 2. Установить причину недоступности сети
============================================================================

Где выполнять
  Рабочий компьютер, PowerShell

Перед выполнением

============================================================================

============================================================================

Где выполнять
  Рабочий компьютер, PowerShell

Перед выполнением

Ожидаемый результат

Если результат отличается
  Ошибка L2TP 789 означает сбой согласования защиты. Зафиксируйте сообщение и восстановите VPN-доступ. При возвращении связи сначала проверьте существующую фоновую задачу.


Windows вернула L2TP 789. До восстановления VPN команды SSH к engine и хостам завершались тайм-аутом. Длительная задача копирования была запущена через nohup на гипервизоре и продолжила работу.

После восстановления доступа сначала проверяйте журнал существующей задачи и её результат. Повторный запуск копирования может потребовать ещё 500 ГиБ и затереть контекст диагностики.

На каждом Linux-сервере создайте свой защищённый каталог текущего инцидента:


============================================================================
ШАГ 4. Создать каталог текущего инцидента
============================================================================

Где выполнять
  Bash на каждом Linux-сервере, который участвует в работах

Перед выполнением
  Откройте нужный сервер по SSH и проверьте его имя.

Что делают команды
  umask ограничивает доступ к новым файлам. RECOVERY_DIR хранит путь к журналам и копиям. install создаёт каталог, date и hostname фиксируют место и время, df проверяет место под материалы.

НАЧАЛО КОМАНД (bash)
umask 077
export RECOVERY_DIR="/var/tmp/recovery-$(date +%Y%m%d-%H%M%S)"
install -d -m 700 "$RECOVERY_DIR"
printf '%s\n' "$RECOVERY_DIR"
date
hostname
df -h /var/tmp
КОНЕЦ КОМАНД

Ожидаемый результат
  Получен путь вида /var/tmp/recovery-20261109-120000, каталог доступен root, в /var/tmp достаточно места.

Если результат отличается
  Если места мало, выберите другую исправную ФС до создания metadump или крупных журналов. Запишите путь, чтобы после переподключения использовать тот же каталог.


Блоки Bash ниже выполняются в SSH-сеансе соответствующего сервера. Переменные живут в конкретном сеансе. При переподключении восстановите значения путей из журнала работ.

Удобно держать отдельные окна для Bash на engine, интерактивного Python на engine и Bash на каждом гипервизоре. В двух окнах engine задайте одинаковый RECOVERY_DIR, скопировав уже созданный путь. Для выхода из Python используйте exit(). При новом Python-сеансе заново задайте выбранные vm_id, ids и объект domain перед соответствующим разделом.

При передаче Bash-сценария из Windows использовали удаление CR, чтобы окончания строк CRLF не ломали команды. Пример для подготовленного файла step.sh на рабочем компьютере:


============================================================================
ШАГ 5. Передать подготовленный сценарий из Windows
============================================================================

Где выполнять
  Рабочий компьютер, PowerShell. Дополнительный способ выполнения

Перед выполнением
  Только когда файл step.sh уже подготовлен и просмотрен. Его команды должны предназначаться именно для указанного сервера.

Что делают команды
  Get-Content читает файл целиком, SSH передаёт его серверу, tr удаляет CR из окончаний строк Windows, bash читает команды из стандартного ввода.

НАЧАЛО КОМАНД (powershell)
Get-Content -Raw .\step.sh | ssh root@10.249.254.127 "tr -d '\r' | bash -s"
КОНЕЦ КОМАНД

Ожидаемый результат
  Сценарий выполняется без ошибок, связанных с символом CR или строками вида $'\\r'.

Если результат отличается
  Если сценарий ожидает интерактивный пароль, используйте обычный SSH-терминал и запустите файл внутри него. Сначала проверьте адрес назначения.


Для интерактивного ввода пароля SDK откройте обычный SSH-терминал и запустите Python-файл внутри него.

Для длительных задач сохраняйте журнал и код завершения. Пример оболочки для уже подготовленного сценария:


============================================================================
ШАГ 6. Запустить длительный подготовленный шаг в фоне
============================================================================

Где выполнять
  Bash на сервере, где должна выполняться задача. Дополнительный шаблон

Перед выполнением
  Файл /root/prepared-recovery-step.sh уже создан, проверен и исполняемый. RECOVERY_DIR экспортирован.

НАЧАЛО КОМАНД (bash)
cat >"$RECOVERY_DIR/api-session.py" <<'PY'
from __future__ import print_function
import atexit
import getpass
import json
import os
import ovirtsdk4
import ovirtsdk4.types as types

base = os.environ['RECOVERY_DIR']
username = raw_input('API login: ').strip()
conn = ovirtsdk4.Connection(
    url='https://ovirt.advengineering.ru/ovirt-engine/api',
    username=username,
    password=getpass.getpass('API password: '),
    ca_file='/etc/pki/ovirt-engine/ca.pem',
    insecure=False,
    debug=False,
    timeout=60,
)
atexit.register(conn.close)
system = conn.system_service()
vms = system.vms_service()

def save_json(filename, value):
    path = os.path.join(base, filename)
    fd = os.open(path, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
    with os.fdopen(fd, 'w') as output:
        json.dump(value, output, indent=2)
    print('Saved', path)

def vm_state(vm_id):
    service = vms.vm_service(vm_id)
    vm = service.get()
    disks = service.disk_attachments_service().list()
    nics = service.nics_service().list()
    return {
        'id': vm.id,
        'name': vm.name,
        'status': str(vm.status),
        'host_id': vm.host.id if vm.host else None,
        'custom_properties': [
            {'name': p.name, 'value': p.value}
            for p in vm.custom_properties or []
        ],
        'disks': [
            {'id': a.id, 'disk_id': a.disk.id,
             'active': a.active, 'bootable': a.bootable}
            for a in disks
        ],
        'nics': [
            {'id': n.id, 'name': n.name,
             'linked': n.linked, 'plugged': n.plugged}
            for n in nics
        ],
    }

print('API session ready')
PY

python -i "$RECOVERY_DIR/api-session.py"

Ожидаемый результат

5. Удаление старой привязки vGPU
================================

Этот сценарий применялся к ВМ, перенесённым на хосты без NVIDIA GPU. После удаления профиля ВМ работает с виртуальным видеоадаптером, GPU-ускорение для приложений теряется. Если на целевом хосте есть требуемая GPU, сначала исследуйте драйвер и подсистему mdev.

В oVirt/RHV 4.3 профиль задавался свойством mdev_type. Для версий с отдельными объектами mediated devices процедура отличается. RHV 4.3, настройка vGPU (https://docs.redhat.com/en/documentation/red_hat_virtualization/4.3/html/setting_up_an_nvidia_gpu_for_a_virtual_machine_in_red_hat_virtualization/assigning_virtual_gpus)

  Подтверждено отсутствие нужной GPU на целевых хостах, ВМ Down, настройки сохранены на шаге 17.

============================================================================
ШАГ 25. Перевыпустить сертификаты существующим CA и обновить PKCS12
============================================================================

Где выполнять
  Bash на engine. Изменяющий шаг OVN

Перед выполнением
  Ключи сверены, копия PKI создана, выбран допустимый срок, Subject/SAN соответствуют вашему контуру.

Что делают команды
  Скрипт скрыто читает пароль PKCS12, проверяет срок CA, подписывает CSR и обновляет контейнеры с существующими ключами. При ошибке подписи восстанавливается прежний сертификат.

НАЧАЛО КОМАНД (bash)
set -euo pipefail
read -rsp 'Existing PKCS12 password: ' PKCS12_PASS
printf '\n'
export PKCS12_PASS

days=1095
openssl x509 -in /etc/pki/ovirt-engine/ca.pem \
    -checkend "$((days * 86400))" -noout

for name in ovirt-provider-ovn ovn-ndb ovn-sdb; do
    openssl pkcs12 -in "/etc/pki/ovirt-engine/keys/$name.p12" \
        -passin env:PKCS12_PASS -noout

    cp -p "/etc/pki/ovirt-engine/certs/$name.cer" \
        "$RECOVERY_DIR/$name.cer.before"

    if ! /usr/share/ovirt-engine/bin/pki-enroll-request.sh \
        --name="$name" \
        --subject="/C=US/O=advengineering.ru/CN=ovirt.advengineering.ru" \
        --days="$days" \
        --san=DNS:ovirt.advengineering.ru \
        >"$RECOVERY_DIR/enroll-$name.log" 2>&1; then
        cp -p "$RECOVERY_DIR/$name.cer.before" \
            "/etc/pki/ovirt-engine/certs/$name.cer"
        restorecon "/etc/pki/ovirt-engine/certs/$name.cer"
        echo "Signing failed; previous certificate restored"
        exit 1
    fi

    openssl verify -CAfile /etc/pki/ovirt-engine/ca.pem \
        "/etc/pki/ovirt-engine/certs/$name.cer"

    openssl pkcs12 -export \
        -in "/etc/pki/ovirt-engine/certs/$name.cer" \
        -inkey "/etc/pki/ovirt-engine/keys/$name.key.nopass" \
        -out "/etc/pki/ovirt-engine/keys/$name.p12" \
        -passout env:PKCS12_PASS

    chmod 600 "/etc/pki/ovirt-engine/keys/$name.p12"
    restorecon "/etc/pki/ovirt-engine/certs/$name.cer" \
        "/etc/pki/ovirt-engine/keys/$name.p12"
    openssl x509 -in "/etc/pki/ovirt-engine/certs/$name.cer" -noout -dates
done

unset PKCS12_PASS
КОНЕЦ КОМАНД

Ожидаемый результат
  Для каждого файла openssl verify сообщает OK, показаны новые даты. В инциденте срок выбрали 1095 дней.

Если результат отличается
  При любой ошибке просмотрите enroll-имя.log и восстановите согласованный комплект до перезапуска. Пароль PKCS12 отличается от доменного пароля API.


Срок 1095 дней выбрали с учётом оставшегося срока CA. Перед следующим перевыпуском пересчитайте его. В инциденте новые сертификаты были действительны до 4 ноября 2029 года.

Если ошибка возникла после изменения части файлов, завершите восстановление согласованного комплекта из защищённой копии либо исправьте конкретный шаг до перезапуска сервисов.

============================================================================
ШАГ 67. Создать и запустить копирование с полной сверкой
============================================================================

Где выполнять
  Bash на adv-hv-04. Длительный изменяющий шаг восстановления диска

Перед выполнением
  Запас ёмкости оценён, исходный снимок открыт для чтения, параметры шага 66 проверены.

Что делают команды
  Сценарий читает весь источник, пишет отдельный файл, делает fsync, контролирует пул и заново читает копию для SHA-256. nohup сохраняет работу при обрыве SSH.

НАЧАЛО КОМАНД (bash)
cat >"$RECOVERY_DIR/copy-verified.py" <<'PY'
from __future__ import print_function
import ctypes
import hashlib
import os
import subprocess
import time

source = os.environ['SOURCE']
destination = os.environ['DEST']
pool = os.environ['THIN_POOL']
size = int(os.environ['EXPECTED_BYTES'])
work = os.environ['RECOVERY_DIR']
chunk_size = 8 * 1024**2
zeros = b'\0' * chunk_size

def log(message):
    print(time.strftime('%H:%M:%S'), message)
    import sys
    sys.stdout.flush()

def check_pool():
    output = subprocess.check_output([
        'lvs', '--noheadings', '-o', 'data_percent,metadata_percent', pool,
    ], close_fds=True)
    data, metadata = map(float, output.split())
    if data >= 91 or metadata >= 90:
        raise RuntimeError('Pool limit reached: %.2f / %.2f' % (data, metadata))
    return data, metadata

def main():
    assert os.path.isfile(source)
    assert os.stat(source).st_size == size
    assert not os.path.exists(destination)
    assert not os.path.exists(os.path.join(work, 'verified.sha256'))
    check_pool()
    os.mkdir(os.path.dirname(destination), 0o700)

    expected = hashlib.sha256()
    position = 0
    started = last = time.time()
    with open(source, 'rb', 0) as src:
        fd = os.open(destination, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
        with os.fdopen(fd, 'wb', 0) as dst:
            while position < size:
                block = src.read(min(chunk_size, size - position))
                if not block:
                    raise IOError('Unexpected EOF at %d' % position)
                expected.update(block)
                if block == zeros[:len(block)]:
                    dst.seek(len(block), os.SEEK_CUR)
                else:
                    dst.write(block)
                position += len(block)
                if time.time() - last >= 30:
                    os.fsync(dst.fileno())
                    data, metadata = check_pool()
                    log('copy %.2f GiB, %.1f MiB/s, pool %.2f / %.2f' % (
                        position / float(1024**3),
                        position / (time.time() - started) / 1024**2,
                        data, metadata))
                    last = time.time()
            dst.truncate(size)
            os.fsync(dst.fileno())
            libc = ctypes.CDLL('libc.so.6')
            advise = libc.posix_fadvise64
            advise.argtypes = [
                ctypes.c_int, ctypes.c_longlong, ctypes.c_longlong, ctypes.c_int,
            ]
            result = advise(dst.fileno(), 0, 0, 4)
            if result:
                log('Cache eviction advisory returned %d' % result)

    log('Source SHA256 ' + expected.hexdigest())
    actual = hashlib.sha256()
    position = 0
    last = time.time()
    with open(destination, 'rb', 0) as dst:
        while True:
            block = dst.read(chunk_size)
            if not block:
                break
            actual.update(block)
            position += len(block)
            if time.time() - last >= 30:
                check_pool()
                log('verify %.2f GiB' % (position / float(1024**3)))
                last = time.time()

    assert position == size
    assert expected.hexdigest() == actual.hexdigest(), 'SHA256 mismatch'
    marker = os.path.join(work, 'verified.sha256')
    fd = os.open(marker, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
    with os.fdopen(fd, 'w') as output:
        output.write(expected.hexdigest() + '  ' + destination + '\n')
        output.flush()
        os.fsync(output.fileno())
    log('Copy verified: %d bytes, SHA256 %s' % (size, expected.hexdigest()))

if __name__ == '__main__':
    main()
PY
