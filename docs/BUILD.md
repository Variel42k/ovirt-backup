# Сборка

Проект собирается одной командой на любой системе, где есть Go и Node. Результат
— **один файл `.run`**: скрипт со вшитым архивом. Копируется на сервер и
запускается; распаковка и установка происходят внутри.

```bash
./run build --target linux/amd64
```

```
готово: dist/jhvirt-1.0.0-linux-amd64.run (14M)
```

Внутри — два статических бинаря, веб-интерфейс, конфигурация, юнит systemd и
установщик.

---

## Что нужно

| | Версия | Зачем |
|---|---|---|
| Go | 1.26+ | бинари |
| Node | 20+ | веб-интерфейс |
| tar, gzip | любые | упаковка комплекта |

Больше ничего. **Компилятор C не нужен:** cgo не используется нигде. Отсюда два
следствия: бинарь получается статическим и работает в любом дистрибутиве
независимо от версии libc, и кросс-компиляция возможна с любой платформы — собрать Linux-бинарь из-под Windows это обычный путь, а не
обходной.

`make` не требуется. Makefile в репозитории есть, но скрипты сборки на него не
опираются: make отсутствует в стандартной установке Windows и в минимальных
образах CI.

---

## Как собрать

### Под текущую платформу

```bash
./run build
```

### Под сервер

```bash
./run build --target linux/amd64    # обычный сервер
./run build --target linux/arm64    # ARM
```

### Полезные ключи

| Ключ | Что делает |
|---|---|
| `--version 1.2.0` | явная версия вместо взятой из git |
| `--skip-web` | только бинари; `web/dist` должен быть собран заранее |
| `--tar` | оставить рядом и обычный `tar.gz` |
| `--no-archive` | разложить в `dist/`, не паковать |

`./run` без аргументов покажет все команды.

Версия по умолчанию берётся из `git describe`. Суффикс `-dirty` означает, что в
рабочем каталоге есть несохранённые правки — он намеренно оставлен видимым,
чтобы «та самая сборка» не спуталась с похожей.

### Windows

`./run` работает в Git Bash (идёт вместе с Git for Windows):

```bash
./run build --target linux/amd64
```

Из PowerShell или cmd — через тот же bash:

```powershell
& "C:\Program Files\Git\bin\bash.exe" run build --target linux/amd64
```

Права на файлы в архиве не зависят от системы сборки: NTFS не хранит бит
исполнения, поэтому бинари упаковываются отдельным проходом с явным режимом
0755. Без этого распакованный на сервере бинарь не запустился бы.

## Что получается

Один файл `dist/jhvirt-1.0.0-linux-amd64.run` — обычный `/bin/sh`-скрипт, к
которому приклеен `tar.gz`. Скрипт находит начало архива по строке-метке,
сверяет вшитую контрольную сумму, распаковывает во временный каталог и
запускает оттуда установщик. Временный каталог удаляется всегда, включая
прерывание по Ctrl+C.

Внутри архива:

```
jhvirt-1.0.0-linux-amd64/
├── bin/
│   ├── justhpc-virt-server     сервис с веб-интерфейсом
│   └── jvbackup                автономный CLI: бэкап, проверка, восстановление
├── web/dist/                   собранный интерфейс
├── config/virt-manager.yaml    конфигурация по умолчанию
├── systemd/jhvirt.service      юнит
├── docs/                       DEPLOY, OPERATIONS, README
├── install.sh                  установка и обновление
└── VERSION
```

Почему один файл, а не архив рядом со скриптом: переносится всегда целиком, а
разошедшиеся версии архива и установщика попросту невозможны.

## Установка

```bash
scp dist/jhvirt-1.0.0-linux-amd64.run server:/tmp/
ssh server 'sudo sh /tmp/jhvirt-1.0.0-linux-amd64.run'
```

Через `sh` — потому что бит исполнения не переживает файловую систему Windows.
Если собирали на Linux, `sudo ./jhvirt-1.0.0-linux-amd64.run` тоже работает.

| Команда | Что делает |
|---|---|
| `sudo sh ./jhvirt-*.run` | установка или обновление в `/opt/jhvirt` |
| `sudo PREFIX=/srv/jhvirt sh ./jhvirt-*.run` | другой каталог |
| `sudo sh ./jhvirt-*.run --uninstall` | удалить службу, сохранив данные |
| `sh ./jhvirt-*.run --extract [каталог]` | только распаковать, ничего не ставить |
| `sh ./jhvirt-*.run --check` | проверить целостность файла |
| `sh ./jhvirt-*.run --version` | версия и платформа без распаковки |

`--extract` нужен, когда установку выполняет не этот скрипт: свой Ansible,
образ, каталог без systemd.

Установщик создаёт системного пользователя `jhvirt`, раскладывает файлы,
ставит юнит и делает `daemon-reload`. Дальше — вручную, и это намеренно:
службу он не запускает, конфигурацию не заполняет, TLS не выпускает.
Установщик, который принимает такие решения молча, хуже, чем несколько лишних
команд.

Каталог `data` получает права `0700`: в нём лежит ключ шифрования секретов.

Дальнейшие шаги — в [DEPLOY.md](DEPLOY.md): конфигурация, TLS, чек-лист.

### Что проверяется до распаковки

- **Контрольная сумма.** Обрезанный при копировании файл ловится здесь, а не
  разворачивается наполовину.
- **Архитектура.** `uname -m` сверяется с той, под которую собрано. Иначе
  несовпадение всплыло бы как `Exec format error` уже после установки, и связь
  с тем, что скопировали не ту сборку, была бы неочевидна.
- **Права root** — до всякой работы, а не в середине.

### Обновление

Тот же файл новой версии. Он определит установленную, остановит службу на время
замены и запустит обратно, если она работала:

```
==> обновление: 1.0.0 -> 1.1.0
    останавливаю службу на время замены
    конфигурация сохранена; новая версия рядом: virt-manager.yaml.new
==> служба обновлена и запущена
```

Конфигурация не перезаписывается. Данные и журналы не трогаются.

Служба останавливается намеренно, а не подменяется на ходу: заменить файл под
работающим процессом Linux позволяет, но применилось бы это только после
перезапуска — и «обновил, а версия старая» стало бы загадкой.

## Разработка

```bash
./run dev     # сервер на :8080
./run web     # интерфейс на :9000, /api проксируется на сервер
```

В режиме разработки интерфейс живёт на своём порту и проксирует `/api` на
сервер, поэтому пересобирать SPA после каждой правки не нужно.

Перед коммитом — одна команда: формат, `go vet`, тесты и проверка типов
интерфейса.

```bash
./run check
```

Гипервизор для тестов не нужен, а вот база нужна — см. ниже.

### Тестам нужна PostgreSQL

Тесты хранилища идут против настоящей базы, а не против упрощённой замены.
`./run test` поднимает её в docker сам, на порту 55432 — чтобы не трогать
локальную PostgreSQL разработчика:

```bash
./run test-db start|stop|status
```

Своя база задаётся через `JHV_TEST_POSTGRES_DSN`.

### Детектор гонок

```bash
./run race
```

Гоняет тесты с детектором в контейнере `golang`. Через контейнер потому, что
детектору нужны `CGO_ENABLED=1` и компилятор C — единственное место во всём
проекте, где cgo вообще требуется, и на машине под Windows его обычно нет.
Образ приносит toolchain с собой, поэтому прогон доступен всем, а не только
тем, кто настроил окружение.

Если компилятор есть локально, работает и `./run test -race`.

Кэши модулей и сборки хранятся в именованных томах docker, поэтому повторный
прогон занимает вдвое меньше первого. Убираются вместе со всем остальным:

```bash
./run clean-all
```

Без базы тест **падает, а не пропускается**. Это не строгость ради строгости:
пропуск выглядит в выводе `go test` как `ok`, и набор, половина которого молча
ничего не проверила, — ровно тот способ, которым дефект PostgreSQL дожил до
боевой установки. Схема тогда проверялась на SQLite, а он типизирован
динамически и прощает то, чего PostgreSQL не прощает.

Каждый тестовый бинарь получает свою базу: `go test ./...` запускает пакеты
параллельно, и в общей базе их миграции создавали бы одни и те же таблицы
наперегонки.

## Docker

```bash
./run docker
```

Образ многоступенчатый: Node собирает интерфейс, Go — бинарь, финальный слой на
Alpine содержит только результат. Внутри `qemu-img` — он нужен для экспорта в
qcow2 и режима проверки `qemu`; без него работает всё остальное.

Готовый стек с базой — в [DEPLOY.md](DEPLOY.md#2-docker--рекомендуемый-путь).

## Если что-то не собирается

| Сообщение | Причина |
|---|---|
| `не найден go` | Go не установлен или не в `PATH` |
| `неизвестная команда` | опечатка; `./run` покажет список |
| `не найден npm` | нет Node; либо соберите с `--skip-web`, если `web/dist` уже готов |
| `нет web/dist/index.html` | указан `--skip-web`, но интерфейс не собран |
| `-race requires cgo` | нет компилятора C; тесты без `-race` пройдут |
| `контрольная сумма не сошлась` | `.run` побился при копировании — перенесите заново, лучше `scp`, а не через общую папку |
| `метка архива не найдена` | файл открывали редактором и он переписал переносы строк; двоичную часть так не сохранить |
| `комплект собран под linux/arm64, а система x86_64` | скопирована сборка не под ту архитектуру |
| `cannot execute: required file not found` при запуске `.run` на сервере | запустите через `sudo sh файл.run` |
