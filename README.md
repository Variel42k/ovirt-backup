# ovirt-backup

Резервное копирование и восстановление виртуальных машин **oVirt** и его форков
(**РЕД Виртуализация**, OLVM, RHV), а также хостов **libvirt/KVM**: горячие
бэкапы без остановки машин, расписания, обязательные реплики, контроль качества
и проверка того, что копии действительно восстанавливаются. Управление
инфраструктурой используется как вспомогательная функция защиты, а не как
назначение продукта.

Статические бинари на Go 1.27 со встроенным веб-интерфейсом. Внешних
зависимостей во время работы нет: ни агентов на гипервизорах, ни изменений на
стороне движка, ни cgo.

В комплекте два инструмента:

| Бинарь | Для чего |
|---|---|
| `ovirt-backup-server` | сервис: веб-интерфейс, мониторинг, расписания, ретенция |
| `jvbackup` | самодостаточный CLI: горячий бэкап KVM, проверка и восстановление **без базы данных и без сервиса** |

Второй существует ровно для того случая, ради которого строится первый: когда
управляющий хост потерян, а данные нужны обратно. Всё необходимое лежит в самом
хранилище копий.

## Что умеет

### Логические точки и реплики

- Для новых заданий первая цель хранения является **основной**, остальные —
  обязательными **репликами** одной точки восстановления.
- В режимах `copy` и `parallel` диски читаются с oVirt/KVM один раз. `copy`
  создаёт реплики из primary, `parallel` раздаёт один поток сразу во все цели;
  только явно выбранный `separate` открывает независимый съём на хранилище.
- Каждый объект после передачи полностью перечитывается в назначении и
  сверяется по SHA-256. `run.json` публикуется последним, поэтому незавершённая
  передача не выглядит готовым бэкапом.
- Очередь и границы успешно скопированных объектов хранятся в PostgreSQL.
  После перезапуска передача продолжается с первого незавершённого объекта.
- Ошибка обязательной реплики не портит основную копию, но оставляет запуск и
  состояние защиты частично выполненными до успешного автоматического повтора.
- Проверка и восстановление принимают явную физическую копию. Если основное
  хранилище недоступно, можно выбрать здоровую реплику со всей цепочкой.

Существующие задания после обновления остаются в совместимом режиме. Действие
«Включить репликацию» создаёт следующую полную точку; OVA в эту модель не входит.

**Мониторинг и оживление**
- Опрос всех подключённых движков по расписанию: хосты, ВМ, диски, домены хранения.
- Дедуплицированные оповещения: недоступность движка, зависший хост, ВМ на паузе
  из-за проблемы с хранилищем, домен без места, провалившийся бэкап, устаревшая копия.
- Автоматические восстановительные действия с ограничителями: запуск ВМ, снятие
  с паузы после `EIO`/`ENOSPC`, активация хоста, перезагрузка хоста по питанию.
  Каждое решение записывается — включая те, что система сознательно не выполнила.
- Режим проверки (dry-run) включён по умолчанию: сначала смотрите журнал, потом
  разрешаете действовать.

**Управление**
- Веб-форма подключения серверов с проверкой связи и загрузкой CA-сертификата движка.
- Питание ВМ (запуск, штатное выключение, отключение питания, пауза, перезагрузка,
  сброс, миграция), обслуживание и фенсинг хостов.
- Требуемое состояние ВМ (`должна работать` / `не вмешиваться`) — то, с чем
  мониторинг сравнивает реальность.
- Включение отслеживания изменённых блоков на дисках прямо из интерфейса.

**Бэкапы**
- Шесть типов: полный через Backup API, инкрементальный, разностный, полный через
  снапшот, экспорт OVA, только конфигурация ВМ.
- Горячий бэкап: ВМ продолжает работать. Опциональная заморозка файловых систем
  гостя через qemu-guest-agent даёт filesystem-consistent копию. Координация
  транзакций приложений отдельными hooks пока остаётся в roadmap.
- Автоматический выбор стратегии: нет отслеживания изменений — переключение на снапшот, нет опорной
  точки — полный бэкап, checkpoint потерян движком — полный бэкап.
- Расписания (cron), лимит длительности и единый отбор ВМ по ID, регулярному
  выражению, кластерам и тегам. Исключения ВМ и дисков применяются раньше
  положительных условий; пустой селектор означает все ВМ сервера.
- Три режима доставки в несколько хранилищ: `copy` (основная копия и очередь
  репликации), `parallel` (одновременная запись) и `separate` (независимый съём
  для каждого хранилища). Персистентная очередь учитывает приоритет задания и
  его собственный предел параллелизма и продолжает работу после перезапуска.
- OVA экспортируется в явно выбранный каталог гипервизора и учитывается как
  внешний артефакт. Для обычных копий можно дополнительно сохранить управляемый
  QCOW2 каждого диска с checksum, шифрованием, репликацией и ретенцией.
- **Рекомендатель**: для каждой ВМ показывает доступные варианты, оценку объёма и
  времени по её собственной истории, причины недоступности и что нужно сделать,
  плюс готовые расписания под приём одним нажатием.
- Снимки конфигурации oVirt Engine — отдельные задания с расписанием, репозиторием,
  шифрованием и ретенцией; снимки можно скачать и сравнить по секциям.
- Нативный бэкап файлов и каталогов доступен под feature gate: именованные
  разрешённые корни, include/exclude, инкременты, дедупликация, шифрование,
  просмотр дерева и выборочное восстановление. Symlink сохраняется как ссылка
  и не позволяет выйти из разрешённого корня.

**Уведомления**

- Внешняя доставка поддерживает SMTP, Telegram и webhook. События сначала
  попадают в PostgreSQL outbox по одному на канал и переживают перезапуск.
- В web задаются минимальная важность, частота и максимум напоминаний, сообщение
  об устранении и остановка повторов после подтверждения. Для каждого типа
  оповещения можно назначить отдельную политику или выключить только внешнюю
  доставку.
- Отдельный alert можно временно отложить или заглушить до устранения, не скрывая
  его из интерфейса. Транспорт повторяет ошибочную отправку до пяти раз;
  семантика доставки at-least-once.

**Хранение**
- Локальный каталог (включая примонтированные NFS/CIFS), S3-совместимое хранилище
  (AWS, MinIO, Ceph RGW), сетевая папка SMB/CIFS, коллекция WebDAV, SFTP. К шаре
  и к WebDAV служба подключается сама, монтировать их на хосте не нужно.
- Раскладка по датам: `jhvirt/<сервер>/<вм>/<ГГГГ>/<ММ>/<ДД>/<запуск>/`.
- Ретенция «дед-отец-сын»: последние N, часовые, суточные, недельные, месячные,
  годовые, предельный возраст. Звено, от которого зависит сохраняемый инкремент,
  не удаляется никогда. Предпросмотр показывает, что политика удалит, до запуска.
- Сжатие на чанк: `zstd` (по умолчанию), `gzip` (распакует любой инструмент),
  `s2` (быстрее всех, сжимает слабее) или `none`. Алгоритм записан в манифесте,
  поэтому смена настройки не мешает читать уже сделанные копии.
- Опциональное шифрование AES-256-GCM.

**Проверка копий**
| Режим | Что доказывает | Стоимость |
|---|---|---|
| `quick` | объекты на месте и нужного размера | секунды |
| `chain` | цепочка собирается, checkpoint-ы стыкуются | секунды |
| `manifest` | данные в хранилище не испортились (SHA-256 каждого чанка) | чтение всего бэкапа |
| `structure` | внутри образа есть разметка и файловые системы | килобайты на диск |
| `restore` | образ действительно собирается байт в байт | чтение + временный диск |
| `qemu` | восстановленный qcow2 проходит `qemu-img check` | как `restore` + qemu-img |
| `source` | сохранённое совпадает с тем, что отдал гипервизор | повторное чтение диска |
| `boot` | гостевая ОС из копии загружается и отвечает через агента | запуск изолированной ВМ |

Режим `structure` закрывает пробел, который не видит ни одна контрольная сумма:
хэш подтверждает точность копии, но не отличает точную копию рабочего диска от
точной копии пустого. Разбор таблицы разделов и суперблоков — единственная
проверка, которая ловит «бэкап цел, а внутри ничего».

Для KVM режим `source` выполняется **в момент бэкапа**, пока точка
согласованности ещё открыта на гипервизоре: это единственный момент, когда
сохранённое можно сверить с оригиналом. Позже такой возможности уже нет.

Режим `boot` — единственный, который отвечает на вопрос «а поднимется ли она».
Условия у него жёстче остальных, и их стоит знать заранее:

- **Нужен KVM-хост.** ВМ поднимается через libvirt, поэтому в интерфейсе
  запрашивается подключение типа `kvm`. Бэкап с oVirt проверить можно — движок
  не умеет стартовать чужой образ, но любой настроенный KVM-хост умеет.
- **ВМ создаётся без сетевых интерфейсов.** Копия боевой системы, попавшая в
  сеть, которую считает своей, займёт адреса и начнёт писать в общее хранилище.
  Изоляция здесь не предосторожность, а разница между проверкой и аварией.
- **Восстанавливаются все диски ВМ.** Для новых копий в `run.json` сохраняются
  архитектура, BIOS/UEFI, тип машины, шины, guest-visible имена и порядок
  загрузки дисков. Сеть, UUID, исходные пути и host devices намеренно не
  переносятся. Один диск можно выбрать вручную только для диагностики.
- **Образы передаются на гипервизор целиком** — по сети сжатыми, на диске
  разреженными. Перед передачей проверяется суммарное свободное место в scratch.
- **Вывод «загрузилась» даёт гостевой агент.** Без `qemu-guest-agent` внутри
  системы проверка честно скажет, что ВМ стартовала, но подтвердить загрузку
  нечем.

`boot` можно запускать вручную у готовой копии, сразу после разового бэкапа или
по расписанию в задании. В двух последних случаях KVM-хост, память, vCPU и время
ожидания сохраняются вместе с настройками проверки; нулевые память и vCPU
означают ресурсы исходной ВМ. Поэтому образы из oVirt
тоже проверяются автоматически, а не требуют ручного перезапуска операции.

**Восстановление**
- В файл на сервере бэкапов (raw или qcow2), в новый диск oVirt, поверх
  существующего диска.
- В новую ВМ для совместимых платформ oVirt→oVirt и KVM→KVM. Предпросмотр
  проверяет имя, место и целевые ресурсы; профиль v2 переносит CPU, память,
  архитектуру, firmware, диски, порядок загрузки и NIC.
- Каждый NIC можно исключить или сопоставить с целевым vNIC profile,
  libvirt-сетью или bridge. По умолчанию NIC отключены, MAC создаются заново,
  а запуск восстановленной ВМ подтверждается отдельно. При ошибке выполняется
  идемпотентная очистка созданных ресурсов.
- Копия типа `config` может создать ВМ без дисков, но такая машина явно
  помечается как не содержащая данных и не запускается автоматически.
- Восстановление из инкремента автоматически собирает всю цепочку.
- Отдельный список показывает ход и итог каждого восстановления: операция идёт
  часами в фоне, и без этого списка о её судьбе узнать неоткуда. Собранный файл
  остаётся на сервере бэкапов по указанному пути — через веб файлы не отдаются.

**Документация в интерфейсе**

Кнопка «?» стоит рядом с полями, о которых обычно и возникает вопрос: тип
бэкапа, «полный каждые N», поведение при недоступном отслеживании изменений,
заморозка ФС гостя, правила
хранения, режим проверки. Выбранный тип бэкапа объясняется прямо в форме
задания — работает ли ВМ, что типу нужно, чего стоит восстановление из него и
о чём помнить.

Отдельный раздел **«Документация»** содержит эксплуатационную и техническую
справку: схемы потоков oVirt и KVM/libvirt,
горячее копирование raw и qcow2, взаимодействие с ovirt-imageio, NBD, QEMU,
хранилищами и библиотеками кодеков, уровни согласованности, цепочки, хранение и
проверку копий, восстановление новой ВМ, файловые и Engine-снимки, уведомления,
перенос приложения и TLS. Раздел доступен всем вошедшим пользователям.

Тексты живут на бэкенде (`internal/api/help.go`, отдаётся через `GET /help`)
там же, где названия типов, чтобы не разъезжаться с кодом; тест не даёт добавить
тип бэкапа, не описав его.

**Что делается через веб**

Вся повседневная работа: подключения обоих типов, инвентарь, питание ВМ и
действия над хостами, задания и расписания, разовые бэкапы, все восемь режимов
проверки, восстановление дисков и новых ВМ, снимки конфигурации Engine,
файловые бэкапы (если включён feature gate), хранилища, разовый прогон правил
хранения с предпросмотром, график доступности подключения, оповещения,
пользователи и аудит.

Через веб настраиваются глобальное сжатие новых копий, ротация файлового
журнала, системный IANA-часовой пояс и пороги качества бэкапов. Светлая,
тёмная или системная тема выбирается в основном меню. Runtime-переопределения
хранятся в PostgreSQL и действуют без перезапуска. Адрес базы, ключ шифрования,
сетевые порты, разрешённые файловые корни и базовые интервалы опроса остаются в
`config/ovirt-backup.yaml` и `JHV_*`. `jvbackup` — сознательно вторая точка
входа на случай, когда сервис недоступен.

### Контроль качества бэкапов

Раздел **«Защита»** использует расписание, а не фиксированные 48 часов. Вкладка
«Состояние» показывает худшую обязательную реплику каждой ВМ, последнюю полную
копию, следующую точку и проверку восстановления. «Динамика» показывает
успешность, пропуски, длительность, скорость и объёмы за 24 часа, 7, 30 или 90
дней. «Хранилища» хранит замеры каждые 15 минут и строит прогноз минимум по
семи дневным медианам. Для S3 и для серверов, не сообщающих квоту, свободное
место явно помечено как неизвестное.

Prometheus доступен по `GET /metrics` с отдельным Bearer-токеном. Установщики
создают token-файл `0600`: `/opt/jhvirt/config/metrics.token` для systemd и
`/app/data/metrics.token` в постоянном Docker volume. Cookie и обычные API-токены
к этому endpoint не подходят. Подробности: [OPERATIONS.md](docs/OPERATIONS.md).

## Развёртывание

Поддерживаются два боевых пути: Docker Compose и нативная служба systemd.
В обоих случаях установщик готовит конфигурацию, запускает сервис и ждёт
`/readyz`. Без OIDC он печатает одноразовый пароль `local-admin`; с Keycloak
локальный вход по умолчанию выключен, а администраторы приложения назначаются
группой `virt-admins`.

Docker Compose v2:

```bash
cd deploy
./install.sh --mode docker --url http://virt.example.org:8080
```

Для старого Compose v1 используется `--mode docker-compose`. Схема URL важна:
`https://` включает флаг `Secure` у сессионной cookie, поэтому его указывают
только при реально настроенном TLS или обратном прокси.

Установщик умеет сам выпустить и подключить самоподписанный сертификат:

```bash
sudo sh ./ovirt-backup-*.run --mode docker \
  --url https://virt.example.org:8080 --tls self-signed
```

Существующая PEM-пара подключается через `--tls files`,
`--tls-cert-file` и `--tls-key-file`. Повторный запуск той же команды меняет
сертификат текущей инсталляции, не сбрасывая её настройки.

Compose разделяет публичную и внутреннюю сети, не публикует PostgreSQL на хост,
использует отдельные роли БД для приложения и Keycloak, read-only root,
минимальные capabilities и лимиты CPU/RAM/PID. Пароли БД, bootstrap и OIDC
client secret лежат в файлах `0600` внутри volumes, а базовые образы закреплены
digest. После bootstrap приложение пересоздаётся без одноразового пароля, а
временная административная запись Keycloak заменяется проверенной постоянной
записью и удаляется.
Отдельный `recovery.token` хранится только на хосте; контейнер видит его SHA-256,
а сброс выполняется `sudo /opt/jhvirt/bin/ovirt-backup-recover-admin` с отзывом
всех сессий и выдаваемых из БД токенов. Пароль постоянного администратора
встроенного Keycloak восстанавливается отдельной host-only командой
`sudo /opt/jhvirt/bin/ovirt-backup-recover-keycloak`: она не пересоздаёт realm,
пользователей или MFA и удаляет временную служебную запись до показа нового
пароля. `install.sh` также создаёт ежедневные проверенные dump БД приложения и
Keycloak и отдельную копию `secret.key`; каталог задаётся
`--dr-backup-dir` и в production должен находиться вне системного диска.

Перенос на новый сервер выполняется тем же установщиком. На старом узле:

```bash
sudo sh ./ovirt-backup-*.run \
  --migration-export /root/jhvirt-migration.tar.gz
```

На новом узле:

```bash
sudo sh ./ovirt-backup-*.run \
  --migrate-from /root/jhvirt-migration.tar.gz
```

Пакет содержит dump PostgreSQL, YAML/env, `secret.key`, токены и TLS-пару.
Исходные путь установки и системный пользователь сохраняются, если на новом
узле не задать другие `PREFIX`/`USER_NAME`. Каталоги самих бекапов в архив не
входят: их mount points нужно подключить отдельно. Оба действия доступны и в
интерактивном меню.

Перенос выполняется только между одинаковыми runtime-режимами
(Docker→Docker или systemd→systemd). Архив имеет права `0600` и checksum от
повреждения, но не зашифрован и не подписан; передавайте его по защищённому
каналу. Внешние репозитории, file-backup roots и restore-каталоги подключаются
на новом сервере отдельно с подходящими UID/GID/ACL.

Вариант один — боевой. Ознакомительного с готовыми паролями нет намеренно:
конфигурация «пока так, потом заменим» остаётся в бою чаще, чем заменяется, а
по журналу неотличима от настоящей.

Полная процедура с TLS, сохранностью ключа шифрования и приёмочным прогоном —
**[DEPLOY.md](docs/DEPLOY.md)**. Диагностика установки, PostgreSQL,
авторизации, подключений, бэкапов и KVM собрана в
**[TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md)**. Границы контейнерной защиты,
роли БД, размещение секретов и проверочные команды — в
**[SECURITY.md](docs/SECURITY.md)**.

### Systemd

```bash
./run build --target linux/amd64
```

Соберёт один файл `dist/ovirt-backup-<версия>-linux-amd64.run` — установщик со вшитым
архивом: бинари, интерфейс, конфигурация, юнит systemd. На сервере ничего
распаковывать не нужно:

```bash
sudo sh ./ovirt-backup-<версия>-linux-amd64.run \
  --mode systemd --url http://virt.example.org:8080
```

На Ubuntu/Debian и RHEL/Alma/Rocky установщик сам поставит и инициализирует
локальную PostgreSQL, создаст системного пользователя, env-файл и unit. Для
внешней базы передайте `--database-url-file /root/jhvirt.dsn`; файл должен
содержать одну DSN-строку и иметь права `0600`.

Пункт «удалить» в интерактивном меню предлагает снять Docker Compose,
systemd-службу или оба варианта, затем отдельно предлагает сохранить или удалить
YAML/env-файлы. Для автоматизации используйте `--uninstall=docker`,
`--uninstall=systemd` или `--uninstall=all`; по умолчанию конфигурация
сохраняется, для её удаления добавьте `--remove-config`. PostgreSQL, база, ключ
шифрования, контейнерные тома и файлы бэкапов в обоих случаях сохраняются.

Нужны Go 1.27+ и Node 20+. Компилятор C и `make` не требуются, поэтому собрать
Linux-бинарь можно и из-под Windows. Подробности — [docs/BUILD.md](docs/BUILD.md).

### Разработка

Все команды — через `./run`; он же собирает и проверяет. `make` не нужен, но
Makefile есть и делегирует сюда же.

```bash
./run dev         # сервер на :8080
./run web         # интерфейс на :9000 с проксированием /api
./run check       # формат, go vet, тесты, проверка типов
./run sbom        # состав зависимостей в формате CycloneDX
./run vuln        # уязвимости: govulncheck, grype, trivy
./run             # список команд
```

`sbom` и `vuln` в `check` не входят: им нужна сеть, а `check` должен проходить и
без неё. Гоняет их CI на каждый push; подробности — в
[docs/BUILD.md](docs/BUILD.md#состав-зависимостей-и-уязвимости).

## Первые шаги в интерфейсе

1. **Серверы → Подключить сервер.** Укажите адрес движка (`https://engine.example.org`,
   без `/ovirt-engine/api`), пользователя (`admin@internal`) и пароль.
   Нажмите **Получить** рядом с полем CA-сертификата — сертификат скачается с движка;
   сверьте отпечаток и сохраните. **Проверить подключение** покажет версию, число
   хостов и ВМ, а при ошибке — что именно исправить.
2. **Хранилища → Добавить хранилище.** Локальный каталог, S3, SMB/CIFS, WebDAV или SFTP.
   Проверка выполняется сразу: запись, чтение, сверка, удаление пробного объекта.
3. **Серверы → ваш сервер → ВМ → нужная машина.** Экран покажет варианты бэкапа
   с обоснованием, рекомендуемый вариант и готовые расписания. Если у дисков не
   включён инкрементальный режим — там же кнопка «Включить отслеживание изменений».
4. **Создайте задание** из готового расписания или вручную на странице
   «Задания бэкапа».
5. Через сутки откройте бэкап и нажмите **Проверить** в режиме `restore` —
   убедитесь, что копия собирается. Резервная копия, которую ни разу не
   восстанавливали, — это гипотеза, а не бэкап.

## Конфигурация

Точные пути для Docker из репозитория, Docker из `.run` и systemd, порядок
применения настроек и правила их сохранения описаны в
**[CONFIGURATION.md](docs/CONFIGURATION.md)**.

Основной файл в исходниках — `config/ovirt-backup.yaml`. Любой параметр
переопределяется переменной окружения
`JHV_<ПУТЬ_КЛЮЧА_ЧЕРЕЗ_ПОДЧЁРКИВАНИЯ>`:

```bash
JHV_SERVER_PORT=9443
JHV_DATABASE_URL="host=db.example.org user=jhvirt password=secret dbname=jhvirt sslmode=require"
JHV_MONITOR_REMEDIATION_DRY_RUN=false
JHV_BACKUP_TRANSFER_PREFER_PROXY=true
```

Ключевые параметры:

| Параметр | Смысл |
|---|---|
| `database.url` | подключение к PostgreSQL одной строкой |
| `monitor.interval` | период опроса движков |
| `monitor.backup_quality.*` | свежесть, проверки, деградация скорости, место и срок истории |
| `scheduler.timezone` | системная IANA-зона cron, web, отчётов, уведомлений и журнала; меняется в web без перезапуска |
| `monitor.remediation.dry_run` | `true` — только фиксировать намеченные действия (стартовое значение; дальше режим переключается в интерфейсе и хранится в БД) |
| `monitor.remediation.archive_dir` | куда складывать архивы периодов наблюдения |
| `monitor.remediation.allow_host_fence` | разрешить автоматическую перезагрузку хоста по питанию |
| `backup.workers` | сколько бэкапов выполняется одновременно |
| `backup.chunk_size` | шаг сетки чанков (по умолчанию 4 МиБ) |
| `backup.compression` | `zstd`, `gzip`, `s2` или `none` для новых запусков |
| `backup.compression_level` | уровень `1..9`; через web не изменяется |
| `backup.transfer.prefer_proxy` | качать через прокси движка, если хосты недоступны напрямую |
| `logging.file` | путь файлового журнала; пусто — только stdout/journald |
| `logging.max_size_mb`, `max_backups`, `max_age_days` | ротация по размеру, числу и возрасту |
| `secrets.key_file` | ключ шифрования паролей подключений и ключей хранилищ |
| `metrics.enabled`, `metrics.token_file` | защищённый экспорт Prometheus |
| `auth.recovery_token_hash` | SHA-256 host-only токена аварийного сброса; сам токен в конфигурацию не помещается |

**Ключ шифрования** создаётся при первом старте в `data/secret.key`. Без него
сохранённые пароли не расшифровать — включите его в резервную копию сервиса.

Администратор может изменить глобальное сжатие в «Настройки → Система»,
ротацию — в «Настройки → Журнал», пороги — в «Настройки → Мониторинг».
Эти переопределения хранятся в PostgreSQL,
имеют приоритет над YAML/окружением и применяются без перезапуска. Сброс в web
удаляет переопределение. Уже выполняющийся бэкап сохраняет выбранный при старте
алгоритм; существующие и смешанные цепочки читаются по манифестам.

## Требования к среде

- **Движок**: oVirt 4.4+ / РЕД Виртуализация соответствующей версии для
  инкрементальных бэкапов. На более старых доступен полный бэкап через снапшот.
- **Сетевая доступность**: сервис обращается к движку (443) и к `ovirt-imageio`
  на гипервизорах (54322). Если хосты недоступны напрямую, включите
  `backup.transfer.prefer_proxy` — трафик пойдёт через прокси движка (54323),
  медленнее, но без прямого доступа к сети хранения.
- **Диски для инкрементов**: формат qcow2 и включённый режим `incremental`.
  Диски `raw` бэкапятся только целиком (через снапшот).
- **qemu-img**: не обязателен. Нужен для экспорта в qcow2 и режима проверки
  `qemu`. Offline bundle из `.run` не скачивает его при установке; для этих
  двух функций используйте собственный образ с `qemu-img` или systemd-хост,
  где пакет установлен администратором.
- **Пробный запуск**: KVM-хост той же архитектуры, что и гость, с доступной
  требуемой BIOS/UEFI-прошивкой и местом в scratch под занятые блоки всех
  дисков. На хосте нужны аппаратная виртуализация (`/dev/kvm`), QEMU и libvirt;
  SSH-пользователь должен иметь доступ к libvirt и право записи в scratch.
  Для подтверждения загрузки внутри гостя нужен `qemu-guest-agent`.

## Горячий бэкап KVM без oVirt: `jvbackup`

Работает напрямую с libvirt по SSH — на гипервизоре ничего не устанавливается,
кроме уже имеющегося `libvirtd`. Порт нужен только 22: по тому же SSH-каналу
идёт и управление, и поток данных NBD.

```bash
# что вообще будет скопировано у домена
jvbackup inspect -host kvm1 -user root -key ~/.ssh/id_ed25519 -domain db-01

# полный бэкап, гость продолжает работать
jvbackup backup -host kvm1 -user root -key ~/.ssh/id_ed25519 \
                -domain db-01 -repo /backup

# инкремент: опорная точка ищется в самом хранилище
jvbackup backup -host kvm1 -user root -key ~/.ssh/id_ed25519 \
                -domain db-01 -repo /backup -type incremental

# со сверкой каждого блока с источником, пока точка ещё открыта
jvbackup backup ... -verify-source 1

jvbackup list   -repo /backup
jvbackup verify -repo /backup -run <id> -mode structure
jvbackup restore -repo /backup -run <id> -out /var/tmp -format qcow2

# абсолютные даты в выводе можно привести к нужной IANA-зоне
jvbackup list -repo /backup --timezone Asia/Yekaterinburg

# то же самое из сетевого хранилища: S3, шара SMB, коллекция WebDAV
jvbackup list -repo s3://key:secret@s3.example.org/backups
jvbackup list -repo 'smb://EXAMPLE;svc:pass@nas.example.org/backups'
jvbackup list -repo 'webdavs://backup:pass@cloud.example.org/remote.php/dav/files/backup'
```

Требования на гипервизоре: libvirt 6.0+, диски в формате qcow2 для инкрементов,
место под scratch-файлы (см. [`docs/DISK-ARCHITECTURE.md`](docs/DISK-ARCHITECTURE.md#5-что-происходит-во-время-горячего-бэкапа)).

Что происходит внутри: libvirt открывает точку согласованности и NBD-сервер,
собственный клиент NBD (`pkg/nbd`) спрашивает у QEMU карту изменённых блоков и
забирает только их, гость при этом не останавливается ни на миг.
