# Конфигурация и данные

Этот документ отвечает на три практических вопроса:

1. где находится конфигурация для каждого способа установки;
2. какой файл нужно менять;
3. что сохраняется при обновлении и удалении.

Системная настройка разрешения имён движков и гипервизоров вынесена в
[DNS.md](DNS.md).

## 1. Краткая таблица путей

При стандартном `PREFIX=/opt/jhvirt`:

Название продукта и новые артефакты — `ovirt-backup`. Идентификаторы
`/opt/jhvirt`, `jhvirt.service`, `jhvirt.env`, `JHV_*`, база `jhvirt` и cookie
`jhvirt_session` намеренно сохранены: их переименование разорвало бы обычное
обновление, существующие сессии и привязку к данным.

| Режим | Основной YAML | Переменные окружения | Запуск |
|---|---|---|---|
| Docker из репозитория | `<репозиторий>/config/ovirt-backup.yaml` | `<репозиторий>/deploy/.env` | `<репозиторий>/deploy/docker-compose.yml` |
| Docker из `.run` | `/opt/jhvirt/config/ovirt-backup.yaml` | `/opt/jhvirt/compose/.env` | `/opt/jhvirt/compose/docker-compose.yml` |
| systemd из `.run` | `/opt/jhvirt/config/ovirt-backup.yaml` | `/opt/jhvirt/config/jhvirt.env` | `/etc/systemd/system/jhvirt.service` |

TLS-материалы, установленные через `install.sh`, находятся здесь:

| Режим | Сертификат | Закрытый ключ |
|---|---|---|
| Docker | `/app/data/tls/server.crt` в volume `jhvirt-data` | `/app/data/tls/server.key`, UID `10001`, режим `0600` |
| systemd | `<PREFIX>/config/tls/server.crt` | `<PREFIX>/config/tls/server.key`, пользователь службы, режим `0600` |

При установке с другим `PREFIX` замените `/opt/jhvirt` указанным каталогом:

```bash
sudo PREFIX=/srv/jhvirt sh ./ovirt-backup-*.run
```

Unit всегда устанавливается в `/etc/systemd/system/jhvirt.service`, но пути
внутри него рендерятся с фактическим `PREFIX`.

## 2. Что считается конфигурацией

Настройки собираются в следующем порядке, каждый следующий уровень
перекрывает предыдущий:

1. встроенные значения по умолчанию;
2. `ovirt-backup.yaml`;
3. переменные окружения `JHV_*`;
4. сохранённые в PostgreSQL runtime-переопределения для поддерживаемых
   параметров.

Имя переменной строится из YAML-пути: точки заменяются подчёркиваниями, имя
переводится в верхний регистр и добавляется префикс `JHV_`:

```text
server.port                     -> JHV_SERVER_PORT
server.external_url             -> JHV_SERVER_EXTERNAL_URL
database.url                    -> JHV_DATABASE_URL
monitor.remediation.dry_run     -> JHV_MONITOR_REMEDIATION_DRY_RUN
backup.transfer.prefer_proxy    -> JHV_BACKUP_TRANSFER_PREFER_PROXY
```

`JHV_DATABASE_URL` имеет приоритет над отдельными полями
`database.postgres.*`.

Runtime-переопределения доступны администратору в интерфейсе:

| Экран | Параметры | Применение |
|---|---|---|
| «Настройки → Система» | `backup.compression` | только к новым запускам бэкапа |
| «Настройки → Система» | `scheduler.timezone` | меняет системную зону и сразу пересчитывает будущие точки cron; активные операции не прерываются |
| «Настройки → Журнал» | `logging.max_size_mb`, `logging.max_backups`, `logging.max_age_days` | сразу, без перезапуска |

Интерфейс показывает источник эффективного значения: `config` означает YAML
или окружение, `database` — переопределение в PostgreSQL. Кнопка сброса удаляет
только запись из БД и сразу возвращает значение конфигурации. Уровень сжатия
`backup.compression_level` остаётся параметром YAML/окружения и в интерфейсе
доступен только для чтения. Уже запущенный бэкап сохраняет алгоритм, выбранный
при его старте; цепочка может состоять из звеньев с разными алгоритмами.

Часовой пояс задаётся именем из базы IANA, например `UTC`, `Europe/Moscow` или
`Asia/Yekaterinburg`. Эта зона общая для cron, web, отчётов, уведомлений и
человекочитаемых timestamp журна. PostgreSQL, manifests и API хранят время в UTC;
преобразование делается только для показа. После сохранения все открытые web-сессии
получают `settings.changed`, а планировщик перерегистрирует cron-задания и обновляет
их `next_run_at` без перезапуска службы. Уже выполняющиеся запуски продолжаются.
Сброс возвращает `scheduler.timezone` из YAML/окружения; в Docker его стартовое значение
обычно приходит из `TZ`.

Переходы DST обрабатываются правилами IANA и `robfig/cron`, а не фиксированным
смещением. Если весной заданного местного времени не существует, эта точка не
запускается. Если осенью местный час повторяется, cron-точка в этом часе может
выполниться дважды — по одному разу для каждого UTC-смещения. Для заданий, где двойной
запуск недопустим, используйте `UTC`.

Подключения к oVirt/KVM, пользователи, задания, история, runtime-переопределения
и состояние авто-восстановления, изменённое через интерфейс, находятся в
PostgreSQL. Их нет в YAML или `.env`.

## 3. Docker из репозитория

Рабочий каталог:

```bash
cd <репозиторий>/deploy
```

Файлы:

```text
../config/ovirt-backup.yaml   полная конфигурация приложения
.env                          параметры Compose и секреты PostgreSQL
docker-compose.yml            описание контейнеров и привязка переменных
```

`.env` создаёт `install.sh`. В нём находятся, в частности:

| Переменная | Назначение |
|---|---|
| `JHV_EXTERNAL_URL` | внешний адрес браузера и схема сессионной cookie |
| `JHV_PORT` | опубликованный host-порт; внутри контейнера сервер слушает 8080 |
| `JHV_TLS_ENABLED`, `JHV_TLS_CERT_FILE`, `JHV_TLS_KEY_FILE` | собственный TLS; установщик хранит пару внутри `jhvirt-data` |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | локальная контейнерная PostgreSQL |
| `JHV_BACKUP_DIR` | host-каталог, смонтированный как `/backups` |
| `JHV_RESTORE_DIR` | host-каталог, смонтированный как `/restores` |
| `TZ` | стартовая системная IANA-зона; web-override из PostgreSQL имеет приоритет |

YAML копируется в образ как `/app/config/ovirt-backup.yaml`. Не редактируйте
его внутри контейнера: изменение исчезнет при пересоздании. После изменения
host-файла пересоберите образ:

```bash
cd <репозиторий>/deploy
docker compose build ovirt-backup
docker compose run --rm --no-deps ovirt-backup -check-config
docker compose up -d
PORT="$(sed -n 's/^JHV_PORT=//p' .env)"
curl -fsS "http://127.0.0.1:${PORT:-8080}/readyz"
```

После изменения только `.env` достаточно пересоздать контейнер:

```bash
docker compose up -d
```

Для Compose v1 замените `docker compose` на `docker-compose`.

## 4. Docker из `.run`

Стандартные пути:

```text
/opt/jhvirt/config/ovirt-backup.yaml
/opt/jhvirt/compose/.env
/opt/jhvirt/compose/docker-compose.yml
```

Редактирование и применение:

```bash
sudoedit /opt/jhvirt/config/ovirt-backup.yaml
sudoedit /opt/jhvirt/compose/.env

cd /opt/jhvirt/compose
sudo docker compose build ovirt-backup
sudo docker compose run --rm --no-deps ovirt-backup -check-config
sudo docker compose up -d
```

При повторном запуске `.run` существующий YAML сохраняется, а конфигурация из
новой версии записывается как
`/opt/jhvirt/config/ovirt-backup.yaml.new`. Сравните файлы вручную и перенесите
нужные новые параметры. `.env` также сохраняется; установщик изменяет в нём
только внешний URL и host-порт согласно переданным `--url` и `--port`.

## 5. Systemd

Стандартные пути:

```text
/opt/jhvirt/config/ovirt-backup.yaml   основные настройки
/opt/jhvirt/config/jhvirt.env          секреты и переопределения JHV_*
/etc/systemd/system/jhvirt.service     unit
/opt/jhvirt/data/secret.key            ключ шифрования
/opt/jhvirt/logs/                      файлы журналов, если включены
```

Посмотреть фактические пути, включая нестандартный `PREFIX`:

```bash
sudo systemctl cat jhvirt
sudo systemctl show jhvirt -p FragmentPath -p ExecStart -p EnvironmentFiles
```

Изменение YAML:

```bash
sudoedit /opt/jhvirt/config/ovirt-backup.yaml
```

Изменение переменных или DSN:

```bash
sudoedit /opt/jhvirt/config/jhvirt.env
sudo chmod 600 /opt/jhvirt/config/jhvirt.env
sudo chown jhvirt:jhvirt /opt/jhvirt/config/jhvirt.env
```

Не передавайте содержимое `jhvirt.env` в диагностических сообщениях: там
может находиться пароль PostgreSQL.

Перед перезапуском проверьте итоговую конфигурацию от имени службы:

```bash
sudo systemd-run --quiet --wait --pipe --collect \
  --unit="jhvirt-config-check-$$" \
  --uid=jhvirt --gid=jhvirt \
  --working-directory=/opt/jhvirt \
  --property=EnvironmentFile=/opt/jhvirt/config/jhvirt.env \
  /opt/jhvirt/bin/ovirt-backup-server \
  -config /opt/jhvirt/config/ovirt-backup.yaml -check-config

sudo systemctl restart jhvirt
curl -fsS http://127.0.0.1:8080/readyz
```

При обновлении существующий `ovirt-backup.yaml` не перезаписывается. Новый
образец появляется рядом как `ovirt-backup.yaml.new`; `jhvirt.env` также
сохраняется. При первом обновлении с прежнего имени файла установщик копирует
`virt-manager.yaml` в `ovirt-backup.yaml`, оставляя исходный файл на месте.

## 6. Ключ, база и каталоги данных

Не путайте конфигурацию с данными приложения:

| Объект | Docker | systemd |
|---|---|---|
| Ключ шифрования | volume `jhvirt-data`, файл `/app/data/secret.key` | `<PREFIX>/data/secret.key` |
| PostgreSQL | именованный volume `postgres-data` | локальная или внешняя PostgreSQL |
| Подключения, задания, пользователи | PostgreSQL | PostgreSQL |
| Бэкапы ВМ | host-путь из `JHV_BACKUP_DIR` или внешнее хранилище | путь/хранилище из YAML |
| Восстановленные образы | host-путь из `JHV_RESTORE_DIR` | разрешённые каталоги из YAML и unit |
| TLS приложения | каталог `tls/` в `jhvirt-data` | `<PREFIX>/config/tls` |

Надёжно получить Docker-ключ, не завися от внутреннего пути Docker volume:

```bash
cd <каталог-compose>
docker compose cp ovirt-backup:/app/data/secret.key \
  ./secret.key.backup
chmod 600 ./secret.key.backup
```

`secret.key` не является заменяемой настройкой. Потеря этого файла делает
сохранённые пароли подключений и зашифрованные копии нерасшифровываемыми.

## 7. Что сохраняется

| Операция | YAML | `.env`/`jhvirt.env` | `secret.key` | PostgreSQL и тома |
|---|---|---|---|---|
| Обновление Docker `.run` | сохраняется, новый образец `.new` | сохраняется; URL и порт обновляются | сохраняется | сохраняются |
| Обновление systemd | сохраняется, новый образец `.new` | сохраняется | сохраняется | сохраняются |
| `--uninstall=docker` | сохраняется | сохраняется | volume сохраняется | volumes сохраняются |
| `--uninstall=systemd` | сохраняется | сохраняется | сохраняется | PostgreSQL сохраняется |
| `--uninstall=all` | сохраняется | сохраняется | сохраняется | PostgreSQL и volumes сохраняются |
| `--uninstall=… --remove-config` | удаляется, если не нужен оставшемуся режиму | env выбранного режима удаляется | сохраняется | PostgreSQL и volumes сохраняются |
| `--migration-export` / `--migrate-from` | переносится и переписывается при новом `PREFIX` | переносится с правами `0600` | переносится обязательно | dump восстанавливается либо сохраняется DSN внешней БД |

Интерактивное удаление задаёт тот же выбор отдельным пунктом; по умолчанию
конфигурация сохраняется. В Git-репозитории versioned YAML не удаляется.
Полное удаление `/opt/jhvirt`, Docker volumes, ключа или базы выполняется только
вручную. Перед этим сохраните `secret.key`, нужную конфигурацию, env-файл и дамп
PostgreSQL.

## Мониторинг качества и Prometheus

Базовые пороги находятся в `monitor.backup_quality`:

```yaml
monitor:
  backup_quality:
    stale_intervals: 2
    verify_max_age_days: 7
    performance_window_runs: 10
    performance_degradation_percent: 50
    performance_consecutive_runs: 3
    storage_warning_free_percent: 15
    storage_critical_free_percent: 5
    storage_warning_forecast_days: 30
    storage_critical_forecast_days: 7
    history_retention_days: 90
```

Администратор меняет этот блок на ходу в **Настройки → Мониторинг**. Полный
набор значений записывается в единственную строку `runtime_settings`; источник
в ответе API и форме обозначен как `database`. Сброс удаляет все поля
переопределения и немедленно возвращает YAML/окружение (`config`). Частичное
переопределение не применяется: так критический и предупреждающий пороги не
могут оказаться взяты из разных версий настройки.

Экспорт метрик настраивается отдельно:

```yaml
metrics:
  enabled: true
  token_file: "/opt/jhvirt/config/metrics.token"
```

При `enabled: true` файл должен существовать, содержать непустой токен и иметь
права без доступа группы и остальных, обычно `0600`. Это не `auth.api_tokens`:
endpoint `/metrics` находится вне cookie-аутентификации и принимает только
этот секрет. При выключенном экспорте endpoint отвечает `404`, чтобы не
раскрывать лишнюю поверхность.

Установщики создают и сохраняют файл автоматически:

| Режим | Token-файл |
|---|---|
| systemd | `/opt/jhvirt/config/metrics.token`, владелец `jhvirt`, `0600` |
| Docker Compose | `/app/data/metrics.token` в volume `ovirt-backup_jhvirt-data`, `0600` |

Обновление не заменяет токен. Обычное удаление сохраняет его; токен удаляется
только вместе с конфигурацией (`--remove-config`). Не помещайте его в
`prometheus.yml` открытым текстом: используйте `bearer_token_file` и права
файловой системы.

Не выводите `.env` или `jhvirt.env` целиком: они содержат секреты.

### Grafana

Готовый дашборд — `deploy/grafana/jhvirt-overview.json`. Импортируется как есть:
**Dashboards → New → Import → Upload JSON**, затем выбрать источник данных
Prometheus. Идентификатор `jhvirt-overview` постоянный, поэтому повторный
импорт обновляет тот же дашборд, а не плодит копии.

Что на нём: машины под защитой и не покрытые ни одним заданием, состояния
реплик, открытые критические оповещения, аварийная готовность, возраст
последней успешной копии по каждой ВМ, длительность и скорость последнего
запуска, свободное место и прогноз заполнения хранилищ, состояние репликации
и отставание самой старой незавершённой копии.

Сбор метрик требует токена — endpoint `/metrics` вне cookie-аутентификации и
принимает только его:

```yaml
scrape_configs:
  - job_name: jhvirt
    scheme: https
    bearer_token_file: /etc/prometheus/jhvirt.token
    static_configs:
      - targets: ["virt.example.org:8080"]
```

Токен лежит в `metrics.token_file` установки; скопируйте его файлом и раздайте
права так же строго — `0600` и владелец Prometheus. Открытым текстом в
`prometheus.yml` ему не место.

Две особенности, о которых стоит знать при правке панелей:

- метрики с окончанием `_total` здесь — **не счётчики Prometheus**, а текущее
  число строк в базе. Оборачивать их в `rate()` бессмысленно: значение может
  уменьшаться, когда старые записи вычищает ретенция;
- имена ВМ и хранилищ приходят отдельными метриками `ovirt_backup_vm_info` и
  `ovirt_backup_storage_info` и подставляются через `group_left`. Без этого на
  панелях были бы одни идентификаторы, читать которые невозможно.

## Внешний вход (OIDC)

Служба умеет принимать вход через внешнего провайдера: Keycloak, Red
Virtualization SSO, ADFS, Authentik. Пароль пользователя при этом через службу
не проходит вовсе — она получает от провайдера подписанный токен и заводит по
нему свою обычную сессию. Двухфакторная проверка, единый вход и мгновенный
отзыв доступа остаются заботой провайдера.

```yaml
auth:
  oidc:
    enabled: true
    issuer: "https://keycloak.example.org/realms/infra"
    client_id: "jhvirt"
    client_secret: "..."
    redirect_url: "https://virt.example.org/api/v1/auth/oidc/callback"
    scopes: ["openid", "profile", "email", "groups"]
    button_label: "Войти через Keycloak"
    groups_claim: "groups"
    role_mapping:
      "virt-admins": "admin"
      "virt-operators": "operator"
      "virt-readers": "viewer"
    default_role: ""
    post_logout_redirect_url: "https://virt.example.org/login"
    session_ttl: 1h
    allow_local_login: true
```

`redirect_url` должен совпадать с зарегистрированным у провайдера точно, вплоть
до схемы и завершающего пути, и указывать на `/api/v1/auth/oidc/callback` того
адреса, по которому до службы доходит браузер.

### Как назначается роль

Группы берутся из утверждения `groups_claim`. Имя допускает вложенность через
точку — `resource_access.jhvirt.roles` у Keycloak с ролями клиента. Если в
токене их нет, служба спрашивает `/userinfo`: ADFS и Azure членство в токен не
кладут, и без этого запроса вход у них отказывался бы всем подряд.

- **Сопоставление без учёта регистра.** `VIRT-Admins` и `virt-admins` — одно и
  то же: каталоги пишут имена по-разному, а оператор переносит их руками.
- **Побеждает старшая роль** (`admin` > `operator` > `viewer`). Пользователь
  обычно состоит в нескольких группах, и права не должны зависеть от порядка
  элементов в токене.
- **Ни одна группа не отобразилась и `default_role` пуст — вход запрещён.**
  В сообщении на странице входа перечислены пришедшие группы: без них причину
  пришлось бы искать в журнале провайдера и журнале службы одновременно.
- **Роль пересчитывается на каждом входе.** Группу отбирают тогда, когда доступ
  пора прекратить, и выданная однажды роль это событие не переживает.

### Выход и срок сессии

Выход закрывает и сессию у провайдера: `POST /api/v1/auth/logout` возвращает
`logout_url`, интерфейс уводит браузер туда. Без этого «Выйти» защищает только
на вид — сессия провайдера остаётся, и следующее нажатие кнопки входа пускает
обратно, ничего не спросив. На общем компьютере это и есть вся разница.

Адрес берётся из `end_session_endpoint` провайдера, к нему добавляется
`id_token_hint` — тот самый токен, по которому заводилась сессия; он хранится
в строке сессии и уходит вместе с ней. Если провайдер выхода не предлагает,
закрывается только своя сессия.

`post_logout_redirect_url` передаётся, только если задан: у провайдера он
обязан быть в списке разрешённых (в Keycloak — *Valid post logout redirect
URIs*), а незарегистрированный превращает выход в страницу ошибки.

`session_ttl` для внешних входов короче общего (по умолчанию час). Роль
пересчитывается при каждом входе, но уже выданная сессия живёт своим сроком:
у человека, которого убрали из группы в каталоге, права здесь держатся до её
конца. Мгновенного отзыва это не даёт — для него нужно хранить refresh-токен и
переспрашивать провайдера; сейчас граница составляет `session_ttl`.

### Учётные записи

Связь ведётся по `sub` — неизменному идентификатору у провайдера, поэтому
переименование в каталоге не заводит вторую запись и не теряет права. Имя
берётся из `preferred_username`, затем `email`.

Если такое имя уже занято, запись заводится под именем `<имя>@oidc`, а
существующая не трогается: совпадение имён почти наверняка означает местную
учётную запись, и привязка к ней отдала бы её любому, кто завёл у провайдера
пользователя `admin`.

Пароля у внешней записи нет: войти по паролю она не может, и задать ей пароль
через управление пользователями нельзя. Флаг «отключена» остаётся местным
рубильником — очередной успешный вход у провайдера его не отменяет.

### Вход по паролю рядом с внешним

`allow_local_login: true` по умолчанию, и выключать его не рекомендуется. Это
система восстановления: если единственный путь внутрь лежит через провайдера,
а провайдер живёт на той самой виртуальной машине, которую восстанавливают,
консоль восстановления недоступна ровно тогда, когда она нужна.

При `allow_local_login: false` форма имени и пароля на странице входа не
показывается, а `POST /api/v1/auth/login` отвечает `403`. Статические
`auth.api_tokens` продолжают работать — они и есть запасной путь для
интеграций.

### Несколько доменов — одним провайдером

Подключать в службе второго провайдера не нужно и не следует. Несколько
каталогов сводит воедино сам Keycloak: в одном realm заводится по подключению
User Federation на каждый домен (LDAP или Active Directory), а наружу отдаётся
один `issuer`. Служба видит одного провайдера и один набор групп.

Из этого следует единственное требование к настройке: группы допуска должны
быть либо собственными группами Keycloak, в которые включаются пользователи
из разных каталогов, либо иметь неконфликтующие имена между доменами. Иначе
`domain-admins` из двух разных каталогов дадут одну и ту же роль здесь.

Второй провайдер в конфигурации службы понадобился бы только при двух
независимых точках входа — например, при переезде с одного Keycloak на другой,
когда какое-то время должны работать оба.

### Двухфакторная проверка

В службе для неё ничего настраивать не нужно и нечего: пароль через неё не
проходит. Второй фактор включается в realm провайдера — в Keycloak это
Required Action «Configure OTP» (FreeOTP, Google Authenticator и совместимые)
либо WebAuthn с аппаратными ключами и passkeys. Служба получает уже
подписанный токен, выданный после всех проверок.

**Важная оговорка.** Вход по паролю, который остаётся включённым, идёт мимо
провайдера — а значит, и мимо второго фактора. Локальные учётные записи
поэтому имеет смысл держать аварийными: одна-две, длинный пароль, доступ к
интерфейсу ограничен сетью. Все входы, удачные и нет, попадают в аудит, а
подбор пароля притормаживается нарастающей паузой. Если локальные записи
станут повседневными, второй фактор придётся делать и для них — уже в самой
службе.

### Keycloak: что нужно завести на его стороне

- **Клиент** с секретом (`Client authentication: On`), включённым `Standard flow`
  и точным `redirect_uri` — с точностью до порта и пути.
- **Mapper групп.** Без него `groups` в токене не будет вовсе, все группы
  придут пустыми, и войти не сможет никто: тип `Group Membership`,
  `Token Claim Name: groups`, `Full group path: Off` (иначе группы приедут как
  `/virt-admins` и не совпадут с настройкой), включённый `Add to ID token`.
- **Заполненный профиль пользователя.** При пустых имени и фамилии Keycloak
  требует действие `Verify Profile` и до возврата в службу дело не доходит.

Проверка целиком, включая обмен кода и подпись, есть в тестах:

```bash
JHV_TEST_OIDC_ISSUER=http://localhost:8081/realms/jhvirt-check JHV_TEST_OIDC_CLIENT_SECRET=... JHV_TEST_OIDC_PASSWORD=... go test ./internal/api/ -run TestOIDCAgainstKeycloak -count=1
```

Без этих переменных тест пропускается; как поднять Keycloak в docker, написано
в его заголовке (`internal/api/oidc_keycloak_test.go`).

### Проверка

1. `GET /api/v1/auth/oidc/info` отвечает без аутентификации и показывает, видит
   ли служба настройки: `{"enabled":true,"button_label":"…","local_login":true}`.
2. Кнопка на странице входа ведёт на `/api/v1/auth/oidc/start`; браузер уходит
   к провайдеру и возвращается на `redirect_url`.
3. Неудача возвращает на страницу входа с причиной в адресе
   (`/login?oidc_error=…`); подробности — в журнале службы по строке
   «внешний вход не удался».

К провайдеру служба обращается при первом входе, а не при запуске: провайдер,
лежащий в момент старта, не должен мешать службе подняться.

## Несколько экземпляров службы

```yaml
cluster:
  leader_election: true
  poll_interval: 15s
```

Очередь переносов безопасна для нескольких процессов сама по себе: задача
берётся с арендой, и двое за неё не возьмутся. А планировщик, наблюдение и
авто-восстановление — нет: два экземпляра выполнили бы каждое задание дважды и
подрались бы за действия над одной ВМ. Поэтому они работают только у ведущего.

Место ведущего держится консультативной блокировкой PostgreSQL на отдельном
соединении. Она отпускается сама, когда экземпляр падает, — ждать истечения
срока не нужно. Ведомый проверяет освобождение раз в `poll_interval`, ведущий с
той же частотой убеждается, что место всё ещё за ним.

**Выключено по умолчанию.** При одном экземпляре выборы ничего не дают, а
менять поведение работающей установки на ровном месте незачем. Включать
обязательно **до** запуска второго экземпляра: иначе оба сочтут себя ведущими
и задания пойдут по два раза.

Проверить, кто ведущий, можно по журналу: при получении места пишется строка
«экземпляр стал ведущим».

## Оповещения наружу

```yaml
notifications:
  enabled: true
  min_severity: "critical"
  telegram:
    bot_token: "123456:AA..."
    chat_id: "-1001234567890"
  email:
    smtp_host: "smtp.example.org"
    smtp_port: 587
    username: "jhvirt@example.org"
    password: "..."
    from: "jhvirt@example.org"
    to: ["duty@example.org"]
  webhook:
    url: "https://alerts.example.org/hook"
    token: "..."
```

Достаточно любого одного канала. Credentials каналов по-прежнему задаются в
YAML/окружении и требуют перезапуска: API никогда не возвращает SMTP-пароль,
Telegram token или webhook token. Если доставка включена без канала, служба
через YAML, проверка конфигурации откажет в запуске; при runtime-включении web
явно покажет, что отправлять пока некуда.

Частота и исключения меняются без перезапуска в **Настройки → Уведомления**.
Глобально задаются порог, интервал, максимум повторов, сообщение об устранении
и остановка повторов после «Принять». Для каждого `kind` можно переопределить
эти значения, выбрать каналы либо полностью отключить внешнюю доставку —
например, для `backup_unprotected`, не скрывая само оповещение в web.

По умолчанию сообщение уходит один раз, когда проблема загорелась. Повтор
включается только явным ненулевым интервалом. Для отдельного активного случая
на странице оповещений доступны snooze на 1/24 часа, mute до устранения и
возобновление.

`min_severity: critical` по умолчанию по той же причине: предупреждений много,
и будить человека они не должны.

Доставка не задерживает мониторинг: событие и отдельная строка для каждого
канала сначала сохраняются в PostgreSQL outbox. Перезапуск процесса не теряет
их, а несколько экземпляров разбирают очередь через leases. Ошибка одного
канала не дублирует уже успешные каналы. Транспортная ошибка повторяется через
1, 5, 15 и 60 минут, максимум пять попыток; это не считается напоминанием о
продолжающейся проблеме. История и последняя ошибка видны в настройках.

Доставка имеет семантику at-least-once. Если процесс завершится после того,
как внешний SMTP/webhook уже принял сообщение, но до фиксации результата в
PostgreSQL, после истечения lease возможен один дубликат. Получателю webhook
следует дедуплицировать сообщения по alert/event/sequence, если это критично.

## Нативный файловый бэкап

Функция отделена от заданий ВМ и выключена по умолчанию. Администратор сначала
задаёт разрешённые исходные и целевые корни в YAML, затем оператор выбирает их
по ID в разделе **«Файловые бекапы»**:

```yaml
file_backup:
  enabled: true
  roots:
    - id: application-data
      name: Данные приложений
      path: /srv/applications
      restore_roots:
        - /srv/restore
        - /mnt/incident-restore
```

`id` должен быть уникальным, а `path` и каждый элемент `restore_roots` —
абсолютными путями. Исходный `path` и фактические пути восстановления не
возвращаются через API: web получает только имя, ID и число доступных целей.
В задании сохраняются ID корня, относительные include-пути и exclude-glob,
поэтому запрос не может подменить allowlist произвольным путём.

Canonical path каждой операции обязан оставаться внутри выбранного корня.
Symlink сохраняется как ссылка и не обходится; при восстановлении существующий
файл по умолчанию не перезаписывается. Разрешение `overwrite` задаётся явно в
конкретном запросе, но всё равно не позволяет выйти из `restore_roots`.

В Docker эти каталоги должны быть отдельно смонтированы в контейнер с теми же
путями, которые указаны в YAML, например:

```yaml
services:
  ovirt-backup:
    volumes:
      - /srv/applications:/srv/applications:ro
      - /srv/restore:/srv/restore
```

Исходный корень разумно монтировать read-only. После изменения `file_backup` или
Docker mounts требуется пересоздать контейнер; runtime-редактирование allowlist
намеренно не поддерживается.

## Хранилища копий

Хранилища не задаются в YAML: они хранятся в PostgreSQL, потому что их
добавляют и правят на ходу, а пароли и ключи лежат зашифрованными на
`secrets.key_file`. Настраиваются они в **Хранилища → Добавить хранилище** или
через `POST /api/v1/storages`.

| Тип | Обязательные поля | Свободное место |
|---|---|---|
| `local` | `base_path` | `statfs`, всегда |
| `s3` | `endpoint`, `bucket`, `access_key`, `secret_key` | не сообщается протоколом |
| `smb` | `host`, `share`, `username`, `password` | у шары, всегда |
| `webdav` | `endpoint`, `username`, `password` | свойства квоты RFC 4331, если сервер их отдаёт |
| `sftp` | `host`, `username`, и `password` или `private_key` | расширение `statvfs`, если поддерживается |

Необязательные поля: `base_path` — каталог внутри шары или коллекции,
`domain` — домен Active Directory для SMB, `port` — если он не 445 для SMB и не
22 для SFTP, `insecure_tls` — не проверять сертификат WebDAV, `rate_limit` —
предел записи в байтах в секунду.

Секретные поля наружу не возвращаются. При правке пустое значение означает
«оставить прежнее»: иначе смена любого другого поля требовала бы вводить пароль
заново.

`insecure_tls` допускается только для WebDAV и нужен для NAS с самоподписанным
сертификатом. Пока проверка отключена, соединение можно подменить.

Служба сама подключается к SMB и WebDAV; монтировать их на хосте не нужно.
Смонтированная шара по-прежнему работает как `local` — это разумно там, где она
уже смонтирована для других задач. Подробнее, вместе с разбором частых отказов,
— в разделе «Сетевые хранилища: SMB и WebDAV» руководства по эксплуатации.

## Репликация, Object Lock и аварийная готовность

```yaml
backup:
  replication_workers: 2

disaster_recovery:
  enabled: true
  postgres_dump_path: /var/backups/ovirt-backup/postgres
  postgres_dump_max_age: 24h
  secret_key_backup_path: /var/backups/ovirt-backup/secret.key
  check_interval: 1h
```

`backup.replication_workers` задаёт число фоновых передач. Очередь находится в
PostgreSQL; уменьшение или перезапуск процесса не теряет незавершённые объекты.
Изменение параметра требует перезапуска службы.

Лимит записи задаётся у конкретного хранилища в web в МиБ/с. В API и PostgreSQL
поле `rate_limit` хранится в байтах в секунду; `0` означает отсутствие лимита.
Один ограничитель разделяется всеми параллельными потоками данного backend.
Для server-side copy между префиксами одного S3 endpoint лимит не применяется,
поскольку тело объекта не проходит через сервис.

`disaster_recovery` ничего не копирует. Внешний планировщик должен регулярно
создавать `pg_dump` и байт-в-байт копировать активный `secrets.key_file` в другой
контур. Сервис проверяет свежесть и непустой размер дампа, чтение и права `0600`,
а для ключа ещё и совпадение SHA-256. Путь дампа может указывать на файл или на
каталог: в каталоге проверяется самый новый обычный файл.

Для S3 флаг Object Lock включается у конкретного хранилища через web. Требуется
bucket, созданный с поддержкой Object Lock, и срок `1..36500` дней. Используется
режим Governance. Служебная health-проба и staging не блокируются; финальные
объекты публикуются с retention только после проверки переданных данных.

Пути DR не должны находиться в том же файловом разделе, контейнерном томе или
S3 bucket, что основная инсталляция. Для systemd дайте пользователю `jhvirt`
право чтения файлов и каталогов, не расширяя права самих файлов выше `0600`.
