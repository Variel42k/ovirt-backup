# REST API

База: `/api/v1`. Ответы — JSON в UTF-8. Коллекции обёрнуты в `{"items": [...], "total": N}`.

## Аутентификация

Сессионная cookie после `POST /auth/login` либо токен доступа в заголовке
`Authorization: Bearer <token>` — см. [Токены доступа](#токены-доступа).

Cookie называется `jhvirt_session`, имеет `HttpOnly`, `SameSite=Lax`, путь `/`
и срок из `auth.session_ttl`. Флаг `Secure` включается, если собственный TLS
приложения активен или `server.external_url` начинается с `https://`.
`X-Forwarded-Proto` сам по себе этот выбор не меняет: внешний URL является
явным production-контрактом оператора.

```bash
curl -c cookies.txt -X POST http://localhost:8080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"local-admin","password":"…"}'

curl -b cookies.txt http://localhost:8080/api/v1/dashboard
```

Для проверки входа всегда выполняйте второй запрос. Login `200` ещё не
доказывает, что браузер вернёт cookie. Если приложение настроено на HTTPS, но
страница открыта по HTTP, Secure-cookie будет отброшена и `/auth/me` ответит
`401`. Пошаговое исправление:
[TROUBLESHOOTING.md](TROUBLESHOOTING.md#пароль-принят-но-снова-появляется-форма-входа).

### Роли и права

Матрица прав по разделам, встроенные роли и настройка своих — в
[ROLES.md](ROLES.md). Здесь — механика для того, кто пишет клиента.

Доступ решается **правом**, а не именем роли. Право имеет вид
`раздел.действие`, например `jobs.write`. Роль — именованный набор прав.

`GET /auth/me` возвращает права вошедшего:

```json
{
  "username": "operator1",
  "role": "operator",
  "permissions": ["servers.read", "jobs.read", "jobs.write", "…"],
  "can_write": true,
  "can_administer": false
}
```

`can_write` и `can_administer` оставлены для уже написанных скриптов и выведены
из прав, а не из имени роли: у настраиваемой роли имя произвольное, и сравнение
с `admin` соврало бы для любой из них.

Действий четыре:

| Действие | Что открывает |
|---|---|
| `read` | видеть раздел и его содержимое |
| `write` | повседневные действия: запустить, отменить, подтвердить |
| `admin` | то, что настраивается однажды: подключения, хранилища, параметры |
| `disruptive` | обрыв чужой работы без остановки гостевой ОС |

Четвёртое существует ровно для одного права — `servers.disruptive`. Им закрыты
сброс ВМ и перезагрузка хоста по питанию: фенсинг уносит все машины на хосте
разом, и складывать его в `servers.write` рядом с «запустить ВМ» значит выдавать
оба права одному человеку, когда нужно только первое.

Проверяется оно **внутри обработчика**, а не на маршруте: у всех действий над
ВМ один адрес, и какое из них разрушительное, видно только из тела запроса.
Отказ называет недостающее право.

Тем же правом закрыт и `POST /remediations`: ручное восстановление приводит к
тем же вызовам движка, и без проверки право обходилось бы запросом туда.

Три роли встроены и живут в коде, а не в базе: `admin`, `operator`, `viewer`.
Их набор прав в точности повторяет то, что эти роли могли до появления прав.
Встроенные нельзя удалить или переименовать — на них ссылаются учётные записи и
сопоставление групп у провайдера. Держать их в коде нужно ещё и потому, что
новый раздел добавляет новое право, и администратор должен получить его сразу:
роль, записанная в базу при установке, о нём не узнала бы, и раздел оказался бы
закрыт для всех.

| Метод | Путь | Требует |
|---|---|---|
| `GET` | `/permissions` | `users.admin` |
| `GET` | `/roles` | `users.admin` |
| `POST` | `/roles` | `users.admin` |
| `PUT` | `/roles/{id}` | `users.admin` |
| `DELETE` | `/roles/{id}` | `users.admin` |

`GET /permissions` отдаёт каталог: разделы, права, названия и подсказки. Из него
строится редактор ролей — второй список прав в интерфейсе разошёлся бы с этим.

```bash
curl -b cookies.txt -X POST http://localhost:8080/api/v1/roles \
  -H 'Content-Type: application/json' \
  -d '{
        "name": "backup-operator",
        "title": "Оператор резервного копирования",
        "permissions": ["jobs.read", "jobs.write", "backups.read", "backups.write"]
      }'
```

Имя роли — строчные латинские буквы, цифры, дефис и подчёркивание; оно
подставляется в `users.role`, в `auth.oidc.role_mapping` и в токены доступа.
Переименовать роль нельзя: ссылки на неё указывали бы на роль, которой больше
нет, и права исчезли бы без сообщения. Удалить роль, назначенную кому-то, тоже
нельзя — сначала переведите эти учётные записи на другую.

Права роли применяются сразу после правки: кеш сбрасывается, а не ждёт своего
срока. Правят роль чаще всего затем, чтобы доступ **отобрать**.

Отказ называет недостающее право:

```json
{"error": "недостаточно прав для этой операции: требуется jobs.write", "code": "forbidden"}
```

Скрывать его нечего — право есть в каталоге, — а разбор «почему у меня 403» без
него превращается в переписку с администратором.

### Выключатель управления

Управление ВМ и хостами отключается целиком настройкой `management.enabled`
(см. [CONFIGURATION.md](CONFIGURATION.md#управление-виртуализацией-как-выключить)).
При `false` действия над ВМ, действия над хостами и ручное восстановление
отвечают **403** с кодом `management_disabled`, а робот авто-восстановления не
запускается. Бэкап, восстановление и чтение инвентаря продолжают работать.

Состояние выключателя интерфейс узнаёт из `GET /meta`, поле
`capabilities.management_enabled`.

### Карантин удаления

`DELETE /backups/{id}` не стирает данные сразу. Копия помечается удалённой и
исчезает из рабочих списков, но объекты остаются в хранилище до срока
`backup.purge_delay` (по умолчанию 72 часа):

```jsonc
{ "status": "quarantined", "purge_after": "2026-08-26T04:12:07Z" }
```

Ответ различает карантин и стирание намеренно: `deleted` там, где данные ещё
целы, заставило бы оператора думать, что место освободилось.

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/backups/trash` | копии в карантине — те, что ещё можно вернуть |
| `POST` | `/backups/{id}/undelete` | вернуть копию из карантина |
| `DELETE` | `/backups/{id}?purge=true` | стереть данные немедленно, минуя карантин |

Смысл в промежутке: удаление копий делают перед тем, как зашифровать
инфраструктуру, и секунд между командой и потерей истории слишком мало, чтобы
кто-то успел вмешаться. За трое суток ошибку замечают, а удаление успевает
попасть и в журнал аудита, и в оповещения.

Что нужно знать:

- **Карантин занимает место.** Прогноз ёмкости его пока не вычитает.
- **Вернуть можно только пока данные целы.** После стирания `undelete` отвечает
  отказом: возвращать нечего.
- **Зависимости проверяются до карантина, а не после.** Инкремент без опорной
  точки не восстанавливается, и узнавать об этом через трое суток, когда данные
  уже стёрты, — худший из вариантов.
- **`backup.purge_delay: 0` отключает карантин**, и удаление снова становится
  необратимым.

### Согласование опасных действий

Утечка одной учётной записи не должна давать возможности уничтожить копии.
Часть действий поэтому требует подписи второго человека.

| Уровень | Правило | Действия |
|---|---|---|
| `quorum` | несколько подтверждений до выполнения | удаление хранилища, смена его цели, отключение вывода аудита, правка самой политики |
| `veto` | одно подтверждение, выполнение через окно отмены | применение политики хранения, удаление задания и подключения |
| `audit` | выполняется сразу, остаётся в журнале | удаление одной копии, ручное восстановительное действие |

Опасный запрос без заявки возвращает **202** и ничего не выполняет:

```bash
curl -b cookies.txt -X DELETE \
  'http://localhost:8080/api/v1/storages/<id>?reason=хранилище+выведено+из+эксплуатации'
```

```jsonc
{
  "status": "approval_required",
  "request": { "id": "…", "state": "pending", "quorum": 2, "summary": "удаление хранилища «Ночные копии», в нём 412 копий" },
  "approver_group": "approvers"
}
```

Обоснование обязательно: не короче 10 символов для заявки и 20 для аварийного
обхода. Заявка без объяснения подтверждается не глядя.

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/approvals?include_closed=` | заявки |
| `POST` | `/approvals/{id}/vote` | `{"approve":true}` — голос; инициатор за себя не голосует |
| `POST` | `/approvals/{id}/cancel` | отозвать заявку; для `scheduled` это вето |
| `GET` | `/approval-actions` | каталог действий и действующие политики (`users.admin`) |
| `PUT` | `/approval-policies` | изменить политику — само проходит согласование |
| `GET/POST/PUT/DELETE` | `/approval-groups` | группы согласующих (`users.admin`) |
| `GET` | `/break-glass` | история выполнений в обход (`audit.read`) |
| `GET` | `/approval-delegations?all=` | делегирования, где вы участвуете; `all=true` — все (`users.admin`) |
| `POST` | `/approval-delegations` | передать своё право голоса на время |
| `POST` | `/approval-delegations/{id}/revoke` | отозвать делегирование |

После сбора кворума действие выполняется повторным запросом со ссылкой на
заявку:

```bash
curl -b cookies.txt -X DELETE 'http://localhost:8080/api/v1/storages/<id>?approval=<request-id>'
```

**Смена цели хранилища решается по содержимому запроса.** `PUT /storages/{id}`
проходит сразу, когда меняются название, описание или ограничение полосы, и
требует кворума, когда меняются тип, адрес, каталог, узел, порт, bucket,
префикс, шара, домен, пользователь или учётные данные. Под одним адресом живут
две разные операции: увод копий в другое место и переименование, — и кворум за
переименование сделал бы согласование помехой вместо защиты.

Описание заявки перечисляет, что именно меняется («каталог: «/mnt/old» →
«/mnt/new»»), но **не содержит секретов** — ни старых, ни новых: заявка живёт в
базе и уходит в оповещения, то есть ключ оказался бы сразу в двух местах,
откуда его не отозвать. Замена учётных данных отмечается словами.

**Заявка привязана к действию и объекту.** Подтверждение на удаление одного
хранилища не разрешает удалить другое — иначе достаточно было бы согласовать
удаление пустого и подставить в адрес идентификатор боевого.

Четыре правила, которые стоит знать:

- **Один голос «против» закрывает заявку.** Согласование существует, чтобы
  кто-то мог остановить действие, а не чтобы набрать большинство.
- **Истечение срока не выполняет действие.** Заявка переходит в `expired`.
  Иначе достаточно было бы дождаться отпуска согласующих. Окно вето — другое
  дело: там подтверждение уже собрано, и молчание означает согласие.
- **Резервная группа.** Если кворум не собран за отведённое время, а в политике
  задана `fallback_group_name`, заявка передаётся ей и срок продлевается.
- **Пока группа согласующих не заведена, действия выполняются без
  согласования** — иначе завести её было бы нельзя. В журнале аудита это видно
  пометкой `<действие>.unguarded`.

#### Что происходит после окна вето

На уровне `veto` заявка переходит в `scheduled`, а когда окно отмены выходит —
действие **выполняется само**. Пока его доводил человек повторным запросом,
окно работало наполовину: о забытой заявке никто не вспоминал, ретенция не
применялась, а согласующие были уверены, что всё прошло.

Выполняется не воспроизведением HTTP-запроса, а вызовом того же кода, что и
обработчик. Хранить тело запроса ради повтора значило бы складывать в базу и
секреты из него, а подделывать запрос с чужой сессией — заводить внутри службы
способ действовать от чужого имени.

| Действие | Доводится само |
|---|---|
| `job.delete`, `server.delete` | да — хватает идентификатора объекта |
| `retention.apply` | да — параметры (сервер, ВМ, хранилище, политика) сохраняются в заявке; секретов среди них нет |
| действия уровня `quorum` | нет: там подтверждение собирает человек, он же и выполняет |

В журнале аудита такое действие записано на актора **`служба`**, а не на того,
кто подтвердил: он нажал кнопку сутки назад и в момент выполнения ничего не
делал.

Если выполнить не удалось, заявка **не закрывается**: причина попадает в поле
`error`, поднимается оповещение `approval_failed`, и попытка повторяется через
15 минут. Молча пропавшее действие, которое все считают выполненным, хуже
отказа. Исключение — объект, которого уже нет: значит, кто-то довёл дело
руками, и заявка закрывается выполненной.

#### Делегирование права голоса

Согласующий уезжает — кворум перестаёт собираться, и работа встаёт до его
возвращения. Резервная группа помогает лишь отчасти: она включается по
таймауту, то есть после того, как заявка уже провисела положенное время.
Делегирование закрывает случай, когда об отсутствии известно заранее.

```bash
curl -b cookies.txt -X POST http://localhost:8080/api/v1/approval-delegations   -d '{"delegate":"ivanov","ttl_hours":336,"reason":"отпуск до 12-го","password":"…"}'
```

```jsonc
{
  "delegation": { "id": "…", "delegator": "petrov", "delegate": "ivanov",
                  "expires_at": "2026-09-06T09:00:00Z" },
  "token": "jhvd.AbCdEfGh.…",
  "warning": "Токен показывается один раз…"
}
```

Делегат голосует, добавив к обычному запросу два поля:

```bash
curl -b delegate-cookies.txt -X POST http://localhost:8080/api/v1/approvals/<id>/vote   -d '{"approve":true,"delegation_token":"jhvd.…","delegation_password":"…"}'
```

Устройство выбрано так, чтобы делегирование не стало обходным путём вокруг
самого согласования:

| Правило | Зачем |
|---|---|
| Передаёт только сам согласующий, за другого — нельзя | иначе администратор собирает себе кворум из делегатов |
| Делегат назван поимённо и сначала входит под собой | токен, работающий у любого, кому его переслали, — обычный общий пароль |
| К токену нужен отдельный пароль, передаваемый другим каналом | перехваченный токен сам по себе бесполезен |
| Срок обязателен, не больше 30 суток | бессрочная передача права голоса — это вторая учётная запись у того же человека |
| Голос засчитывается делегирующему, а не делегату | иначе один человек с двумя делегированиями закрывает кворум в одиночку |
| Инициатор не подтверждает свою заявку и по делегированию | проверка «не голосуй за себя» смотрит на того, чей голос, и такое пропустила бы |

В журнале аудита делегированный голос называет обоих: `approval.vote` с
пометкой «по делегированию от X, подал Y». Строка «проголосовал X», когда X в
отпуске, — это начало разбора инцидента, которого не было.

Отказ при проверке делегирования всегда один и тот же — **403** без объяснения
причины. «Токен просрочен» и «неверный пароль» — два разных ответа, из которых
складывается перебор: первый подтверждает, что токен существует. Владелец
настоящего токена видит своё делегирование в списке и причину знает.

Истёкшие делегирования остаются видимыми ещё неделю, потом убираются: «почему у
меня перестало работать» спрашивают в тот же день.

#### Оповещения о заявках

Новая заявка поднимает оповещение `approval_pending`, выполнение в обход —
`break_glass_used` (важность `critical`). Оба адресованы `security` — отдельной
ленте «Доступ и согласование», чтобы сообщение о попытке удалить хранилище не
терялось среди предупреждений о свободном месте.

В подробностях оповещения есть **прямая ссылка на заявку** вида
`<external_url>/settings?tab=approvals&approval=<id>`. Она открывает нужную
заявку после входа, но сама ничего не выполняет и без входа не пускает:
одноразовый токен в адресе дал бы отмену в один клик ценой того, что право вето
осело бы в журналах почтового сервера, прокси и в истории браузера.

Оповещения идут по обычным каналам — почта, Telegram, webhook, — и закрываются
сами при любом исходе заявки, включая истечение срока. Это не украшение:
заявка, о которой согласующие не узнали, доживает до таймаута и закрывается, а
согласование превращается в способ не дать сделать работу.

#### Аварийный доступ

```bash
curl -b cookies.txt -X DELETE \
  'http://localhost:8080/api/v1/storages/<id>?break_glass=true&reason=инцидент+INC-42,+согласующие+недоступны'
```

Запретить обход нельзя: согласующие бывают недоступны, а действие нужно сейчас.
Смысл в том, что тихо им воспользоваться невозможно — событие попадает в
`/break-glass`, в журнал аудита пометкой `<действие>.break_glass` и в список
оповещённых заносятся все согласующие.

### Токены доступа

Для интеграций, которые не могут держать cookie: скриптов, систем мониторинга,
соседних служб. Выпускает и отзывает их администратор.

| Метод | Путь | Кто |
|---|---|---|
| `GET` | `/api-tokens` | admin |
| `POST` | `/api-tokens` | admin |
| `PUT` | `/api-tokens/{id}` | admin |
| `DELETE` | `/api-tokens/{id}` | admin |

```bash
curl -b cookies.txt -X POST http://localhost:8080/api/v1/api-tokens \
  -H 'Content-Type: application/json' \
  -d '{"name":"prometheus","role":"viewer","expires_in_days":90}'
```

```json
{
  "id": "…", "name": "prometheus", "prefix": "8xKf2Qn1",
  "role": "viewer", "expires_at": "2026-11-20T…", "disabled": false,
  "token": "jhv.8xKf2Qn1.EhT9…"
}
```

**Поле `token` возвращается один раз.** В базе хранится только хеш секретной
части, восстановить по нему выданное нельзя. Потерян — выпускайте новый.

Вид токена — `jhv.<префикс>.<секрет>`. Префикс лежит в базе открытым: по нему
строка находится по индексу, и лишь потом сверяется секрет. Он же делает токен
узнаваемым — по `jhv.` его находят и в журнале, и в репозитории, куда он
однажды попадёт по недосмотру.

В журнале аудита такой токен отмечается как `токен:<имя>`. Имя поэтому и
обязательно: без него запись неотличима от действия человека.

Изменить у выпущенного токена можно роль, срок и признак отключения. Секрет —
нельзя: это выпуск нового токена, и выглядеть он должен как выпуск нового.

```bash
# отозвать, не удаляя (история использования останется)
curl -b cookies.txt -X PUT http://localhost:8080/api/v1/api-tokens/<id> \
  -H 'Content-Type: application/json' -d '{"disabled":true}'
```

В `expires_in_days` значение `0` означает «бессрочно», отрицательное — «снять
ранее заданный срок». Поле `last_used_at` обновляется не чаще раза в минуту:
опрашивающий монитор иначе превращал бы каждую проверку токена в запись в базу.

#### Токены из файла настроек устарели

Список `auth.api_tokens` продолжает работать ради уже настроенных интеграций,
но каждый такой токен даёт права администратора, не имеет срока, отзывается
только перезапуском службы и в аудите отмечается как `api-token (файл
настроек)` — без различения между собой. Служба предупреждает об этом при
каждом старте, пока список не пуст.

### Внешний вход (OIDC)

Три точки, доступные без сессии:

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/auth/oidc/info` | `{"enabled":bool,"button_label":string,"local_login":bool}` — что показывать на странице входа |
| `GET` | `/auth/oidc/start` | перенаправление к провайдеру; `?redirect=/путь` задаёт, куда вернуть после входа |
| `GET` | `/auth/oidc/callback` | возврат от провайдера; при успехе выдаёт ту же `jhvirt_session` |

Проходить их нужно браузером: это цепочка перенаправлений, и XHR отработает её
молча и без результата. Ошибка возвращает на `/login?oidc_error=<причина>`,
подробности остаются в журнале службы.

`POST /auth/logout` у сессии, заведённой через провайдера, возвращает
`{"status":"ok","logout_url":"…"}` — по этому адресу интерфейс уводит браузер,
чтобы закрылась и сессия провайдера. У входа по паролю поля нет.

`start` и `callback` защищены `state`, `nonce` и PKCE (S256); начатый вход
живёт 10 минут и используется один раз. Подпись токена проверяется по JWKS
провайдера.

Когда `auth.oidc.allow_local_login: false`, `POST /auth/login` отвечает `403`
с кодом `local_login_disabled`. Токены из `auth.api_tokens` при этом
продолжают работать.

Настройка провайдера и правила назначения ролей:
[CONFIGURATION.md](CONFIGURATION.md#внешний-вход-oidc).

## Ошибки

```json
{ "error": "человекочитаемое сообщение", "code": "not_found" }
```

| Код | HTTP | Смысл |
|---|---|---|
| `unauthorized` | 401 | нет сессии или она истекла |
| `csrf_origin_required` | 403 | браузерный запрос с cookie не передал Origin |
| `csrf_origin_denied` | 403 | Origin не совпадает с `external_url` и CORS allowlist |
| `too_many_attempts` | 429 | слишком много неудачных входов подряд |
| `forbidden` | 403 | роли недостаточно |
| `local_login_disabled` | 403 | вход по паролю выключен, остаётся внешний провайдер |
| `oidc_disabled` | 404 | внешний вход не настроен |
| `bad_request` | 400 | некорректный запрос |
| `not_found` | 404 | объект не найден |
| `conflict` | 409 | нарушение уникальности |
| `job_busy` | 409 | задание ещё выполняется с прошлого раза |
| `engine_auth` | 502 | движок отверг наши учётные данные |
| `engine_not_found` | 404 | движок не знает такой объект |
| `engine_conflict` | 409 | движок отказал: объект в неподходящем состоянии |
| `internal` | 500 | необработанная ошибка; подробности в журнале службы |

`too_many_attempts` сопровождается заголовком `Retry-After` с числом секунд.
Пауза растёт с каждой неудачей до 15 минут и считается по учётной записи, а не
по адресу: адрес берётся из `X-Forwarded-For`, который подделывается. Успешный
вход обнуляет счётчик.

`job_busy` — не поломка, а состояние: предыдущий запуск задания не закончился.
Интерфейсу стоит показывать его именно так, а не как ошибку.

## Runtime-настройки

Все методы раздела требуют роль `admin`. Настройки сохраняются в PostgreSQL и
применяются без перезапуска процесса.

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/settings/runtime` | эффективные значения и их источник |
| `PUT/DELETE` | `/settings/runtime/compression` | задать алгоритм или вернуть конфигурационный |
| `PUT/DELETE` | `/settings/runtime/timezone` | задать системную IANA-зону или вернуть конфигурационную |
| `PUT/DELETE` | `/settings/runtime/log-rotation` | задать политику ротации или вернуть конфигурационную |

```jsonc
// PUT /settings/runtime/compression
{ "compression": "gzip" } // zstd|gzip|s2|none

// PUT /settings/runtime/timezone
{ "timezone": "Asia/Yekaterinburg" }

// PUT /settings/runtime/log-rotation
{ "max_size_mb": 200, "max_backups": 14, "max_age_days": 60 }

// GET и ответы PUT/DELETE
{
  "compression": {
    "value": "gzip", "level": 3, "source": "database",
    "options": [
      { "value": "zstd", "title": "ZSTD", "description": "…" },
      { "value": "gzip", "title": "GZIP", "description": "…" },
      { "value": "s2", "title": "S2", "description": "…" },
      { "value": "none", "title": "NONE", "description": "…" }
    ]
  },
  "timezone": {
    "value": "Asia/Yekaterinburg", "source": "database"
  },
  "log_rotation": {
    "max_size_mb": 200, "max_backups": 14,
    "max_age_days": 60, "source": "database"
  }
}
```

`DELETE` удаляет переопределение и возвращает значения из YAML/окружения.
Сжатие меняется только для новых запусков; активный запуск использует алгоритм,
зафиксированный при старте. `compression_level` через этот API не изменяется.
Смена часового пояса немедленно пересчитывает будущие точки всех cron-заданий,
но не отменяет и не перезапускает уже выполняющиеся бэкапы. Эта же зона используется web,
отчётами, уведомлениями и журналом; открытые web-сессии получают SSE-событие
`settings.changed`. Неизвестная IANA-зона возвращает `400`.

### Безопасное подключение

`POST /servers/provision` (право `servers.admin`) подключает движок так, чтобы
административная учётная запись **не сохранялась**. Она используется один раз:
под ней создаётся роль с минимальным набором прав и выдаётся отдельной
сервисной записи, под которой служба и работает дальше.

```bash
curl -b cookies.txt -X POST http://localhost:8080/api/v1/servers/provision \
  -H 'Content-Type: application/json' \
  -d '{
        "name": "Прод",
        "engine_url": "https://engine.example.org",
        "admin_username": "admin@internal", "admin_password": "…",
        "service_username": "jhvirt-backup@internal", "service_password": "…"
      }'
```

Ответ — отчёт по шагам плюс проверка доступа уже под сервисной записью:

```jsonc
{
  "ok": true,
  "steps": [
    { "step": "подключение администратором", "ok": true, "note": "движок 4.5.5" },
    { "step": "роль jhvirt-backup", "ok": true, "note": "создана" },
    { "step": "назначение роли", "ok": true, "note": "на уровне системы" }
  ],
  "access": { "ready": true, "checks": [ { "what": "чтение дисков виртуальной машины", "ok": true, "required": true } ] },
  "server_id": "…"
}
```

**Сервисную запись служба не создаёт и создать не может.** Движок
пользователями не управляет — они приходят из домена аутентификации; во
встроенном домене запись заводится на самом движке:

```bash
ovirt-aaa-jdbc-tool user add jhvirt-backup
ovirt-aaa-jdbc-tool user password-reset jhvirt-backup
```

Без `password-reset` войти под ней нельзя. Через REST служба лишь показывает
движку уже существующего пользователя домена и выдаёт ему права.

Состав прав роли задаётся полем `permits`; без него берётся набор по умолчанию.
Он **предварительный**: состав групп действий у разных версий движка
отличается, поэтому итог проверяется не документацией, а разделом `access` в
ответе — он показывает, что под этой ролью реально получается. `ready: false`
означает, что подключение не сохранено и чего-то не хватает.

### Предупреждение о лишних правах

`POST /servers/probe` возвращает поле `excess_privileges`, когда учётная запись
может больше, чем нужно для резервного копирования:

```jsonc
{
  "ok": true, "product_name": "oVirt Engine", "version": "4.5.5",
  "excess_privileges": [
    { "what": "управление пользователями движка",
      "why": "учётная запись видит список пользователей — значит может и раздавать права" }
  ]
}
```

Определяется фактом, а не по имени: административную запись называют как
угодно, а безобидное имя может нести роль уровня системы. Подключение при этом
не запрещается — но пароль такой записи ляжет в базу службы и будет годиться
для любых действий с виртуализацией, включая те, которых в интерфейсе нет.

## Хранилища

| Метод | Путь | Описание |
|---|---|---|
| `GET/POST` | `/storages` | список, создать (admin) |
| `GET/PUT/DELETE` | `/storages/{id}` | получить, изменить, удалить |
| `POST` | `/storages/{id}/check` | проверка записи и чтения |

Секреты (`secret_key`, `password`, `private_key`) принимаются, но никогда не
возвращаются. Удаление хранилища с живыми бэкапами требует `?force=true`.

Поле `kind` принимает `local`, `s3`, `smb`, `webdav`, `sftp`. Обязательные поля
каждого типа перечислены в разделе «Хранилища копий» документа по конфигурации;
список типов с названиями и описаниями отдаёт `GET /meta`, и интерфейс строит
форму по нему. Для `smb` заполняются `host`, `share`, `username`, `password` и
необязательные `domain`, `port`, `base_path`; для `webdav` — `endpoint`,
`username`, `password` и необязательные `base_path`, `insecure_tls`. Флаг
`insecure_tls` принимается только для `webdav`, `object_lock_enabled` — только
для `s3`.

Поле `rate_limit` задаёт общий предел потоковой записи в байтах в секунду для
всех одновременных операций с экземпляром хранилища; `0` снимает ограничение.
Предел применяется ко всем типам хранилищ. Нативный server-side copy внутри одного
S3 endpoint не передаёт данные через сервис и потому этим пределом не замедляется.

## Задания

| Метод | Путь | Описание |
|---|---|---|
| `GET/POST` | `/jobs` | список, создать |
| `GET/PUT/DELETE` | `/jobs/{id}` | получить, изменить, удалить |
| `POST` | `/jobs/{id}/run` | запустить немедленно |
| `GET` | `/jobs/{id}/preview` | какие ВМ попадают под отбор и почему |

```jsonc
{
  "name": "Ночной инкремент",
  "server_id": "…",
  "vm_ids": [],
  "vm_name_regex": "^(prod|infra)-",
  "cluster_ids": ["…"],
  "tags": ["critical"],             // положительные условия объединяются через OR
  "exclude_vm_ids": ["…"],          // исключения применяются первыми
  "exclude_disk_ids": ["…"],        // пустой selector — все ВМ сервера
  "type": "incremental",
  "full_every": 7,
  "fallback_type": "snapshot",        // если CBT недоступен
  "schedule": "0 1 * * *",
  "storage_target_ids": ["…"],
  "storage_mode": "copy",             // copy|parallel|separate
  "priority": 10,                      // больше — раньше в персистентной очереди
  "concurrency": 2,                    // предел только для этого задания
  "retention": { "keep_last": 3, "keep_daily": 7, "keep_weekly": 4, "keep_monthly": 6 },
  "quiesce": true,
  "export_qcow2": true,
  "verify_after": "boot",
  "verify_options": {
    "boot_host_id": "…",             // включённое подключение типа kvm
    "memory_mib": 0, "vcpus": 0,   // 0 — ресурсы исходной ВМ
    "timeout_sec": 300, "keep_on_failure": false
  },
  "encrypt": false
}
```

Для legacy-клиентов принимается `replication_enabled`: `true` соответствует
`storage_mode: "copy"`. В новых клиентах источником истины служит
`storage_mode`: `copy` снимает одну основную копию и ставит остальные в очередь,
`parallel` пишет доступные цели одновременно и дозаписывает отказавшие,
`separate` независимо читает источник для каждого хранилища.

У задания типа `ova` вместо `storage_target_ids` обязательны `ova_host_id` и
`ova_directory`. OVA остаётся внешним артефактом на гипервизоре, не участвует в
обычной репликации и ретенции. `export_qcow2` относится к управляемым артефактам
обычного бэкапа; до запуска проверяется наличие `qemu-img`.

```jsonc
{ "target": "disk", "target_disk_id": "…", "confirm": true }   // затирает диск

// POST /backups/{id}/restore-vm/plan и /restore-vm
// storage_domain_id означает storage domain для oVirt и storage pool для KVM.
// Неуказанные NIC по умолчанию создаются отключёнными, MAC всегда новый.
{
  "server_id": "…", "name": "vm-restored", "cluster_id": "…",
  "storage_domain_id": "…", "start": false,
  "network_mappings": [
    { "nic_id": "nic-1", "target_kind": "vnic_profile",
      "target_id": "…", "connected": false },
    { "nic_id": "nic-2", "exclude": true }
  ]
}
```

Каталог восстановления ограничен списком не из осторожности вообще: путь задаёт
клиент, а результат — образ на десятки гигабайт, то есть без списка любой
оператор мог бы заполнить раздел с базой или положить файл в каталог
конфигурации. Проверка выполняется до ответа, поэтому запрещённый каталог
виден сразу, а не всплывает как «восстановление не выполнено».

Удаление отклоняется, если от точки зависят более поздние инкременты.

Полное восстановление поддерживает oVirt→oVirt и KVM→KVM. Межплатформенная
конвертация не выполняется. Preview возвращает `warnings`, `blockers`, диски,
NIC и оценку места. Для старых точек недостающие части профиля восстанавливаются
по исходному oVirt JSON или libvirt XML с предупреждением. При ошибке служба
откатывает созданные ресурсы; неполная очистка остаётся в поле ошибки запуска.
Конфигурационная точка может создать ВМ без дисков, но автоматический запуск в
этом случае запрещён.

## Нативный файловый бэкап

Функция доступна всегда. Клиент выбирает ID именованного корня и относительные
пути; абсолютный исходный путь через API передать нельзя. Если roots не заданы,
служба публикует корень `default` для `file-sources` рабочего каталога.

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/file-backup/roots` | доступные именованные корни; поле `enabled` всегда `true` для совместимости |
| `GET/POST` | `/file-backup/jobs` | список и создание файловых заданий |
| `GET/PUT/DELETE` | `/file-backup/jobs/{id}` | получить, изменить или удалить задание |
| `POST` | `/file-backup/jobs/{id}/run` | запустить; ответ `202` содержит запуск |
| `GET` | `/file-backup/runs?job_id={id}&limit=100` | точки файлового бэкапа |
| `GET/DELETE` | `/file-backup/runs/{id}` | получить или удалить точку с данными |
| `GET` | `/file-backup/runs/{id}/tree` | manifest и дерево файлов |
| `POST` | `/file-backup/runs/{id}/restore` | восстановить набор или выбранные пути |

```jsonc
// POST /file-backup/jobs
{
  "name": "Конфигурация приложений", "enabled": true,
  "root_id": "application-data",
  "include_paths": ["config", "certificates/server.pem"],
  "exclude_globs": ["**/*.tmp", "cache/**"],
  "storage_target_ids": ["…"], "storage_mode": "copy",
  "incremental": true, "encrypt": true, "schedule": "0 3 * * *",
  "retention": { "keep_last": 3, "keep_daily": 7 }
}

// POST /file-backup/runs/{id}/restore
{
  "restore_root_index": 0, "destination": "incident-2026-08-21",
  "paths": ["config/app.yaml", "certificates"], "overwrite": false
}
```

`destination` также относительный и обязан оставаться внутри выбранного
`restore_root_index`. По умолчанию существующие файлы не перезаписываются.
Symlink хранится и восстанавливается как ссылка, но при сканировании не
обходится; canonical path не может выйти из allowlist. Изменившийся во время
чтения файл перечитывается один раз, затем точка завершается как `partial` со
списком `unstable_paths`.

### Адресат оповещения

У каждого оповещения есть поле `audience` — кому оно предназначено:

| Значение | Кому | Что попадает |
|---|---|---|
| `backup` | оператору резервного копирования | задание не прошло, копия устарела, проверка провалилась, нет CBT |
| `infrastructure` | администратору виртуализации | движок недоступен, хост завис, ВМ на паузе, домену хранения не хватает места |
| `service` | администратору самой службы | хранилище копий недоступно, кончается место, аварийная готовность нарушена |

`GET /alerts?audience=backup` отбирает по нему. Разделение нужно потому, что
одна общая лента одинаково будит и того, кто отвечает за бэкапы, и того, кто
отвечает за гипервизоры: человек, которому девять из десяти сообщений не
адресованы, перестаёт читать все десять.

Адресат **выводится из `kind`** и в базе не хранится — колонка означала бы
миграцию на каждое изменение раскладки и расхождение между старыми записями и
новыми. Раскладка живёт в `internal/model/alert_audience.go`, и тест не даёт
завести тип оповещения, который в неё не попал.

Список адресатов с названиями приходит в `GET /meta` полем `alert_audiences` —
повторять его в клиенте не нужно.

Схожие по имени типы попадают к разным людям, и это намеренно:
`storage_domain_low_space` — место в домене хранения гипервизора
(`infrastructure`), а `storage_capacity_low` — место в хранилище копий
(`service`).

```jsonc
// POST /remediations — обходит cooldown и лимит попыток
{ "server_id": "…", "scope": "vm", "object_id": "…",
  "action": "vm_start", "reason": "по заявке", "confirm": false }
```

`action`: `vm_start`, `vm_unpause`, `vm_reset`, `host_activate`, `host_fence`,
`engine_reconnect`. Разрушительные (`vm_reset`, `host_fence`) требуют
`confirm: true`.

`GET /coverage` сохранён для старых клиентов, но использует прежнюю форму
ответа. Новые клиенты должны читать `/monitoring/backup-quality`: его свежесть
рассчитывается по каждому cron-интервалу и каждой обязательной реплике.

Успешность `backup_job_runs` означает, что все выбранные ВМ и все назначенные
хранилища получили полные дочерние копии. Ответ `POST /jobs/{id}/run`:

```json
{"status":"queued","job_run_id":"…","vms":4,"replicas":8}
```

Жизненный цикл общего запуска: `running` → `waiting_copies` → `success`.
`waiting_copies` означает, что primary уже может быть пригоден, но обязательные
реплики или производные артефакты ещё не завершены. Конечные альтернативы —
`partial` и `failed`; успех primary не подменяет ими требование всех целей.

### Настройки и история уведомлений (admin)

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/settings/notifications` | эффективная глобальная настройка, per-kind policies и известные типы |
| `PUT` | `/settings/notifications` | атомарно заменить runtime-настройку и правила |
| `DELETE` | `/settings/notifications` | удалить database override и вернуться к YAML/default |

```jsonc
// PUT /settings/notifications
{
  "settings": {
    "enabled": true,
    "min_severity": "critical",
    "default_repeat_minutes": 120,
    "notify_on_resolved": true,
    "ack_stops_repeats": true,

  },

    {
      "kind": "backup_unprotected",

    }

```

`configured_channels` и `source` присутствуют в ответе, но credentials
SMTP/Telegram/webhook никогда не возвращаются и по этому API не меняются.
Пустой `channels` у policy означает все настроенные каналы. Значение
`default_repeat_minutes: 0` отключает напоминания, `max_repeats: 0` не
ограничивает их количество, если интервал ненулевой.

```jsonc
// POST /alerts/{id}/notifications
{ "action": "snooze", "until": "2026-08-22T06:00:00Z", "reason": "окно работ" }
// либо { "action": "mute", "reason": "принятый риск" }
// либо { "action": "unmute" }
```

Mute/snooze не скрывает alert в web и не меняет его state. Outbox создаёт
отдельную строку на канал и доставляет at-least-once; webhook-получатель может
дедуплицировать по `alert_id`, `event` и `sequence`.

### `/metrics`

`GET /metrics` находится вне `/api/v1` и cookie-аутентификации. При
`metrics.enabled: false` возвращается `404`. При включении нужен отдельный
заголовок:

```http
Authorization: Bearer <содержимое metrics.token_file>
```

Отсутствующий или неверный токен даёт `401`. Сравнение выполняется в постоянное
время. Endpoint не принимает `auth.api_tokens` и не выводит URL с учётными
данными, DSN, токены, cookie или ключи. Имена объектов находятся только в
`*_info`-метриках; рабочие ряды маркированы стабильными ID.

## Поток событий

`GET /events` — server-sent events. Типы: `server_state`, `inventory`, `alert`,
`remediation`, `backup_run`, `verify_run`, `restore_run`, `replication`,
`storage_target`, `job`, `settings.changed`.

```javascript
const source = new EventSource('/api/v1/events', { withCredentials: true })
source.addEventListener('alert', (e) => console.log(JSON.parse(e.data)))
```

Доставка намеренно с потерями: подписчик, переставший читать, не должен
останавливать мониторинг. После переподключения интерфейс перечитывает состояние.

| Метод | Путь | Описание |
|---|---|---|
| `GET/POST` | `/users` | список, создать (admin) |
