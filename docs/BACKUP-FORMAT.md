# Формат хранения бэкапов

Формат задокументирован намеренно: архив, который читается только одной
программой, — это заложник этой программы. Всё, что нужно для восстановления,
лежит рядом с данными, а не в базе сервиса.

## Раскладка

```
jhvirt/
└── <сервер>/
    └── <имя-вм>-<8 симв. id>/
        └── 2026/08/03/
            └── <uuid-запуска>/
                ├── run.json                       — метаданные запуска
                ├── vm-config.json                 — конфигурация oVirt ВМ на момент копии
                ├── vm-config.xml                  — исходный XML домена KVM (вместо JSON)
                ├── disk-00-<disk-id>.manifest     — карта чанков (zstd + JSON)
                ├── disk-00-<disk-id>.data         — данные
                ├── disk-01-<disk-id>.manifest
                └── disk-01-<disk-id>.data
```

Имена сегментов приводятся к ASCII: кириллица транслитерируется, остальное
заменяется дефисами. Каталог `БД-Продакшн` станет `bd-prodakshn`, и его можно
набрать в консоли любой системы.

Дата в пути — дата запуска в UTC. Она нужна человеку и позволяет ретенции
перечислять день, не листая весь bucket.

## `run.json`

Записывается последним. Его наличие означает, что бэкап завершён: незавершённый
запуск не оставляет этого файла, и по нему архив отличает целое от обрывка,
независимо от базы данных.

## Манифест диска

zstd-сжатый JSON (магия `28 B5 2F FD`; несжатый JSON тоже читается).

```json
{
  "format": "jhvirt-disk", "version": 1,
  "run_id": "…", "chain_id": "…", "parent_run_id": "…", "chain_index": 2,
  "type": "incremental",
  "disk_id": "…", "alias": "db-01_Disk1", "disk_index": 0,
  "virtual_size": 107374182400,
  "chunk_size": 4194304,
  "compression": "zstd", "encrypted": false,
  "data_key": "…/disk-00-….data",
  "data_sha256": "…",
  "logical_bytes": 809500672, "stored_bytes": 402653184,
  "chunks": [
    { "i": 0,    "l": 4194304, "b": 0,       "s": 1048576, "h": "<sha256 открытых данных>" },
    { "i": 1024, "l": 4194304, "b": 1048576, "s": 2097152, "h": "…" }
  ]
}
```

Поля чанка сокращены до одной буквы не из любви к краткости: диск на 1 ТиБ при
сетке 4 МиБ даёт 262 144 записи, и разница между короткими и длинными именами —
десятки мегабайт на манифест.

| Поле | Смысл |
|---|---|
| `i` | номер чанка в сетке; смещение в образе = `i × chunk_size` |
| `l` | логическая длина (последний чанк диска может быть короче) |
| `b` | смещение в объекте данных |
| `s` | сколько байт занято после сжатия и шифрования |
| `h` | SHA-256 **исходных** байт, hex |

## Объект данных

Чанки записаны подряд в порядке возрастания `i`. Каждый обработан независимо:
сжат алгоритмом из поля `compression` (если сжатие не дало выигрыша — записан
как есть, длины `l` и `s` совпадают) и, при включённом шифровании, запечатан
AES-256-GCM с 12-байтовым nonce в начале.

Алгоритм каждого звена читается из его манифеста, а не из текущих настроек
программы. Поэтому цепочка `full(zstd) → incremental(gzip) → incremental(s2)`
проверяется и восстанавливается как обычно. Уровень сжатия для чтения не нужен:
он влияет только на запись нового чанка.

| `compression` | когда выбирать |
|---|---|
| `zstd` | по умолчанию: плотно и быстро |
| `gzip` | когда важно, чтобы чанк распаковывался чем угодно, вплоть до `gunzip` на аварийном носителе |
| `s2` | когда узкое место процессор, а не канал: быстрее zstd, сжимает слабее |
| `none` | когда сжимает само хранилище (ZFS, дедуплицирующая СХД) |

Даже при выбранном алгоритме отдельный несжимаемый чанк хранится без сжатия.
После расшифровки читатель сравнивает размер хранимого чанка с `l`: равенство
означает исходные байты, отличие — поток кодека из манифеста. Шифрование, если
включено, остаётся последним преобразованием при записи и снимается первым.

Порядок обязателен: сжатие до шифрования. Наоборот не имеет смысла —
шифрованные байты не сжимаются.

Независимость чанков — условие того, чтобы восстановление и проверка могли
адресоваться к произвольному месту образа, а не разжимали терабайт ради
последнего блока.

`data_sha256` в манифесте — хэш всего объекта как он лежит в хранилище. Он
позволяет проверить объект одним потоковым чтением, ничего не разбирая.

## Сборка образа из цепочки

1. Взять цепочку от полного бэкапа к нужной точке (по `parent_run_id`).
2. Пройти манифесты от корня к листу, заполняя карту `номер чанка → (манифест, чанк)`.
   Более поздний запуск перекрывает более ранний.
3. Для каждого номера от `0` до `ceil(virtual_size / chunk_size) - 1`:
   - чанк есть в карте — прочитать `s` байт по смещению `b` из соответствующего
     `.data`, расшифровать, распаковать, сверить SHA-256, записать по смещению
     `i × chunk_size`;
   - чанка нет — область нулевая.

Отсутствие чанка во всей цепочке означает ноль, потому что полный бэкап
сохраняет каждый непустой экстент. Именно поэтому цепочка, у которой потерян
корень, отвергается: без него «нет чанка» перестало бы значить «ноль».

Пример на Python (без сжатия и шифрования, для наглядности):

```python
import json, zstandard, hashlib

manifests = [json.loads(zstandard.ZstdDecompressor().decompress(open(p, 'rb').read()))
             for p in chain_paths]          # от корня к листу

grid, owner = {}, {}
for idx, m in enumerate(manifests):
    for c in m['chunks']:
        grid[c['i']] = c
        owner[c['i']] = idx

size, cs = manifests[-1]['virtual_size'], manifests[0]['chunk_size']
with open('restored.raw', 'wb') as out:
    out.truncate(size)                       # разреженный файл
    for c_index, chunk in sorted(grid.items()):
        m = manifests[owner[c_index]]
        with open(m['data_key'], 'rb') as data:
            data.seek(chunk['b'])
            raw = data.read(chunk['s'])
        plain = raw if chunk['s'] == chunk['l'] else zstandard.ZstdDecompressor().decompress(raw)
        assert hashlib.sha256(plain).hexdigest() == chunk['h']
        out.seek(c_index * cs)
        out.write(plain)
```

## Совместимость версий

`version` в манифесте — версия формата. Читатель отказывается разбирать манифест
с версией новее той, что знает, вместо того чтобы догадываться. Поле `format`
отсекает чужие файлы, случайно оказавшиеся в каталоге.

`vm_profile.version` версионируется отдельно. Поля профиля добавлены совместимо:
старые копии без него по-прежнему восстанавливаются, а boot-проверка использует
ограниченный совместимый профиль. Для точного многодискового запуска снимите
новую полную точку после обновления.

Ошибки отсутствующего родителя, повреждённой цепочки и аварийное чтение без
базы описаны в [TROUBLESHOOTING.md](TROUBLESHOOTING.md#10-восстановление).

## Шифрование

При включённом шифровании каждый чанк запечатан AES-256-GCM ключом из
`secrets.key_file`. Манифест остаётся открытым: он не содержит данных ВМ, зато
позволяет разобрать архив и понять, что в нём, даже если ключ утерян.

**Ключ шифрования не восстанавливается.** Потеря `data/secret.key` означает
потерю зашифрованных бэкапов и сохранённых паролей подключений. Включайте его в
резервную копию сервиса и храните отдельно от бэкапов ВМ.

## Физические копии одной точки

`backup_runs` описывает логическую точку восстановления. Одна и та же точка
может физически присутствовать в основном хранилище и нескольких репликах. Это
не меняет `run.json`, дисковые манифесты или объект данных: зашифрованные и
сжатые объекты переносятся байт в байт без расшифрования и повторного сжатия.

Репликация перечисляет все объекты префикса запуска, кроме `run.json`, передаёт
их и полностью перечитывает назначение для сверки SHA-256. `run.json`
передаётся и проверяется последним. Поэтому наличие `run.json` означает, что
физическая копия опубликована целиком; staging и оборванные передачи не должны
интерпретироваться как точка восстановления.

Для инкремента в назначении сначала публикуется вся родительская цепочка от
полной точки к листу. Восстановление выбирает одно физическое хранилище для всей
цепочки и не смешивает звенья из разных хранилищ.
