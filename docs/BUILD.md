# Сборка

Проект собирается одной командой на любой системе, где есть Go и Node. Результат
— **один файл `.run`**: скрипт со вшитым архивом. Копируется на сервер и
запускается; распаковка и установка происходят внутри.

```bash
./run build --target linux/amd64
```

```
готово: dist/ovirt-backup-1.0.0-linux-amd64.run (14M)
```

Внутри — два статических бинаря, веб-интерфейс, конфигурация, юнит systemd и
установщик.

---

## Что нужно

| | Версия | Зачем |
|---|---|---|
| Go | 1.27+ | бинари |
| Node | 20+ | веб-интерфейс |
| tar, gzip | любые | упаковка комплекта |

Больше ничего. **Компилятор C не нужен:** cgo не используется нигде. Отсюда два
следствия: бинарь получается статическим и работает в любом дистрибутиве
независимо от версии libc, и кросс-компиляция возможна с любой платформы — собрать Linux-бинарь из-под Windows это обычный путь, а не
обходной.

`make` не требуется. Makefile в репозитории есть, но скрипты сборки на него не
опираются: make отсутствует в стандартной установке Windows и в минимальных
образах CI.

---

## Как собрать

### Под текущую платформу

```bash
./run build
```

### Под сервер

```bash
./run build --target linux/amd64    # обычный сервер
./run build --target linux/arm64    # ARM
```

### Полезные ключи

| Ключ | Что делает |
|---|---|
| `--version 1.2.0` | явная версия вместо взятой из git |
| `--skip-web` | только бинари; `web/dist` должен быть собран заранее |
| `--tar` | оставить рядом и обычный `tar.gz` |
| `--no-archive` | разложить в `dist/`, не паковать |
| `--sign-key <fingerprint>` | создать detached GPG-подпись `.run.asc` |

`./run` без аргументов покажет все команды.

Версия по умолчанию берётся из `git describe`. Суффикс `-dirty` означает, что в
рабочем каталоге есть несохранённые правки — он намеренно оставлен видимым,
чтобы «та самая сборка» не спуталась с похожей.

### Windows

`./run` работает в Git Bash (идёт вместе с Git for Windows):

```bash
./run build --target linux/amd64
```

Из PowerShell или cmd — через тот же bash:

```powershell
& "C:\Program Files\Git\bin\bash.exe" run build --target linux/amd64
```

Права на файлы в архиве не зависят от системы сборки: NTFS не хранит бит
исполнения, поэтому бинари упаковываются отдельным проходом с явным режимом
0755. Без этого распакованный на сервере бинарь не запустился бы.

## Что получается

Один файл `dist/ovirt-backup-1.0.0-linux-amd64.run` — обычный `/bin/sh`-скрипт, к
которому приклеен `tar.gz`. Скрипт находит начало архива по строке-метке,
сверяет вшитую контрольную сумму, распаковывает во временный каталог и
запускает оттуда установщик. Временный каталог удаляется всегда, включая
прерывание по Ctrl+C.

Рядом всегда создаётся `ovirt-backup-...run.sha256`. Контрольная сумма ловит
повреждение, но не доказывает происхождение, если `.run` и `.sha256` подменили
вместе. Для доверенной поставки подпишите файл закрытым ключом машины сборки:

```bash
gpg --list-secret-keys --keyid-format LONG
./run build --target linux/amd64 --sign-key B57ED08E2C217400
```

Получится `ovirt-backup-...run.asc`. На сервере сначала импортируйте только
публичный ключ сборки и проверьте оба файла, затем запускайте установщик:

```bash
sha256sum -c ovirt-backup-*.run.sha256
gpg --verify ovirt-backup-*.run.asc ovirt-backup-*.run
sudo sh ./ovirt-backup-*.run
```

В Git Bash команды пишутся без PowerShell-префикса `&`. Закрытый ключ и файл
`private-key.asc` на стенд не передаются.

Внутри архива:

```
ovirt-backup-1.0.0-linux-amd64/
├── bin/
│   ├── ovirt-backup-server     сервис с веб-интерфейсом
│   └── jvbackup                автономный CLI: бэкап, проверка, восстановление
├── web/dist/                   собранный интерфейс
├── config/ovirt-backup.yaml    конфигурация по умолчанию
├── systemd/jhvirt.service      юнит
├── compose/                    docker-compose.yml и .env.example
├── Dockerfile                  образ из готового бинаря, без Go и Node
├── docs/                       вся документация проекта
├── install.sh                  установка и обновление
└── VERSION
```

Dockerfile в комплекте не собирает проект: бинарь и интерфейс уже лежат рядом,
их собрали на машине сборки. Поэтому образ строится за секунды и на сервере не
нужны ни Go, ни Node, ни исходники.

Почему один файл, а не архив рядом со скриптом: переносится всегда целиком, а
разошедшиеся версии архива и установщика попросту невозможны.

## Установка

```bash
scp dist/ovirt-backup-1.0.0-linux-amd64.run server:/tmp/
ssh server 'sudo sh /tmp/ovirt-backup-1.0.0-linux-amd64.run'
```

Через `sh` — потому что бит исполнения не переживает файловую систему Windows.
Если собирали на Linux, `sudo ./ovirt-backup-1.0.0-linux-amd64.run` тоже работает.

Установщик поддерживает Docker Compose v2, старый `docker-compose` v1 и
нативную службу systemd:

```
Чем запускать?

  1) docker compose   — сервис и PostgreSQL в контейнерах
  2) docker-compose   — то же через Compose v1
  3) systemd          — нативная служба и локальная PostgreSQL
  4) перенести сюда    — восстановить пакет со старого сервера
  5) подготовить перенос — создать пакет на текущем сервере
  6) удалить          — выбрать Docker Compose, systemd или оба варианта
```

После выбора удаления установщик показывает отдельное меню целей и запрашивает
подтверждение.

| Команда | Что делает |
|---|---|
| `sudo sh ./ovirt-backup-*.run` | выбор способа диалогом |
| `sudo sh ./ovirt-backup-*.run --mode docker --url http://host:8080` | без диалога: Docker Compose v2 |
| `sudo sh ./ovirt-backup-*.run --mode docker-compose --url http://host:8080` | без диалога: Compose v1 |
| `sudo sh ./ovirt-backup-*.run --mode systemd --url http://host:8080` | локальная PostgreSQL и systemd |
| `sudo sh ./ovirt-backup-*.run --mode systemd --url … --database-url-file /root/jhvirt.dsn` | systemd с внешней PostgreSQL |
| `sudo PREFIX=/srv/jhvirt sh ./ovirt-backup-*.run` | другой каталог |
| `sudo sh ./ovirt-backup-*.run --migration-export /root/jhvirt-migration.tar.gz` | остановить приложение и создать пакет переноса |
| `sudo sh ./ovirt-backup-*.run --migrate-from /root/jhvirt-migration.tar.gz` | импортировать настройки, ключи и БД на пустой сервер |
| `sudo sh ./ovirt-backup-*.run --mode docker --url https://host:8080 --tls self-signed` | выпустить и подключить самоподписанный сертификат |
| `sudo sh ./ovirt-backup-*.run --mode docker --url https://host:8080 --tls files --tls-cert-file server.crt --tls-key-file server.key` | подключить готовую PEM-пару |
| `sudo sh ./ovirt-backup-*.run --uninstall` | интерактивно выбрать цель; без терминала снять оба варианта |
| `sudo sh ./ovirt-backup-*.run --uninstall=docker` | снять только Compose-контейнеры и сеть |
| `sudo sh ./ovirt-backup-*.run --uninstall=systemd` | снять только `jhvirt.service` |
| `sudo sh ./ovirt-backup-*.run --uninstall=all` | снять Docker Compose и systemd |
| `sudo sh ./ovirt-backup-*.run --uninstall=all --remove-config` | дополнительно удалить YAML/env; ключи и данные сохранить |
| `sh ./ovirt-backup-*.run --extract [каталог]` | только распаковать, ничего не ставить |
| `sh ./ovirt-backup-*.run --check` | проверить целостность файла |
| `sh ./ovirt-backup-*.run --version` | версия и платформа без распаковки |

`--extract` нужен, когда установку выполняет не этот скрипт: свой Ansible,
образ, каталог без systemd.

Экспорт/импорт поддерживает одинаковый runtime-режим (Docker→Docker либо
systemd→systemd). Пакет переносит конфигурацию, PostgreSQL, `secret.key`, токены
и управляемый TLS, но не терабайтные backup/file/restore roots. Установщик
сохраняет исходные `PREFIX`, пользователя и, если возможно, UID/GID; другой путь
или имя задаются окружением при импорте. Оборванный импорт продолжается только
с тем же архивом по marker с его SHA-256.

Миграционный tar имеет права `0600`, но не зашифрован и не подписан. Встроенные
checksum ловят повреждение отдельных entries после упаковки, но не
аутентифицируют архив целиком. Полная процедура и cutover-чек-лист находятся в
[DEPLOY.md](DEPLOY.md#перенос-приложения-на-другой-сервер).

Production-сборка web использует только `npm ci`: расхождение
`package-lock.json` считается ошибкой и не маскируется переходом на
`npm install`. В CI сторонние Actions закреплены полными commit SHA, installer
сканеров скачивается с commit URL и проверяется известным SHA-256 до запуска;
релизные архивы сканеров затем сверяются с опубликованными checksum.

В unattended-режиме `--url` обязателен: от его схемы зависит флаг `Secure` у
сессионной cookie. Для systemd установщик на Ubuntu/Debian или RHEL/Alma/Rocky
ставит PostgreSQL, создаёт локальную роль и базу, формирует env и unit,
проверяет конфигурацию, запускает службу и ждёт readiness. По выбору он
выпускает самоподписанный TLS-сертификат или проверяет и подключает готовую
PEM-пару. Повторный запуск меняет TLS текущей инсталляции без сброса её
настроек.

Внешняя DSN передаётся через файл `0600`, чтобы пароль не попадал в историю
команд. Локальная база работает через Unix socket и peer-аутентификацию без
пароля в env.

Каталог `data` получает права `0700`: в нём лежит ключ шифрования секретов.

Дальнейшие шаги — в [DEPLOY.md](DEPLOY.md): пошаговая установка, проверка
авторизации, TLS и production-чек-лист. Ошибки установщика разбираются в
[TROUBLESHOOTING.md](TROUBLESHOOTING.md).

### Что проверяется до распаковки

- **Контрольная сумма.** Обрезанный при копировании файл ловится здесь, а не
  разворачивается наполовину.
- **Архитектура.** `uname -m` сверяется с той, под которую собрано. Иначе
  несовпадение всплыло бы как `Exec format error` уже после установки, и связь
  с тем, что скопировали не ту сборку, была бы неочевидна.
- **Права root** — до всякой работы, а не в середине.

### Обновление

Тот же файл новой версии. Он определит установленную, остановит службу на время
замены и запустит обратно, если она работала:

```
==> обновление: 1.0.0 -> 1.1.0
    останавливаю службу на время замены
    конфигурация сохранена; новая версия рядом: ovirt-backup.yaml.new
==> служба обновлена и запущена
```

Конфигурация не перезаписывается. Данные и журналы не трогаются.

Служба останавливается намеренно, а не подменяется на ходу: заменить файл под
работающим процессом Linux позволяет, но применилось бы это только после
перезапуска — и «обновил, а версия старая» стало бы загадкой.

## Разработка

```bash
./run dev     # сервер на :8080
./run web     # интерфейс на :9000, /api проксируется на сервер
```

В режиме разработки интерфейс живёт на своём порту и проксирует `/api` на
сервер, поэтому пересобирать SPA после каждой правки не нужно.

Перед коммитом — одна команда: формат, `go vet`, тесты и проверка типов
интерфейса.

```bash
./run check
```

Гипервизор для тестов не нужен, а вот база нужна — см. ниже.

Браузерные acceptance-тесты запускаются против уже работающей тестовой
инсталляции:

```bash
cd web
JHV_E2E_URL=https://127.0.0.1:58080 \
JHV_E2E_PASSWORD='<пароль admin>' \
JHV_E2E_INSECURE_TLS=true \
npm run e2e
```

`JHV_E2E_INSECURE_TLS=true` нужен только для тестовой инсталляции с самоподписанным
сертификатом; по умолчанию Chromium сохраняет обычную проверку доверия.

Текущий Playwright-набор проверяет system/light/dark и контраст, немедленную
смену часового пояса в нескольких сессиях, доступность страниц Engine/file
backup и основные controls репликации, каталога, Object Lock и DR. Он не
заменяет стендовые прогоны реального backup/restore, installer migration и
доставки SMTP/Telegram/webhook.

Минимальная приёмка стабилизационного релиза: миграция копии production-БД,
Docker Desktop smoke, oVirt→oVirt и KVM→KVM restore с rollback, обязательные
реплики при отказе одной цели, файловый incremental/selective restore и
уведомление с транспортным retry. Команды эксплуатации приведены в
[DEPLOY.md](DEPLOY.md#11-production-чек-лист), а статус восстановления — в
[PLAN-RECOVERY.md](PLAN-RECOVERY.md).

### Тестам нужна PostgreSQL

Тесты хранилища идут против настоящей базы, а не против упрощённой замены.
`./run test` поднимает её в docker сам, на порту 55432 — чтобы не трогать
локальную PostgreSQL разработчика:

```bash
./run test-db start|stop|status
```

Своя база задаётся через `JHV_TEST_POSTGRES_DSN`.

### Детектор гонок

```bash
./run race
```

Гоняет тесты с детектором в контейнере `golang`. Через контейнер потому, что
детектору нужны `CGO_ENABLED=1` и компилятор C — единственное место во всём
проекте, где cgo вообще требуется, и на машине под Windows его обычно нет.
Образ приносит toolchain с собой, поэтому прогон доступен всем, а не только
тем, кто настроил окружение.

Если компилятор есть локально, работает и `./run test -race`.

Кэши модулей и сборки хранятся в именованных томах docker, поэтому повторный
прогон занимает вдвое меньше первого. Убираются вместе со всем остальным:

```bash
./run clean-all
```

Без базы тест **падает, а не пропускается**. Это не строгость ради строгости:
пропуск выглядит в выводе `go test` как `ok`, и набор, половина которого молча
ничего не проверила, — ровно тот способ, которым дефект PostgreSQL дожил до
боевой установки. Схема тогда проверялась на SQLite, а он типизирован
динамически и прощает то, чего PostgreSQL не прощает.

Каждый тестовый бинарь получает свою базу: `go test ./...` запускает пакеты
параллельно, и в общей базе их миграции создавали бы одни и те же таблицы
наперегонки.

## Состав зависимостей и уязвимости

```bash
./run sbom     # состав в формате CycloneDX → dist/sbom/
./run vuln     # govulncheck, grype, trivy
```

В `check` они не входят: обеим командам нужна сеть, а `./run check` должен
проходить и без неё. Гоняет их CI на каждый push и pull request.

### Что во что смотрит

| Инструмент | На что смотрит | Чего не видит |
|---|---|---|
| `govulncheck` | вызывается ли уязвимая функция — по всему графу модулей Go | всё, что вне Go |
| `grype` | состав CycloneDX: модули Go, пакеты npm, действия CI | достижимость кода |
| `trivy fs` | то же плюс секреты в дереве и оба `Dockerfile` | достижимость кода; `docker-compose.yml` |
| `trivy image` | пакеты внутри собранного образа; в source-образе также qemu-img | исходники |

`govulncheck` стоит особняком и валит проверку любой находкой. Он единственный
смотрит не на номер версии, а на то, вызывается ли уязвимое место вообще,
поэтому ложных срабатываний у него почти нет.

Остальные валят проверку только на `high` и `critical` **и только там, где
исправление существует** (`--only-fixed`, `--ignore-unfixed`). Без этого порога
список растёт за счёт того, чего починить нельзя, к длинному списку привыкают и
перестают читать — а вместе с ним перестают замечать и то, что починить как раз
можно.

`grype` и `trivy` держатся рядом намеренно: базы у них разные, и каждая
регулярно знает то, чего не знает вторая. Стоит это лишней минуты прогона.

**`docker-compose.yml` не проверяет никто.** Среди типов настроек, которые
понимает `trivy`, compose отсутствует, а именно в нём заданы права контейнера:
`read_only`, `cap_drop`, `no-new-privileges`, проброс портов. Здесь на
автоматику рассчитывать нельзя — проверяется глазами.

### Объявленный состав и полный

Их важно не путать, иначе проверка кажется полнее, чем есть.

По дереву исходников виден **объявленный** состав: `go.mod` перечисляет
61 модуль. В бинарь попадает около 280 — остальные транзитивные, и в `go.mod`
их нет. Поэтому `./run vuln` без собранного образа проверяет `grype`-ом только
первую цифру.

Дыры в этом нет: весь граф модулей Go проверяет `govulncheck`, и делает это
точнее любого сканера по версиям. Непроверенным без образа остаётся базовый
образ. Для source-сборки это `alpine`, `qemu-img`, `ca-certificates`; offline
bundle из `.run` использует закреплённый Alpine без сетевой установки пакетов.
Команда об этом говорит прямо и предлагает собрать образ.

**Полный состав есть только у образа.** В нём и бинарь со всем графом, и
собранный интерфейс, и пакеты дистрибутива. Это же и есть то, что уезжает на
сервер.

### Каталоги прошлой сборки исключены

`bin/`, `dist/` и `web/dist/` в состав не попадают, и не ради скорости.

`syft` читает собранный бинарь и берёт версию `stdlib` **из него**, а не из
`go.mod`. Бинарь, собранный месяц назад прошлым Go, приносит в состав
исходников уязвимости того Go: при первом прогоне здесь так и вышло — шесть
находок уровня high в `stdlib`, все из двухнедельного бинаря в `bin/`, ни одной
в самом проекте.

Такой состав не воспроизводим: он зависит от того, что случайно осталось в
каталоге. Настоящую версию `stdlib` показывает состав образа, где бинарь
собран только что.

### Откуда берутся сами инструменты

Из PATH, если они там есть. Если нет — собираются из исходников через модульный
прокси Go.

Своих бинарей `syft`, `grype` и `trivy` здесь не скачивается: они раздаются
релизами на GitHub, а он доступен не из всякой сети, где этот проект собирают.
Через `proxy.golang.org` то же самое ставится везде, где уже работает
`go mod download`, — то есть везде, где проект вообще собирается.

Первый прогон занимает минуты: инструменты собираются. Дальше их забирает кэш
сборки Go.

`trivy` собирается не тем Go, что весь остальной проект: `./run` закрепляет ему
`GOTOOLCHAIN=go1.26.6` и `GOEXPERIMENT=jsonv2`. С версии 0.7x он использует
`encoding/json/v2`. В Go 1.26 этот пакет был закрыт экспериментальным флагом, в
Go 1.27 он открылся — но уже без `SkipFunc`, на который trivy опирается. Под
1.27 сборка падает на `undefined: json.SkipFunc`, и `GOEXPERIMENT` тут не
помогает: флаг стал пустышкой. `trivy` — отдельный модуль, поэтому собрать его
прежним Go можно, не возвращая туда весь проект; нужный тулчейн Go скачает сам.

Закрепление снимается, когда выйдет `trivy` под открытый `json/v2`. Признак —
сборка проходит без обеих переменных:

```
go run github.com/aquasecurity/trivy/cmd/trivy@<версия> --version
```

Версия инструмента в метаданных состава остаётся `[not provided]`: `go install`
не проставляет её через `-ldflags`, как это делает официальная сборка. На
результат это не влияет — версия закреплена в `./run`.

Версии закреплены в самом `./run` — `SYFT_VERSION`, `GRYPE_VERSION`,
`TRIVY_VERSION`, `GOVULNCHECK_VERSION`. У сканера обновляется не только код, но
и база правил, поэтому «последний» однажды красит вчера зелёную сборку, ничего
не изменив в проекте. Версия поднимается отдельным решением, когда видно, что
именно изменилось.

### Состав образа снимается отдельно

`./run sbom` делает два файла, если образ собран:

- `dist/sbom/source.cdx.json` — по исходникам: `go.mod` и `web/package-lock.json`;
- `dist/sbom/image.cdx.json` — по образу `ovirt-backup:<версия>`.

Второй нужен потому, что в образе есть то, чего нет в исходниках: базовый
alpine, `qemu-img`, `ca-certificates`. Уязвимость приходит оттуда не реже, чем
из `go.mod`, а по составу исходников её не видно вовсе. Нет образа — команда
скажет об этом и сделает только первый файл; собрать образ можно через
`./run docker`.

CycloneDX выбран потому, что его читают и `grype`, и `trivy`, и
[Dependency-Track](https://dependencytrack.org/), если состав понадобится
хранить с историей по времени. Сам по себе файл состава ничего не проверяет —
это опись, по которой проверяют другие.

CI выкладывает оба файла артефактом сборки `sbom-cyclonedx` и хранит 90 дней.
Состав, который не едет вместе с поставкой, бесполезен: через полгода после
релиза вопрос «что там внутри» задают именно про ту сборку, которая уехала.

## Docker

```bash
./run docker
```

Образ многоступенчатый: Node собирает интерфейс, Go — бинарь, финальный слой на
Alpine содержит только результат. Внутри `qemu-img` — он нужен для экспорта в
qcow2 и режима проверки `qemu`; без него работает всё остальное.

Готовый стек с базой — в
[пошаговой Docker-инструкции](DEPLOY.md#4-установка-docker-compose).

## Если что-то не собирается

Ошибки уже собранного установщика, Docker, systemd и PostgreSQL вынесены в
[TROUBLESHOOTING.md](TROUBLESHOOTING.md). Ниже только ошибки этапа сборки.

| Сообщение | Причина |
|---|---|
| `не найден go` | Go не установлен или не в `PATH` |
| `неизвестная команда` | опечатка; `./run` покажет список |
| `не найден npm` | нет Node; либо соберите с `--skip-web`, если `web/dist` уже готов |
| `нет web/dist/index.html` | указан `--skip-web`, но интерфейс не собран |
| `-race requires cgo` | нет компилятора C; тесты без `-race` пройдут |
| `контрольная сумма не сошлась` | `.run` побился при копировании — перенесите заново, лучше `scp`, а не через общую папку |
| `метка архива не найдена` | файл открывали редактором и он переписал переносы строк; двоичную часть так не сохранить |
| `комплект собран под linux/arm64, а система x86_64` | скопирована сборка не под ту архитектуру |
| `cannot execute: required file not found` при запуске `.run` на сервере | запустите через `sudo sh файл.run` |
