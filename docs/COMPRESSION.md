# Сжатие резервных копий дисков

Блочные копии oVirt и KVM поддерживают `zstd`, `gzip`, `s2`, `lz4`, `brotli`
и `none`. Все включённые кодеки работают **без потерь**. Это сжатие чанков
в репозитории, а не изменение формата рабочего диска ВМ или её файловой системы.

## Выбор в веб интерфейсе

- **Настройки → Общие → Система → Сжатие** задаёт общий алгоритм.
- **Задания ВМ → создать или изменить → Проверка → Алгоритм сжатия** задаёт
  переопределение для конкретного задания. Выбор также показан на шаге «Итог».
- В карточке ВМ тот же выбор доступен при разовом запуске блочной копии.

«Системная настройка» хранится как пустая строка `compression: ""` и означает
выбор эффективного системного алгоритма при начале запуска. `none` явно
выключает сжатие, даже если системная настройка — zstd или другой кодек.
Алгоритм задания сохраняется в PostgreSQL. У старых заданий после миграции
`0074_job_compression.sql` остаётся наследование прежней системной настройки.

Явный выбор задания передаётся в сохраняемую очередь вместе с запросом.
Изменение задания не переписывает уже сформированный запрос очереди. Если
в запросе оставлено наследование, системный алгоритм определяется при начале
исполнения. Уже выполняющийся запуск сохраняет выбранный им алгоритм.

## Предварительная оценка и фактическая экономия

В форме задания и разового запуска кнопка **«Оценить сжатие до бэкапа»**
позволяет сравнить алгоритмы до первой сохранённой копии. Для задания с
несколькими ВМ выбирается одна ВМ: результат не переносится автоматически
на остальные машины группы. Применяются исключения дисков задания.

После отдельного подтверждения служба открывает временную точку чтения:
oVirt с Backup API либо pull-backup работающей ВМ KVM. Служба не включает
и не выключает ВМ. oVirt Engine может кратковременно заморозить запись гостя
при фиксации точки. Это реальные операции виртуализации с нагрузкой и
расходом временного места, а не вычисление по инвентарному размеру диска.
Старый Engine без Backup API, остановленная KVM ВМ и нативный Proxmox-путь
этим способом не оцениваются.

Оценка читает до **64 МиБ**, не больше 16 чанков с максимум 4 МиБ на чанк,
с распределением по выбранным дискам (не больше 16 дисков). Если доступна
карта заполненных областей, выборка распределяется по ним; иначе используется
выборка по виртуальному размеру с предупреждением о меньшей представительности.
Нулевые чанки учитываются отдельно и исключаются из сравнения алгоритмов.
Если непустых данных нет, процент сжатия не выдумывается.
Чтение ограничено 32 МиБ/с либо меньшим положительным системным пределом.
Сбор выборки и сравнение имеют общий срок 3 минуты; обязательная очистка
получает отдельный контекст до 5 минут. На время запроса занят один слот
`backup.heavy_workers`; исходные данные выборки хранятся только в памяти.

Точка чтения закрывается до сравнения кодеков. Каждый алгоритм обрабатывает
одни и те же непустые чанки независимо, с системным уровнем и правилом «если
сжатие не уменьшило размер, оставить исходные байты». Таблица показывает:
алгоритм, процент сокращения выборки, размер после сжатия и время обработки
выборки. Последнее не является прогнозом скорости полного бэкапа.
Кнопка «Выбрать» переносит алгоритм в форму; задание ещё нужно сохранить.

Прогноз относится к выборке текущих данных. Шифрование, метаданные, реплики,
дополнительные образы и будущая карта изменений инкремента в него не входят.
Одинаковое количество проб на диск не является взвешенной оценкой всего
объёма ВМ. Показатель нельзя умножать на виртуальную ёмкость и выдавать
полученное число за гарантированный размер копии.

После записи в карточке бэкапа и таблице дисков показано фактическое
сокращение: `100 × (1 − сумма stored_bytes / сумма logical_bytes)` по успешно
записанным дискам с манифестом. Здесь `logical_bytes` — охваченные данные
диска данного запуска, а не виртуальная ёмкость ВМ. Этот показатель включает
накладные расходы шифрования; пропуск пустоты, неизменённые области,
метаданные, реплики и дополнительные QCOW2-артефакты в него не входят.
Пока запуск идёт, учитываются только завершённые диски. Увеличение размера
показывается отдельно; для нулевого охвата или отсутствующих данных выводится
прочерк. Поэтому фактическое значение может отличаться от прогноза кодека.

Отмена окна прерывает запрос и инициирует очистку. До окончания очистки ВМ
может оставаться занятой оценкой. Владение временными ресурсами хранится в
PostgreSQL (`0075_compression_previews.sql`); после перезапуска служба повторяет
очистку осиротевших записей раз в минуту, не захватывая работающие запросы.
Закрываются только ресурсы с точной собственной меткой или сокетом. Ошибка
очистки сохраняет блокировку конфликтующих бэкапов, миграций и автодействий
до успешного завершения очистки. Отдельный checkpoint oVirt, который движок
не разрешает удалить после закрытия точки, может остаться в Engine; это
фиксируется предупреждением в журнале приложения.

API: `POST /servers/{id}/vms/{vmID}/compression-preview`, права `servers.read`
и `backups.write`. Тело: `{"confirm_source_read":true,"exclude_disk_ids":[]}`.
Ответ содержит дату выборки, размеры чанка/выборки/нулевых и сравниваемых
данных, диски, уровень, строки `results` и предупреждения. Без явного
подтверждения источник не читается. Дисковые байты не возвращаются клиенту
и не публикуются в репозитории. События создания точки и передачи могут
попадать в штатный аудит самого гипервизора.

## Алгоритмы и уровни

| Алгоритм | Назначение | Уровень в проекте |
|---|---|---|
| zstd | Основной универсальный вариант | 1 — быстрый; 2–5 — стандартный; 6–8 — повышенное сжатие; 9 — максимальный профиль |
| gzip | Независимые gzip-потоки для чанков | 1–9 |
| s2 | Быстрый блочный кодек S2 | 1–5 — обычный; 6–8 — Better; 9 — Best |
| lz4 | Независимые LZ4 frames, быстрый режим по умолчанию | 1–5 — Fast; 6–8 — HC Level3; 9 — HC Level9 |
| brotli | Дополнительный универсальный кодек без потерь | Quality 1–9; окно LGWin 22 |
| none | Хранение без сжатия | Не используется |

Числа уровней разных кодеков не означают одинаковые затраты CPU или одинаковую
плотность. Общий `backup.compression_level` задаётся через YAML или окружение;
отдельный выбор уровня для задания в этой реализации не добавлен.
Более затратный уровень может уменьшить размер, но увеличить время копирования.
Сравнивать алгоритмы следует на характерных данных и с учётом восстановления.
Гарантия, что один алгоритм всегда лучше другого, не даётся.

## Формат и совместимость

Каждый чанк сжимается независимо. Если результат не меньше исходных данных,
сохраняются исходные байты. Затем, при включённой защите, применяется шифрование.
SHA-256 относится к исходным данным. При чтении сначала снимается шифрование,
затем используется алгоритм из манифеста соответствующего звена.

Новая сборка читает старые копии zstd, gzip, S2 и несжатые данные. Цепочка может
сочетать разные алгоритмы, включая новые LZ4 и Brotli. Смена настройки не требует
перезаписи старых копий. Старые сборки без новых кодеков не смогут читать новые
звенья LZ4/Brotli: перед откатом версии нужно учесть это ограничение и сохранить
совместимую среду восстановления. Сжатие JSON-манифестов zstd не меняется.

Скопированные в реплики объекты не пересжимаются: сохраняются их байты и
манифесты. Для декодирования LZ4/Brotli не нужны внешние словари, модели,
GPU или сетевой сервис. Новые декодеры ограничивают выдачу ожидаемой длиной
чанка плюс один байт; несовпадение длины приводит к ошибке.

Выбор относится к основным блочным копиям. OVA и копии только конфигурации
не предлагают это поле. Proxmox использует нативный vzdump с zstd и не
получает второй слой сжатия чанков. Дополнительные управляемые QCOW2-артефакты
сохраняют свой формат и не пересжимаются этим переключателем.

## API

`GET /meta` возвращает `compression_options` — значения, названия и описания
поддержанных кодеков. Тот же список используется в runtime-настройках.

```json
{ "compression": "lz4" }
```

Поле принимается при создании/изменении задания и в `POST /backups` для разового
блочного запуска. Пустая строка возвращает наследование. При изменении задания
прежним клиентом отсутствие поля сохраняет ранее выбранное переопределение;
для сброса нужно явно передать пустую строку. Имена нормализуются в нижний регистр.
Неизвестные кодеки отклоняются. Явное переопределение для Proxmox, OVA или
копии только конфигурации отклоняется с объяснением.

## Локальная проверка

Результаты локальных проверок и синтетического сравнения находятся в
[отчёте](../test-reports/2026-10-30-compression/README.md). CPU-тест использует
1 МиБ искусственно повторяющихся данных, уровень 3 и включает SHA-256.
Он не измеряет чтение диска, сеть, шифрование или скорость реальной ВМ.
Для выбора рабочего алгоритма нужен собственный тест с характерными образами.

## Нейросетевое сжатие

**Технически возможно** построить нейросетевой кодек без потерь: модель
предсказывает вероятности символов, а энтропийный кодер сохраняет точную
последовательность. Исследовательские реализации существуют, например
[NNCP](https://bellard.org/nncp/) и
[Language Modeling is Compression](https://github.com/google-deepmind/language_modeling_is_compression).
Они не включены в рабочий формат этого проекта.

Результаты на текстах не доказывают выигрыш на произвольных образах ВМ.
Например, автор [ts_zip](https://bellard.org/ts_zip/) прямо отмечает ориентацию
на текст, слабый результат на бинарных данных, меньшую скорость и отсутствие
обещания совместимости между версиями. Это не готовая замена кодека образов ВМ.

Для опытного нейросетевого кодека потребуется отдельная проверка:

1. Побайтовое восстановление и совпадение SHA-256 для всех типов данных.
2. Детерминированный декодер на поддержанных CPU/GPU и версиях runtime.
3. Сохранение версии формата, весов, токенизатора, параметров и их хешей вместе
   с комплектом восстановления; проверка лицензий и состава поставки.
4. Работа без Интернета и без передачи данных ВМ внешнему сервису.
5. Независимое чтение чанка, ограничение ресурсов, обнаружение повреждения,
   поведение при прерывании и недоступности модели.
6. Измерение размера **вместе с обязательными моделями**, времени записи,
   восстановления, CPU/GPU/RAM и влияния на RTO на реальных тестовых образах.

Обычное нейросетевое сжатие изображений с потерями для дисков непригодно:
меняться не должен ни один байт файловой системы. Альтернатива для следующего
этапа — автоматический выбор обычного кодека по пробе данных. Такой выбор может
обходиться без модели; декодирование останется на стандартных алгоритмах.
Ни нейросетевой кодек, ни автоматический выбор в этой реализации не добавлены.
