# Архитектура дисков QEMU и что из неё следует для бэкапа

Документ объясняет, почему горячий бэкап вообще возможен, где именно проходят
его границы и какие решения в коде продиктованы устройством qcow2, а не вкусом.

---

## 1. Что такое «диск» работающей ВМ

Внутри гостя `/dev/vda` — обычное блочное устройство. Снаружи это **граф узлов
блочного слоя QEMU**, а не файл.

```
гость → virtio-blk → [ format: qcow2 ] → [ file: /var/lib/libvirt/images/vm.qcow2 ]
                            │
                            └── backing → [ format: qcow2 ] → [ file: base.qcow2 ]
```

Ключевые следствия:

- **Верхний слой (active layer) — единственный, куда пишет гость.** Всё, что
  ниже, доступно только на чтение.
- **Читать файл активного слоя напрямую нельзя.** Метаданные qcow2 (таблицы
  отображения) обновляются асинхронно относительно данных. Копия, снятая `cp`
  с работающего диска, почти наверняка окажется несогласованной: часть таблиц
  укажет на кластеры, которых ещё нет.
- Именно поэтому весь бэкап идёт **через QEMU**, а не мимо него. QEMU —
  единственный, кто знает, где сейчас лежит консистентное состояние.

---

## 2. Внутри qcow2

Формат придуман, чтобы образ занимал место по факту записи и умел ветвиться.

```
┌──────────────┬─────────────┬──────────┬─────────────────────────┐
│ Header       │ L1 table    │ refcount │ кластеры данных и L2    │
│ + extensions │             │ tables   │                         │
└──────────────┴─────────────┴──────────┴─────────────────────────┘
```

- **Кластер** — единица выделения, по умолчанию 64 КиБ. Всё адресуется
  кластерами.
- **Двухуровневая таблица L1 → L2 → кластер.** Гостевое смещение делится на
  индексы в L1 и L2; L2 хранит физическое смещение кластера в файле. Отсюда
  разреженность: кластер, в который никогда не писали, просто отсутствует в
  таблице, и чтение из него возвращает нули.
- **refcount-таблицы** считают ссылки на каждый кластер. Нужны для внутренних
  снапшотов и для безопасного освобождения места.
- **backing file** — ссылка на нижний образ. Отсутствующий в L2 кластер ищется
  в backing-файле, и только если его нет и там — читается как нули.
- **Расширения заголовка.** В одном из них живут **persistent dirty bitmaps** —
  то, ради чего всё это здесь описано.

**Почему инкременты только для qcow2.** Битмапу изменённых блоков негде жить в
формате `raw`: там нет заголовка, нет расширений, нет метаданных вообще — только
байты. Никакая версия QEMU это не обойдёт, поэтому `raw`-диск можно копировать
только целиком, и код честно переключается на полный бэкап, а не делает вид,
что инкремент удался.

## 3. Dirty bitmap — сердце инкрементального бэкапа

Битмап — это набор бит, каждый из которых говорит: «этот участок диска
изменился с момента, когда битмап начал считать».

| Свойство | Значение |
|---|---|
| Гранулярность | по умолчанию 64 КиБ, кратна размеру кластера |
| Накладные расходы | ~2 МиБ битмапа на 1 ТиБ диска при гранулярности 64 КиБ |
| Хранение | внутри qcow2 (persistent) или только в памяти (transient) |
| Переживает выключение ВМ | только persistent |
| Переживает миграцию | да, битмапы мигрируют вместе с ВМ |
| Переживает `kill -9` qemu | нет — битмап помечается неконсистентным |

Последняя строка важна: после аварийного завершения QEMU битмап получает флаг
`in-use` и становится негодным. libvirt в этом случае перестаёт показывать
checkpoint как пригодный, и наш код обязан это заметить — что и делает
`HasCheckpoint` перед каждым инкрементом.

**Гранулярность против точности.** Бит покрывает 64 КиБ. Изменение одного байта
помечает грязными все 64 КиБ. Наша сетка чанков (4 МиБ) огрубляет это ещё раз.
Итог: инкремент всегда чуть больше реально изменённого объёма, и это плата за
то, что слияние цепочки при восстановлении сводится к «побеждает самый свежий
чанк» без арифметики диапазонов.

---

## 4. Checkpoint libvirt = битмап QEMU

libvirt добавляет поверх битмапов понятие **checkpoint** — именованную точку во
времени для всей ВМ сразу.

```
checkpoint A ──► checkpoint B ──► checkpoint C
   bitmap A        bitmap B         bitmap C     (в каждом qcow2 диске)
```

- Создание checkpoint = создание битмапа на каждом указанном диске.
- «Что изменилось с A» = объединение битмапов A, B, C… до текущего момента.
  libvirt делает это слияние во **временный** битмап на время бэкапа, а
  постоянные не трогает.
- Удаление checkpoint в середине цепочки — не потеря данных: libvirt сливает
  его битмап в потомка. Но бэкапы, ссылавшиеся на него, теряют опору.

Из-за этого в коде checkpoint создаётся **тем же вызовом**, что и бэкап
(`DomainBackupBegin` принимает описание checkpoint вторым аргументом). Иначе
между «снять копию» и «поставить метку» образовалась бы щель, и записи гостя,
попавшие в неё, не попали бы ни в текущую копию, ни в следующий инкремент.

## 5. Что происходит во время горячего бэкапа

Механизм называется **copy-before-write**.

```
             гость пишет в блок X
                     │
                     ▼
        ┌────────────────────────┐
        │  фильтр copy-before-   │  1. старое содержимое X → scratch
        │  write                 │  2. новое содержимое X → активный слой
        └────────────────────────┘
                     │
   NBD-экспорт читает X ──► из scratch, если гость уже перезаписал
                       └──► из активного слоя, если ещё нет
```

Гость не останавливается ни на миг. Точка согласованности фиксируется в момент
`DomainBackupBegin`; всё, что записано после, в копию не попадает.

**Scratch-файл — главный операционный риск.** Он растёт по мере того, как гость
перезаписывает блоки, пока идёт чтение. Нагруженная СУБД при медленном чтении
может потребовать неожиданно много места, а его нехватка прерывает бэкап.
Отсюда в коде: проверка свободного места перед началом, и удаление scratch в
`defer` с контекстом, переживающим отмену.

**Почему бэкап обязательно надо закрывать.** Открытое задание держит фильтр
copy-before-write. Забытый бэкап — это scratch, растущий до заполнения тома, и
невозможность начать следующий. Поэтому `EndBackup` вызывается из `defer` при
любом исходе, а при старте сервис ищет и закрывает чужие незавершённые задания.

## 6. Как данные выходят наружу: NBD и контексты метаданных

В pull-режиме libvirt поднимает NBD-сервер и ждёт, пока читатель заберёт данные.

Клиент запрашивает два «контекста метаданных»:

| Контекст | Что отвечает | Для чего |
|---|---|---|
| `base:allocation` | выделен ли участок, читается ли он как нули | полный бэкап: не читать дыры |
| `qemu:dirty-bitmap:ИМЯ` | изменился ли участок с checkpoint | инкремент: читать только изменённое |

Ответ приходит командой `NBD_CMD_BLOCK_STATUS` в виде списка экстентов
(смещение, длина, флаги). Это и есть карта, по которой строится список чанков.

Важная деталь протокола, стоившая одного пойманного тестом бага: сервер
отвечает **за все согласованные контексты сразу**, порядок не определён, а флаг
«последний чанк» может оказаться на ответе для контекста, который нам не нужен.
Клиент обязан проверять этот флаг у каждого чанка независимо от того, что он с
данными сделал.

### Асимметрия полного и инкрементального отбора

Это самое неочевидное правило во всём инструменте.

- **Полный бэкап**: берём то, что содержит данные; дыры и нули пропускаем.
  Отсутствие чанка во всей цепочке означает «нули» — значит, пропуск корректен.
- **Инкремент**: берём **строго то, что помечено грязным**, не глядя на
  выделенность.

Почему нельзя пропустить грязный, но обнулившийся участок: гость выполнил TRIM,
область стала дырой и одновременно помечена изменённой. Если её не сохранить,
чанк будет отсутствовать в этом запуске — а отсутствие в инкременте означает
«не изменилось», и восстановление достанет **старые данные из родителя**.
Пользователь получил бы файл, который он удалил месяц назад, вместо пустоты.
Поэтому нули сохраняются явно; сжатие делает это почти бесплатным
(4 МиБ нулей → десятки байт).

Правило закреплено тестом `TestIncrementalStoresDirtyRegionsThatBecameZero`.

## 7. Уровни согласованности

| Уровень | Как достигается | Что переживает |
|---|---|---|
| **Crash-consistent** | ничего дополнительно | как выдернули питание: журналируемая ФС восстановится, незаписанные буферы потеряны |
| **Filesystem-consistent** | `fsfreeze` через qemu-guest-agent | ФС в согласованном состоянии, приложения — нет |
| **Application-consistent** | VSS (Windows) или backup mode СУБД | транзакции целы |

`fsfreeze` замораживает файловые системы на доли секунды — ровно до фиксации
точки. Но он ничего не знает о транзакциях: СУБД нужно переводить в backup mode
своими средствами.

**Разморозка обязательна при любом исходе.** Гость, оставшийся с замороженной
ФС, перестаёт обслуживать что угодно. В коде это `defer` с отдельным
контекстом и отдельным сообщением в журнале капсом.

## 8. Что ломает инкременты

| Причина | Признак | Реакция кода |
|---|---|---|
| Диск в формате `raw` | битмап негде хранить | полный бэкап **на горячую**, checkpoint не создаётся |
| Аварийное завершение QEMU | битмап помечен неконсистентным | `HasCheckpoint` = false → полный бэкап |
| Checkpoint удалён вручную | libvirt его не находит | полный бэкап |
| ВМ пересоздана | битмапы ушли вместе со старым qcow2 | полный бэкап |
| Диск расширен | битмап покрывает старый размер | новая область читается как изменённая |
| Цепочка выросла | восстановление требует N звеньев | `full_every` принудительно рвёт цепочку |

Во всех случаях выбирается корректное действие, а причина попадает в журнал и в
запись о запуске. Молча выполнить «инкремент», который на самом деле неполон, —
единственный по-настоящему недопустимый вариант.

---

## 9. Границы механизма

- **Общие (shareable) диски** не бэкапятся: они принадлежат нескольким ВМ,
  копирование по разу на каждую размножило бы данные и сделало восстановление
  неоднозначным.
- **Проброшенные LUN и устройства** — данные живут на СХД, гипервизор их не
  видит как образ.
- **Память ВМ** в копию не входит: восстановленная машина загружается заново,
  а не продолжает с того же места.
- **Смешанная ВМ** (часть дисков qcow2, часть raw) целиком уходит на полный
  бэкап. Инкремент по части дисков создал бы точку восстановления, где диски
  относятся к разным моментам времени.

---

## 10. Как это отражено в коде

| Свойство архитектуры | Где учтено |
|---|---|
| Битмап только в qcow2 | `libvirtx.Disk.SupportsCBT`, `kvm.diskSetCBTReady` |
| checkpoint = битмап на диск | `libvirtx.CheckpointSpec` |
| Точка и метка одним вызовом | `Conn.BeginBackup(dom, spec, checkpoint)` |
| scratch растёт и должен исчезнуть | `PrepareScratchDir`, `RemoveScratch` в `defer` |
| Бэкап обязан закрываться | `EndBackup` в `defer` с `context.WithoutCancel` |
| Два контекста метаданных | `nbd.ContextBaseAllocation`, `nbd.DirtyBitmapContext` |
| Флаг DONE у любого чанка | `nbd.Client.BlockStatus` |
| Грязные нули сохраняются явно | `kvm.SelectFromExtents` |
| Разморозка при любом исходе | `Driver.thaw` |
| Потеря checkpoint → полный | `Driver.Resolve` |
