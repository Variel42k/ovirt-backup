# Эксплуатация

Установка по шагам находится в [DEPLOY.md](DEPLOY.md). Полный каталог ошибок
Docker, systemd, PostgreSQL, авторизации, oVirt и KVM находится в
[TROUBLESHOOTING.md](TROUBLESHOOTING.md). Здесь описаны регулярные операции
после успешного развёртывания.

Пути файлов настройки, приоритет YAML и `JHV_*`, а также сохранность при
обновлении и удалении описаны в [CONFIGURATION.md](CONFIGURATION.md).

## Проверка живости

```bash
curl -fsS http://localhost:8080/healthz    # процесс отвечает
curl -fsS http://localhost:8080/readyz     # база доступна, сколько бэкапов идёт
```

Оба эндпоинта не требуют аутентификации — их вызывает балансировщик.

## Первый запуск

При установке Docker или systemd с новой локальной базой через `install.sh`
пароль администратора печатает сам установщик, в конце, вместе с адресом
интерфейса. Он задаёт пароль заранее и после успешного старта стирает его из
`.env`.

При подключении новой внешней PostgreSQL установщик не может заранее знать,
пуста ли удалённая таблица пользователей. Если база действительно пустая,
служба создаст администратора и один раз напечатает пароль в
`journalctl -u jhvirt`. Альтернатива — сразу выполнить описанный ниже сброс
пароля `admin`.

Ниже — про запуск в обход установщика (свой `.env`, systemd, ручной старт).
Тогда пароль генерирует служба и выводит один раз, отдельным блоком в stderr:

```
════════════════════════════════════════════════════════════
  СОЗДАНА УЧЁТНАЯ ЗАПИСЬ АДМИНИСТРАТОРА

  пользователь: admin
  пароль:       <...>
════════════════════════════════════════════════════════════
```

Блок, а не поле в строке журнала: в поле пароль оказывался в конце длинной
фразы, узкий терминал её переносил, и при копировании в пароль попадал перенос
строки. Вход тогда отвечал «неверный пароль» — сообщение, из которого причину
не видно.

В открытом виде пароль не хранится нигде. Если он потерян:

```bash
sudo systemd-run --quiet --wait --pipe --collect \
  --uid=jhvirt --gid=jhvirt --working-directory=/opt/jhvirt \
  --property=EnvironmentFile=/opt/jhvirt/config/jhvirt.env \
  /opt/jhvirt/bin/ovirt-backup-server -reset-password admin
```

Команда печатает новый пароль тем же блоком и завершается, не поднимая сервис;
свой пароль можно задать через `JHV_NEW_PASSWORD` (не короче 10 символов).
Все действующие сессии этой учётной записи закрываются, а если запись была
заблокирована — разблокируется. В Docker:

```bash
docker compose run --rm ovirt-backup -reset-password admin
```

Удалять строку из таблицы `users` руками больше не нужно.

## Режим проверки авто-восстановления

Авто-восстановление начинает работу в режиме проверки: решения принимаются и
записываются, но не выполняются. Это не настройка, а наблюдение — у него есть
начало и конец, и оба видны в «Настройки → Система».

Этот режим относится только к автоматическому устранению сбоев: запуску VM,
активации хоста и fencing. Он не означает, что восстановление бэкапов является
тестовым, и не ограничивает проверки образов или ручное восстановление.

Пока режим включён, каждое решение сохраняется в PostgreSQL, истории режима и
его JSON-архиве: объект, подключение, предложенное действие, причина, номер
попытки и результат проверки политики. Повторяющиеся решения не засоряют
обычный журнал, шапку, список оповещений и всплывающие уведомления. Для
временной подробной диагностики установите уровень `debug`: на нём решения
пишутся в файловый журнал или поток службы.

Переключение — тумблером в интерфейсе, на ходу, без перезапуска. Выход из
режима требует подтверждения и основания: после него автоматика начнёт трогать
боевые машины. В этот момент все решения периода собираются в архив — JSON со
сводкой и полным списком, — который остаётся в `monitor.remediation.archive_dir`
и открывается из истории режимов. Это и есть обоснование того, что автоматике
доверили боевые машины.

Выбранный режим хранится в базе и переживает перезапуск: оператор, не
закончивший наблюдение, не должен получить работающую автоматику из-за
перезагрузки службы.

## Мониторинг ввода-вывода и путей до хранилища

Вкладка «Ввод-вывод» на странице подключения отвечает на два разных вопроса, и
их важно не путать.

**Медленно ли работает диск гостю.** Верхний график: сплошные линии — объём в
секунду, пунктир — задержка на операцию. Смотреть надо на пунктир. Диск с низкой
скоростью и низкой задержкой просто не нагружен; низкая скорость при высокой
задержке — это и есть «тормозит». По одному объёму эти два случая неразличимы:
оба выглядят как линия у нуля. Задержка берётся из накопленного времени операций
QEMU; если гипервизор её не отдаёт (старая версия, неподдерживаемый драйвер),
пунктир отсутствует, а не рисуется нулём.

**Доходит ли трафик до СХД.** Нижняя таблица и график. NFS о потере пакетов не
сообщает — сообщает о том, что она с ним сделала:

| Показатель | Что означает |
|---|---|
| Повторы | вызов остался без ответа и был отправлен снова |
| Таймауты | клиент исчерпал расписание повторов; гость увидел зависший диск |
| Плохие xid | ответ пришёл на вызов, который уже сочли потерянным |
| Отклик | среднее время ответа сервера за интервал |

Единичные повторы бывают на исправной сети. Устойчивый процент (порог — 1% от
операций) и **любой** таймаут поднимают оповещение `storage_path_degraded`.
Разорванная сессия iSCSI — оповещение критическое сразу.

Источники данных: `/proc/self/mountstats` для NFS, sysfs для состояния сессий
iSCSI, `DomainBlockStatsFlags` libvirt для дисков.

**Работает только для подключений типа KVM.** Всё перечисленное требует доступа
к гипервизору по SSH; движок oVirt статистику монтирований своих хостов наружу
не отдаёт, и получить её через него неоткуда.

Сбор включается `monitor.collect_io_stats` (по умолчанию включён), срок хранения
— `monitor.io_retention` (неделя). Метрики снимаются тем же проходом, что и
состояние: отдельный опрос удвоил бы нагрузку на гипервизор ради тех же данных.

## Журнал службы

Вкладка «Настройки → Журнал», только для администратора: журнал не содержит
секретов, но перечисляет все ВМ, хосты и операторов установки — это карта
инфраструктуры.

**Ротация двойная.** По размеру — перед тем, как файл перерастёт
`max_size_mb`. И раз в
сутки в полночь, даже если размер не достигнут. Второе нужно потому, что
`max_age_days` чистит архивы, а не активный файл: на тихой установке он иначе
рос бы годами, ни разу не сменившись, и предельный возраст к нему бы не
применился. Пустой файл в полночь не меняется — иначе каталог заполнили бы
пустые архивы и вытеснили настоящие из `max_backups`. Архивы всегда сжимаются
gzip одним фоновым worker.

Размер файла, число архивов и срок хранения меняются на этой же вкладке и
сохраняются в PostgreSQL. Новая политика применяется без перезапуска, в том
числе во время записи. Допустимые диапазоны: `1..10240` МиБ, `1..1000` архивов,
`1..3650` дней. Интерфейс показывает источник `config` или `database`; сброс
удаляет переопределение из БД. Если `logging.file` пуст, политика всё равно
сохраняется, но начнёт работать после включения файлового журнала и перезапуска.

Сменить файл вручную можно кнопкой; смена, как и изменение уровня, попадает в
аудит.

**Уровень меняется на ходу.** `trace, debug, info, warn, error` — переключение
действует немедленно и до перезапуска службы, постоянное значение остаётся в
`logging.level`. Это сделано ради разбора аварий: поднять подробность обычно
нужно тогда, когда перезапускать мониторинг меньше всего хочется. Само
изменение пишется в журнал — иначе внезапно замолчавший или, наоборот,
залитый журнал ничем себя не объясняет.

| Параметр | Значение по умолчанию |
|---|---|
| `logging.file` | `./logs/jhvirt.log`; пусто — только поток службы |
| `logging.level` | `info` |
| `logging.format` | `console` (в Docker — `json`) |
| `logging.max_size_mb` | 100 |
| `logging.max_backups` | 7 |
| `logging.max_age_days` | 30 |

В Docker файл задаётся переменной `JHV_LOG_FILE`, которая передаётся приложению
как `JHV_LOGGING_FILE`. Установщик записывает `/app/logs/jhvirt.log`; если
переменная не задана при ручном запуске Compose, журнал остаётся только в
потоке контейнера и просмотр файлов из интерфейса недоступен.

## Качество защиты

Раздел «Защита» рассчитывается от cron-расписаний. Для каждой комбинации
`задание × ВМ × хранилище` проверяются свежесть, последний исход, полнота
неисключённых дисков, настроенная проверка восстановления и скорость. Если ВМ
входит в несколько заданий или имеет несколько реплик, её состояние равно
худшему результату. Успешная основная копия не закрывает ошибку второй реплики.

| Состояние | Условие |
|---|---|
| Нет защиты | ВМ не входит во включённое задание с расписанием либо полной успешной копии ещё нет |
| Ошибка реплики | последний запуск в назначенное хранилище завершился ошибкой |
| Неполная копия | не записан обязательный диск; явно исключённый диск дефектом не считается |
| Просрочено | полная успешная копия старше `stale_intervals` интервалов задания |
| Проверка просрочена | у задания есть `verify_after`, но за срок не было успеха того же режима |
| Скорость снизилась | несколько запусков подряд ниже порога от медианы предыдущих сопоставимых запусков |
| В порядке | все перечисленные проверки успешны для всех реплик |

Сопоставимыми для скорости считаются запуски той же ВМ, задания, реплики, типа
бэкапа и алгоритма сжатия. По умолчанию три последних запуска должны быть ниже
50% медианы предыдущих десяти. Смена zstd на gzip поэтому не создаёт ложную
деградацию.

Каждое срабатывание расписания создаёт `backup_job_runs`, а дочерние
`backup_runs` получают его `job_run_id`. Итог общего запуска рассчитывается
только по этим дочерним строкам. После простоя число точек агрегируется в одну
строку `missed`; при `scheduler.catch_up_missed: true` запускается одна последняя
точка, при `false` пропуск только фиксируется. Конфликт с ещё выполняющимся
экземпляром также считается пропуском.

## Что резервировать в самом сервисе

| Что | Зачем |
|---|---|
| `data/secret.key` | без него не расшифровать пароли подключений и зашифрованные бэкапы |
| База PostgreSQL | каталог копий, задания, история, учётные записи |
| YAML и `.env`/`jhvirt.env` | настройки и секреты; точные пути зависят от режима и перечислены в [CONFIGURATION.md](CONFIGURATION.md) |

Снимок базы снимается на живой службе, останавливать её не нужно:

```bash
pg_dump -U jhvirt jhvirt > /srv/backups/jhvirt-$(date +%F).sql
```

В Docker — `docker compose exec -T postgres pg_dump -U jhvirt jhvirt > …`.



Данные бэкапов самодостаточны: каталог запуска содержит `run.json` и манифесты,
и разбирается без базы (см. [BACKUP-FORMAT.md](BACKUP-FORMAT.md)).

`secret.key` копируйте **отдельно от базы и не в то хранилище, где лежат
копии**. Резерв, уехавший вместе с тем, что он защищает, спасает ровно от тех
аварий, от которых и так спасла бы вторая копия базы, — и ни от одной из тех,
ради которых он делается.

## Сетевые хранилища: SMB и WebDAV

Служба подключается к сетевой папке и к коллекции WebDAV сама. Монтировать их на
хосте не нужно, и это не только вопрос удобства: при монтировании учётные данные
лежат в `/etc/fstab` или в файле credentials, о шаре знает только администратор
хоста, а в интерфейсе видно локальный каталог. Отвалившаяся сеть выглядит тогда
как «нет прав на локальный путь» — сообщение, из которого причину не видно.

Монтирование остаётся рабочим способом: тип «локальный каталог» на точке
монтирования работал раньше и работает сейчас. Смысл имеет там, где шара уже
смонтирована для других задач.

**SMB/CIFS.** Работает с сетевой папкой Windows, Samba, TrueNAS, Synology —
всем, что говорит на SMB2 или SMB3.

| Поле | Что вводить |
|---|---|
| Сервер | имя или адрес: `nas.example.org` |
| Порт | 445, если не переопределён |
| Сетевая папка | только имя шары: `backups`, а не `\\nas\backups` |
| Домен | домен Active Directory или рабочая группа; для локальной учётной записи NAS оставляется пустым |
| Пользователь, пароль | учётная запись с правом записи в шару |
| Путь внутри папки | необязательно; каталог создаётся сам |

Анонимный доступ к шаре не поддерживается: бэкапы — это данные, за доступ к
которым кто-то должен отвечать по имени.

**WebDAV.** Работает с Nextcloud, ownCloud и сервисом WebDAV на NAS. Адрес
указывается полностью, вплоть до пути сервиса:
`https://nas.example.org/remote.php/dav/files/backup`. В Nextcloud лучше завести
отдельный пароль приложения — обычный пароль перестанет работать в тот день,
когда пользователю включат второй фактор.

Возобновления прерванной передачи в WebDAV нет: оборванный объект передаётся
заново целиком. Для дисков в сотни гигабайт это заметно, поэтому основным
хранилищем WebDAV стоит делать только при небольших объёмах, а для крупных
предпочесть SMB, S3 или локальный каталог.

Проверка сертификата отключается отдельным флагом и только для WebDAV. Нужна она
для NAS с самоподписанным сертификатом; пока проверка отключена, соединение
можно подменить.

**Как объект появляется в хранилище.** Данные пишутся под временным именем и
переименовываются, когда объект дописан. Обрыв оставляет файл с пометкой
`.jhv-tmp`, а не усечённый объект под именем готового: отсутствующий объект — это
«точка не состоялась», обрезанный — «точка есть, но внутри мусор», и второе
обнаруживается позже и дороже. Оставшиеся `.jhv-tmp` от прерванных запусков
удаляются вручную и ни на что не влияют.

Проверка хранилища записывает пробный объект, читает его обратно, сравнивает и
удаляет. «Доступно» означает именно «можно писать и читать», а не «сервер
отвечает». Каталог хранилища создаётся при первой проверке и перед первой
записью.

| Симптом | Причина |
|---|---|
| `NT_STATUS_LOGON_FAILURE` | неверный логин, пароль или домен |
| `NT_STATUS_BAD_NETWORK_NAME` | нет такой шары; проверьте, что в поле имя, а не путь |
| `NT_STATUS_ACCESS_DENIED` | учётная запись видит шару, но писать в неё не может |
| WebDAV `401` | сервер не принял логин или пароль; в Nextcloud — нужен пароль приложения |
| WebDAV `403` | доступ есть, прав на запись нет |
| WebDAV `405` | по этому адресу WebDAV не отвечает: адрес указан не до коллекции |
| WebDAV `409` | нет родительского каталога; каталог сервиса создать нельзя, он должен существовать |
| `x509: certificate signed by unknown authority` | самоподписанный сертификат; либо добавьте доверие, либо снимите проверку осознанно |

## Репликация и физические копии

У нового задания первое хранилище является основным, остальные обязательными
репликами. Способ доставки в реплики выбирается в форме задания списком «как
данные попадают в остальные хранилища»:

| Способ | Что происходит | Чем платите |
|---|---|---|
| Копирование из основного | ВМ читается один раз в основное, оттуда очередь переносит в реплики | основное хранилище читается второй раз; копия появляется с задержкой |
| Параллельная запись | данные идут во все хранилища за один проход по диску | скорость равна скорости самого медленного хранилища |
| Отдельный бэкап на каждое | на каждое хранилище выполняется свой запуск | диск снимается с гипервизора столько раз, сколько хранилищ |

Существующие задания при обновлении сохраняют прежнее поведение: включённая
репликация становится «копированием из основного», выключенная — «отдельным
бэкапом на каждое».

При параллельной записи недоступность реплики не прерывает запуск: основная
копия публикуется, а для отвалившегося хранилища заводится заявка, и его догоняет
та же очередь. Реплика, записанная параллельно, сразу учитывается как готовая
физическая копия.

Дальше описан режим копирования из основного. Гипервизор читается только в
основную копию. После публикации `run.json` постоянная очередь передаёт те же
объекты в реплики двумя workers по умолчанию. Для одинакового S3 endpoint используется server-side copy; для
local, S3 и SFTP данные идут потоком через сервис с действующими лимитами.
Лимит задаётся в форме хранилища в МиБ/с и является общим для параллельных
потоков записи. Значение `0` означает отсутствие ограничения. Нативный
server-side copy внутри одного S3 endpoint лимит не использует. SMB и WebDAV
переливаются так же, как local и SFTP: потоком через службу.

Статусы видны в **Бэкапы → Копии** и **Бэкапы → Репликация**:

| Статус | Значение |
|---|---|
| `pending` | ожидает свободного worker или родительскую цепочку |
| `copying` | объекты передаются |
| `verifying` | назначение перечитывается и сверяется по SHA-256 |
| `succeeded` | копия опубликована и пригодна для чтения |
| `failed` | попытка неуспешна, назначен автоматический повтор |
| `canceled` | оператор отменил передачу; автоматический повтор остановлен |
| `locked` | цепочка структурно недоступна либо удаление запрещено Object Lock |

Повторы выполняются через `1m, 5m, 15m, 1h, 4h, 12h`, затем каждые `24h` без
ограничения числа попыток. Успешные объекты фиксируются в PostgreSQL. При
повторе сервис перепроверяет их хеш в назначении и пропускает только реально
сохранившиеся объекты; оборванный объект передаётся заново целиком.

Для инкремента сначала догоняются родители от полной точки к последней. Пока
родитель не опубликован, дочерний `run.json` не создаётся. Если здорового
источника больше нет, копия блокируется и создаётся критическое оповещение.

Ошибка реплики не удаляет основную точку, но общий запуск задания остаётся
частичным. После успешного повтора итог пересчитывается, оповещение закрывается,
а защита возвращается в норму. Отключение обязательного хранилища приостанавливает
очередь, но не делает реплику необязательной.

### Проверка и восстановление из реплики

В диалогах проверки и восстановления выберите физическую копию. Без явного
выбора сервер пробует успешную основную, затем первую успешную реплику. Вся
цепочка должна находиться в одном хранилище: звенья из разных мест не смешиваются.
Практическая аварийная проверка: отключить основное хранилище, выполнить
`verify`, восстановить из выбранной реплики и загрузить изолированную ВМ.

### Ретенция

Политика применяется к логическим точкам, а не к каждой копии независимо.
Основной источник не удаляется, пока обязательная реплика не завершена.
Физические реплики удаляются раньше основной, а родитель, от которого зависит
оставшийся инкремент, сохраняется. Объект под Governance Object Lock остаётся
учтённым как `locked`; удаление будет повторено после истечения retention.

### Каталог после потери PostgreSQL

Откройте хранилище и запустите **Сканировать каталог**. Просмотр ничего не
импортирует автоматически. Состояния `importable` и `additional_copy` можно
выбрать для явного импорта; при выборе инкремента доступные родители добавляются
автоматически. `conflict`, `corrupt`, `missing_parent` и `missing_object`
требуют устранить причину. Импорт транзакционный и идемпотентный.

## Оповещения наружу

Оповещения видны в интерфейсе всегда, но узнаёт о них только тот, кто в эту
минуту смотрит на экран. Настройте доставку — почтой, в Telegram или на свой
webhook: `notifications` в конфигурации, подробности в
[CONFIGURATION.md](CONFIGURATION.md#оповещения-наружу).

По умолчанию сообщение уходит **один раз**. В **Настройки → Уведомления** можно
задать напоминания, максимум повторов, сообщение об устранении и отдельные
правила по типу. На странице активного оповещения можно приостановить внешнюю
доставку или отключить её только для этого случая; из web оно не исчезает.

По умолчанию наружу уходят только критические. Порог меняется параметром
`notifications.min_severity`.

Что проверить, если сообщения не приходят:

1. `notifications.enabled: true` и настроен хотя бы один канал — иначе служба
   не запустится и скажет об этом при старте;
2. в web-настройках перечислен хотя бы один настроенный канал;
3. в «Последних доставках» нет `failed`, а у `queued` видна причина следующей
   попытки;
4. транспортная ошибка повторяется из PostgreSQL outbox и переживает
   перезапуск. Успешный webhook не отправляется заново из-за отказа SMTP.

## Аварийная готовность самого сервиса

Бэкапы ВМ недостаточны для восстановления управляющего сервиса. Отдельно нужны:

1. свежий `pg_dump` PostgreSQL;
2. байт-в-байт копия активного `secret.key`;
3. конфигурация и token-файлы;
4. доступ к физическим хранилищам копий.

Включите `disaster_recovery` в YAML после настройки внешнего backup job. Страница
**Настройки → Аварийная готовность** и endpoint
`POST /api/v1/disaster-recovery/check` запускают проверку сразу. Сервис требует
непустой свежий дамп, чтение и права `0600`, а у внешнего ключа сверяет SHA-256 с
активным. Автоматической отправки ключа или запуска `pg_dump` нет.

Для планового переноса используйте installer migration, а не ручное копирование
отдельных файлов. Экспорт согласованно останавливает приложение, упаковывает
PostgreSQL, YAML/env, `secret.key`, токены и TLS; импорт проверяет права,
UID/GID, SAN сертификата и умеет продолжить оборванную раскладку. Репозитории и
разрешённые file/restore roots заранее подключаются на новом сервере. Пошаговый
cutover: [DEPLOY.md](DEPLOY.md#перенос-приложения-на-другой-сервер).

## Типовые ситуации

Ниже оставлены частые эксплуатационные случаи. Расширенная диагностика с
проверками установки и точными командами исправления находится в
[TROUBLESHOOTING.md](TROUBLESHOOTING.md).

### Движок недоступен

Оповещение `engine_unreachable`, состояние сервера `offline`. Сервис
автоматически пересоздаёт клиент (единственное, что он делает сам в этом случае).

Если в сообщении «отверг учётные данные» — это не авария движка, а истёкший или
изменённый пароль. Поправьте подключение: **Серверы → изменить**.

### ВМ на паузе из-за хранилища

Оповещение `vm_paused`, `pause_status = eio` или `enospc`. Сначала разберитесь с
хранилищем — сервис снимет ВМ с паузы сам (если разрешено `allow_vm_unpause`),
и она снова встанет на паузу, если проблема не устранена.

`enospc` почти всегда означает тонкий том, упершийся в границу домена. Смотрите
оповещение `storage_domain_low_space` по тому же серверу.

### Хост не отвечает

Оповещение `host_non_responsive`. Автоматическая перезагрузка по питанию
выключена по умолчанию и требует одновременно:

- `monitor.remediation.allow_host_fence: true` в конфигурации,
- настроенного управления питанием на самом хосте в oVirt,
- `failure_threshold` подряд неудачных проверок.

Она останавливает все ВМ хоста. Включайте, только если хосты действительно
одноразовые и ВМ переедут сами.

### Бэкап завершается ошибкой «диски заблокированы»

Признак незакрытого бэкапа на движке от прерванного запуска. Сервис
разбирает такие хвосты при старте; если он не перезапускался — перезапустите.
Вручную:

```bash
# посмотреть открытые бэкапы ВМ
curl -k -u admin@internal:PASS \
  "https://engine/ovirt-engine/api/vms/<vm-id>/backups" -H "Accept: application/json"
# закрыть
curl -k -u admin@internal:PASS -X POST \
  "https://engine/ovirt-engine/api/vms/<vm-id>/backups/<backup-id>/finalize" \
  -H "Content-Type: application/json" -d '{}'
```

### Бэкап неожиданно стал полным вместо инкрементального

Штатное поведение в трёх случаях, и каждый попадает в журнал с причиной:

- нет опорной точки (первый запуск или предыдущие удалены ретенцией);
- движок больше не знает checkpoint предыдущего запуска;
- цепочка достигла длины `full_every`.

### Инкременты не включаются

Инкрементальный бэкап требует, чтобы **у всех** дисков ВМ был режим
`incremental`, а он возможен только для qcow2. Экран ВМ показывает, какие диски
мешают, и даёт включить режим. Диски `raw` придётся конвертировать средствами
движка или согласиться на копию через снапшот.

Изменённые блоки начинают отслеживаться со следующего полного бэкапа — первый
запуск после включения будет полным.

**Диски `raw` при этом бэкапятся как обычно и без остановки ВМ.** Недоступны им
только инкременты: битмап изменённых блоков хранится в заголовке qcow2, и для
raw его негде держать. На oVirt такая ВМ копируется через временный снапшот, на
KVM — тем же горячим pull-режимом, только без checkpoint. Разница не в полноте
копии (данных в ней столько же), а в том, что каждый запуск читает весь занятый
объём.

### Контейнеры не поднимаются: «required variable … is missing a value»

В docker-compose v1 это может выглядеть как трейсбек Python, в конце которого
`RuntimeError` с тем же текстом про незаполненный пароль.

Значит, `.env` собран вручную из `.env.example`, где пароль базы пуст
намеренно — иначе он оказался бы одинаковым во всех установках. Compose
считает пустое значение таким же отсутствующим, как незаданное.

Готовит `.env` установщик:

```bash
cd deploy && ./install.sh
```

Он же и запускает. В существующем `.env` сохраняются пароль базы и остальные
настройки; установщик меняет только внешний URL и порт. PostgreSQL держит
исходный пароль в томе и новый без явной миграции не примет.

Заполнить руками тоже можно:

```bash
sed -i "s|^POSTGRES_PASSWORD=$|POSTGRES_PASSWORD=$(openssl rand -hex 24)|" .env
```

### Задание не запустилось: «предыдущий ещё выполняется»

В журнале — предупреждение, в интерфейсе — отказ с кодом `job_busy` (409).
Задание не укладывается в свой интервал: прошлый запуск ещё идёт, а по
расписанию подошёл следующий.

Второй экземпляр не запускается намеренно. Два одновременных бэкапа одной ВМ
соревнуются за родительский чекпоинт, и цепочка после этого оказывается в
неопределённом состоянии.

Что делать: посмотреть, что именно затянулось, в списке запусков. Обычные
причины — хранилище стало медленнее, добавились ВМ, инкремент выродился в
полный. Лечится либо разрежением расписания, либо `max_duration` у задания,
чтобы затянувшийся запуск обрывался сам, либо отменой текущих бэкапов вручную.

### Не пускает по правильному паролю: «слишком много попыток»

Код 429 и заголовок `Retry-After`. Включилась пауза после пяти неудач подряд;
она растёт с каждой следующей до 15 минут и снимается сама.

Считается по учётной записи, поэтому паузу мог вызвать кто-то другой, кто
подбирал пароль к этому же имени — посмотрите аудит: попытки записаны там с
адресом. Учётная запись при этом **не заблокирована**: жёсткая блокировка
после N попыток дала бы любому желающему возможность закрыть вход
администратору, зная только логин.

Снимают паузу три вещи: истечение её срока, успешный вход и перезапуск службы —
счётчик живёт в памяти процесса и наружу не сохраняется.

Смена пароля с консоли паузу **не** снимает: это отдельный процесс, он до
таблицы работающей службы не дотягивается. Если ждать нельзя:

```bash
sudo systemctl restart jhvirt
```

В Docker — `docker compose restart ovirt-backup`.

### Пароль принят, но интерфейс снова показывает вход

Полная проверка login-cookie-`/auth/me` и команды исправления приведены в
[разделе «Авторизация»](TROUBLESHOOTING.md#пароль-принят-но-снова-появляется-форма-входа).

Проверьте схему внешнего URL. Если браузер открыт по `http://`, а
`JHV_SERVER_EXTERNAL_URL` начинается с `https://`, ответ login создаёт cookie с
флагом `Secure`, которую браузер не отправляет по открытому HTTP. В результате
сам login отвечает 200, а следующий `/api/v1/auth/me` — 401.

Для systemd значение лежит в `/opt/jhvirt/config/jhvirt.env`, для Docker — в
`.env` как `JHV_EXTERNAL_URL`. Исправьте его так, чтобы схема совпадала с
фактическим адресом браузера, и перезапустите службу. `https://` указывайте при
реальном TLS, в том числе когда его завершает обратный прокси.

### Восстановление в файл отклонено: «каталог не разрешён»

Код 400. Каталог из запроса не входит ни в один из разрешённых: это
`backup.temp_dir` и всё, что перечислено в `backup.restore_dirs`.

Ограничение существует потому, что путь задаёт клиент, а результат — образ на
десятки гигабайт: без списка любой оператор мог бы заполнить раздел с базой
или положить файл в каталог конфигурации.

Нужен другой каталог — добавьте его в `backup.restore_dirs` и перезапустите
службу. В Docker путь должен быть ещё и смонтирован в контейнер, а при
установке через systemd — прописан в `ReadWritePaths` юнита, иначе запись
отклонит уже ядро.

### Временный снапшот не удалился

Сообщение «не удалось удалить временный снапшот». Снапшот с описанием
`jhvirt backup <run-id>` удаляется в интерфейсе движка. Оставленный снапшот
наращивает цепочку образов диска и со временем упирается в место домена.

### Хранилище бэкапов недоступно

Оповещение `storage_target_unreachable`, проверка идёт каждые 15 минут.
Кнопка **Проверить** на странице хранилищ делает полный круг: запись, чтение,
сверка, удаление пробного объекта — то есть проверяет права на запись, а не
только сетевую доступность.

## Восстановление

Порядок от наименее рискованного к наиболее:

1. **В файл** — ничего в oVirt не трогает. Годится для выемки отдельных файлов:
   получившийся raw монтируется через `losetup`/`kpartx`.
2. **В новый диск** — создаёт диск в выбранном домене и заливает образ.
   Существующие данные не затрагиваются.
3. **Поверх существующего диска** — необратимо. Остановите ВМ, которая его
   использует. Интерфейс требует явного подтверждения.
4. **В новую ВМ** — поддерживается для oVirt→oVirt и KVM→KVM. Сначала выполните
   preview, сопоставьте каждый нужный NIC, затем отдельно решите, запускать ли
   машину. Межплатформенной конвертации нет.

Восстановление из инкремента само собирает цепочку. Если какое-то звено удалено,
операция отклоняется до начала записи, а не на середине.

При создании новой ВМ сеть по умолчанию отсоединена, а MAC генерируются заново:
копия production-гостя не должна оказаться рядом с оригиналом автоматически.
Следите за `restore_runs`, а не только за HTTP-ответом `202`: там видны фаза,
процент, целевой VM ID и ошибки rollback. Для `config`-точки допустима ВМ без
дисков, но автоматический старт запрещён.

### Файлы, каталоги и снимки Engine

Нативный файловый бэкап включается через `file_backup.enabled` и использует
только именованные roots из YAML. Перед первым боевым запуском проверьте:

1. source root смонтирован read-only, если службе не нужна запись;
2. restore root доступен на запись UID службы/контейнера;
3. include/exclude не захватывают временные и socket-файлы;
4. выборочное восстановление выполняется без `overwrite`, затем сравнивается с
   источником; перезапись включается только для конкретного запроса;
5. `partial` и список `unstable_paths` разобраны — это файлы, которые дважды
   менялись во время чтения.

Symlink сохраняется как ссылка и не обходится; hardlink восстанавливается как
ссылка на первую запись. Смена allowlist требует изменения конфигурации и
перезапуска, она намеренно не является runtime-настройкой web.

Снимки конфигурации oVirt Engine создаются отдельными server-level заданиями.
После первого запуска скачайте JSON, проверьте число missing sections и
сравните два последовательных снимка. Они страхуют топологию, profiles, роли и
разрешения, но не содержат секреты Engine и не применяются автоматически.

### Проверка перед тем, как она понадобится

Раз в период (месяц — разумный интервал) прогоняйте по одной ВМ проверку в
режиме `restore`: она собирает образ целиком тем же кодом, что и настоящее
восстановление. Режим `manifest` дешевле и ловит порчу в хранилище, но не
проверяет, что цепочка складывается.

Настройте `verify_after` в заданиях: `chain` почти бесплатен и ловит разрыв
цепочки в тот же день, когда он возник.

Для критичных ВМ заведите отдельное редкое задание с `verify_after: boot` и
выберите KVM-хост для проверки. Сервис соберёт все диски, передаст их на
гипервизор, запустит ВМ без сети с сохранёнными архитектурой, BIOS/UEFI,
шинами и порядком загрузки, дождётся `qemu-guest-agent` и удалит временные
ВМ и образы. Нулевые память и vCPU означают исходные ресурсы. Опцию сохранения
при ошибке включайте только на время диагностики:
оставленные объекты удаляются вручную.

## Обслуживание

Служебные задачи работают сами:

| Задача | Период | Что делает |
|---|---|---|
| ретенция | 1 ч | применяет политики заданий |
| просроченные бэкапы | 1 ч | удаляет копии с истёкшим сроком |
| проверка хранилищ | 15 мин | доступность и запись |
| качество бэкапов | 15 мин | свежесть по расписанию, реплики, проверки и деградация скорости |
| очистка истории | 6 ч | пробы состояния и ёмкости, закрытые оповещения, истёкшие сессии |

### Ретенция: сначала посмотреть, потом применить

Предпросмотр показывает построчно, что политика оставит и что удалит, с
причиной по каждой копии:

```bash
curl -s -b cookies.txt -X POST http://localhost:8080/api/v1/retention/preview \
  -H 'Content-Type: application/json' \
  -d '{"server_id":"…","vm_id":"…","storage_target_id":"…",
       "policy":{"keep_last":3,"keep_daily":7,"keep_weekly":4,"keep_monthly":6}}'
```

Пустая политика (все нули) означает «не удалять ничего» — так форма, отправленная
с нулями, не сносит архив.

## Журналы

`logging.format: json` для сбора в централизованную систему, `console` — для
чтения человеком. Уровень `debug` показывает каждый HTTP-запрос к движку.

Сообщения, требующие внимания:

| Текст | Что делать |
|---|---|
| `НЕ УДАЛОСЬ РАЗМОРОЗИТЬ файловые системы гостя` | проверить ВМ: гость может остаться с замороженной ФС |
| `не удалось закрыть бэкап на движке` | закрыть вручную, иначе диски ВМ заблокированы |
| `не удалось удалить временный снапшот` | удалить в интерфейсе движка |
| `хранилище приняло N байт вместо M` | объект повреждён; бэкап помечен неуспешным |

## Ёмкость хранилищ

Служба сохраняет результат `Usage` каждые 15 минут и хранит его по умолчанию
90 дней. График использует медиану проб внутри суток. Прогноз появляется только
после семи суток истории и равен `текущее свободное место / медианный суточный
рост занятого места`. Нулевой или отрицательный рост означает, что дата
заполнения не вычисляется.

Локальный backend получает квоту через `statfs`. SMB спрашивает свободное место
у самой шары и отвечает всегда. SFTP использует расширение `statvfs`, если сервер
его поддерживает. WebDAV читает свойства `quota-available-bytes` и
`quota-used-bytes` из RFC 4331 — Nextcloud и ownCloud их отдают, простой
`mod_dav` обычно нет. S3 сообщает сумму объектов, но не свободное место bucket:
интерфейс показывает объём и рост со статусом «квота неизвестна». Значение `0`
для свободного места в таком случае не означает заполненный bucket.

## Prometheus и Grafana

Проверка endpoint с systemd-установки:

```bash
TOKEN_FILE=/opt/jhvirt/config/metrics.token
curl -fsS -H "Authorization: Bearer $(sudo cat "$TOKEN_FILE")" \
  http://127.0.0.1:8080/metrics | head
```

Рекомендуемая конфигурация Prometheus на том же хосте:

```yaml
scrape_configs:
  - job_name: ovirt-backup
    metrics_path: /metrics
    scheme: http
    bearer_token_file: /etc/prometheus/secrets/ovirt-backup.token
    static_configs:
      - targets: ["127.0.0.1:8080"]
```

Скопируйте token-файл в каталог, читаемый только пользователем Prometheus;
сам сервисный файл не делайте group-readable ради scrape. При удалённом
Prometheus передавайте `/metrics` только через TLS или защищённую сеть: Bearer
даёт доступ к операционным именам и состояниям, хотя пароли и ключи в метрики
никогда не попадают.

Основные ряды используют стабильные `vm_id`, `job_id` и `storage_target_id`.
Имена вынесены в `ovirt_backup_vm_info`, `ovirt_backup_job_info` и
`ovirt_backup_storage_info`, чтобы переименование ВМ не создавало новый
временной ряд. Для панели Grafana используйте:

- `ovirt_backup_protection_state` и `ovirt_backup_last_success_timestamp_seconds`;
- `rate(ovirt_backup_runs_total[24h])`, длительность и скорость последних копий;
- `ovirt_backup_storage_free_bytes` и `ovirt_backup_storage_forecast_days`;
- `ovirt_backup_alerts_open{severity="critical"}`;
- стандартные `go_*` и `process_*`.
